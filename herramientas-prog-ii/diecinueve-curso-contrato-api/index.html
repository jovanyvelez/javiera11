Unidad 00 · Apertura

La API que deja al cliente decidir el id

La clase 18 dejó una API que funciona. Hoy vas a descubrir que funcionar no es suficiente: esa API tiene dos agujeros abiertos, y los dos tienen que ver con la misma pregunta — ¿qué tiene derecho a saber el cliente?

⏱ 20 minutos 📄 Lectura y diagnóstico 🧭 Producto: los dos agujeros, demostrados

0.1 · Lo que entregaste la clase pasada

La clase 18 terminó con una aplicación que hacía las cuatro cosas: crear, listar, leer y borrar. Todo con un único modelo, el mismo para recibir el cuerpo, para guardar en la tabla y para devolver en la respuesta. Y el taller pedía que dejar escrito qué problema le quedaba. Este es el problema:

ejemplo — lo que hace la API de la clase 18 
# Un solo modelo para todo
class Producto(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True)
    precio: float
    cantidad: int
    descripcion: str | None = None


# Y el POST usa ese mismo modelo
@app.post("/productos/")
def crear_producto(producto: Producto, session: SessionDep) -> Producto:
    session.add(producto)
    session.commit()
    session.refresh(producto)
    return producto

0.2 · Agujero número uno: el cliente elige el identificador

Mira el id del modelo: es un campo más. Y el POST acepta un Producto entero. ¿Qué pasa si el cliente manda un id que ya existe?

terminal — el cliente manda un id que ya existe
curl -X POST http://127.0.0.1:8000/productos/ -H "Content-Type: application/json" -d '{"id":99,"nombre":"Teclado mecánico","precio":189900,"cantidad":7}'
{"id":99,"cantidad":7,"precio":189900.0,"nombre":"Teclado mecánico","descripcion":null}
 
curl http://127.0.0.1:8000/productos/99
{"id":99,"cantidad":7,"precio":189900.0,"nombre":"Teclado mecánico","descripcion":null}

El servidor aceptó un id=99 porque se lo mandaron. Si ese 99 ya existía, lo que ha pasado es que el producto viejo ha desaparecido y en su lugar está otro. Nadie lo ha hackeado: ha sido un POST normal, con un campo de más.

Advertencia — el identificador no es un dato, es una decisión

Decidir qué registro se toca es tarea del servidor o de la base de datos, nunca del cliente. El cliente dice «quiero crear un producto»; el servidor responde «este es el que te toca, el 7». La clase 12 ya te mostró por qué: si el identificador lo elige el cliente, la concurrencia se rompe.

0.3 · Agujero número dos: todo lo que se guarda, se devuelve

El segundo agujero es más discreto y aparece más adelante. Hoy el modelo tiene cuatro campos y todos son públicos, así que no se nota. Pero en una tienda real hay un campo que no es del cliente: lo que a la tienda le cuesta el producto.

ejemplo — el campo que nadie debe ver 
# Si mañana añades esto al modelo…
class Producto(SQLModel, table=True):
    ...
    costo_proveedor: float   # lo que le cuesta a la tienda

# …la respuesta de la API lo devolverá. A cualquiera que pregunte.

Con un solo modelo, no hay forma de decirlo: el mismo campo que usas para guardar es el que se devuelve. Es como tener una caja con una sola tapa: no puedes guardar algo y a la vez no enseñarlo.

Nota — la idea que ordena la clase

No se trata de «añadir más clases». Se trata de separar tres cosas que hasta ahora iban juntas: lo que la base de datos guarda, lo que el cliente manda y lo que el cliente se lleva. Tres responsabilidades, tres modelos. Y para no repetir los mismos campos cinco veces, la herencia.

Unidad 01 · La separación

Un modelo, cuatro modelos

La solución no es un modelo más grande: son cuatro modelos distintos, cada uno con su trabajo. Y para no escribir los mismos campos cinco veces, se heredan de una clase base: una herencia que, por primera vez en el curso, se usa para organizar y no para «dejar cosas en el sitio».

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: los cinco modelos escritos

1.1 · La clase base

Lo que todos los modelos tienen en común son los campos que el cliente siempre ve: el nombre, el precio, el stock y la descripción. Esos campos van en una clase base, sin table=True: no es una tabla, solo es la lista compartida.

ejemplo — la clase base 
class ProductoBase(SQLModel):
    """Los campos que todos los modelos comparten."""

    nombre: str = Field(index=True, min_length=1, max_length=100)
    precio: float = Field(gt=0)
    cantidad: int = Field(ge=0)
    descripcion: str | None = None

1.2 · Los cuatro modelos que heredan

ejemplo — los cuatro modelos 
# 1. La TABLA: lo que se guarda de verdad
class Producto(ProductoBase, table=True):
    id: int | None = Field(default=None, primary_key=True)
    costo_proveedor: float


# 2. Lo que VE el cliente: sin costo_proveedor, con id siempre presente
class ProductoPublic(ProductoBase):
    id: int


# 3. Lo que ACEPTA el cliente al crear: los campos públicos + el interno
class ProductoCreate(ProductoBase):
    costo_proveedor: float


# 4. Lo que ACEPTA el cliente al editar: todo opcional
class ProductoUpdate(ProductoBase):
    nombre: str | None = Field(default=None, min_length=1, max_length=100)
    precio: float | None = Field(default=None, gt=0)
    cantidad: int | None = Field(default=None, ge=0)
    descripcion: str | None = None
Qué hace cada modelo, y por qué está separado
Modelotable=TrueSu trabajo
ProductoBase no Tiene los campos compartidos. No se usa solo: es la base de la que heredan los otros
Producto sí Es la tabla. Es el único que se guarda en la base de datos
ProductoPublic no Es lo que sale por la puerta. Es el contrato con el cliente
ProductoCreate no Es lo que entra por la puerta al crear. Sin id: eso lo pone la base de datos
ProductoUpdate no Es lo que entra al editar. Todo opcional: solo lo que se quiere cambiar
Precisión — por qué ProductoPublic repite id: int

En el modelo de la tabla, el id es int | None porque puede no existir todavía. En el modelo público, el id es int a secas: cuando te lo devuelven, siempre existe. Ese detalle no es decorativo: convierte «el id puede ser nulo» en una certeza, y el cliente puede escribir código más simple porque sabe que el dato está.

1.3 · Por qué ProductoUpdate repite los campos

Fíjate en que ProductoUpdate vuelve a declarar los cuatro campos de la base. Podría heredarlos tal cual… pero entonces nombre sería obligatorio en toda edición, y no es lo que queremos: si el cliente solo cambia el precio, ¿por qué tiene que mandar el nombre otra vez?

Aplicación — la técnica de «re-declarar para cambiar»

En Python, cuando una subclase vuelve a declarar un atributo, gana la subclase. Así que ProductoUpdate hereda de ProductoBase —y por eso trae descripcion—, pero declara sus propios cuatro campos como opcionales. Es la misma idea de la clase 12, donde el modelo de la edición declare qué campos se pueden tocar.

Unidad 02 · La primera puerta

El id lo pone la base de datos

Con el modelo de entrada ya sin id, la ruta de alta deja de poder aceptar un identificador cualquiera. Pero hay un paso más: convertir lo que llega en el modelo de la tabla. Y ese paso tiene un nombre propio.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: la ruta de alta corregida

2.1 · Dos modelos, una conversión

En la clase 18, el POST recibía un Producto y lo guardaba tal cual: el mismo objeto era lo que entraba y lo que se guardaba. Ahora son dos modelos distintos, así que hay que convertir uno en el otro.

ejemplo — la ruta de alta corregida 
@app.post("/productos/", response_model=ProductoPublic)
def crear_producto(producto: ProductoCreate, session: SessionDep):
    """Recibe un ProductoCreate y guarda un Producto."""

    # El modelo de la tabla se construye a partir del de entrada.
    db_producto = Producto.model_validate(producto)

    session.add(db_producto)
    session.commit()
    session.refresh(db_producto)
    return db_producto

Producto.model_validate(producto) es la conversión: lee el ProductoCreate que llegó del cliente y construye un Producto — el modelo de la tabla — con esos mismos datos. El id no viene del cliente, y por tanto sale None: lo inventa la base de datos al guardar.

2.2 · Comprobación: el cliente ya no manda el id

terminal — el mismo POST de la clase 18, ahora corregido
curl -X POST http://127.0.0.1:8000/productos/ -H "Content-Type: application/json" -d '{"id":99,"nombre":"Teclado mecánico","precio":189900,"cantidad":7,"costo_proveedor":120000}'
{"nombre":"Teclado mecánico","precio":189900.0,"cantidad":7,"descripcion":null,"id":2}
 
# Fíjate: mandó id=99 y se guardó con id=2.
# El id del cliente fue ignorado.
Aplicación — el mismo campo, dos papeles

Antes, el id era un campo más del modelo: lo que el cliente mandara. Ahora ProductoCreate no lo tiene, así que el id que llega en el JSON simplemente no existe para el servidor. No se ignora, no se «corrige»: no existe. Y el id que sale en la respuesta es el que la base de datos generó, que fue el 2.

Advertencia — el campo que «desaparece» no da error

Si mandas id en el cuerpo, FastAPI no se queja: el campo no está en el modelo, y lo que no está en el modelo no se valida. El id se ignora en silencio. Es un comportamiento correcto y muy común en APIs bien hechas: el servidor decide qué se acepta.

2.3 · Lo que dice la documentación

El cambio se ve en /docs, y es la prueba de que el contrato ha cambiado de verdad:

terminal — el cuerpo que acepta el POST, antes y después
# Clase 18 (un solo modelo)
['id', 'nombre', 'precio', 'cantidad', 'descripcion']
 
# Clase 19 (modelos separados)
['nombre', 'precio', 'cantidad', 'descripcion', 'costo_proveedor']
 
# El id ya no está: lo pone la base de datos.

Unidad 03 · La segunda puerta

Los campos que no se devuelven

El id ya está resuelto. Falta el otro agujero: los datos que la tienda guarda pero que no son del cliente. El precio de compra, la nota interna, el proveedor. Entran, se guardan… y no deben salir.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el campo interno filtrado, comprobado

3.1 · El campo que se guarda y no se ve

Añadimos costo_proveedor: lo que a la tienda le cuesta el producto. Es un dato interno, pero el cliente tiene que poder mandarlo, porque es quien trae la mercancía. Entra, se guarda… y no debe salir.

ejemplo — un campo que entra y no sale 
# ENTRADA: el cliente sí lo manda (trae la mercancía)
class ProductoCreate(ProductoBase):
    costo_proveedor: float


# TABLA: se guarda
class Producto(ProductoBase, table=True):
    id: int | None = Field(default=None, primary_key=True)
    costo_proveedor: float


# SALIDA: no está, y por eso no puede salir
class ProductoPublic(ProductoBase):
    id: int

ProductoPublic no tiene costo_proveedor. No es que el servidor lo oculte al final: es que el modelo de salida no lo contempla, así que no hay por dónde se pueda colar.

Precisión — filtrar por modelo, no por código

Habría una forma «fácil» de resolverlo: borrar el campo de la respuesta a mano, con un del producto["costo_proveedor"] antes de devolverla. Funciona… hasta que alguien añada un segundo campo interno y se olvide de borrarlo también. Filtrar por modelo es la solución que no se rompe: si el campo no está en el modelo de salida, no puede salir. Ni hoy ni nunca.

3.2 · Comprobación

terminal — el campo que entra, se guarda y no sale
curl -X POST http://127.0.0.1:8000/productos/ -H "Content-Type: application/json" -d '{"nombre":"Audífonos Bluetooth","precio":129900,"cantidad":14,"descripcion":"30 h de batería","costo_proveedor":80000}'
{"nombre":"Audífonos Bluetooth","precio":129900.0,"cantidad":14,"descripcion":"30 h de batería","id":1}
 
# Se mandó costo_proveedor: 80000. No aparece en la respuesta.
 
curl -s http://127.0.0.1:8000/openapi.json | python -c "import json,sys; d=json.load(sys.stdin); print(list(d['components']['schemas']['ProductoPublic']['properties']))"
['nombre', 'precio', 'cantidad', 'descripcion', 'id']
Aplicación — esto es lo que hace una API de verdad

Una API profesional nunca devuelve sus datos internos. Piensa en una tienda real: el precio de compra no aparece en la etiqueta del producto, pero la caja sí lo sabe. La API es la etiqueta; la base de datos es la caja. Y el modelo es el filtro que lo garantiza sin que tengas que acordarte.

Nota — el mismo patrón en otros sitios

Las contraseñas se guardan hasheadas: nunca devuelves la contraseña de nadie, ni siquiera a esa persona. Los números de tarjeta se guardan enmascarados. Es el mismo patrón: el dato entra, se guarda, y el modelo de salida decide qué sale.

4.2 · Vocabulario del taller

Estas siete palabras aparecerán en el taller final. Léelas ahora; las definiciones son aproximadas y se afinarán en las unidades siguientes.

Modelo de tabla
Una clase con table=True: describe las columnas de una tabla real. Solo hay uno por entidad.
Modelo de datos
Una clase sin table=True: valida y transporta, pero no crea ninguna tabla.
Modelo público
El modelo de salida: exactamente lo que el cliente se lleva. Lo que no está aquí, no sale.
Modelo de entrada
El modelo de lo que el cliente manda. Define qué campos se aceptan y con qué reglas.
response_model
El parámetro con el que FastAPI filtra y valida lo que devuelve una ruta.
Herencia de modelos
Reutilizar los campos compartidos con una clase base, en vez de repetirlos en cada modelo.
Contrato
Lo que la API acepta, lo que devuelve y qué pasa cuando te equivocas. Se escribe en el código.

Ejercicio 5.1 · El PATCH

La clase 11 te enseñó a editar. Con el ORM, editar tiene una forma nueva: el PATCH, que cambia solo lo que el cliente manda. En 35 minutos escribes la ruta y dominas la técnica que hace posible: exclude_unset=True.

⏱ 35 minutos 💻 Ejercicio de desarrollo 🧭 Producto: la ruta de edición parcial funcionando

5.1 · El enunciado

Ejercicio

Editar sin pisar lo demás

La clase 11 tenía un problema: el formulario mandaba los cuatro campos, y si el usuario vaciaba un campo, ese campo se guardaba vacío. El PATCH lo resuelve: el cliente manda únicamente lo que cambió.

Ficha del sistema

Entrada Un cuerpo JSON con uno o varios campos, todos opcionales
Salida El producto completo, ya actualizado
Restricción Un campo que no viene en el cuerpo no se toca
Restricción Un campo que viene vacío sí se toca: vacío no es «no enviado»
Restricción Si el id no existe, la respuesta es 404

Requisitos

  1. La ruta PATCH /productos/{producto_id}: recibe un ProductoUpdate y devuelve el producto actualizado.
  2. model_dump(exclude_unset=True): convierte el modelo recibido en un diccionario con solo los campos que el cliente mandó.
  3. sqlmodel_update(datos): aplica ese diccionario sobre el objeto que hay en la base de datos.
  4. El 404 si el producto no existe.
  5. La comprobación clave: mandar un solo campo y ver que los demás siguen igual.

Modelo de respuesta

La línea que hace todo el trabajo es modelo.model_dump(exclude_unset=True). Sin el exclude_unset=True, el diccionario tendría todos los campos, con los que no mandó el cliente puestos a su valor por defecto: y eso es exactamente el bug de la clase 11.

la ruta del PATCH 
@app.patch("/productos/{producto_id}", response_model=ProductoPublic)
def actualizar_producto(producto_id: int, producto: ProductoUpdate, session: SessionDep):
    """Cambia solo los campos que el cliente mandó."""

    db_producto = session.get(Producto, producto_id)
    if not db_producto:
        raise HTTPException(status_code=404, detail="Producto no encontrado")

    # La magia: solo los campos que el cliente envió de verdad.
    datos = producto.model_dump(exclude_unset=True)

    # Se aplican sobre el objeto que ya está en la base de datos.
    db_producto.sqlmodel_update(datos)

    session.add(db_producto)
    session.commit()
    session.refresh(db_producto)
    return db_producto

El session.add() después del sqlmodel_update() no es redundante: el objeto se modificó en memoria y hay que volver a colgarlo en la sesión para que el commit() lo escriba. Es el mismo add → commit → refresh de la clase 18, con un paso más en medio.

5.2 · Comprobación

La comprobación que lo demuestra todo: manda un solo campo y mira los demás.

terminal — un PATCH con un solo campo
curl -X PATCH http://127.0.0.1:8000/productos/1 -H "Content-Type: application/json" -d '{"precio":99900}'
{"nombre":"Audífonos Bluetooth","precio":99900.0,"cantidad":14,"descripcion":"30 h de batería","id":1}
 
# Mandé solo el precio. El nombre, la cantidad y la descripción
# siguen exactamente igual.
 
curl -X PATCH http://127.0.0.1:8000/productos/1 -H "Content-Type: application/json" -d '{"descripcion":""}'
{"nombre":"Audífonos Bluetooth","precio":99900.0,"cantidad":14,"descripcion":"","id":1}
 
# Una cadena vacía SÍ es un valor: el campo se vació a propósito.
Precisión — «no enviado» no es lo mismo que «vacío»

Mira las dos peticiones. La primera no manda descripcion: el campo no se toca. La segunda manda descripcion: "": el campo se vacía. Las dos se resolvieron con el mismo exclude_unset=True, porque «enviado» y «no enviado» son cosas distintas y el modelo las distingue.

En la clase 11, el formulario HTML mandaba los cuatro campos siempre, así que era imposible distinguirlas. Eso también es una de las razones por las que el PATCH es un avance real y no solo un verbo nuevo.

el contrato de la API, en una tabla 
| Método | Ruta                | Acepta                        | Devuelve         | Errores |
|--------|---------------------|-------------------------------|------------------|---------|

Nota — el modelo de la tabla es el único raro

Mira el primer botón: Producto es el único que tiene las tres columnas en «sí». Es el único que puede entrar (si se lo pasas tal cual) y el único que puede salir. Por eso las rutas no lo usan para nada de eso: lo construyen a partir del modelo de entrada y lo devuelven a través del modelo público.

Modelo de respuesta

El párrafo del entregable 4 es donde se demuestra que entendiste la idea: no es «añadir un campo más», es «añadir un campo más en el modelo correcto».

las ocho comprobaciones del taller 
1. Arrancar: se crea el archivo database.db
2. POST sin id: la respuesta trae un id generado por la base de datos
3. POST mandando id=99: se ignora, el id lo pone la base de datos
4. GET /productos/: devuelve la lista
5. GET /productos/999: devuelve 404

Nota — y lo que viene después

Hay un problema que esta clase no resuelve, y que el tutorial oficial también aplaza: si mañana cambias el modelo (por ejemplo, si precio pasa a ser decimal), create_all() no actualizará la tabla existente. Eso se llama migración, y es el siguiente escalón. Por hoy, con la base de datos recién creada, no hace falta.

7.3 · Síntesis: siete ideas para llevarse

01

Un solo modelo no basta: hay que separar lo que se guarda, lo que se recibe y lo que se devuelve.

02

La herencia evita repetir los campos: una base común y cuatro modelos que se diferencian en lo que cada uno puede y no puede.

03

El id no es un dato que recibe el cliente: es una decisión que toma el servidor, y por eso no está en el modelo de entrada.

04

Un campo que no está en el modelo de salida no puede filtrarse. La seguridad no depende de que te acuerdes, sino de cómo está escrito el código.

05

response_model es el contrato de salida: FastAPI filtra y valida con él, y por eso se pone como parámetro y no como anotación.

06

El PATCH con exclude_unset=True cambia solo lo que se mandó: «no enviado» y «vacío» son cosas distintas.

07

Una API es un contrato, y la documentación se escribe sola a partir del código. Lo que no está en el modelo, no existe para el cliente.
