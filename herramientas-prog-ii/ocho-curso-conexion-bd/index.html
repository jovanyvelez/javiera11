La aplicación que olvida

Una lista de Python vive dentro de un proceso: cuando el servidor se reinicia, desaparece. Una base de datos es la memoria compartida y persistente del sistema. Hoy aprendes a abrir esa puerta desde FastAPI, a comprobar que está abierta y a entender por qué a veces no lo está.

0.1 · El catálogo que se borró solo

El club de robótica montó una tienda pequeña para vender sensores y kits. La primera versión guardaba los productos en una lista de Python. Funcionaba de maravilla: agregar, listar, calcular el total. Hasta que alguien reinició el servidor para actualizar una ruta. Al volver, el catálogo estaba vacío. Los productos existían en la memoria del proceso anterior, y ese proceso ya no estaba.

La segunda versión guardaba todo en un archivo JSON. Aguantó el reinicio, pero apareció otro problema: dos personas del club abrieron la tienda a la vez, cada una con su copia del archivo, y la última en guardar borró los cambios de la otra. El archivo no sabe de concurrencia. Una base de datos sí.

Distinción — una lista es memoria de un proceso; una base de datos es memoria de un sistema

Una lista vive y muere con el proceso que la creó. Una base de datos vive aparte, atiende a varios clientes a la vez, controla quién puede leer qué y sobrevive a los reinicios. Esa separación es la que convierte un ejercicio en una aplicación. Y también es la que introduce una palabra nueva en tu vocabulario: conexión.

Lo que cambia cuando los datos salen del proceso
Lista en memoriaBase de datos
PersistenciaSe pierde al reiniciarSobrevive a reinicios y despliegues
ConcurrenciaUn proceso, una copiaVarios clientes con transacciones
ConsultasRecorres la lista enteraSELECT, índices, filtros
IntegridadLa cuidar el programadorRestricciones NOT NULL, UNIQUE, CHECK
AccesoQuien tenga el procesoUsuarios, roles y permisos
RespaldoNo hayCopias, réplicas y recuperación

0.2 · La cadena: FastAPI, el driver y PostgreSQL

Tu aplicación no habla con PostgreSQL directamente. Habla con un driver, una librería que traduce entre Python y el protocolo de la base de datos. En este curso el driver es asyncpg, porque es asíncrono y deja que el servidor atienda otras peticiones mientras espera la respuesta.

Hay tres objetos que conviene no confundir desde el primer día: la conexión (un canal abierto con la base), el pool (un conjunto de conexiones reutilizables) y la sesión (el estado de una conexión mientras dura una petición). La conexión es el recurso; el pool es el administrador; la sesión es el uso.

0.3 · Qué significa «conectar»

La palabra «conectar» esconde cinco pasos. Si uno falla, el error es distinto, y por eso el diagnóstico importa tanto como el código.

Los cinco pasos de una conexión
PasoQué ocurreError típico
1. Resolver el hostEl nombre se traduce a una dirección IPsocket.gaierror
2. Abrir TCPSe intenta llegar al puerto 5432ConnectionRefusedError
3. Negociar TLSSi el servidor lo exige, se cifra el canalError de certificado o sslmode
4. AutenticarseUsuario y contraseña contra el servidorInvalidPasswordError (28P01)
5. Elegir la baseSe entra a la base indicada en la URLInvalidCatalogNameError (3D000)
Nota — conectar no es una línea, es un ciclo de vida

Una conexión se abre, se usa y se cierra. Si se abre al arrancar y se olvida al apagar, el servidor de base de datos acumula conexiones zombis. Si se abre en cada petición y no se cierra, se agota el límite. La solución profesional es un pool con un lifespan que lo abra y lo cierre en el momento correcto. Es exactamente lo que vas a construir.

1.1 · PostgreSQL en treinta segundos

PostgreSQL es un servidor de bases de datos relacionales. No es un archivo ni una librería: es un proceso que escucha en un puerto, recibe conexiones y responde consultas SQL. Dentro de ese servidor puede haber varias bases de datos; dentro de cada base, varias tablas; dentro de cada tabla, filas con columnas tipadas.

Servidor
El proceso de PostgreSQL. Escucha en un host y un puerto; puede atender a muchos clientes a la vez.
Base de datos
Un espacio aislado con sus propias tablas, usuarios y permisos. No se pueden consultar tablas de otra base sin conectarse a ella.
Tabla
Una colección de filas con la misma forma. Cada columna tiene un tipo y, si hace falta, una restricción.
Fila
Un registro concreto. En productos, un producto con su nombre y su precio.
SQL
El idioma para pedir y modificar datos: SELECT, INSERT, UPDATE, DELETE.

1.2 · La tabla del proyecto

La tabla productos es el contrato de los datos. Los tipos y las restricciones no son adornos: son la última línea de defensa antes de que un dato malo quede guardado para siempre.

sql/schema.sql — la tabla productos 
CREATE TABLE IF NOT EXISTS productos (
    id BIGSERIAL PRIMARY KEY,
    nombre TEXT NOT NULL UNIQUE
        CHECK (char_length(btrim(nombre)) BETWEEN 2 AND 80),
    precio NUMERIC(10, 2) NOT NULL
        CHECK (precio > 0),
    creado_en TIMESTAMPTZ NOT NULL DEFAULT now()
);
Las decisiones de la tabla y su porqué
Columna o restricciónQué hacePor qué
BIGSERIALEntero grande que se incrementa soloNo dependes de que el cliente invente el id
NOT NULLObliga a que el valor existaUn producto sin nombre no es un producto
UNIQUE del nombreNo admite dos productos con el mismo nombreEvita duplicados y permite responder 409 con un caso concreto
CHECK del nombreEntre 2 y 80 caracteres, sin contar espacios extremosEvita basura y textos imposibles de mostrar
NUMERIC(10, 2)Hasta 10 dígitos, 2 decimales exactosEl dinero no se guarda en coma flotante
CHECK del precioMayor que ceroUn producto gratis o negativo es un error de captura
TIMESTAMPTZFecha y hora con zona horariaSirve aunque el servidor cambie de zona
Precisión — NUMERIC no es float

NUMERIC(10, 2) guarda centavos exactos. float guarda una aproximación binaria, y sumar muchos precios con float puede producir 0.30000000000000004. En esta clase leeremos el precio con precio::float8 para que el JSON sea simple, pero la base lo guarda exacto. En un sistema de facturación, el precio se maneja como Decimal de principio a fin.

1.3 · La URL de conexión (DSN)

Una DSN (Data Source Name) es una sola cadena con todo lo necesario para conectarse. Tiene la forma de una URL, y cada parte tiene un nombre.

Advertencia — la contraseña también se codifica

Si la contraseña es a@b:c, la DSN no puede ser postgresql://club:a@b:c@localhost/club: el driver interpretaría mal el host y el puerto. Los caracteres especiales se escriben en porcentaje: @ → %40, : → %3A, / → %2F, # → %23. Es el mismo mecanismo de la clase 7 cuando el navegador codificaba un formulario.

.env.example — una plantilla que sí puede ir al repositorio 
# Copia este archivo como .env y pon tus valores reales.
# .env NO se sube al repositorio: contiene una contraseña.
DATABASE_URL=postgresql://club:club@localhost:5432/club
Nota — la contraseña no se escribe en el código

Nunca pongas una contraseña real en main.py ni en un commit. El código lee DATABASE_URL del entorno; el archivo .env queda fuera de Git y el repositorio solo guarda .env.example. Si una credencial se filtra, se rota en la base de datos y se cambia en el entorno; no basta con borrar el archivo.

1.4 · La primera conexión con asyncpg

asyncpg es el driver. connect() abre una conexión; close() la cierra. Entre las dos llamadas se pueden ejecutar consultas con fetch, fetchrow, fetchval o execute.

probar_conexion.py — una conexión, una consulta, un cierre 
import asyncio
import os

import asyncpg


async def main() -> None:
    conn = await asyncpg.connect(os.environ["DATABASE_URL"], timeout=10.0)
    try:
        version = await conn.fetchval("SELECT version()")
        print(version)

        # La consulta más pequeña que demuestra que la base responde.
        print("ping:", await conn.fetchval("SELECT 1"))
    finally:
        await conn.close()


if __name__ == "__main__":
    asyncio.run(main())

fetchval
Devuelve el primer valor de la primera fila. Ideal para SELECT 1, un count(*) o un RETURNING id.
fetchrow
Devuelve una fila completa como Record, o None si no hay resultados. Hay que comprobar el None antes de acceder a una columna.
fetch
Devuelve una lista de filas. Nunca es None: si no hay resultados, es una lista vacía.
execute
Ejecuta una sentencia que no devuelve filas y retorna un texto como INSERT 0 1.
Record
Una fila de asyncpg. Se comporta como un diccionario y como una tupla; dict(fila) la convierte para el JSON.

1.5 · SQL con parámetros, nunca con concatenación

El SQL se escribe con marcadores $1, $2, y los valores se pasan aparte. El driver los envía como datos, no como texto. Esto evita la inyección SQL, el equivalente de dejar la puerta del formulario abierta pero esta vez del lado de la base de datos.

la diferencia entre datos y código 
# MAL: el nombre del usuario se convierte en parte del SQL
sql = f"SELECT id FROM productos WHERE nombre = '{nombre}'"
await conn.fetch(sql)

# BIEN: el nombre viaja como parámetro; PostgreSQL lo trata como dato
await conn.fetch("SELECT id FROM productos WHERE nombre = $1", nombre)
Advertencia — los marcadores de asyncpg son $1

Si vienes de otras librerías, quizá esperes %s o ?. asyncpg usa $1, $2, y el orden importa. Un ? no se sustituye: se envía tal cual y PostgreSQL responde con un error de sintaxis. Es uno de los errores más comunes al cambiar de driver.

1.6 · ¿Y si abro una conexión por petición?

Funciona en una demostración y se cae en cuanto hay concurrencia. Abrir una conexión implica resolver el host, abrir TCP, negociar TLS y autenticarse: entre 10 y 50 milisegundos que se suman a cada petición. Además, PostgreSQL tiene un límite de conexiones simultáneas; si cada petición abre una, cien usuarios pueden dejar al servidor sin conexiones disponibles.

Aplicación — la regla que resuelve el problema

Abre un pool al arrancar la aplicación, pide una conexión prestada por petición y devuélvela al terminar. El pool mantiene unas pocas conexiones vivas y las reutiliza. Es la unidad siguiente, y es la pieza que separa un script de una API.

Unidad 02 · El recurso compartido

El pool: unas pocas conexiones que atienden a todos

Abrir una conexión es caro y PostgreSQL tiene un límite. Un pool mantiene unas pocas conexiones vivas, las presta por petición y las recupera. Esta unidad explica cómo se configura, cómo se usa sin fugas y qué pasa cuando se agota.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: la clase Database con connect, close y ping

2.1 · El costo de abrir una conexión

Cada conexión nueva recorre los cinco pasos de la unidad 0: DNS, TCP, TLS, autenticación y selección de base. En una red local eso puede tomar entre 10 y 50 milisegundos; contra un servidor administrado, más. Si una API recibe cien peticiones por segundo y abre una conexión por petición, está gastando casi todo su tiempo en saludar.

Tres formas de obtener una conexión
EstrategiaQué haceProblema
Una conexión globalSe abre una vez y la comparten todas las peticionesUna consulta lenta bloquea a las demás; no hay concurrencia real
Una conexión por peticiónSe abre y se cierra en cada solicitudLatencia alta y riesgo de agotar max_connections
Un poolMantiene N conexiones vivas y las prestaHay que configurarlo y devolver siempre la conexión

2.2 · Los parámetros de create_pool

    dsn=db_url,
    min_size=1,
    max_size=10,
    timeout=10.0,
    command_timeout=30.0,
    max_inactive_connection_lifetime=300.0,

Cada parámetro y su efecto
ParámetroValor de la claseQué controla
min_size1Conexiones que se abren de entrada y se mantienen vivas
max_size10Máximo de conexiones simultáneas del pool
timeout10.0Segundos máximos para abrir una conexión
command_timeout30.0Segundos máximos por consulta; al excederse, PostgreSQL la cancela

Precisión — max_size no se elige por intuición

El límite real lo pone PostgreSQL con max_connections, y cada worker de la API tiene su propio pool. Diez conexiones por worker multiplicadas por cuatro workers son cuarenta conexiones. Si el servidor solo admite cien y hay otras aplicaciones, el número tiene que bajar. La fórmula no es «más grande es mejor»: es «tantas como hagan falta para atender la concurrencia, sin ahogar al servidor».

2.3 · La clase Database

El pool no se crea en una variable suelta: se encapsula en una clase pequeña que sabe abrirlo, cerrarlo y decir si está listo. Así la aplicación tiene un solo punto de verdad sobre la conexión.

database.py — el pool encapsulado 
"""Capa de acceso a PostgreSQL con un pool de asyncpg."""

import asyncio

import asyncpg
from loguru import logger


class PoolNotReadyError(RuntimeError):
    """Se lanza cuando se pide una conexión antes de crear el pool."""


class Database:
    """Administra el pool de conexiones de la aplicación."""

    def __init__(self) -> None:
        self.pool: asyncpg.Pool | None = None

    async def connect(self, db_url: str) -> None:
        if self.pool is not None:
            return
        self.pool = await asyncpg.create_pool(
            dsn=db_url,
            min_size=1,
            max_size=10,
            timeout=10.0,
            command_timeout=30.0,
            max_inactive_connection_lifetime=300.0,
        )
        logger.info("Pool de conexiones abierto")

    async def close(self) -> None:
        if self.pool is None:
            return
        await self.pool.close()
        self.pool = None
        logger.info("Pool de conexiones cerrado")

    @property
    def is_connected(self) -> bool:
        return self.pool is not None

    async def ping(self) -> bool:
        """Comprueba que la base responde con una consulta mínima."""
        if self.pool is None:
            return False
        try:
            await asyncio.wait_for(self.pool.fetchval("SELECT 1"), timeout=2.0)
            return True
        except (TimeoutError, OSError, asyncpg.PostgresError):
            return False


db = Database()
PoolNotReadyError
Una excepción propia, no de asyncpg. Sirve para distinguir «la base no está lista» de «la base rechazó la consulta» y responder 503 en vez de 500.
connect() idempotente
Si el pool ya existe, no hace nada. Así el lifespan puede llamarlo sin miedo a crear dos pools si el arranque se repite.
close()
Cierra todas las conexiones y deja el pool en None. Sin esto, el servidor de base de datos conserva conexiones abiertas hasta que expiran.
ping()
Ejecuta SELECT 1 con un límite de dos segundos. Es la consulta más barata que demuestra que la base responde ahora, no que respondió al arrancar.
asyncio.wait_for
Envuelve la consulta y lanza TimeoutError si tarda más de lo permitido. Evita que un health check se quede colgado esperando.

2.4 · Pedir una conexión sin fugas

El pool se usa con async with. Al entrar se adquiere una conexión; al salir se devuelve, incluso si el bloque lanza una excepción. Esa garantía es la diferencia entre un pool sano y un pool que se agota a la media hora.

usar el pool: préstamo y devolución 
async with db.pool.acquire() as conn:
    filas = await conn.fetch("SELECT id, nombre FROM productos")
    # Al salir del bloque, la conexión vuelve al pool.

# También existen atajos que adquieren y devuelven por ti:
filas = await db.pool.fetch("SELECT id, nombre FROM productos")
total = await db.pool.fetchval("SELECT count(*) FROM productos")
Advertencia — no retengas una conexión mientras esperas otra cosa

Si dentro del async with llamas a una API externa, generas un PDF o esperas una respuesta lenta, la conexión queda ocupada sin estar haciendo nada. Con diez conexiones y diez peticiones lentas, el pool se agota y las demás esperan. La regla es: adquiere la conexión lo más tarde posible y devuélvela lo antes posible.

2.5 · Transacciones: todo o nada

Una transacción agrupa varias sentencias para que se guarden juntas o no se guarde ninguna. Es la herramienta para operaciones que no tienen sentido a medias: descontar stock y registrar la venta, por ejemplo.

una transacción con asyncpg 
async with db.pool.acquire() as conn:
    async with conn.transaction():
        await conn.execute(
            "UPDATE productos SET precio = precio * 1.10 WHERE id = $1", producto_id
        )
        await conn.execute(
            "INSERT INTO auditoria (producto_id, accion) VALUES ($1, 'precio')",
            producto_id,
        )
    # Si algo falla dentro del bloque, se hace rollback automático.
    # Si todo termina bien, se hace commit al salir.
Nota — una transacción no es un pool

La transacción vive dentro de una conexión. No se comparte entre peticiones ni se guarda en una variable global. Si dos peticiones necesitan transacciones, cada una adquiere su propia conexión y abre su propia transacción. Mezclar esos dos conceptos produce errores imposibles de reproducir.

2.6 · Cuando el pool se agota

pool.acquire() espera hasta timeout segundos a que se libere una conexión. Si no lo consigue, lanza TimeoutError. Las causas habituales son tres:

  1. Fuga: una ruta adquirió una conexión y no la devolvió porque no usó async with o porque el yield de la dependencia nunca se reanudó.
  2. Consulta lenta: todas las conexiones están esperando a PostgreSQL; command_timeout debería cancelarlas.
  3. Pool demasiado pequeño: la concurrencia real supera max_size. Se mide antes de aumentar.
observar el pool antes de cambiar números 
logger.info(
    "pool: size={} idle={} max={}",
    db.pool.get_size(),
    db.pool.get_idle_size(),
    db.pool.get_max_size(),
)

Unidad 03 · El ciclo de vida

Lifespan y dependencia: abrir una vez, prestar por petición

El pool tiene que abrirse antes de la primera petición y cerrarse después de la última. Ese es el trabajo de lifespan. La conexión que usa cada ruta se pide con una dependencia que la devuelve sola. Juntas forman el patrón que usarás en todos tus proyectos.

3.1 · El lifecycle de la aplicación

──▶ servir
peticiones

main.py — el lifespan 
import os
from contextlib import asynccontextmanager

from fastapi import FastAPI
from loguru import logger

from database import db


@asynccontextmanager
async def lifespan(app: FastAPI):
    db_url = os.getenv("DATABASE_URL")
    if not db_url:
        raise RuntimeError("La variable de entorno DATABASE_URL no está definida")

    await db.connect(db_url)
    logger.info("Aplicación lista para atender peticiones")
    try:
        yield
    finally:
        await db.close()
        logger.info("Aplicación detenida")


app = FastAPI(title="Tienda del Club", lifespan=lifespan)
Antes del yield
Todo lo que debe existir antes de atender la primera petición: el pool, clientes, cachés. Si algo falla aquí, la aplicación no arranca.
Después del yield
La limpieza ordenada: cerrar el pool, vaciar colas, cerrar clientes. Se ejecuta una sola vez, cuando el servidor se apaga.
app.state
El lugar donde FastAPI guarda objetos compartidos. Aquí usamos el singleton db de database.py; en proyectos grandes también se puede guardar en app.state.db.
Fail fast
Si la base no está disponible al arrancar, es mejor no arrancar que aceptar peticiones que van a fallar. El orquestador reinicia el servicio y el error queda visible en los registros.
Advertencia — @app.on_event está de salida

Durante años se usaron @app.on_event("startup") y @app.on_event("shutdown"). Hoy se considera una API heredada: el lifespan es el mecanismo recomendado por FastAPI y Starlette. Si ves tutoriales viejos con on_event, funciona, pero no es el estilo que debes copiar.

3.2 · La dependencia get_connection

Una dependencia es una función que FastAPI ejecuta antes de tu ruta y cuyo resultado inyecta como parámetro. Si la función usa yield, FastAPI también ejecuta el código de limpieza cuando la respuesta termina. Esa es la pieza que devuelve la conexión al pool.

database.py — la dependencia y su alias 
from typing import Annotated, AsyncGenerator

import asyncpg
from fastapi import Depends

# Añade esto al final de database.py.
# PoolNotReadyError y db ya están definidos arriba.


async def get_connection() -> AsyncGenerator[asyncpg.Connection, None]:
    """Cede una conexión del pool y la devuelve al terminar la petición."""
    if db.pool is None:
        raise PoolNotReadyError("La base de datos no está lista todavía")

    async with db.pool.acquire() as conn:
        yield conn


ConnectionDep = Annotated[asyncpg.Connection, Depends(get_connection)]
Precisión — el alias ConnectionDep no es un adorno

ConnectionDep empaqueta el tipo y la dependencia en un solo nombre. Las rutas quedan cortas, el editor sabe qué tipo reciben y la dependencia se puede cambiar en un solo lugar. Es el estilo que FastAPI recomienda con Annotated: el tipo sigue siendo el tipo, y la dependencia viaja como metadato.

main.py — usar la dependencia en una ruta 
from database import ConnectionDep


@app.get("/productos")
async def listar_productos(conn: ConnectionDep) -> list[dict]:
    filas = await conn.fetch(
        "SELECT id, nombre, precio::float8 AS precio FROM productos ORDER BY id"
    )
    return [dict(fila) for fila in filas]
Nota — por qué yield y no return

Con return, la conexión se devolvería antes de que la ruta la use. Con yield, FastAPI pausa la dependencia, entrega la conexión, espera a que la ruta termine y reanuda el bloque para salir del async with. Es el mismo patrón de with open(...) de la clase 5, pero asíncrono y con una conexión de red.

3.3 · El health check que sí sirve

Un endpoint /health que solo devuelve {"ok": true} no comprueba nada. El health check útil consulta la dependencia crítica con un timeout corto y responde 503 si no está disponible. Los balanceadores y orquestadores usan ese código para decidir si mandan tráfico.

database.py — pool, dependencia y ping 
"""Capa de acceso a PostgreSQL con un pool de asyncpg."""

import asyncio
from typing import Annotated, AsyncGenerator

import asyncpg
from fastapi import Depends
from loguru import logger


class PoolNotReadyError(RuntimeError):
    """Se lanza cuando se pide una conexión antes de crear el pool."""


class Database:
    """Administra el pool de conexiones de la aplicación."""

    def __init__(self) -> None:
        self.pool: asyncpg.Pool | None = None

    async def connect(self, db_url: str) -> None:
        if self.pool is not None:
            return
        self.pool = await asyncpg.create_pool(
            dsn=db_url,
            min_size=1,
            max_size=10,
            timeout=10.0,
            command_timeout=30.0,
            max_inactive_connection_lifetime=300.0,
        )
        logger.info("Pool de conexiones abierto")

    async def close(self) -> None:
        if self.pool is None:
            return
        await self.pool.close()
        self.pool = None
        logger.info("Pool de conexiones cerrado")

    @property
    def is_connected(self) -> bool:
        return self.pool is not None

    async def ping(self) -> bool:
        """Comprueba que la base responde con una consulta mínima."""
        if self.pool is None:
            return False
        try:
            await asyncio.wait_for(self.pool.fetchval("SELECT 1"), timeout=2.0)
            return True
        except (TimeoutError, OSError, asyncpg.PostgresError):
            return False


db = Database()


async def get_connection() -> AsyncGenerator[asyncpg.Connection, None]:
    """Cede una conexión del pool y la devuelve al terminar la petición."""
    if db.pool is None:
        raise PoolNotReadyError("La base de datos no está lista todavía")

    async with db.pool.acquire() as conn:
        yield conn


ConnectionDep = Annotated[asyncpg.Connection, Depends(get_connection)]

5.7 · Antes de dar la actividad por terminada

  1. GET /health responde 200 con la base arriba y 503 con la base abajo.
  2. POST /productos responde 201 y devuelve el id generado por PostgreSQL.
  3. GET /productos devuelve la lista y sobrevive al reinicio de la API.
  4. La tabla tiene NOT NULL, CHECK y UNIQUE; la API no es la única defensa.
  5. Ninguna consulta usa f-string ni concatenación: todos los valores van como $1, $2.
  6. La DSN se lee de DATABASE_URL y no hay contraseñas en el código.

6.4 · Convertir excepciones en respuestas HTTP

El cliente no debe recibir un stack trace ni el detalle interno de PostgreSQL. El servidor registra el detalle completo y devuelve un mensaje breve, con un código que el cliente pueda interpretar.

main.py — manejadores de error de la base 
import asyncpg
from fastapi import Request
from fastapi.responses import JSONResponse
from loguru import logger

from database import PoolNotReadyError


@app.exception_handler(PoolNotReadyError)
async def pool_no_listo(request: Request, exc: PoolNotReadyError) -> JSONResponse:
    logger.warning("Pool no listo: {}", exc)
    return JSONResponse(
        {"detail": "La base de datos no está disponible. Intenta de nuevo en unos segundos."},
        status_code=503,
        headers={"Retry-After": "5"},
    )


@app.exception_handler(asyncpg.UniqueViolationError)
async def valor_duplicado(
    request: Request, exc: asyncpg.UniqueViolationError
) -> JSONResponse:
    logger.warning("Conflicto en la base: {}", exc)
    return JSONResponse(
        {"detail": "Ya existe un producto con ese nombre."},
        status_code=409,
    )


@app.exception_handler(asyncpg.QueryCanceledError)
async def consulta_cancelada(
    request: Request, exc: asyncpg.QueryCanceledError
) -> JSONResponse:
    logger.warning("Consulta cancelada: {}", exc)
    return JSONResponse(
        {"detail": "La consulta tardó demasiado. Intenta con menos datos."},
        status_code=504,
    )


@app.exception_handler(asyncpg.PostgresError)
async def error_postgres(request: Request, exc: asyncpg.PostgresError) -> JSONResponse:
    logger.error("PostgreSQL {}: {}", exc.sqlstate, exc)
    return JSONResponse(
        {"detail": "Error al acceder a la base de datos."},
        status_code=500,
    )
PoolNotReadyError → 503
El servicio aún no está listo o perdió la base. Retry-After le dice al cliente cuándo volver a intentar.
UniqueViolationError → 409
El dato es válido, pero choca con una regla de unicidad. El cliente puede corregir el valor y reintentar.
QueryCanceledError → 504
La consulta superó el tiempo permitido. Es un problema de rendimiento, no de datos inválidos.
PostgresError → 500
La red de seguridad para todo lo demás. El cliente recibe un mensaje genérico; el detalle queda en los registros.
El orden importa
Los manejadores específicos se evalúan antes que el genérico. Si registras PostgresError y UniqueViolationError, el conflicto debe caer en el específico.
Advertencia — nunca devuelvas exc.detail al cliente

El detalle de PostgreSQL puede incluir el nombre de la tabla, la restricción, la columna o incluso el valor que falló. Eso es información para el equipo, no para quien usa la API. El mensaje público dice qué puede hacer el cliente; el registro dice qué pasó exactamente.

6.6 · Seguridad de la conexión

Mínimo privilegio
El usuario de la API no debe ser postgres ni un superusuario. Solo necesita SELECT, INSERT, UPDATE y DELETE sobre sus tablas. En el compose de clase, club es superusuario por comodidad; en producción se crea un rol aparte con permisos mínimos.
TLS en tránsito
Si la base está fuera de tu computador, usa sslmode=require o el certificado del proveedor. Sin TLS, la contraseña y los datos viajan legibles por la red.
Secretos fuera del código
La DSN vive en el entorno. No se imprime en logs, no se devuelve en /health y no se sube a Git. .env va en .gitignore.
Consultas parametrizadas
Todo valor va como $1, $2. Concatenar texto convierte una entrada en código SQL y es la puerta de la inyección.
Detalle interno, solo en logs
El cliente recibe un mensaje accionable; el equipo recibe el SQLSTATE, el detalle y la consulta en los registros.
Respaldos y migraciones
Una conexión no protege los datos: los protege una política de respaldo y un esquema versionado. Eso viene en el taller y en la clase siguiente.

7.2 · Las pruebas de integración

Una prueba de integración usa una base de datos real. Es más lenta que una prueba unitaria, pero demuestra lo que de verdad importa: que el pool se abre, que la tabla existe y que el SQL funciona. El marcador skipif evita que la suite falle en una máquina sin base.

terminal — instalar pytest 
uv add --dev pytest
uv run --env-file .env pytest -q

# Si ya exportaste DATABASE_URL en la terminal,
# también funciona: uv run pytest -q
test_db.py — cuatro pruebas contra PostgreSQL 
import os
from uuid import uuid4

import pytest
from fastapi.testclient import TestClient

from main import app

pytestmark = pytest.mark.skipif(
    not os.getenv("DATABASE_URL"),
    reason="Requiere un PostgreSQL con DATABASE_URL definida",
)


def test_health_con_base_arriba():
    with TestClient(app) as cliente:
        respuesta = cliente.get("/health")
        assert respuesta.status_code == 200
        assert respuesta.json()["db"] == "ok"


def test_crear_y_listar_producto():
    nombre = f"Sensor {uuid4().hex[:8]}"
    with TestClient(app) as cliente:
        creado = cliente.post(
            "/productos", json={"nombre": nombre, "precio": 12.5}
        )
        assert creado.status_code == 201
        producto = creado.json()
        assert producto["nombre"] == nombre
        assert producto["id"] > 0

        listado = cliente.get("/productos")
        assert listado.status_code == 200
        assert any(p["id"] == producto["id"] for p in listado.json())


def test_producto_invalido_devuelve_422():
    with TestClient(app) as cliente:
        respuesta = cliente.post(
            "/productos", json={"nombre": "X", "precio": -1}
        )
        assert respuesta.status_code == 422


def test_nombre_duplicado_devuelve_409():
    nombre = f"Kit {uuid4().hex[:8]}"
    with TestClient(app) as cliente:
        primero = cliente.post(
            "/productos", json={"nombre": nombre, "precio": 20}
        )
        assert primero.status_code == 201

        repetido = cliente.post(
            "/productos", json={"nombre": nombre, "precio": 25}
        )
        assert repetido.status_code == 409
        assert "Ya existe" in repetido.json()["detail"]
Precisión — with TestClient(app) no es decoración

Usar TestClient(app) sin el with no ejecuta el lifespan: el pool nunca se abre y todas las rutas fallan con PoolNotReadyError. El with arranca la aplicación, ejecuta el lifespan, corre la prueba y apaga la aplicación. Es la forma correcta de probar recursos que viven en el ciclo de vida.

Advertencia — la prueba de conflicto necesita el manejador

test_nombre_duplicado_devuelve_409 espera el manejador de UniqueViolationError de la unidad 6. Si todavía no lo añadiste, la segunda inserción terminará en 500 y la prueba fallará. Añade los cuatro manejadores antes de ejecutar la suite.

Nota — por qué el nombre lleva un identificador único

La tabla tiene UNIQUE en nombre. Si todas las pruebas usaran «Sensor», la segunda ejecución fallaría con 409 antes de probar lo que quería. uuid4().hex[:8] genera un sufijo distinto en cada corrida y mantiene las pruebas repetibles. Es una buena costumbre en integración: cada prueba crea sus propios datos.

7.4 · Síntesis: siete ideas para llevarse

01

Una base de datos es la memoria compartida y persistente del sistema; una lista de Python es solo la memoria de un proceso.

02

Una conexión tiene un ciclo de vida: se abre, se usa y se cierra. Y cuesta: DNS, TCP, TLS y autenticación.

03

El pool reutiliza un número pequeño de conexiones; async with garantiza que siempre vuelvan.

04

El lifespan abre el pool antes de la primera petición y lo cierra después de la última. No es un detalle: es el orden correcto.

05

La dependencia con yield presta una conexión por petición y la devuelve al terminar, incluso si la ruta falla.

06

Un health check consulta la dependencia crítica ahora, con timeout, y responde 503 cuando no está.

07

Los errores tienen capas y SQLSTATE. El cliente recibe un mensaje accionable; el equipo recibe el detalle en los logs.

7.5 · Puente hacia la próxima clase

Tu API ya guarda y lee datos reales. Lo que sigue es hacer que ese esquema evolucione sin romper lo que ya funciona, y que las consultas sigan siendo rápidas cuando la tabla crezca.

  1. Migraciones. schema.sql sirve para crear la primera versión; cuando la tabla cambie, necesitarás migraciones versionadas (Alembic) y no un archivo que se ejecuta a mano.
  2. Índices y consultas. Un SELECT con WHERE sobre una tabla grande necesita el índice correcto. El EXPLAIN ANALYZE es la herramienta para decidir, no la intuición.
  3. Un ORM, cuando el proyecto crezca. SQLAlchemy o SQLModel añaden comodidad y migraciones, pero solo después de entender la conexión, el pool y el SQL que hay debajo. Ese día llega en las clases 18 y 19: la primera pone el modelo por encima del SQL y la segunda separa lo que entra de lo que sale.
