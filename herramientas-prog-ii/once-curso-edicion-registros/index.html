Unidad 00 · Apertura

El catálogo que nadie puede corregir

En las clases anteriores aprendiste a crear datos y a mostrar datos. Hoy toca la tercera de las cuatro operaciones: corregir lo que ya está guardado. Es la operación que más se parece a la vida real, porque los datos guardados casi nunca están bien la primera vez.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: el mapa de las cuatro operaciones

0.1 · La tienda TechStore

La tienda TechStore vende audífonos, mouse y teclados. Su catálogo vive en una tabla productos de PostgreSQL, y la aplicación web —FastAPI con HTMX— ya funciona: se abre /productos y ahí está la lista, con el nombre, el precio y las unidades disponibles de cada artículo.

Un martes por la tarde, el jefe descubre que el teclado mecánico aparece con el precio 189.900 cuando debería ser 189.900… no, cuando debería ser 189.900 con el precio anterior, que era la mitad. Es un error de una tecla. Y entonces se descubre el problema de verdad:

Distinción — no se puede corregir lo que no se puede editar

La tabla productos se puede modificar con un UPDATE en SQL. Pero en la aplicación no hay ningún botón «Editar». El catálogo es de solo lectura: se ve, se lista, se imprime… y no se puede cambiar. El único camino es abrir una terminal, escribir SQL a mano, acordarse del id correcto y rezar para no equivocarse de fila.

Ese es el problema de hoy: darle a la aplicación una manera de corregir un registro. Y parece un detalle, hasta que uno descubre que «corregir un registro» son en realidad dos problemas distintos, y que el segundo tiene una trampa que puede borrar los datos que el usuario acababa de escribir.

Nota — por qué la «U» merece una clase entera

Crear un registro es escribir: la información viene del usuario y se guarda tal cual. Actualizar es escribir sobre algo que ya existe: hay que cargarlo, mostrarlo, recibirlo, compararlo, decidir si vale la pena cambiarlo y, si no vale, devolverlo intacto. Esa última parte —la que parece un detalle— es la que hoy se lleva media clase.

Unidad 01 · El mapa

El viaje de una edición

Corregir un registro son dos viajes al servidor, no uno. El primero carga el formulario con lo que hay guardado; el segundo guarda lo que el usuario escribió. Esta unidad dibuja el mapa completo y muestra las cuatro etiquetas de HTMX que lo hacen posible sin recargar la página.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el diagrama de los dos viajes

1.1 · Dos viajes, no uno

La intuición dice que editar es «mandar los datos y ya». Pero el servidor no sabe qué está guardado hasta que alguien se lo pregunta. Y la pantalla no puede mostrar un formulario con los valores actuales si no los ha recibido. Por eso el proceso son dos idas y venidas.

1 · GET
Pide el formulario

El botón «Editar» pide /productos/5/editar y el servidor responde con el formulario vacío… con los datos dentro.

◀── HTML
del formulario

Nota — por qué no es un solo viaje

Podrías «optimizar» y mandar solo el campo cambiado. Pero entonces el formulario aparecería vacío, el usuario no vería los demás valores, y al guardar se borrarían. Es el error clásico de la edición: parece que funciona y está destruyendo datos.

1.2 · La primera vuelta: pedir el formulario

La ruta que entrega el formulario es una sola línea de firma y dos de cuerpo. Todavía no la escribiremos —eso es el ejercicio de la unidad 6— pero sí hay que entender qué tiene que hacer.

vistas.py — la ruta que carga el formulario 
async def editar_producto_vista(request: Request, conn: ConnectionDep, producto_id: int):
    # 1. Buscar el registro en la base de datos
    producto = await obtener_producto(conn, producto_id)

    # 2. Si no existe, avisar (no reventar)
    if producto is None:
        return templates.TemplateResponse(

    # 3. Devolver el formulario con los valores guardados
    return templates.TemplateResponse(
        request=request,

            "cantidad": producto["cantidad"],

            "errores": {},
        },
    )

1.3 · La segunda vuelta: enviar los cambios

La ruta que guarda es la que decide. Recibe los cuatro campos del formulario y tiene tres caminos posibles:

Los tres finales de la ruta POST /productos/{id}
SituaciónQué haceRespondeCódigo
Los datos no son válidos No toca la base de datos. Vuelve el formulario con lo que escribió el usuario y un mensaje por campo fila_editar.html 422
Los datos son válidos Ejecuta el UPDATE sobre ese id y devuelve la fila nueva fila_actualizada.html 200

Advertencia — el orden de las comprobaciones importa

Si primero ejecutas el UPDATE y después compruebas si el id existe, ya es tarde. Y si validas después de guardar, un precio negativo ya está en la base de datos. El orden correcto es siempre el mismo: buscar → validar → guardar.

1.4 · Las cuatro etiquetas de HTMX

HTMX es lo que hace que todo esto ocurra sin recargar la página. No es magia: son cuatro atributos en el HTML que le dicen al navegador qué pedir y a quién reemplazar.

Las cuatro etiquetas y lo que hace cada una
AtributoQué significaEjemplo
hx-get Al hacer clic, pide esta URL hx-get="/productos/5/editar"
hx-post Al enviar el formulario, manda los datos a esta URL hx-post="/productos/5"
hx-target A qué elemento se le mete la respuesta hx-target="#producto-5"
hx-swap Cómo se reemplaza: entero o por fuera hx-swap="outerHTML"
componentes/fila_producto.html — la fila con el botón Editar

        <td>{{ producto.nombre }}</td>
        <td>{{ producto.precio }}</td>
        <td>{{ producto.cantidad }}</td>
        <td>

                hx-get="/productos/{{ producto.id }}/editar"
                hx-target="#producto-{{ producto.id }}"
                hx-swap="outerHTML">

            </button>

    </tr>

Precisión — qué significa outerHTML

«Reemplaza el elemento entero por su equivalente», incluido él mismo. La alternativa, innerHTML, metería el HTML nuevo dentro del elemento viejo. Como el tbody viejo seguiría ahí, la página terminaría con dos filas del mismo producto: la nueva y la vieja. outerHTML es el que corresponde cuando el servidor devuelve un elemento completo que sustituye a otro.

1.5 · Por qué cada fila es su propio tbody

Un detalle de HTML que parece unimportant y decide que todo funcione: cada producto vive en su propio tbody, no en una sola tabla con muchas filas. Es lo que permite reemplazar una fila y dejar las demás intactas.

Aplicación — la regla general

Cuando un servidor devuelve un fragmento que va a sustituir a una parte de la página, esa parte tiene que ser un elemento identificable por sí solo. Un id único y acotado: id="producto-5". Con eso, hx-target="#producto-5" sabe a quién reemplazar, y el resto de la tabla ni se entera.

2.1 · El contexto: lo que la plantilla necesita

Jinja2 no busca datos por su cuenta: recibe un diccionario llamado context y usa lo que hay dentro. La plantilla fila_editar.html necesita seis cosas.

Las seis claves del contexto y para qué sirve cada una
ClaveQué llevaPor qué está

precioEl precio guardadoÍdem

Precisión — por qué errores se pasa vacío y no se omite

La plantilla tiene esto:

fila_editar.html — la pregunta que se le hace al contexto 
{% if errores.nombre %}<p class="error">{{ errores.nombre }}</p>{% endif %}

Si en el contexto no existiera la clave errores, Jinja2 lanzaría un error al renderizar. Pasándola vacía —un {}— la pregunta simplemente devuelve «falsy» y el mensaje no aparece. Por eso la plantilla es la misma en los dos casos: la que abre el formulario y la que vuelve con errores. Lo único que cambia es lo que lleva errores dentro.

2.2 · El atributo que carga el dato

En HTML, el valor inicial de un campo de texto se escribe en el atributo value. Y en Jinja2, {{ nombre }} es una expresión que se sustituye por el valor de la variable nombre del contexto. Las dos piezas juntas son el mecanismo completo de la carga.

fila_editar.html — los cuatro campos con su valor

</label>

           inputmode="decimal">

Nota — el textarea es distinto

Un textarea no lleva value: su contenido va dentro de la etiqueta, entre <textarea> y </textarea>. Por eso la descripción se escribe así: {{ descripcion }} en el medio. Es un detalle pequeño que rompe la plantilla si se olvida.

2.4 · Por qué el formulario no puede empezar vacío

Advertencia — el error que destruye datos

Imagina que la ruta editar_producto_vista devuelve el formulario con el contexto {"producto": producto, "errores": {}} y se olvida de las claves nombre, precio y cantidad. La plantilla funciona: Jinja2 pone value="" y el formulario aparece vacío.

El usuario ve cuatro campos en blanco, piensa que tiene que escribir el producto completo, escribe solo lo que quiere cambiar… y al Guardar, el UPDATE escribe todos los campos, incluidos los que no tocó. Los otros campos se borran. Y lo peor: la aplicación no dio ningún error. Funcionó. Eso es lo que hace el error tan peligroso.

2.5 · El registro que no existe

Si alguien escribe /productos/99999/editar en la barra del navegador, no hay ningún producto con ese id. El servidor no debe romperse: debe avisar.

producto_no_encontrado.html — el aviso

            <div class="aviso-error">
                No se encontró el producto con id {{ producto_id }}.
            </div>
        </td>
    </tr>

Nota — «no existe» no es un error de servidor

Un id que no está en la tabla es una situación prevista, no un fallo. La respuesta es un HTML con un aviso y un código 200. Si en cambio devuelves un error 500, el usuario ve una página de servidor caído por haber escrito un número en la barra de direcciones. El estado 404 se reserva para cuando la ruta no existe, no el dato.

2.6 · El tipo del precio

Un detalle que solo aparece cuando la base de datos es real: la columna precio es de tipo NUMERIC, y PostgreSQL devuelve los números decimales como Decimal, no como float. La diferencia se ve al imprimir:

El mismo número, vengado de dos maneras distintas
TipoValorQué se imprime
float de Python45900.045900.0
Decimal de PostgreSQL45900.0045900.00
Precisión — por qué importa

Decimal conserva los ceros finales porque en una tabla de precios 45900.00 y 45900.0 no son el mismo número para quien lee la pantalla: uno dice «cuarenta y cinco mil novecientos», el otro «cuarenta y cinco mil novecientos con nada». Los float también acumulan errores de redondeo en las operaciones con dinero; Decimal no. Por eso las columnas de precio son NUMERIC y no REAL.

Unidad 03 · La segunda vuelta

Validar sin perder lo que el usuario escribió

La parte más delicada de editar. El servidor tiene que rechazar los datos malos sin castigar al usuario, y sobre todo sin devolverle un formulario vacío que le haga perder lo que llevaba tres minutos escribiendo. Esta unidad termina con el laboratorio, donde puedes ver el viaje entero.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el laboratorio del editor funcionando

3.1 · La conversión ingenua

Todo formulario envía texto. El precio llega como "45900.00", no como número. La intuición dice «convertirlo»: float(precio). Y esa es exactamente la trampa.

ejemplo — lo que pasa con un precio mal escrito 
precio = "abc"
print(float(precio))
# ValueError: could not convert string to float: 'abc'

Ese ValueError sube por la ruta y FastAPI lo convierte en un error 500: una página de «Internal Server Error» con un volcado de traza en la terminal. El usuario escribió mal un precio y perdió el formulario entero.

Advertencia — el error 500 no es un error de validación

Un 500 dice «el servidor se rompió». Un 422 dice «los datos no sirven». El usuario solo puede corregir lo segundo. Cuando el error 500 aparece, el problema está en tu código: alguien convierte una cadena sin mirar lo que venía.

3.2 · Quién hace la conversión: el esquema

La solución es no convertir a mano. Pydantic convierte y valida en el mismo paso: recibe el texto, lo convierte si puede y, si no puede, te da un error con el detalle de qué campo falló y por qué.

esquemas.py — las reglas, escritas una vez 
from pydantic import BaseModel, Field


class ProductoActualizar(BaseModel):
    """Datos que el estudiante envía al editar un producto."""

    nombre: str = Field(min_length=1, max_length=100)
    precio: float = Field(gt=0)
    cantidad: int = Field(ge=0)
    descripcion: str | None = None
python — lo que hace el esquema con el texto que llega
ProductoActualizar(nombre="Mouse", precio="19.99", cantidad="5")
precio=19.99 cantidad=5 ← el texto se convirtió solo
 
ProductoActualizar(nombre="Mouse", precio="abc", cantidad="5")
ValidationError: precio
Input should be a valid number, unable to parse string as a number
Nota — «19.99» entra bien porque el esquema lo pide como número

Pydantic convierte el texto al tipo que declaraste. Como declaraste precio: float, la cadena "19.99" se convierte en 19.99. Y como declaraste cantidad: int, la cadena "5" se convierte en 5. Si declaraste cantidad: str, se quedaría como texto y tendrías que convertirla tú. El tipo que declaras decide quién convierte.

3.3 · Del error de Pydantic al mensaje del formulario

El mensaje que da Pydantic es técnico: «Input should be a greater than 0». Es preciso, pero un estudiante de once grado no entiende esa frase. La plantilla, en cambio, ya sabe mostrar un mensaje bajo cada campo. Solo falta traducir.

vistas.py — traducir los errores a mensajes del formulario 
MENSAJES = {
    "nombre": "El nombre es obligatorio y no puede pasar de 100 caracteres.",
    "precio": "El precio debe ser un número mayor que cero.",
    "cantidad": "La cantidad debe ser un número entero que no sea negativo.",
}


def errores_en_espanol(excepcion: ValidationError) -> dict[str, str]:
    """Traduce los errores de Pydantic a un mensaje por campo."""
    errores = {}
    for error in excepcion.errors():
        campo = error["loc"][0]
        errores[campo] = MENSAJES.get(campo, "Revisa este valor.")
    return errores

error["loc"][0] es el nombre del campo que falló: Pydantic lo guarda como una lista, y el primer elemento es el campo. Con eso se arma un diccionario {"precio": "El precio debe ser…"}, y la plantilla lo muestra con {{ errores.precio }}.

3.4 · La regla que decide la clase: se conserva lo escrito

Distinción — dos formas de volver a mostrar el formulario

Cuando la validación falla hay dos maneras de responder, y solo una es correcta.

La incorrecta: volver a buscar el registro y mostrar sus valores originales. El usuario ve el formulario limpio, como si no hubiera escrito nada. Pierde su trabajo y no entiende qué pasó. Parece que el servidor «se ha olvidado» de lo que dijo.

La correcta: volver a mostrar el formulario con los valores que el usuario acaba de escribir, más el mensaje de error bajo cada campo que falló. El usuario ve lo que escribió, ve qué está mal, corrige solo ese campo y vuelve a guardar.

La diferencia entre las dos es una línea del contexto: en la correcta se pasan nombre, precio y cantidad con lo que llegó en la petición, no con lo que hay en la base de datos.

vistas.py — la respuesta cuando la validación falla 
async def guardar_producto_vista(request, conn, producto_id, nombre, precio, cantidad, descripcion):
    try:
        datos = ProductoActualizar(
            nombre=nombre or "",
            precio=precio if precio not in (None, "") else None,
            cantidad=cantidad if cantidad not in (None, "") else None,
            descripcion=descripcion or None,
        )
    except ValidationError as excepcion:
        # No se toca la base de datos. Se vuelve a mostrar el formulario
        # con los valores que escribió el usuario y el mensaje de error.
        return templates.TemplateResponse(
            request=request,
            name="componentes/fila_editar.html",
            context={
                "producto": {"id": producto_id},
                "nombre": nombre or "",
                "precio": precio or "",
                "cantidad": cantidad or "",
                "descripcion": descripcion or "",
                "errores": errores_en_espanol(excepcion),
            },
            status_code=422,
        )

5.1 · El enunciado

Ejercicio

Las tres consultas de la tienda TechStore

En repositorio.py hay tres funciones con su TODO. Tu trabajo es escribirlas. No es la parte más vistosa del ejercicio, pero es la que decide que nada se guarde donde no debe.

Ficha del sistema

Entrada Una conexión (conn) y, cuando hace falta, un producto_id
Salida Una lista de diccionarios, un diccionario, o None
Restricción Todas las consultas usan parámetros $1, $2…: nunca se concatena texto recibido dentro del SQL
Restricción El UPDATE identifica el registro por WHERE id = $1 y por nada más
Restricción Las funciones no imprimen: devuelven el dato

Requisitos

  1. obtener_productos(conn): devuelve todos los productos como lista de diccionarios, ordenados por nombre.
  2. obtener_producto(conn, producto_id): devuelve el diccionario del producto con ese id, o None si no existe.
  3. actualizar_producto(conn, producto_id, nombre, precio, cantidad, descripcion): ejecuta el UPDATE y devuelve True si modificó una fila, False si no había ninguna.
  4. Los SELECT con sus cinco columnas: id, nombre, precio, cantidad y descripcion.
  5. El UPDATE completo: las cuatro columnas que cambian y el WHERE id = $1.
  6. Que el UPDATE devuelva un booleano, no la cadena "UPDATE 1" cruda.

Modelo de respuesta

Fíjate en el orden de los parámetros del UPDATE: $1 es el id y los demás van del $2 al $5. El id va primero porque es el que identifica la fila; los que cambian van después, en el orden en que los pones en el SET.

repositorio.py — solución de referencia 
# Este archivo concentra todas las consultas SQL del ejercicio.
# Todas usan parámetros ($1, $2, ...): nunca se concatenan valores
# recibidos del formulario dentro del texto SQL.


async def obtener_productos(conn) -> list[dict]:
    """Devuelve todos los productos, ordenados por nombre."""
    filas = await conn.fetch(
        "SELECT id, nombre, precio, cantidad, descripcion "
        "FROM productos ORDER BY nombre"
    )
    return [dict(fila) for fila in filas]


async def obtener_producto(conn, producto_id: int) -> dict | None:
    """Busca un producto por su clave primaria (id)."""
    fila = await conn.fetchrow(
        "SELECT id, nombre, precio, cantidad, descripcion "
        "FROM productos WHERE id = $1",
        producto_id,
    )
    return dict(fila) if fila else None


async def actualizar_producto(
    conn,
    producto_id: int,
    nombre: str,
    precio: float,
    cantidad: int,
    descripcion: str | None,
) -> bool:
    """Actualiza un producto identificado por su clave primaria (id).

    Devuelve True si la consulta modificó una fila, False si no existía.
    """
    resultado = await conn.execute(
        "UPDATE productos "
        "SET nombre = $2, precio = $3, cantidad = $4, descripcion = $5 "
        "WHERE id = $1",
        producto_id,
        nombre,
        precio,
        cantidad,
        descripcion,
    )
    return resultado == "UPDATE 1"

La línea que más se olvida es conn.fetch(...) y conn.fetchrow(...): asyncpg devuelve filas, no diccionarios. Por eso hay que convertirlas con dict(fila). Y fetchrow devuelve None si no encuentra nada: de ahí el if fila else None.

5.2 · La regla que no se negocia: nunca concatenar

Advertencia — la forma prohibida

Esta consulta parece más cómoda y es un error grave:

ejemplo — la forma que NO se debe escribir 
# ¡NUNCA! El texto recibido se mete dentro del SQL
consulta = f"UPDATE productos SET nombre = '{nombre}' WHERE id = {id}"

# Si el nombre es:  O'Brien'; DROP TABLE productos; --
# la consulta se convierte en dos sentencias y la tabla se va.

Con parámetros, el mismo nombre llega como un valor y no como parte del texto de la consulta. PostgreSQL lo trata como dato, nunca como código.

La misma operación, escrita de las dos maneras
Con concatenaciónCon parámetros
El texto llega al servidor Como parte de la instrucción Como un valor, con su tipo
Un ' en el nombre Rompe la consulta Es simplemente un apóstrofo
Un id con texto Se ejecuta la consulta equivocada PostgreSQL dice que el tipo no coincide
Un DROP TABLE Borra la tabla Se guarda como texto, sin efecto
Precisión — cómo funciona por dentro

Cuando envías una consulta con $1, el servidor de PostgreSQL la prepara primero: analiza el texto, decide qué hacer con cada hueco y guarda un plan. Solo entonces llegan los valores, ya separados del texto. Por eso una consulta parametrizada además de ser segura es más rápida: el plan se calcula una vez y se reutiliza.

5.3 · «UPDATE 1» y «UPDATE 0»

Cuando asyncpg ejecuta un UPDATE, no devuelve las filas modificadas: devuelve una cadena con el número de filas afectadas. Eso es lo que te dice si el registro existía.

Lo que devuelve la consulta y lo que significa
DevuelveSignificaQué debe hacer la ruta
"UPDATE 1" Se modificó una fila: el producto existía Devolver fila_actualizada.html
"UPDATE 0" No se modificó nada: el id no existe Devolver producto_no_encontrado.html

Restricción La ruta nunca escribe texto directamente: siempre devuelve una plantilla

Requisitos

  2. POST /productos/{producto_id}: valida con ProductoActualizar y, según el resultado, responde con uno de los tres fragmentos.
  3. La traducción de errores: la función errores_en_espanol() que convierte los errores de Pydantic en un mensaje por campo.
  4. La comprobación de existencia en el POST: buscar el producto antes de guardar, para poder avisar si no está.

Pista — por qué se vuelve a leer el producto

Después del UPDATE podrías mostrar los valores que tú enviaste. Pero volver a leerlo es más honesto: lo que se pinta en pantalla es exactamente lo que quedó guardado, con el formato de la base de datos (un Decimal con dos decimales, por ejemplo). Y si la base de datos cambiara el valor por su cuenta, la pantalla mostraría la verdad.

Modelo de respuesta

La estructura de la ruta del POST es la que resuelve el problema de la clase: primero el try/except que valida, y solo si no hay errores se toca la base de datos.

vistas.py — la ruta que guarda, solución de referencia 
async def guardar_producto_vista(
    request: Request,
    conn: ConnectionDep,
    producto_id: int,
    nombre: Annotated[str | None, Form()] = None,
    precio: Annotated[str | None, Form()] = None,
    cantidad: Annotated[str | None, Form()] = None,
    descripcion: Annotated[str | None, Form()] = None,
):
    try:
        datos = ProductoActualizar(
            nombre=nombre or "",
            precio=precio if precio not in (None, "") else None,
            cantidad=cantidad if cantidad not in (None, "") else None,
            descripcion=descripcion or None,
        )
    except ValidationError as excepcion:
        return templates.TemplateResponse(
            request=request,
            name="componentes/fila_editar.html",
            context={
                "producto": {"id": producto_id},
                "nombre": nombre or "",
                "precio": precio or "",
                "cantidad": cantidad or "",
                "descripcion": descripcion or "",
                "errores": errores_en_espanol(excepcion),
            },
            status_code=422,
        )

    producto = await obtener_producto(conn, producto_id)
    if producto is None:
        return templates.TemplateResponse(
            request=request,
            name="componentes/producto_no_encontrado.html",
            context={"producto_id": producto_id},
        )

    await actualizar_producto(
        conn,
        producto_id,
        datos.nombre,
        datos.precio,
        datos.cantidad,
        datos.descripcion,
    )

    actualizado = await obtener_producto(conn, producto_id)
    return templates.TemplateResponse(
        request=request,
        name="componentes/fila_actualizada.html",
        context={"producto": actualizado},
    )

Nota una cosa: el try/except cubre solo la construcción del esquema. Si el UPDATE fallara, su error se vería: y debe verse, porque sería un problema real de la aplicación.

7.2 · El caso que no está en la lista

La lista de comprobaciones es buena, pero está pensada para el camino previsto. Un buen programador busca el camino que no está previsto. El más importante de esta clase es este:

Advertencia — «Guardar» dos veces

Si el usuario pulsa «Guardar» dos veces muy rápido, se mandan dos peticiones. Las dos validan bien y las dos ejecutan su UPDATE. El resultado visible es el mismo, así que parece inofensivo… pero la segunda petición se ejecutó con los datos anteriores en la base de datos y puede dejar la fila en un estado inesperado.

¿Cómo lo resolverías? Pistas: el botón se puede deshabilitar mientras se guarda; o se puede usar SELECT ... FOR UPDATE para bloquear la fila; o se puede incluir un número de versión en la tabla y comprobar que no haya cambiado. Ninguna de las tres es obligatoria en el ejercicio, pero saber que el problema existe ya te pone por delante del 90 % de los que developpen esto.

7.4 · Síntesis: siete ideas para llevarse

01

Editar es un viaje de ida y vuelta: primero se carga lo guardado, después se guarda lo nuevo.

02

El formulario de edición llega lleno. Un formulario vacío no es «limpio»: es un formulario que va a borrar lo que no toques.

03

El orden no se negocia: buscar, validar y luego guardar. Al revés, un dato malo llega a la base de datos.

04

Cuando la validación falla, el usuario recibe lo que escribió: perder su trabajo es la peor respuesta posible.

05

Un 422 significa «el dato no sirve»; un 500 significa «el servidor se rompió». Solo el primero se puede corregir.

06

Las consultas se parametrizan siempre. Un valor pegado dentro del texto SQL puede cambiar lo que la consulta hace.

07

WHERE id = $1 es lo que separa «corregir un registro» de «corregir todos los registros».
