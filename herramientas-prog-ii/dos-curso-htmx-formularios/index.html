Unidad 00 · Apertura

Del formulario que recarga la página al fragmento que se actualiza solo

La clase 1 dejó el mapa: el navegador pide, el servidor responde, el contrato es HTTP. Esta clase baja ese mapa a un caso concreto y muy común —el formulario— y construye encima una capa que elimina de un plumón la recarga de página: HTMX, en su versión 4, que es la que se usa hoy.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: entorno listo

0.1 · El problema que HTMX viene a resolver

Consideremos el formulario más sencillo del mundo: una caja de texto, un botón de «Buscar» y una lista de resultados debajo. Con HTML puro, al pulsar el botón el navegador hace lo que ha hecho desde 1993: envía el formulario al servidor, recibe una página HTML completa y reemplaza la página entera. El usuario pierde la posición del scroll, la página parpadea, y el servidor tiene que reconstruir desde cero cosas que no cambiaron.

La alternativa clásica es escribir JavaScript a mano: interceptar el envío, llamar a fetch(), recibir JSON, modificar el DOM. Funciona, pero se pierde algo importante: el servidor deja de producir HTML y pasa a producir datos, y entonces hay que reconstruir en el navegador la presentación que el servidor ya sabe generar.

La tercera vía

HTMX propone una tercera opción: mantener al servidor como productor de HTML, y limitar la petición a la parte de la página que realmente cambia. El servidor sigue renvolviendo HTML —con sus plantillas, sus condicionales y su lógica—, pero devuelve un fragmento en lugar de una página completa, y el navegador lo coloca en el sitio exacto que le indiques.

La consecuencia práctica es que el JavaScript escrito a mano desaparece casi por completo: no hace falta

Unidad 01 · El modelo

El modelo de HTMX: el atributo como verbo

HTMX tiene pocas ideas y muchos atributos. Si entiendes el modelo mental que hay detrás, los atributos son solo consecuencia. Esta unidad construye ese modelo y lo aplica a un caso real.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: primer fragmento

1.1 · La idea central

HTMX pertenece a una familia de estilos llamada hipermedia: en lugar de que el cliente consuma datos y los presente, el servidor produce directamente el HTML que el navegador debe mostrar. La página no se «construye» en el navegador: se reemplaza por algo que el servidor ya escribió.

De ahí se sigue todo: si el servidor produce HTML, no hace falta traducir ese HTML a JSON y reconstruirlo en el cliente. Solo hace falta decidir qué fragmento se pide y dónde se coloca. Eso son, respectivamente, el atributo hx-get (o hx-post) y el atributo hx-target.

1.2 · Los verbos: del método HTTP al atributo

El primer grupo de atributos de HTMX es casi una traducción de los métodos HTTP que estudiaste en la clase 1. La correspondencia no es casual: el atributo es el método.

Atributos que equivalen a los métodos HTTP
AtributoMétodo HTTPUso típico
hx-getGETConsultar y mostrar un fragmento
hx-postPOSTEnviar un formulario, crear un recurso
hx-putPUTReemplazar un recurso completo
hx-patchPATCHModificar un recurso parcialmente
hx-deleteDELETEEliminar un recurso
Precisión

El atributo hx-get no es «el botón que carga cosas»: es la petición. Si el elemento que lo lleva es un <form>, HTMX envía el GET con los valores del formulario como parámetros de consulta. Si el elemento es un <form method="post"> con hx-post, el método es ese.

1.3 · Dónde y cómo se coloca la respuesta

hx-target
El elemento que será reemplazado. Un selector CSS: #resultado, .lista, closest form, this, next .error.
hx-swap
Cómo se inserta la respuesta. Por defecto, innerHTML: se reemplaza el contenido interior del objetivo, y el objetivo en sí permanece.
hx-trigger
Qué evento dispara la petición. Por defecto, click para botones y enlaces, y submit para formularios. Puede ser load, change, keyup changed delay:300ms…
hx-swap-oob
Marca un fragmento de la respuesta para que se actualice otro elemento distinto del objetivo principal.
Valores de hx-swap
ValorQué hace exactamenteEjemplo de uso
innerHTMLReemplaza el contenido interior del objetivoActualizar una lista (por defecto)
outerHTMLReemplaza el elemento completo, incluido él mismoReemplazar un formulario entero por su versión con errores
textContentReemplaza solo el texto, sin interpretar el HTMLActualizar un contador o un total
beforeendInserta al final, dentro del objetivoAñadir un elemento a una lista
afterbeginInseta al principio, dentro del objetivoMostrar primero el elemento más reciente
beforebeginInserta justo antes del elementoColocar un mensaje de aviso encima
afterendInserta justo después del elementoColocar un botón «editar» junto a cada fila
deleteElimina el elemento del DOMBorrar una fila de una lista
noneNo intercambia nadaCuando el efecto lo produce otro elemento

1.4 · El ciclo de una petición HTMX

Vale la pena mirar con detalle lo que ocurre entre que el usuario hace clic y que el fragmento aparece. La comparación con la clase 1 es instructiva: allí describimos las siete fases de una petición HTTP; aquí describimos las mismas, más el trabajo específico que hace HTMX.

1 El evento ocurre · ClienteUn clic, un submit, un change. HTMX intercepta el evento: se anula el comportamiento por defecto y no se recarga la página.
2 Se construye la petición · ClienteMétodo, URL, cabeceras y — si el elemento es un formulario — los valores de sus campos. Los parámetros de la URL y las cabeceras se combinan con el cuerpo del formulario.
3 Viaje de red · RedLas fases 2 a 4 de la clase 1: DNS, conexión TCP/TLS y envío. HTMX usa internamente fetch() desde la versión 4.
4 El servidor produce el fragmento · ServidorEnruta, valida, ejecuta la lógica y renderiza una plantilla Jinja2. Devuelve solo la porción de HTML necesaria, con su código de estado.
5 La respuesta vuelve · Servidor → ClienteEl fragmento HTML llega completo. El código de estado —200, 422, 404— llega con él, y en HTMX 4 eso tiene consecuencias nuevas.
6 El intercambio · ClienteHTMX coloca el fragmento en el objetivo según hx-target y hx-swap. No hay recarga: solo cambia esa porción del DOM.
7 El contenido nuevo se procesa · ClienteHTMX examina el HTML que acaba de insertar: si dentro hay elementos con atributos hx-*, también quedan activos. Es la propiedad que hace que los fragmentos se puedan componer entre sí.
Nota

La fase 7 es la que casi nadie menciona y la que más sorprende. Un fragmento no es un trozo de página muerto: es una página en miniatura que puede tener sus propios botones con hx-get. Por eso los formularios que devuelven «el formulario con errores» pueden seguir siendo interactivos después del intercambio.

Ejemplo guiado 1.1 — El primer fragmento, de extremo a extremo 12 min

Vamos a construir el caso de la unidad 0: una lista de libros que se carga sin recargar la página. Cuatro archivos, cuatro decisiones.

1
El servidor: la ruta que devuelve un fragmento

La ruta no devuelve JSON ni una página completa: devuelve una plantilla, y esa plantilla es el fragmento. Fíjate en la firma moderna de TemplateResponse: request va como argumento con nombre, y el contexto en un diccionario aparte.

main.py 
from contextlib import asynccontextmanager
from typing import Annotated

from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates


def lifespan(app: FastAPI):
    # Aquí se abrirían y cerrarían recursos (base de datos, caché)
    yield


app = FastAPI(lifespan=lifespan)
templates = Jinja2Templates(directory="templates")

LIBROS = [
    {"id": 1, "titulo": "Cien años de soledad", "disponible": True},
    {"id": 2, "titulo": "Pedro Páramo", "disponible": False},
]


@app.get("/api/libros", response_class=HTMLResponse)
async def listar_libros(request: Request):
    return templates.TemplateResponse(
        request=request,
        name="fragmento_libros.html",
        context={"libros": LIBROS},
    )
2
La plantilla del fragmento

Esta plantilla no es una página: es un trozo. Por eso no lleva <html>, ni <head>, ni <body>. Solo el contenido que se va a insertar.

templates/fragmento_libros.html 
<ul class="lista-libros">
  <li class="libro">
    <span class="titulo">{{ libro["titulo"] }}</span>
    <span class="estado">
      <span class="{{ 'disponible' if libro['disponible'] else 'prestado' }}">
        {{ 'Disponible' if libro["disponible"] else 'Prestado' }}
      </span>
    </span>
  </li>
</ul>
3
La página: un contenedor que se llena solo

hx-trigger="load" significa «haz la petición en cuanto este elemento exista en la página». El contenido inicial —«Cargando…»— es lo que el usuario ve mientras viaja la petición; se reemplaza en cuanto llega el fragmento.

templates/index.html 
<h1>Catálogo</h1>

<div id="catalogo"
     hx-get="/api/libros"
     hx-trigger="load"
     hx-swap="innerHTML">
  <p>Cargando…</p>
</div>
4
Comprobación

Añade la ruta de la página completa al main.py y comprueba en el navegador que la lista aparece sin que la página se recargue. En las DevTools, pestaña Network, la petición /api/libros aparecerá con tipo fetch y sin una segunda petición al documento HTML.

Observa: si al recargar la página aparece la lista de inmediato en el HTML de origen, es que la ruta de la página está haciendo el trabajo de la ruta del fragmento. El fragmento debe llegar después, por AJAX.

Aplicación

Añade un segundo botón a la página que pida el mismo fragmento con hx-get y hx-target="#catalogo". Comprueba que el contenido se reemplaza y que el resto de la página (el título, el menú) no se mueve. Anota en el cuaderno qué observable del modelo de la clase 1 se mantiene y cuál es nuevo.

Unidad 02 · La versión

HTMX 4.0: qué cambió y por qué importa

HTMX 4.0 no es una actualización menor: cambió el comportamiento por defecto de la biblioteca en puntos que afectan directamente al código que escribiremos. Conocerlos no es un detalle menor: es la diferencia entre que la aplicación funcione o no.

⏱ 30 minutos 📄 Lectura comparada 🧭 Producto: guía de migración

2.1 · Las tres grandes

La versión 4.0.0 se publicó el 28 de agosto de 2026. El autor resume el cambio en una frase: «casi idéntico a la versión 2 para el usuario, con tres diferencias profundas». Son esas tres las que cambian el código.

1 · fetch() en lugar de XMLHttpRequest
La biblioteca reescribió su transporte interno. Para ti casi no cambia nada… salvo que todos los eventos htmx:xhr:* desaparecieron, porque no hay XHR que observar. Y aparecen capacidades que antes eran imposibles: el streaming de HTML y los websockets, que dependían de que la biblioteca controlara la respuesta byte a byte.
2 · La herencia es explícita
Antes, un atributo hx-target en un contenedor se heredaba a todos sus descendientes. Ahora no: hay que añadir el sufijo :inherited de forma explícita. Es el cambio que más rompe cosas, y lo veremos en detalle.
3 · Las respuestas de error también se intercambian
En la versión 2, una respuesta 4xx o 5xx no se insertaba en la página: se descartaba. En la versión 4, sí se inserta (las únicas excepciones son 204 y 304). Esto es exactamente lo que hace posible mostrar los errores de validación de un formulario en línea, que es el tema central de esta clase.
Aplicación — por qué esto importa para los formularios

El cambio 3 es la buena noticia: el servidor puede responder 422 con un fragmento HTML que contiene los mensajes de error, y ese fragmento se inserta en el formulario. Antes de HTMX 4 había que hacer malabares con hx-swap="none" y un evento htmx:responseError para inyectar el error a mano.

2.2 · La herencia explícita, en detalle

La herencia automática era cómoda y impredecible. Cómoda porque un solo atributo bastaba; impredecible porque era imposible saber de un vistazo qué botón de una tabla iba a usar el hx-target de tres niveles más arriba.

herencia — versión 2 frente a versión 4 
# HTMX 2: el botón heredaba hx-target y hx-swap del contenedor
<div hx-get="/api/detalle" hx-target="#panel">
  <button>Ver detalle</button>
</div>

# HTMX 4: hay que pedirlo explícitamente con el sufijo :inherited
<div hx-get:inherited="/api/detalle"
     hx-target:inherited="#panel">
  <button>Ver detalle</button>
</div>
Advertencia — el fallo silencioso

El síntoma típico de olvidar el :inherited es desconcertante: el atributo parece funcionar (el botón sí hace la petición), pero el resultado se inserta en el sitio equivocado, o no se inserta en ninguno. En el caso de hx-headers con un token CSRF, el síntoma es aún peor: el servidor empieza a responder 403 sin que nada parezca roto.

Regla práctica: si un atributo hx-* estaba en un padre y los hijos lo usaban, en la versión 4 hay que añadirle :inherited.

2.5 · Lo que no cambió

Es igual de importante saber qué se mantiene, porque significa que el grueso de lo que ya sabes sigue siendo válido:

  • Los atributos principales: hx-get, hx-post, hx-put, hx-delete, hx-target, hx-swap, hx-trigger, hx-vals, hx-include, hx-confirm, hx-indicator, hx-boost.
  • Los valores de hx-swap: innerHTML, outerHTML, textContent, beforeend, afterbegin, beforebegin, afterend, delete, none.
  • La idea central: el servidor produce HTML y el navegador coloca un fragmento.
  • La ausencia de JavaScript propio: HTMX es una librería declarativa, se escribe HTML, no se escribe código.
Nota — el tamaño de la biblioteca

HTMX 4 sigue siendo una librería pequeña: unos 14 KB comprimidos, sin dependencias. Todo lo que hace cabe en un archivo y no necesita compilación. Para un curso de grado once eso es una ventaja práctica: el único «dependency» que hay que descargar es el propio archivo del CDN.

2.6 · Herramientas de migración

Si parte de tu proyecto ya usaba HTMX 2, existen dos puentes. Ninguno es obligatorio en una aplicación nueva, pero conviene conocerlos.

terminal — verificador de actualización 
# Analiza una carpeta de plantillas y señala los problemas
npx htmx.org@4.0.0 upgrade-check -- ./templates
script — puentes de compatibilidad 
// Puente 1: restaurar la herencia implícita (comportamiento de la versión 2)
htmx.config.implicitInheritance = true;

// Puente 2: volver a descartar las respuestas de error
htmx.config.noSwap = [204, 304, '4xx', '5xx'];

// Puente 3: cargar la extensión htmx-2-compat
// <script src="https://unpkg.com/htmx.org@4.0.0/dist/ext/htmx-2-compat.js"></script>
Precisión

Los puentes sirven para hacer que una aplicación de HTMX 2 siga funcionando mientras se migra pieza a pieza. No son la estrategia recomendada para una aplicación nueva: si empiezas hoy, escribe directamente con las reglas de la versión 4. La única excepción razonable es un proyecto heredado que no puedes tocar entero.

Ejemplo guiado 2.1 — Migrar un fragmento de la versión 2 a la 4 10 min

Partimos de un fragmento escrito para HTMX 2 y lo llevamos a la versión 4. El ejercicio sirve aunque escribas desde cero: muestra qué hay que revisar en un proyecto existente.

1
El código original (HTMX 2)

Un panel que carga un detalle y un botón que lo borra. El botón no declara hx-target: lo hereda del contenedor. Y el borrado usa hx-disable para desactivar el botón mientras dura la petición.

antes — HTMX 2 
<div id="panel"
     hx-get="/api/detalle"
     hx-target="#resultado"
     hx-trigger="load">

  <button hx-delete="/api/prestamos/7"
          hx-disabled-elt="this">
    Eliminar
  </button>
</div>
2
El código migrado (HTMX 4)

Tres cambios y una decisión de diseño.

después — HTMX 4 
<div id="panel"
     hx-get:inherited="/api/detalle"
     hx-target:inherited="#resultado"
     hx-trigger="load">

  <button hx-delete="/api/prestamos/7"
          hx-disable="this">
    Eliminar
  </button>
</div>
3
El inventario de cambios

hx-target → hx-target:inherited y hx-get → hx-get:inherited, porque el botón los necesita. hx-disabled-elt → hx-disable, porque ese nombre ahora significa otra cosa. Y una decisión: el hx-delete ya no incluye los valores del formulario, así que si el borrado necesita algún dato, hay que añadir hx-include="closest form".

Observa: el botón no tenía hx-target propio. Al heredar el del contenedor, en la versión 4 el borrado insertaría su respuesta en #resultado… pero solo si se le dice. Sin :inherited, cada botón necesita su propio objetivo, que suele ser lo más claro.

Unidad 03 · Los datos

Anatomía de un formulario: el contrato de los datos

Un formulario no es una caja con campos: es un contrato entre el navegador y el servidor sobre qué datos se envían y con qué nombre. Entender ese contrato es lo que separa «el formulario no funciona» de «el navegador no envió el campo porque le falta el name».

3.1 · Las piezas de un formulario

Todo formulario tiene tres capas: el contenedor (<form>), los campos (<input>, <select>, <textarea>) y sus etiquetas (<label>). El atributo que las conecta es name.

html — un campo completo 
<label for="estudiante">Nombre del estudiante</label>

<input
  type="text"
  id="estudiante"
  name="estudiante"
  required
  minlength="3"
  maxlength="80"
  autocomplete="name"
  placeholder="Ana Torres">
name
El nombre de la clave con la que el valor viajará al servidor. Sin name, el campo no se envía. Es el atributo más importante del formulario y el que más se olvida.
id
El identificador dentro de la página. Lo usan el atributo for de la etiqueta y las reglas de CSS. No tiene relación directa con el servidor.
for (de la etiqueta)
Apunta al id del campo. Al pulsarlo, el navegador coloca el cursor en el campo. Es un detalle de accesibilidad, no de funcionalidad.
type
El tipo de dato esperado. No solo cambia el aspecto: determina la validación nativa y el teclado que aparece en el móvil.
Distinción — id no es name

Son nombres parecidos con propósitos distintos y con una consecuencia práctica: un campo puede tener id="correo" y name="email". El servidor recibiría la clave email, no correo. Cuando un formulario «no manda los datos», la primera comprobación es siempre esta: ¿el campo tiene name? ¿y el name es el que la ruta espera?

3.2 · La validación nativa del navegador

Los navegadores modernos validan los formularios por su cuenta, sin una sola línea de JavaScript. Es una de las mayores-herramientas disponibles y la mayoría de los estudiantes la desconocen.

Atributos de validación nativa
AtributoQué compruebaEjemplo
requiredQue no esté vacío<input required>
type="email"Que tenga forma de correo<input type="email">
type="number"Que sea un número (y no texto)<input type="number">
min / maxRango de valores numéricos<input type="number" min="1" max="30">
minlength / maxlengthLongitud del texto<input minlength="3" maxlength="80">
patternUna expresión regular<input pattern="[0-9]{3}-[0-9]{3}">

Advertencia — novalidate desactiva la primera barrera

Añadir novalidate al formulario no elimina la necesidad de validar: elimina la validación del navegador. Si lo haces, el servidor se convierte en la única barrera, y el usuario pierde la retroalimentación inmediata. Úsalo solo cuando el servidor sea capaz de devolver un fragmento de error bien diseñado: que es precisamente lo que aprenderemos en la unidad 6.

Precisión — la validación del navegador no es seguridad

La validación nativa es una comodidad de experiencia de usuario: evita un viaje de ida y vuelta al servidor para descubrir que faltaba un campo. No es una garantía, porque quien quiere saltársela puede: la petición se puede escribir a mano, o se puede llamar a la ruta directamente con curl. Es la misma frontera de la clase 1: la verificación que importa es la del servidor.

3.3 · El formulario completo

html — formulario de solicitud de préstamo 
<form id="formulario-prestamo"
      method="post"
      action="/api/prestamos">

  <label for="estudiante">Estudiante</label>
  <input type="text" id="estudiante"
         name="estudiante" required
         minlength="3" maxlength="80">

  <label for="correo">Correo institucional</label>
  <input type="email" id="correo"
         name="correo" required>

  <label for="dias">Días de préstamo</label>
  <input type="number" id="dias"
         name="dias" min="1" max="30"
         value="7" required>

  <button type="submit">Solicitar préstamo</button>
</form>
Nota

Fíjate en que el formulario tiene method="post" y action. Con HTMX, esos dos atributos se vuelven irrelevantes mientras el formulario no se envíe de la manera tradicional: los sustituyen hx-post y hx-target. Pero conviene dejarlos: si el JavaScript falla o se desactiva, el formulario sigue funcionando como un formulario normal. Es una degradación elegante.

Unidad 05 · El servidor

Formularios en FastAPI: recibir y validar

El formulario es la mitad del problema. La otra mitad es el servidor: recibir los datos con la clave correcta, validarlos de verdad y responder con algo útil. Esta unidad cierra el circuito con el framework moderno.

⏱ 35 minutos 💻 Práctica guiada 🧭 Producto: ruta con validación

5.1 · La pieza que faltaba: python-multipart

FastAPI no puede leer formularios por su cuenta. El parsing de multipart/form-data y de application/x-www-form-urlencoded lo hace una biblioteca aparte, python-multipart, y por eso el error que verás si la olvidas es engañoso: dice que «falta python-multipart» cuando lo que falta es instalarlo.

En esta clase no hace falta instalar nada: uv add "fastapi[standard]" ya lo incluye. Si en algún momento instalas FastAPI sin el grupo standard, recuerda añadir uv add python-multipart.

5.2 · Recibir los campos: Form() y Annotated

La forma moderna de declarar un campo de formulario en FastAPI combina dos cosas: el tipo de Python, que dice de qué tipo es el dato, y Annotated, que dice de dónde viene y con qué restricciones. El valor por defecto se escribe en el lugar habitual, y la metadata va al lado.

main.py — recibir datos del formulario 
from typing import Annotated

from fastapi import FastAPI, Form, Request
from fastapi.responses import HTMLResponse


@app.post("/api/prestamos", response_class=HTMLResponse)
async def crear_prestamo(
    request: Request,
    estudiante: Annotated[str, Form(min_length=3, max_length=80)],
    correo: Annotated[str, Form(max_length=120)],
    dias: Annotated[int, Form(ge=1, le=30)],
):
    prestamo = {
        "estudiante": estudiante,
        "correo": correo,
        "dias": dias,
    }
    return templates.TemplateResponse(
        request=request,
        name="fragmento_prestamo_creado.html",
        context={"prestamo": prestamo},
    )
Nota

Fíjate en que estudiante, correo y dias son los nombres de los parámetros de la función, y también tienen que ser los valores del atributo name del HTML. Es la misma correspondencia de la clase 1 entre la ruta y la función que la atiende. Si el HTML dice name="dias_prestamo" y la función dice dias, FastAPI devolverá un error de validación por campo ausente.

5.3 · Formularios con número variable de campos

A veces el número de campos no se conoce de antemano: un formulario dinámico generado a partir de una base de datos, o un formulario con una lista de casillas repetibles. En ese caso se lee el formulario completo de la petición:

main.py — formulario dinámico 
from starlette.datastructures import FormData


@app.post("/api/dinamico")
async def recibir_dinamico(request: Request):
    formulario: FormData = await request.form()
    # formulario es un diccionario con múltiples valores por clave:
    # formulario.get("nombre") y formulario.getlist("opciones")
    return {"recibido": dict(formulario)}
Precisión

request.form() es una función asíncrona: hay que esperarla con await. Y devuelve un FormData, que se parece a un diccionario pero admite claves repetidas (útil para listas de casillas). En el 90 % de los casos, con campos conocidos y de cantidad fija, la forma declarativa con Form() es mejor: deja que FastAPI haga la validación, la conversión de tipos y la documentación automática.

5.4 · El modelo Pydantic como contrato

Cuando el formulario tiene varios campos con reglas relacionadas, conviene declarar un modelo Pydantic y usarlo como contrato. La ventaja no es estética: es que el mismo modelo puede validar y serializar, y que la documentación de la API se genera sola.

main.py — modelo de formulario 
from pydantic import BaseModel, Field


class PrestamoForm(BaseModel):
    estudiante: Annotated[str, Field(min_length=3, max_length=80)]
    correo: Annotated[str, Field(max_length=120)]
    dias: Annotated[int, Field(ge=1, le=30)]


@app.post("/api/prestamos/modelo", response_class=HTMLResponse)
async def crear_con_modelo(request: Request, datos: Annotated[PrestamoForm, Form()]):
    return templates.TemplateResponse(
        request=request,
        name="fragmento_prestamo_creado.html",
        context={"prestamo": datos.model_dump()},
    )
Precisión — la sintaxis de Pydantic v2

Si has visto tutoriales antiguos, notarás que aquí no hay class Config ni @validator: ambos son de Pydantic v1 y ya no funcionan. FastAPI 0.126.0 eliminó el soporte de Pydantic v1 por completo. En la versión 2, la configuración se escribe con model_config = ConfigDict(...) y las validaciones de campo con Field(...), que es justo lo que se ve arriba.

5.5 · Renderizar la respuesta con Jinja2

La firma moderna de TemplateResponse usa argumentos con nombre. Fíjate en el orden: request es el primero y va con su nombre, el nombre de la plantilla va con su nombre, y el contexto es un diccionario aparte. La forma antigua (TemplateResponse("x.html", {"request": request})) está obsoleta desde FastAPI 0.108.0.

Aplicación — dos datos, dos rutas

En el contexto de la plantilla, prestamo["estudiante"] es un diccionario normal de Python. Pero para el HTML, casi siempre conviene un objeto con atributos: prestamo.estudiante se lee mejor en la plantilla y Pydantic lo ofrece con model_dump() (diccionario) o directamente como atributo si pasas el modelo.

5.6 · Las dos capas de validación, juntas

Advertencia — el error 422 por defecto

Cuando FastAPI rechaza los datos, su respuesta por defecto es JSON: {"detail":[{"type":"string_too_short","loc":["body","estudiante"],…}]}. Ese JSON es perfecto para un programa, pero en una página web se vería como un bloque de texto feo dentro del formulario. En la unidad 6 lo cambiamos por un fragmento HTML con los mensajes de error, que es justo para lo que sirve el nuevo comportamiento de HTMX 4.

Unidad 06 · El control

Errores, estados y control fino

Esta es la unidad donde todo lo anterior encaja. HTMX 4 permite que el servidor responda con un fragmento de error y que ese fragmento aparezca en línea, dentro del formulario, sin recarga. Con eso, los demás atributos pasan a ser afinado: indicadores de carga, deshabilitar botones, confirmar, sincronizar.

⏱ 35 minutos 💻 Práctica guiada 🧭 Producto: errores en línea

6.1 · El gran cambio: el error también se inserta

En HTMX 2, una respuesta 422 no se insertaba en la página: HTMX la descartaba y disparaba el evento htmx:responseError. Mostrar el error al usuario exigía escribir JavaScript que inyectara el HTML a mano. En HTMX 4, la respuesta se inserta como cualquier otra, y ese problema desaparece.

Advertencia — la contrapartida

Como ahora se inserta todo, también se inserta lo que no debería. Si tu servidor devuelve una página de error completa de FastAPI (con su HTML, sus estilos y su menú) y esa página aterriza dentro de tu formulario, el resultado es un desastre visual. La regla es simple: diseña tus respuestas de error como contenido de intercambio, o usa hx-status para dirigirlas a otro sitio.

6.2 · Dirigir la respuesta según el código: hx-status

El atributo hx-status es nuevo en la versión 4 y resuelve ese problema. Su sintaxis es hx-status:CÓDIGO="clave:valor clave:valor", donde el código puede ser exacto (422), un comodín de dos cifras (50x) o de una (5xx). Se evalúan por especificidad: primero el código exacto, luego el comodín de dos, luego el de uno.

html — directing respuestas por código 
<form hx-post="/api/prestamos"
      hx-target="#formulario"
      hx-swap="outerHTML"
      hx-status:422="target:#errores"
      hx-status:5xx="swap:none">
  <div id="errores"></div>
  <button type="submit">Enviar</button>
</form>

6.3 · El patrón completo: formulario + fragmento de error

Este es el patrón central de la clase. Se compone de tres piezas: un manejador de errores de validación en FastAPI que devuelve HTML en vez de JSON, una plantilla de fragmento de error, y el formulario que dice dónde colocar cada respuesta.

main.py — manejar los errores de validación como HTML 
from fastapi.exceptions import RequestValidationError


@app.exception_handler(RequestValidationError)
async def errores_de_validacion(request: Request, exc: RequestValidationError):
    # exc.errors() trae la lista de fallos: campo, tipo de error y mensaje
    return templates.TemplateResponse(
        request=request,
        name="fragmento_errores.html",
        context={"errores": exc.errors()},
        status_code=422,
    )
templates/fragmento_errores.html 
<div class="aviso aviso-error">
  <strong>No se pudo registrar el préstamo</strong>
  <ul>
    <li> <strong>{{ error["loc"][-1] }}</strong>: {{ error["msg"] }}</li>
  </ul>
</div>
Aplicación — dos formas de llegar al mismo sitio

La forma más directa es esta: el servidor responde 422 y, gracias a HTMX 4, el fragmento de error se inserta. La forma más_controlada usa hx-status:422="target:#errores" para dirigir el fragmento a un contenedor de errores concreto, dejando el formulario intacto para que el usuario corrija. Producción la segunda; la primera es más fácil de empezar, y por eso conviene entender las dos.

hx-syncReemplaza la petición en curso en vez de ponerla en colahx-sync="this:abort"
Precisión — el indicador necesita una clase

hx-indicator no muestra nada por sí solo: el elemento indicado debe tener la clase htmx-indicator, que es la que HTMX quita y pone durante la petición. El CSS típico es de dos líneas:

css — el indicador 
.htmx-indicator {
  opacity: 0;
}

.htmx-request .htmx-indicator {
  opacity: 1;
}

6.5 · Actualizar varias partes a la vez

A veces la respuesta debe modificar más de un elemento: el formulario, un contador y una lista. HTMX resuelve esto con dos mecanismos.

Intercambio fuera de banda (hx-swap-oob)
Un elemento de la respuesta marcado con hx-swap-oob="selector" se actualiza en el lugar que indique el selector, sin tocar el objetivo principal. En HTMX 4, estos elementos se intercambian después del contenido principal (en la versión 2 se intercambiaban antes).
<hx-partial>
Nuevo en HTMX 4. Es una forma más clara de actualizar varios objetivos: se encierran en una etiqueta <hx-partial> y cada hijo indica su propio destino.
Intercambio con morphing
Nuevo en HTMX 4: hx-swap="outerMorph" o "innerMorph". En lugar de borrar y recrear el contenido, lo modifica, y por eso conserva el foco del cursor dentro de un campo de texto. Es la diferencia entre que el usuario pierda lo que estaba escribiendo y no.

6.6 · Los eventos, con sus nombres nuevos

js — escuchar los eventos de HTMX 4 
// En HTMX 4 los eventos usan el patrón htmx:fase:acción

document.body.addEventListener("htmx:before:request", (e) => {
  console.log("Se va a pedir:", e.detail.requestConfig.url);
});

document.body.addEventListener("htmx:after:request", (e) => {
  console.log("Respuesta:", e.detail.xhr.status, "o", e.detail.successful);
});

document.body.addEventListener("htmx:after:swap", (e) => {
  console.log("Ya se insertó el fragmento en:", e.detail.target.id);
});
Precisión

En HTMX 4, el objeto de la respuesta ya no es un XMLHttpRequest: la propiedad e.detail.xhr puede no existir. Para consultar el código de estado, usa e.detail.xhr.status solo si existe, o el nuevo e.detail.successful y el contexto e.detail.requestConfig. Este es otro punto donde la documentación antigua lleva a errores.

Un formulario completo, de la validación nativa al error en línea

Aplicación de todo lo anterior. El encargo es construir un formulario que funcione de verdad: con validación en el navegador, validación en el servidor, y los errores mostrados en el lugar donde el usuario los puede corregir.

Encargo

Solicitud de préstamo en la biblioteca del colegio

La biblioteca quiere que el estudiante pida un préstamo sin salir de la página: elige el libro, indica cuántos días lo quiere y deja su correo. Si algo está mal, el error aparece junto al formulario, no en una página nueva.

Ficha del sistema

Camposlibro (número), estudiante (texto), correo (texto), días (número)
ReglasEl nombre tiene entre 3 y 80 caracteres; el días va de 1 a 30; el libro debe ser un entero positivo

Restricción del tallerLos datos todavía no se guardan: basta con validarlos y responder

Entregables

  1. El formulario HTML (templates/index.html): los cuatro campos con su name e id, la validación nativa correspondiente a las reglas, y los atributos hx-post, hx-target y hx-swap.
  2. La ruta (main.py): POST /api/prestamos con Annotated y Form(), aplicando las tres reglas con las restricciones correctas.
  3. Las dos respuestas: un fragmento de éxito (préstamo registrado) y un fragmento de error (lista de los problemas encontrados), con su manejador de RequestValidationError devolviendo 422 y HTML.
  4. El control fino: un indicador de carga (hx-indicator con su clase CSS) y el botón deshabilitado durante el envío (hx-disable).
  5. Un argumento escrito: por qué el formulario valida dos veces y qué pasaría si el servidor no validara.

C. El manejador de errores

@app.exception_handler(RequestValidationError)
async def errores_de_validacion(request: Request, exc: RequestValidationError):
    return templates.TemplateResponse(
        request=request,
        name="fragmento_errores.html",
        context={"errores": exc.errors()},
        status_code=422,
    )

D. El argumento

Decisión: validar dos veces, en el navegador y en el servidor. Motivo: la validación del navegador da una respuesta inmediata y evita viajes innecesarios; la del servidor es la única que garantiza la regla, porque el cliente es controlable por el usuario. Consecuencia: hay que escribir las restricciones dos veces, y conviene que ambas coincidan exactamente; si divergen, el usuario recibe un error que el navegador creía imposible. Alternativa descartada: novalidate en el formulario, que elimina la primera capa pero obliga a que el servidor devuelva siempre un fragmento de error bien diseñado.

7.2 · Síntesis: siete ideas para llevarse

01

HTMX no es AJAX con otro nombre: el servidor sigue produciendo HTML y el navegador coloca un fragmento.

02

El atributo es el método HTTP: hx-get es un GET, hx-post es un POST.

03

En HTMX 4 la herencia es explícita: sin :inherited, un hijo no hereda nada.

04

El atributo name es el contrato del formulario: sin él, el campo no viaja.

05

La validación nativa es comodidad; la del servidor es garantía. Las dos, y en ese orden de importancia.

06

En HTMX 4 las respuestas de error también se insertan: por eso un 422 puede mostrarse en línea.

07

Un fragmento con atributos hx-* sigue vivo después de insertarse: por eso los formularios se pueden componer.
