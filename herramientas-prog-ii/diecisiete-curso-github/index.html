0.1 · Tres accidentes que GitHub evita

«Se me dañó el compu y perdí el semestre»: el proyecto que solo existe en un disco. «Te paso el zip por WhatsApp»: la colaboración del paleolítico. «Ese repo es de hace 3 meses y no dice ni qué es»: el proyecto sin README ni historia. Los tres mueren hoy.

Git ya guarda las fotos de tu proyecto. GitHub es la red social donde las publicas: le pone una URL, un botón de compartir, comentarios (issues), la posibilidad de que otros propongan cambios (Pull Requests) y un jardín de actividad que premia tu constancia. El álbum funciona sin red social… pero la red social no funciona sin álbum. Por eso esta clase viene después de la 16.

Distinción — Git no es GitHub

Git es un programa que vive en tu computador: toma las fotos (commits), trabaja sin internet y es libre para siempre. GitHub es un sitio web (github.com) que guarda una copia del álbum en la nube y le pone una interfaz social. Uno no sustituye al otro: se necesitan. Si Git se cae, tu historia sigue local; si GitHub se cae, tu historia sigue en tu disco.

Lo que cambia cuando el álbum sale de tu disco
Solo Git (clase 16)Git + GitHub (hoy)
Dónde viveUn discoDisco + nube, sincronizados
RespaldoNinguno, si el disco muereLa nube guarda archivos e historial
CompartirZip, pendrive, WhatsAppUna URL que cualquiera puede abrir
ColaborarMandar archivos y rezarRamas, Pull Requests, issues
PortafolioInvisiblePerfil, README y constancia pública
InternetNo hace faltaHace falta para push y pull

Unidad 01 · El remoto

Git vs GitHub y la dirección de tu álbum

Un remoto es simplemente una dirección donde hay otra copia del álbum. Git la guarda con un apodo —por tradición, origin— y de ahí nacen los dos comandos de la clase: push y pull.

⏱ 30 minutos 📄 Lectura y demo 🧭 Producto: el viaje del commit, de los dos mundos

1.2 · El remote: el apodo de una URL

Registrar un remoto no sube nada. Solo le dice a Git: «hay otro álbum en esta dirección, y le pondré origin». Es guardar un contacto en el celular: se hace una vez y queda en la configuración del repo.

terminal — registrar y verificar el remote 
git remote add origin https://github.com/tuusuario/biblioteca.git

git remote -v
# origin  https://github.com/tuusuario/biblioteca.git (fetch)
# origin  https://github.com/tuusuario/biblioteca.git (push)
Nota — ¿por qué «origin»?

Es solo el apodo tradicional. Podrías llamarlo mi-nube y todo funcionaría igual… pero el mundo dice origin, y con el mundo conviene seguirlo. Si un tutorial dice git push origin main, está usando ese apodo; si lo hubieras llamado mi-nube, escribirías git push mi-nube main.

// 1. Entra a github.com con tu cuenta → botón "+" → "New repository".
// 2. Repository name:  biblioteca

    Advertencia — el README inicial es una trampa
    

      Si marcas «Add a README file», GitHub crea un commit allá que tú no tienes en tu compu. Al
      hacer el primer push, las dos historias chocan y Git rechaza el envío. El repo de la web debe
      nacer vacío: tu historial local es el que manda. El README lo escribes tú,
      aquí, y lo subes con commit.

La URL azul de siempre: https://github.com/…. Te identificas con el navegador la primera vez y el sistema lo recuerda. Perfecto para empezar.

Un formato raro: git@github.com:…. Requiere generar llaves criptográficas y subirlas a GitHub. Más rápido para profesionales; lo verás en la vida real.

2.4 · El ciclo diario


  

    

      

        

        la rutina permanente de toda persona que programa
      

      
    


#   ┌──► git pull      (bajar lo nuevo de la nube)
#   │        │
#   │        ▼
#   │   editar + git add + git commit   (la clase 16)
#   │        │
#   │        ▼
#   └──  git push     (subir tus fotos nuevas)

  


  

    Villano: ! [rejected] — fetch first
    

      Trabajando con otra persona, esto va a pasar (es una certeza, no una posibilidad). No es un
      error: es Git protegiendo el álbum común. Significa «en la nube hay commits que tú no tienes
      y no voy a dejar que los tapes». La solución es la rutina en orden:
      git pull (y si hay conflicto, resolverlo como en la clase 16), y recién entonces
      git push. El rechazo es la red de seguridad trabajando.

3.3 · Licencia MIT: «puedes usar esto, dame crédito»


  

    Un repo sin licencia es técnicamente «todos los derechos reservados»: nadie debería copiarlo.
    Los repos de estudiantes usan la licencia MIT: permiso libre de usar y
    modificar, con crédito. En la web: botón Add file → Create new file → nómbralo
    LICENSE → GitHub te ofrece la plantilla → eliges MIT → commit. Un archivo, cero
    drama legal, seriedad instantánea.
  


  

    Villano: el repo fantasma
    

      El repo sin README, con nombres como proyecto-final o prueba2 y sin
      una línea de descripción, da la impresión exacta de estar abandonado — aunque el código adentro
      sea brillante. En GitHub la primera impresión es digital: quien entra decide en 10 segundos si
      sigue leyendo o cierra la pestaña. Además, en la página del repo, el ícono ⚙️ te deja poner una
      descripción de una línea y topics (fastapi,
      python, postgresql): dos detalles que multiplican la seriedad.

      No deben existir allá. Si aparecen, para todo: un secreto en un repo público
      se considera comprometido desde el primer segundo. Avisa a tu profe, cambia la clave y
      arreglen el historial antes de seguir.
    

  


  

    

      

        

        terminal — comprobación rápida
      

      
    


git ls-files | grep -E '\.env|__pycache__'
# Debe salir VACÍO. Si imprime algo, ese archivo se está
# rastreando y viajó (o viajará) a la nube.

 Unidad 06 · El equipo

    
Colaborar: Pull Requests, issues y portafolio

    

      Todo lo de la clase 16 (ramas) y el push de hoy se combinan en el flujo colaborativo estándar
      del planeta: cada cambio viaja en una rama propia, se propone con un Pull Request
      y se decide en equipo. Es el chat donde el código discute antes de entrar a main.
    

    

      ⏱ 35 minutos
      📄 Lectura y práctica
      🧭 Producto: primer PR archivado y un issue educado
    

  


  
6.1 · El flujo completo de un Pull Request


  

    

      

        

        terminal + web — el flujo estándar
      

      
    


# 1. Rama nueva para la misión (clase 16):
git switch -c fix/titulo-inicio
# …edita algo pequeño, add, commit…
git add .
git commit -m "Corregir acentos del título de inicio"

# 2. Subir la RAMA a la nube (la primera vez lleva -u):
git push -u origin fix/titulo-inicio
# remote: Create a pull request for 'fix/titulo-inicio' on GitHub
# ← ¡GitHub te da el link del PR!

# 3. Abre ese link (o el botón verde "Compare & pull request").
#    Escribe título y descripción y "Create".
# 4. En "Files changed" revisa tu propio diff con calma.
# 5. Botón verde "Merge pull request" → "Confirm merge".
# 6. Vuelve a tu compu y baja el main actualizado:
git switch main
git pull
git branch -d fix/titulo-inicio

  


  

    

      Dos formas de entrar a main
      
        
Directo a mainVía Pull Request

      
      
        
CuándoTrabajas sol@ en un proyecto chicoEquipo — o para ti del futuro

        
RevisiónNadie mira el diffOtra persona comenta y aprueba

        
HistoriaCommits sueltos en mainUna página con el diff y la discusión

        
ProtecciónNingunamain queda intocada sin revisión

      
    

  


  
6.2 · Issues: la sala de pendientes


  

    Un issue es la conversación de «esto está mal / falta»: un pendiente con dueño,
    descripción y comentarios. Un issue amable tiene cuatro partes — y el que lo lee entiende sin
    preguntar.
  


  

    

      

        

        issue — la plantilla que sí se lee
      

      
    


Título: La página de libros muestra "Sin libros" aunque sí hay

Pasos para reproducirlo:
1. Entrar a /libros
2. Registrar un autor con libros

Qué esperaba: Ver la lista de libros del autor
Qué pasa en realidad: "Sin libros" (y la consola muestra un error 500)

# NO:  "no funciona" / "está dañado" / "urgente!!!"
# SÍ:  pasos concretos + esperado + real.

  


  

    Villano: el push directo a main en equipo
    

      Dos personas empujando directo a main todo el día es el clásico «¿por qué mi
      código que funcionaba ya no funciona?», con la agravante de que nadie sabe quién rompió qué.
      El PR no es burocracia: es el cinturón de seguridad del equipo. Cada cambio tiene una página
      con su historia, y git blame deja de ser un dedo apuntador: todo pasó por un PR
      visible.
    

  


  
6.3 · El jardín verde: tu marcador de constancia


  

    En tu perfil, la grilla de cuadritos es el gráfico de contribuciones: cada
    cuadro un día, cada cuadrito verde un día con commits tuyos. A los 16–17 años puede parecer un
    juego… pero cuando apliques a una beca o a un primer trabajo tech, esa grilla verde y continua
    es evidencia pública de constancia, con fecha. Cada push la riega.

7.3 · Las tres reglas que este taller no negocia


  

    Regla 1 — el repo de la web nace vacío
    

      Sin README inicial, sin licencia, sin .gitignore en la web. Esos archivos crearían
      commits allá que tú no tienes aquí, y el primer push chocaría. Tu historial local es el que
      manda; la vitrina la escribes tú y la subes con commit.
    

  


  

    Regla 2 — ningún secreto en la nube
    

      Un .env publicado se considera comprometido desde el primer segundo: no vale
      borrarlo y seguir. Se cambia la clave, se arregla el .gitignore y se revisa el
      historial. En un repo público, esto no es un detalle: es lo primero que mira quien audita.
    

  


  

    Regla 3 — la URL se entiende sin ti
    

      Abre tu repo en el celular de tu compañero. Si necesita que le expliques qué es, cómo se
      ejecuta o qué hace, el README todavía no está. El estándar no es «mi código funciona»: es
      «otra persona puede entrar, entender y correrlo sin preguntarme».
