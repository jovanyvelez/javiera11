💡 ¿Por qué validar?

Los datos que llegan del usuario no son de confianza. Pueden estar vacíos, mal escritos o ser malintencionados. Validar antes de guardar evita errores y protege la base de datos. Pydantic hace esta validación automáticamente.

🧱 Modelos Pydantic: la forma de los datos

⏱️ 35 minutos · "Definir qué datos esperamos"

🧠 ¿Qué es un modelo Pydantic?

Un modelo Pydantic es una clase que describe la forma de los datos: qué campos tiene y de qué tipo es cada uno. Se crea heredando de BaseModel. Cuando FastAPI recibe datos, los valida contra el modelo: si no coinciden, los rechaza.

esquemas.py — un modelo simple 
from pydantic import BaseModel

class AutorCrear(BaseModel):
    nombre: str
    pais: str | None = None
    nacimiento: int | None = None

💡 Tipos = reglas

Cada campo declara su tipo: nombre debe ser texto (str), nacimiento debe ser número (int). El | None significa "puede estar vacío". Si llega un dato del tipo equivocado, Pydantic lo rechaza.

🏷️ Field: reglas de validación

⏱️ 35 minutos · "Poner límites a los datos"

🧠 La idea central

Con Field puedes agregar reglas a cada campo. Por ejemplo, que el nombre tenga al menos 1 carácter (min_length=1) o que el año de nacimiento sea mayor o igual a 0 (ge=0). Si un dato no cumple la regla, Pydantic lo rechaza.

esquemas.py — con reglas 
from pydantic import BaseModel, Field

class AutorCrear(BaseModel):
    nombre: str = Field(min_length=1, description="Nombre completo del autor")
    pais: str | None = None
    nacimiento: int | None = Field(default=None, ge=0, description="Año de nacimiento")

🦹 El villano: el nombre vacío

Sin min_length=1, un usuario podría crear un autor con nombre vacío (""). Eso ensucia la base de datos. Con la regla, Pydantic rechaza el nombre vacío antes de que llegue a la BD.

💡 Reglas comunes de Field

min_length (longitud mínima), max_length (máxima), ge (mayor o igual), le (menor o igual), gt (mayor que), lt (menor que). Además, description="..." agrega una explicación que aparece en la documentación automática /docs de FastAPI. Son como las reglas de un formulario, pero en el backend.

📝 Form: el formulario llega como modelo

⏱️ 35 minutos · "Recibir un formulario HTML ya validado"

🧠 La idea central

Cuando un formulario HTML envía datos, estos llegan como form data (pares clave=valor). Lo elegante del estilo FastAPI: no recibimos campo por campo. Recibimos el modelo Pydantic completo con Annotated[AutorCrear, Form()], y FastAPI extrae cada campo del formulario, lo valida con las reglas del modelo y nos entrega el objeto listo para usar.

vistas.py — el formulario llega como modelo 
from typing import Annotated
from fastapi import Form

@router.post("/autores")
async def crear_autor(
    autor: Annotated[AutorCrear, Form()],
):
    # autor YA es un objeto validado: si algo no cumple, FastAPI
    # respondió 422 antes de llegar a esta línea 🛡️
    await crear_autor(conn, autor.nombre, autor.pais, autor.nacimiento)

💡 ¿Qué significa Annotated?

Annotated[Tipo, extra] envuelve un tipo con información extra: le dice a FastAPI "esto es un AutorCrear, y además viene de un formulario". Es el estilo oficial que la documentación de FastAPI recomienda para todos los parámetros (Query, Form, Body…). Y un detalle clave: los name de los <input> del HTML deben llamarse igual que los campos del modelo (nombre, pais, nacimiento).

🦹 El villano: el campo extra

Por defecto, si el formulario manda un campo que no está en el modelo, FastAPI lo ignora. Si quieres rechazarlo, el modelo puede configurarse: model_config = {"extra": "forbid"}. Así ningún dato sospechoso se cuela en tu app.

💡 Form vs Query vs Body

El mismo modelo puede llegar por caminos distintos: Annotated[AutorCrear, Form()] (viene de un formulario HTML), Annotated[AutorCrear, Body()] (viene como JSON, útil para APIs) o campo por campo con Query() (viene de la URL). El modelo es el mismo: solo cambia de dónde sale el dato. Para formularios necesitas python-multipart, que ya instalamos con el proyecto.

🚫 422: el error de validación

⏱️ 35 minutos · "Cuando los datos no pasan la prueba"

🧠 La idea central

Cuando los datos no cumplen las reglas del modelo, FastAPI responde con el código 422 Unprocessable Entity. Es la forma del servidor de decir "recibí tus datos, pero no son válidos". El error incluye un detalle de qué falló y por qué.

🦹 El villano: el dato inválido

Si un usuario envía nacimiento="abc" (texto en vez de número), Pydantic no puede convertirlo a int y responde 422. Sin esta validación, el dato "abc" llegaría a la base de datos y causaría un error más grave (o datos corruptos).

lo que devuelve FastAPI cuando falla la validación 
// respuesta 422: un detalle de QUÉ falló y DÓNDE
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["body", "nacimiento"],
      "msg": "Input should be a valid integer",
      "input": "abc"
    }
  ]
}

💡 Cómo leer el detalle

loc te dice el campo que falló ("nacimiento"), msg explica por qué en inglés, input muestra lo que envió el usuario, y type clasifica el error. Con esa información, el frontend puede mostrar un mensaje útil: "el año de nacimiento debe ser un número".

✅

200

Todo bien: los datos son válidos y se procesaron.

🚫

422

Datos inválidos: no cumplen las reglas del modelo.

🔍

404

No encontrado: la ruta o el recurso no existe.

💥

500

Error interno: algo se rompió en el servidor.

💡 El 422 es tu amigo

El 422 no es un error "malo": es el servidor protegiéndose. Te dice exactamente qué campo falló y por qué. En el frontend, puedes usar ese detalle para mostrar un mensaje al usuario: "el año de nacimiento debe ser un número".

📐 Esquemas: entrada, salida y tipo de retorno

⏱️ 35 minutos · "Validar lo que entra, filtrar lo que sale"

🧠 La idea central

Igual que separamos el SQL en repositorio.py, separamos los modelos Pydantic en esquemas.py. Y al estilo FastAPI, los modelos se separan según su misión: los de entrada describen lo que aceptamos del usuario, y los de salida describen lo que devolvemos en la respuesta.

esquemas.py — modelo de entrada y modelo de salida 
from pydantic import BaseModel, Field

# ENTRADA: lo que el usuario envía (sin id, la BD lo asigna)
class AutorCrear(BaseModel):
    nombre: str = Field(min_length=1)
    pais: str | None = None
    nacimiento: int | None = Field(default=None, ge=0)

# SALIDA: lo que devolvemos (con id, ya guardado)
class AutorLeer(BaseModel):
    id: int
    nombre: str
    pais: str | None = None
    nacimiento: int | None = None
vistas.py — la ruta declara su tipo de retorno 
@router.post("/autores")
async def crear_autor(
    autor: Annotated[AutorCrear, Form()],
) -> AutorLeer:
    datos = await crear_autor(conn, autor.nombre, autor.pais, autor.nacimiento)
    return AutorLeer(**datos)  # **datos = "todos los campos del dict"

💡 Para qué usa FastAPI el tipo de retorno

Cuando la ruta declara -> AutorLeer, FastAPI hace tres cosas con eso: 1) valida que lo que devuelves cumpla el modelo (si tu código se equivoca, no manda datos rotos), 2) documenta la respuesta en /docs, y 3) serializa a JSON con Pydantic, que por dentro está escrito en Rust y vuela 🚀. Lo mismo vale para -> list[AutorLeer] cuando devuelves varios.

🦹 El villano: el campo de más en la respuesta

Si la ruta devolviera el dict crudo de la BD, y mañana alguien agrega una columna clave_secreta… se devuelve tal cual a quien sea. En cambio, con -> AutorLeer, FastAPI filtra la salida: solo viajan los campos declarados en el modelo. Lo que no está declarado, no sale. Eso es seguridad por diseño.
