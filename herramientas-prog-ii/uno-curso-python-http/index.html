⚡ async/await: el superpoder de la concurrencia

⏱️ 35 minutos · "Hacer muchas cosas sin congelarse"

🦹 El villano: el programa que se congela

Imagina que tu app pide datos a una base de datos y esa petición tarda 1 segundo. Si el programa es síncrono, durante ese segundo no hace nada más: se queda congelado esperando. Si llegan 100 usuarios, cada uno espera su turno. La app se siente lenta y "se cae" sin haberse caído.

🧠 La idea central

Con async y await, una función puede esperar una respuesta sin bloquear el resto del programa. Mientras espera, el programa atiende a otros usuarios. Es como un mesero que, en vez de quedarse parado esperando el plato, atiende a otras mesas y vuelve cuando la cocina está lista.

python — async/await 
async def obtener_autores():
    # await = "espera aquí, pero no congeles el programa"
    datos = await base_de_datos.consultar("SELECT * FROM autores")
    return datos

💡 async def + await = función asíncrona

Una función con async def es asíncrona. Dentro de ella, usas await para esperar operaciones lentas (consultas a BD, peticiones de red) sin bloquear. FastAPI está construido 100% sobre esto: por eso es tan rápido con muchos usuarios.

🔄 Actividad en pareja — 2 minutos

Con su compañero/a: imaginen un restaurante con 1 mesero. ¿Atiende más mesas si (a) espera cada plato de pie antes de tomar el siguiente pedido, o (b) anota todos los pedidos y vuelve cuando cada plato está listo? ¿Cuál es síncrono y cuál asíncrono?

🔍 En la vida real

Netflix no puede congelarse cada vez que alguien pide una película. Su backend usa async/await para atender a millones de usuarios a la vez. Cuando tu app pide datos, el servidor "anota tu pedido" y sigue atendiendo a los demás mientras la base de datos responde.

🌐 HTTP: el idioma de la web

⏱️ 35 minutos · "Cómo se comunican el navegador y el servidor"

🧠 ¿Qué es HTTP?

HTTP (HyperText Transfer Protocol) es el idioma que usan el navegador y el servidor para hablar. Cuando escribes una URL y presionas Enter, tu navegador envía un request (petición) y el servidor responde con un response (respuesta). Todo lo que ves en la web viaja por HTTP.

📊 Los métodos HTTP (verbos)

Cada request lleva un método que dice qué quieres hacer. Son como verbos:

MétodoQué haceEjemplo
GETLeer / pedir datosVer la lista de autores
POSTCrear algo nuevoCrear un autor
PUTActualizar algoEditar un autor
DELETEBorrar algoEliminar un autor

💡 CRUD = los 4 verbos

Crear, Leer, Actualizar y Borrar (en inglés CRUD: Create, Read, Update, Delete) se mapean a los 4 métodos HTTP: POST, GET, PUT y DELETE. Casi toda app web es, en el fondo, un CRUD. Nuestro proyecto de autores es exactamente eso.

🔍 En la vida real

Cada vez que das "me gusta" en una foto, tu teléfono envía un POST. Cada vez que cargas tu feed, envía un GET. Cada vez que editas tu perfil, un PUT. Y cuando borras un mensaje, un DELETE. Ya usas HTTP todo el día sin saberlo.

📨 Request/Response: el ciclo de la web

⏱️ 35 minutos · "El viaje completo de una petición"

🦹 El villano: el servidor que atiende de a uno

Si un servidor atiende un request a la vez, cuando llegan 100 usuarios, el número 100 espera a que terminen los 99 anteriores. Con async/await, el servidor atiende a todos "a la vez": mientras espera la respuesta de la BD para el usuario 1, ya está procesando al usuario 2.

🧠 El ciclo request → response

Toda interacción web sigue el mismo ciclo: el cliente (navegador) envía un request, el servidor lo procesa y devuelve un response. El response incluye un código de estado que dice si todo salió bien o no.

📊 Códigos de estado más comunes

CódigoSignificadoCuándo lo ves
200OK, todo bienLa página cargó correctamente
404No encontradoLa URL no existe
422Datos inválidosEnviaste datos mal formados
500Error del servidorAlgo se rompió por dentro

💡 El 422 será tu amigo

En nuestro proyecto, cuando un usuario envía un formulario con datos inválidos (por ejemplo, un año de nacimiento que no es número), FastAPI responde 422. Es la forma del servidor de decir "tus datos no están bien". Lo veremos en la clase de Pydantic.

🔍 En la vida real

Cuando una página tarda en cargar, muchas veces no es tu internet: es que el servidor está atendiendo de a uno (síncrono) en vez de en paralelo (asíncrono). Por eso las empresas invierten en backends asíncronos como FastAPI.

📦 JSON: el formato de los datos

⏱️ 35 minutos · "Cómo viajan los datos por la web"

🧠 ¿Qué es JSON?

JSON (JavaScript Object Notation) es un formato de texto para representar datos. Es el idioma universal de las APIs: cuando un servidor devuelve datos, casi siempre los devuelve en JSON. Se parece mucho a los diccionarios de Python.

json — un autor y una lista de autores 
// Un autor (objeto JSON)
{"id": 1, "nombre": "Gabriel García Márquez", "pais": "Colombia"}

// Una lista de autores (array de objetos)
[
  {"id": 1, "nombre": "Gabo"},
  {"id": 2, "nombre": "Cortázar"}
]

💡 JSON ≈ diccionario de Python

Un objeto JSON es casi idéntico a un diccionario de Python. La diferencia es que JSON es texto (para viajar por internet) y el diccionario es un objeto en memoria. FastAPI convierte automáticamente entre ambos: tú devuelves un diccionario y FastAPI lo envía como JSON.

🦹 El villano: el JSON mal formado

Si un JSON tiene una coma de más, una llave sin cerrar o una comilla mal puesta, se rompe todo. El cliente no puede leerlo. Por eso es importante que el servidor genere JSON válido siempre. FastAPI lo hace por ti, pero es bueno saber qué hay debajo.

🛠️ Taller: diagnóstico de una app lenta

⏱️ 40 minutos · "Aplica todo lo aprendido"

🛠️ Taller final El caso de la app que se congela

Una app de biblioteca se volvió lenta: cuando muchos estudiantes entran a la vez, la página tarda segundos en cargar. Tu misión es diagnosticar qué está mal usando lo que aprendiste hoy.

🧠 Las pistas

  • El código usa funciones síncronas (sin async/await).
  • Cada request espera a la base de datos sin hacer nada más.
  • Cuando llegan 50 usuarios, se forman en fila y esperan su turno.

🔄 Actividad en pareja — 10 minutos

Con su compañero/a, respondan por escrito:

  1. ¿Cuál es la causa raíz del problema? (pista: síncrono vs asíncrono)
  2. ¿Qué cambiarían en el código para arreglarlo? (pista: async def y await)
  3. ¿Qué método HTTP usaría la app para mostrar la lista de libros? ¿Y para prestar un libro?
  4. ¿En qué formato devolvería el servidor la lista de libros? (pista: empieza con J)

💡 Respuesta esperada

La causa raíz es que el código es síncrono: cada request bloquea al servidor mientras espera a la BD. La solución es usar async/await para que el servidor atienda a muchos usuarios a la vez. Mostrar libros es un GET, prestar un libro es un POST, y los datos viajan en JSON.
