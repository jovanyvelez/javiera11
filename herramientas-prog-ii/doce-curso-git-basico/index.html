🧠 Git, en una frase

La idea central

Git es un sistema de control de versiones: un diario que registra fotografías completas de tu proyecto (los commits), cada una con fecha, autora y mensaje. En cualquier momento puedes preguntarle "¿cómo estaba esto ayer?" o gritarle "¡devuélveme la foto de ayer!". Es distribuido: el historial completo vive en tu computador, sin necesitar internet ni un servidor. Y es gratis y libre: lo creó Linus Torvalds (el mismo del pinguino Linux) en 2005; hoy lo usa prácticamente todo proyecto de software del planeta. La versión que usamos en este curso es la 2.56.0, la más reciente.

⏳ ¿Qué es Git? La máquina del tiempo

⏱️ 35 minutos · "Un diario que se puede recorrer hacia atrás"

🧠 La idea central

Un sistema de control de versiones responde tres preguntas que el zip no puede: ¿qué cambió?, ¿quién lo cambió? y ¿cómo vuelvo a como estaba?. Git lo hace con una idea simple: cada vez que tú lo ordenas, toma una fotografía del proyecto completo (un commit) y la cuelga en una línea de tiempo. Como cada foto tiene todo, puedes ir a cualquiera y el proyecto queda exactamente como ese día. Y es distribuido: el álbum entero vive en tu computador, dentro de una carpeta escondida llamada .git/. Sin internet, sin servidor, sin permiso de nadie.

💡 Dos reglas de oro de .git/

  • Nunca toques su contenido a mano. No hay razón: todo se hace con comandos. Es la única carpeta del proyecto con esa regla.
  • Borrarla es borrar el álbum: tus archivos quedan igual en la carpeta, pero pierdes toda la historia. Si un día quieres "empezar de cero" el historial, ya sabes cuál es el interruptor… y por qué no hay que tocarlo sin querer.

📸 El commit: la foto que lo cambia todo

⏱️ 35 minutos · "Directorio de trabajo → staging → álbum"

🧠 La idea central

Un commit es una fotografía del proyecto guardada para siempre en el álbum (.git/). Pero Git no fotografía a lo loco: usa tres lugares por donde pasa tu código. En el directorio de trabajo (tu carpeta) vives y editas con toda libertad. El staging area es la posing: le dices a Git estos cambios van a entrar en la próxima foto (git add). Y el repositorio es el álbum donde la foto queda colgada con su etiqueta (git commit -m "mensaje"). Dominar esta clase es dominar el pasillo entre esos tres lugares.

Los tres estados
Quién manda ahí
El comando de la puerta
💻 1 · Directorio de trabajo
Tú: editas, guardas, borras. La vida real de la carpeta.
git status para ver qué andas cambiando
📸 2 · Staging area (la posing)
La lista de lo que ENTRARÁ en la próxima foto.
git add archivo entra · git restore --staged archivo se sale
🗄️ 3 · Repositorio (el álbum)
Las fotos completas con fecha, autora, mensaje y hash único.
git commit -m "mensaje" toma la foto · git log la mira

⚙️ El ciclo real, completo y con salida

Ahora sí: en tu proyecto de verdad. Este es el ciclo básico de Git, el que repetirás miles de veces en tu vida.

el ciclo: editar → add → commit (con respuestas reales) 
# 1. Edita algo real en VS Code (por ejemplo main.py) y guarda. Luego:
git status
#    Changes not staged for commit:
#            modified:   main.py

# 2. ¿Qué cambió exactamente? (líneas con - y +)
git diff
#    - TARIFA_POR_DIA = 500
#    + TARIFA_POR_DIA = 800

# 3. Mándalo a la posing (el punto significa "todo lo que ando cambiando"):
git add .
#    (no responde nada: es de los pocos comandos silenciosos)

# 4. Verifica la posing antes de la foto:
git status
#    Changes to be committed:
#            modified:   main.py

# 5. ¡FOTO! — el mensaje cuenta QUÉ hiciste y POR QUÉ:
git commit -m "Cambiar tarifa de la multa a $800"
#    [main 9f3c2b1] Cambiar tarifa de la multa a $800
#     1 file changed, 1 insertion(+), 1 deletion(-)

# 6. Mira el álbum:
git log --oneline
#    9f3c2b1 (HEAD -> main) Cambiar tarifa de la multa a $800
#    4a8e7d2 Agregar página de préstamos
#    c1d9f3e Primer commit: proyecto biblioteca
Mensaje ❌ villanoMensaje ✅ profesional
cambiosAgregar página de préstamos
finalCorregir cálculo de la multa con días negativos
arregloCambiar tarifa de la multa a $800
cosas 😱Conectar el pool con lifespan (clase 2)

💡 ¿Qué guarda exactamente un commit?

  • El contenido de todo lo que estaba en la posing (no "el cambio": la foto completa del archivo).
  • La autora: tu user.name y user.email — por eso los configuramos en el módulo 0.
  • Fecha y hora exactas.
  • El mensaje que escribiste.
  • Un hash único (como 9f3c2b1): la huella digital de la foto. Son 40 caracteres; Git muestra 7. No hay dos commits en el mundo con el mismo hash.

🦹 Villano: "¿y para qué la posing? ¡Qué flojera!"

Parece un paso innecesario, pero es el superpoder de Git: te deja decidir qué entra en cada foto. Terminaste el cambio de la multa pero a mitad de camino arreglaste un acento en una plantilla? Puedes hacer dos commits limpios: git add dominio/servicios.py → commit → git add presentacion/templates/inicio.html → commit. Resultado: un diario donde cada foto cuenta una sola historia. git add . (todo) es el atajo para el día a día; git add archivo es la precisión del cirujano. Dominas los dos.

🔎 Leer el diario y cuidar los secretos

⏱️ 35 minutos · "git log, git diff y el .gitignore que salva vidas"

🧠 La idea central

Un historial que no se puede leer no sirve de nada. Git te da cuatro formas de mirar: status (¿cómo estamos ahora?), diff (¿qué cambia entre dos momentos?), log (¿qué fotos hay en el álbum?) y show (muéstrame una foto en detalle). Y como en toda casa hay cosas que no van en el álbum familiar — la basura, las llaves de la puerta — existe .gitignore: la lista de lo que Git debe fingir que no ve. Hoy aprendes las dos cosas: leer el diario y decidir qué no entra en él.

ComandoPregunta que respondeEjemplo estrella
git status¿Cómo está el proyecto ahora mismo?Qué está modificado, qué está en posing
git diff¿Qué cambió sin guardar en la posing?El - TARIFA 500 / + TARIFA 800
git diff --staged¿Qué está listo para la próxima foto?Lo mismo, pero de lo que ya está en posing
git log --oneline¿Qué fotos hay en el álbum?La línea de tiempo completa, una línea por foto
git show 9f3c2b1¿Qué tenía esta foto en detalle?El commit con su cambio línea por línea

🧹 .gitignore: lo que nunca entra en una foto

Hay dos tipos de archivos que nunca deben aparecer en tu álbum: los que se generan solos (basura reciclada como __pycache__/) y los secretos (las llaves de la casa, como .env con tu DATABASE_URL).

.gitignore — créalo con VS Code, en la raíz del proyecto

# (empieza por punto, sin extensión). Contenido para tu biblioteca/:

# Python: carpetas y archivos que Python genera solo (basura reciclada)
__pycache__/
*.pyc
venv/
.venv/

# Secretos: las llaves de la casa. NUNCA en el álbum.

# Basura del sistema operativo
.DS_Store
Thumbs.db

🦹 Villano: el secreto filtrado

Imagina que haces commit de .env con tu DATABASE_URL (que incluye usuario y clave). Luego lo borras y haces otro commit. Mala noticia: la foto donde aparece la clave sigue en el álbum — borrar el archivo hoy no borra las fotos viejas. Y el día que ese álbum se publique (clase 13), la clave queda expuesta con fecha y hora. Por eso la regla es tajante: .gitignore ANTES del primer commit. Y si ya se te coló un secreto: avisa a tu profe — hay formas de limpiarlo, pero ninguna es mágica; lo más sano es cambiar la clave.

💡 La regla mental de los dos grupos

  • No se fotografía lo que se regenera: __pycache__/, venv/… Si borras esa carpeta y un comando la reconstruye, no va en el álbum.
  • No se fotografía lo que es secreto: .env, claves, tokens. Va al álbum un .env.example con los nombres de las variables y valores de mentiras, para que quien clone el proyecto sepa qué necesita.
  • Todo lo demás sí: tu código, tus plantillas, tu README. Ese es exactamente el contenido del álbum.

🌿 Ramas: universos paralelos

⏱️ 35 minutos · "Experimentar sin miedo a romper lo que funciona"

🧠 La idea central

Una rama es una línea de tiempo paralela que nace de una foto del álbum. La rama principal —por convención main— es la historia oficial: lo que funciona y se muestra. Una rama nueva es un universo de prueba: ahí puedes destrozar, rehacer y experimentar todo lo que quieras, porque main ni se entera. Y cuando el experimento funciona, lo fusionas (merge) de vuelta a la historia oficial. Las ramas son la razón por la que los equipos grandes trabajan sin pisarse: cada persona, su universo; el merge, el momento de unirlos.

🛤️ main — la historia oficial

La línea que siempre debe funcionar. Lo que está en main es lo que se muestra, lo que se sube, lo que se defiende. Regla: no se experimenta aquí.

🧪 feature/… — el universo de prueba

Rama nueva para una función: feature/estadisticas. Si sale bien → merge a main. Si sale mal → git branch -d y ni main ni nadie se enteran de que existió. Cero riesgo, cero zips.

el ciclo completo de una rama — con git switch (el comando moderno) 
# 0. ¿En qué rama estoy? (el * marca dónde estás parado)
git branch
#    * main

# 1. Crear el universo paralelo Y entrar a él (-c = create):
git switch -c feature/estadisticas
#    Switched to a new branch 'feature/estadisticas'

# 2. Trabaja normal: edita, add, commit… pero ¡en la rama nueva!
#    (todo lo que hagas vive en ESTE universo, main no cambia)
git add .
git commit -m "Agregar contador de préstamos atrasados"

# 3. Volver a la historia oficial:
git switch main
#    Switched to branch 'main'
#    (abre tu editor: ¡los cambios de la rama no están! calma, viven en la otra)

# 4. Fusionar el universo en la historia oficial:
git merge feature/estadisticas
#    Updating 9f3c2b1..4a8e7d2
#    Fast-forward
#     presentacion/rutas/inicio.py | 2 ++

# 5. Borrar el universo ya fusionado (queda en el álbum):
git branch -d feature/estadisticas
#    Deleted branch feature/estadisticas.

💡 switch vs checkout: el nuevo y el veterano

En tutoriales (y en boca de programadores viejos) verás git checkout -b. Hace lo mismo, pero desde Git 2.23 existe git switch, diseñado a propósito para cambiar y crear ramas — checkout intenta hacer toooodo y por eso confunde. Con tu Git 2.56: usa switch. Reconoce checkout para no asustarte cuando lo veas por ahí.

🦹 Villano: el conflicto (¡y por qué no es un castigo!)

El conflicto pasa cuando dos ramas cambian la misma línea y Git no adivina cuál versión quieres. Un merge te lo avisa así:

git merge feature/estadisticas
#    CONFLICT (content): Merge conflict in dominio/servicios.py
#    Automatic merge failed; fix conflicts and then commit the result.

# Git marca EN TU ARCHIVO el campo de batalla:
<<<<<<< HEAD
TARIFA_POR_DIA = 800          # ← tu versión (main)
=======
TARIFA_POR_DIA = 500          # ← la versión de la rama
>>>>>>> feature/estadisticas

Resolverlo es trivial y te toca a ti, porque solo tú sabes qué querías: 1) abre el archivo, 2) deja la línea como debe quedar, 3) borra las tres marcas (<<<, ===, >>>), 4) git add + git commit. El conflicto no es un error: es Git diciendo "esto no lo voy a decidir por ti".

💡 Nombres de ramas, para que el equipo se entienda

  • minúsculas con guiones: feature/estadisticas, fix/titulo-inicio.
  • el prefijo cuenta la intención: feature/… algo nuevo, fix/… una corrección.
  • Una rama = una misión. Si su nombre necesita la palabra "y", son dos ramas.

🔄 Actividad en pareja — 8 minutos

  1. Cada uno crea una rama feature/su-nombre en su proyecto y hazle un commit (cualquier cambio pequeño).
  2. Vuelve a main y confirma en el editor que el cambio "desapareció". ¿Le pasó algo? ¿Dónde vive ahora?
  3. Haz merge de tu rama a main y verifica que el cambio volvió. ¿Qué dice git log --oneline ahora?
  4. Pregunta de discusión: si dos compañeras hacen merge de ramas que tocaron archivos distintos, ¿habrá conflicto? ¿Y si tocaron la misma línea? Prepárense: en el taller lo van a provocar a propósito. 😈

⏪ Deshacer sin miedo (la navaja suiza)

⏱️ 35 minutos · "En Git casi todo tiene deshacer — casi"

🧠 La idea central

Programar sin miedo es la diferencia entre avanzar rápido y avanzar aterrado. Git te da un deshacer para casi cada situación, pero cada uno es una herramienta distinta: hay quien descarta cambios (restore), quien retoca la última foto (amend), quien saca una foto del álbum privado (reset) y quien añade una foto nueva que anula otra (revert). Y encima existe reflog, el cinturón de seguridad que graba todos tus movimientos. La regla antes de deshacer cualquier cosa: ejecuta git status y lee.

Qué te pasó 😰El comando 😌Qué hace exactamente
"Dañé app.py y quiero que vuelva a como estaba en la última foto"git restore app.pyDescarta los cambios sin guardar en posing. Ojo: los cambios desaparecen para siempre
"Agregué a la posing algo que no era"git restore --staged app.pySaca del staging… pero conserva tus cambios en la carpeta. Puro backspace
"El commit quedó con un mensaje feo"git commit --amend -m "nuevo"Rehace la última foto con mensaje nuevo (mismo contenido)
"Me sobró el último commit (aún no lo he compartido con nadie)"git reset --soft HEAD~1Saca la foto del álbum; los cambios quedan en la posing, intactos
"Hay que deshacer un commit que YA compartieron/subieron"git revert <hash>Crea un commit NUEVO que deshace el anterior. El historial queda limpio y nadie pierde nada
"Hice algo horrible y no sé qué"git reflogLa lista de TODO lo que ha pasado: ahí encuentras el hash donde estabas y vuelves a él
los 4 deshaceres en acción — con respuestas reales 
# 1. Descartar cambios de un archivo (¡sin vuelta atrás!)
git restore main.py
#    (silencioso: abre el editor y el archivo volvió a la última foto)

# 2. Sacar de la posing SIN perder el trabajo:
git restore --staged main.py
#    Updated paths

# 3. Arreglar el mensaje del último commit:
git commit --amend -m "Cambiar tarifa de la multa a $800 por decisión del consejo"

# 4. Deshacer el último commit PERO conservar los cambios:
git reset --soft HEAD~1
#    (HEAD~1 significa "la foto anterior a donde estoy")
#    Ahora git status muestra los cambios en la posing, listos
#    para un commit mejor pensado.

🧹 reset — rehacer la historia

Privado. Saca fotos del álbum como si nunca hubieran existido. Solo para commits que nadie más ha visto. Tres niveles: --soft (conserva en posing), --mixed (conserva en carpeta; el default) y --hard (borra TODO: usar con guantes).

🛟 revert — deshacer sin mentir

Público. No borra nada: crea un commit nuevo que hace exactamente lo contrario de otro. El historial queda contando la verdad: "hicimos esto, y luego lo deshicimos". Es la única forma educada de deshacer lo que ya está compartido (próximamente: en GitHub).

revert + reflog — la red de seguridad completa 
# revert: deshacer el commit 9f3c2b1 SIN borrar la historia:
git revert 9f3c2b1
#    [main a1b2c3d] Revert "Cambiar tarifa de la multa a $800"
#    (git incluso escribe el mensaje por ti)

# reflog: TODO lo que ha pasado en este repositorio, incluso lo
# que "deshiciste". Cada línea es un lugar donde estuvo tu HEAD:
git reflog
#    a1b2c3d (HEAD -> main) revert: Revert "Cambiar tarifa…"
#    9f3c2b1 commit: Cambiar tarifa de la multa a $800
#    4a8e7d2 commit: Agregar página de préstamos
#    c1d9f3e commit (initial): Primer commit: proyecto biblioteca

# ¿Quieres volver a alguno de esos momentos? Ahí está el hash.
# Git guarda tus pasos ~90 días: en la práctica, NADA se pierde
# de verdad. Por eso decimos: equivocarse en Git es barato. 💚

🦹 El villano de verdad: reset --hard en historia compartida

git reset --hard es el único comando de esta clase que puede causar daño real: borra fotos del álbum y los cambios de la carpeta en un solo golpe. En tu borrador privado, es una herramienta legítima ("vamos a empezar esta rama de cero"). Pero si el proyecto ya está compartido con alguien (o subido a GitHub), borrar fotos del álbum común es romper el acuerdo de todos. Regla memorable: privado: reset; compartido: revert.

🔄 Actividad en pareja — 8 minutos

Uno "maneja" y el otro lee el git status en voz alta en cada paso, como piloto y copiloto:

  1. Edita main.py, haz add… y arrepiéntete: git restore --staged. ¿Dónde quedó el cambio?
  2. Arrepiéntete del todo: git restore. ¿Y ahora?
  3. Haz un commit con el mensaje "cosas" 😱 y arréglalo con --amend.
  4. Deshácelo con reset --soft HEAD~1, míralo en la posing, y vuelve a hacer el commit bien.
  5. Para cerrar: git reflog — cuenten cuántas líneas de historia tienen ya. Ese es el tamaño de su red de seguridad.
