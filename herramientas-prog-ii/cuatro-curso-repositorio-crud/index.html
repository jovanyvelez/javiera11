💡 ¿Por qué un archivo "repositorio"?

Separar el SQL en un archivo propio (repositorio.py) es una buena práctica: la ruta se encarga de HTTP, y el repositorio se encarga de la base de datos. Si mañana cambias la BD, solo tocas el repositorio.

📚 El repositorio: donde vive el SQL

⏱️ 35 minutos · "Separar la lógica de datos"

🧠 ¿Qué es un repositorio?

Un repositorio es un archivo (o clase) que contiene todas las consultas a la base de datos. En vez de escribir SQL dentro de las rutas, lo escribimos en funciones del repositorio. Cada función hace una operación: listar, obtener, crear, actualizar o borrar.

🧩

Organizado

Todo el SQL en un solo lugar, fácil de encontrar.

🔁

Reutilizable

La misma función se usa desde varias rutas.

🛡️

Seguro

Centraliza la parametrización para evitar inyección SQL.

🔧

Fácil de cambiar

Si cambias la BD, solo tocas el repositorio.

repositorio.py — estructura 
# Cada función recibe la conexión y hace una operación

async def obtener_autores(conn) -> list[dict]:
    return [dict(r) for r in await conn.fetch("SELECT * FROM autores")]

async def obtener_autor(conn, autor_id):
    ...

async def crear_autor(conn, nombre, pais, nacimiento):
    ...

async def actualizar_autor(conn, autor_id, nombre, pais, nacimiento):
    ...

async def eliminar_autor(conn, autor_id):
    ...

💡 La regla de oro

Cada función del repositorio recibe la conexión como primer argumento y hace una sola cosa. Así el código es fácil de leer y de probar. La ruta llama a la función, no escribe SQL.

🔍 SELECT: leer datos

⏱️ 35 minutos · "Listar y obtener un autor"

🧠 La idea central

Para leer datos usamos SELECT. Hay dos casos: listar todos los autores (fetch) y obtener uno por su id (fetchrow). El WHERE id = $1 filtra por el id, y $1 es un parámetro que se rellena de forma segura.

repositorio.py — leer 
async def obtener_autores(conn) -> list[dict]:
    # fetch devuelve TODAS las filas
    rows = await conn.fetch("SELECT * FROM autores ORDER BY id")
    return [dict(row) for row in rows]

async def obtener_autor(conn, autor_id: int) -> dict | None:
    # fetchrow devuelve UNA fila (o None si no existe)
    row = await conn.fetchrow("SELECT * FROM autores WHERE id = $1", autor_id)
    return dict(row) if row else None

💡 fetch vs fetchrow

fetch devuelve una lista de filas (para "todos los autores"). fetchrow devuelve una sola fila (para "el autor con id 3"). Si no hay resultados, fetchrow devuelve None.

➕ INSERT: crear datos

⏱️ 35 minutos · "Agregar un autor nuevo"

🧠 La idea central

Para crear un autor usamos INSERT INTO. Le pasamos los valores como parámetros ($1, $2, $3) y usamos RETURNING * para que la BD nos devuelva el autor recién creado (con su id nuevo).

repositorio.py — crear 
async def crear_autor(conn, nombre, pais, nacimiento) -> dict:
    row = await conn.fetchrow(
        "INSERT INTO autores (nombre, pais, nacimiento) VALUES ($1, $2, $3) RETURNING *",
        nombre, pais, nacimiento,
    )
    return dict(row)

🦹 El villano: la inyección SQL

Si pegas el valor del usuario directamente en la consulta con un f-string (f"... {nombre}"), un usuario malintencionado podría escribir "; DROP TABLE autores; -- y borrar la tabla. Con parámetros ($1), asyncpg envía el valor por separado y PostgreSQL lo trata como dato, no como código. Siempre parametriza.

💡 RETURNING *

Normalmente INSERT no devuelve nada. Con RETURNING * le pedimos a la BD que nos devuelva la fila recién creada, incluyendo el id que se generó automáticamente. Así sabemos qué id le tocó al nuevo autor.

✏️ UPDATE: actualizar datos

⏱️ 35 minutos · "Editar un autor existente"

🧠 La idea central

Para actualizar un autor usamos UPDATE ... SET ... WHERE. El SET dice qué columnas cambiar, y el WHERE id = $4 dice cuál autor cambiar. Sin el WHERE, actualizarías todos los autores.

repositorio.py — actualizar 
async def actualizar_autor(conn, autor_id, nombre, pais, nacimiento):
    row = await conn.fetchrow(
        "UPDATE autores SET nombre = $1, pais = $2, nacimiento = $3 WHERE id = $4 RETURNING *",
        nombre, pais, nacimiento, autor_id,
    )
    return dict(row) if row else None

🦹 El villano: el UPDATE sin WHERE

Si olvidas el WHERE, el UPDATE cambia todas las filas de la tabla. Imagina editar un autor y que de repente todos los autores tengan el mismo nombre. Por eso el WHERE id = $4 es obligatorio.

💡 Devolver el autor actualizado

Igual que con INSERT, usamos RETURNING * para que la BD nos devuelva el autor ya actualizado. Si el id no existe, fetchrow devuelve None y la función devuelve None.

🗑️ DELETE: borrar datos

⏱️ 35 minutos · "Eliminar un autor"

🧠 La idea central

Para borrar un autor usamos DELETE FROM ... WHERE. Igual que con UPDATE, el WHERE es obligatorio: sin él, borrarías toda la tabla. La función devuelve True si borró algo y False si no.

repositorio.py — borrar 
async def eliminar_autor(conn, autor_id: int) -> bool:
    # execute devuelve un texto como "DELETE 1"
    result = await conn.execute("DELETE FROM autores WHERE id = $1", autor_id)
    return result == "DELETE 1"

🦹 El villano: el DELETE sin WHERE

DELETE FROM autores sin WHERE borra todos los autores de una sola vez. Es uno de los errores más temidos en bases de datos. Por eso siempre, siempre, el DELETE lleva su WHERE.

💡 execute vs fetch

Para DELETE (y a veces INSERT/UPDATE) usamos execute, que no devuelve filas sino un texto indicando cuántas se afectaron (por ejemplo "DELETE 1"). Con eso sabemos si realmente se borró algo.

🧠 Las 5 operaciones

  1. Listar todos los autores → SELECT * FROM autores
  2. Obtener uno por id → SELECT ... WHERE id = $1
  3. Crear → INSERT INTO ... VALUES (...) RETURNING *
  4. Actualizar → UPDATE ... SET ... WHERE id = $4
  5. Borrar → DELETE FROM ... WHERE id = $1
