0.1 · El inventario que nadie puede preguntar

El club de robótica ya tiene su catálogo en PostgreSQL. Sensores, motores, placas y baterías están ahí, guardados, con precio y stock. La presidenta del club entra un lunes y pregunta: «¿cuántos sensores baratos nos quedan?». Nadie sabe responder sin abrir psql y escribir SQL a mano. Y si pregunta otra cosa distinta, hay que escribir otra consulta.

Ese es el punto exacto donde estás. Los datos ya se guardan; lo que falta es que se consulten y que la respuesta llegue a una pantalla que cualquiera pueda leer. Una consulta SELECT es una pregunta escrita en un idioma que la base de datos entiende. Una tabla en el navegador es esa pregunta convertida en algo que se puede ver.

Distinción — guardar es una operación; consultar es una pregunta

Un INSERT escribe: añade una fila y se olvida. Un SELECT lee: no cambia nada y devuelve un conjunto de filas que puede ser enorme, vacío o exactamente el que buscabas. Las dos cosas son SQL, pero resuelven problemas distintos. Esta clase es entera sobre la segunda.

0.2 · La cadena completa: SQL → JSON → HTML

Visualizar un resultado en el navegador no es una magia aparte: es una cadena de tres eslabones que ya conoces por piezas. Hoy los vas a encadenar de principio a fin.

1 · SQL
La pregunta a PostgreSQL. SELECT nombre, precio FROM productos WHERE precio < 50000. Devuelve filas y columnas.
2 · JSON
El formato en que la API se lo cuenta al navegador. Una lista de objetos: [{"nombre": "Sensor…", "precio": 42000}].
3 · HTML
La tabla, la lista o la tarjeta que el usuario ve. Se dibuja con JavaScript (o con HTMX) a partir del JSON.
Precisión — el navegador nunca habla con PostgreSQL

El navegador pide a la API; la API consulta a PostgreSQL; PostgreSQL responde; la API convierte y devuelve JSON; el navegador dibuja. Si alguna vez te tienta abrir la base de datos desde JavaScript del lado del cliente, recuerda que ahí estarías exponiendo la contraseña de la base a cualquiera que abra las herramientas de desarrollo. El SQL vive en el servidor, siempre.

Unidad 01 · La proyección

SELECT: elegir qué mostrar

Una tabla puede tener veinte columnas y mil filas. Casi nunca quieres todo eso en pantalla. SELECT es la parte de la consulta que decide qué columnas salen y qué transformaciones sufren antes de salir.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: cinco consultas de proyección

1.1 · La forma de una consulta

Toda consulta de lectura tiene la misma espina dorsal. Primero qué quieres ver, después de dónde sale. El orden en que se escribe no es el orden en que se ejecuta —lo veremos en la unidad 3—, pero se lee de izquierda a derecha como una frase.

sql — la forma mínima de un SELECT 
SELECT nombre, precio, stock
FROM productos;
SELECT
La lista de columnas o expresiones que quieres ver. Se le llama proyección.
FROM
La tabla de la que salen los datos. Sin FROM solo puedes consultar constantes: SELECT 1 + 1.
;
El punto y coma cierra la sentencia. En psql es obligatorio; en asyncpg no, pero conviene escribirlo.

El resultado de esa consulta es una tabla con tres columnas y tantas filas como productos haya. Esa tabla es exactamente lo que después se convertirá en JSON y, al final, en filas de una tabla HTML.

1.2 · SELECT * y por qué casi nunca conviene

El asterisco significa «todas las columnas». Es cómodo en una consola, para mirar. En una API es una trampa por tres razones concretas:

Tres razones para nombrar las columnas
RazónQué pasa con SELECT *Qué pasa nombrando columnas
Peso Viajan columnas que la pantalla no usa (fechas internas, hashes…) Viaja solo lo que se dibuja
Estabilidad Si alguien añade una columna, el JSON cambia y el front puede romperse El contrato solo cambia si tú lo cambias
Claridad Quien lee el código no sabe qué datos importan La consulta documenta el uso real
Advertencia — un * que se convierte en fuga de datos

Si la tabla usuarios tuviera un hash de contraseña y escribieras SELECT * FROM usuarios para «mostrar el perfil», ese hash viajaría al navegador dentro del JSON. Nombrar columnas no es manía: es una decisión de seguridad.

1.3 · Alias con AS: nombrar lo que sale

Un alias es el nombre con el que la columna llega al resultado. Sirve para abreviar, para traducir y para nombrar expresiones calculadas que no tienen nombre propio.

sql — alias de columna y de expresión 
SELECT
  nombre            AS producto,
  precio            AS precio_unitario,
  stock * precio    AS valor_en_bodega
FROM productos;

Esos tres nombres —producto, precio_unitario, valor_en_bodega— son los que verás en el JSON y en los encabezados de la tabla HTML. El alias es el contrato entre el SQL y quien dibuja.

Precisión — el alias no cambia la tabla

AS solo renombra lo que sale en esta consulta. La tabla productos sigue teniendo su columna precio. Si mañana otra ruta consulta sin alias, verá los nombres originales. El alias vive en la consulta, no en el esquema.

1.4 · DISTINCT: cuando la repetición sobra

Diez productos pueden repartirse en cuatro categorías. Si preguntas solo por la categoría, recibirás diez filas con repeticiones. DISTINCT deduplica el resultado.

sql — categorías sin repetir 
SELECT DISTINCT categoria
FROM productos
ORDER BY categoria;
resultado 
 categoria
-------------
 energia
 kits
 motores
 placas
 sensores
(5 rows)
Nota — DISTINCT actúa sobre la fila completa del resultado

Si escribes SELECT DISTINCT categoria, precio, la deduplicación es sobre el par (categoría, precio): dos productos de la misma categoría y distinto precio producirán dos filas. No es «distinto de cada columna por separado».

1.5 · Expresiones en la lista de columnas

SELECT no se limita a copiar columnas: puede calcular. Cálculos aritméticos, funciones de texto, condiciones con CASE. Todo lo que se calcule sale como una columna nueva, y casi siempre conviene ponerle alias.

sql — calcular y decidir dentro de SELECT 
SELECT
  nombre,
  precio,
  ROUND(precio * 1.19)          AS precio_con_iva,
  CASE
    WHEN stock = 0     THEN 'agotado'
    WHEN stock < 5    THEN 'últimas unidades'
    ELSE 'disponible'
  END                        AS estado
FROM productos;
Aplicación — calcula en SQL o en el navegador

Si el cálculo es del negocio (IVA, stock valorizado, estado de inventario), hazlo en SQL: una sola verdad, un solo sitio donde corregir. Si el cálculo es de presentación (un color, un texto «hace 2 días»), hazlo en el navegador. La regla: lo que se guarda o se decide, en el servidor; lo que se pinta, en el cliente.

1.6 · Práctica guiada: cinco proyecciones

Sobre la tabla productos(id, nombre, categoria, precio, stock, activo), escribe y ejecuta en psql estas cinco consultas. Comprueba el resultado antes de seguir.

  1. Solo nombre y precio, orden alfabético de nombre (lo afinamos en la unidad 3).
  2. nombre como producto y stock como unidades.
  3. Las categorías distintas del catálogo.
  4. nombre y precio * stock como valor_bodega.
  5. Un CASE que marque agotado si stock = 0 y en venta en caso contrario.
sql — cinco proyecciones 
-- 1. Dos columnas
SELECT nombre, precio FROM productos;

-- 2. Alias
SELECT nombre AS producto, stock AS unidades FROM productos;

-- 3. Distintas
SELECT DISTINCT categoria FROM productos;

-- 4. Expresión
SELECT nombre, precio * stock AS valor_bodega FROM productos;

-- 5. Condición
SELECT nombre,
  CASE WHEN stock = 0 THEN 'agotado' ELSE 'en venta' END AS estado
FROM productos;

Unidad 02 · El filtro

WHERE: filtrar con criterio

Proyectar columnas es elegir el ancho de la respuesta. WHERE es elegir qué filas entran en ella. Es la cláusula que convierte una tabla entera en la respuesta a una pregunta concreta.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: filtros seguros con parámetros

2.1 · La cláusula WHERE

WHERE se escribe después de FROM y antes de cualquier cosa que ordene o agrupe. Recibe una condición; la fila pasa si la condición es verdadera, y se descarta si es falsa o desconocida. Ese tercer estado —desconocido— es el de los NULL, y merece su propio apartado.

sql — el filtro mínimo 
SELECT nombre, precio, stock
FROM productos
WHERE stock > 0;

2.2 · Operadores de comparación

Operadores que vas a usar todos los días
OperadorSignificadoEjemplo
=Igual (en SQL no es ==)WHERE categoria = 'sensores'
<> o !=DistintoWHERE activo <> false
< <= > >=Menor, menor o igual, mayor, mayor o igualWHERE precio >= 50000
IS NULLEl valor es nuloWHERE stock IS NULL
IS NOT NULLEl valor no es nuloWHERE precio IS NOT NULL
Advertencia — en SQL la igualdad es un solo =

En Python, JavaScript o C, la igualdad es == y la asignación =. En SQL, = compara. Si escribes WHERE categoria == 'kits', PostgreSQL responde con un error de sintaxis, y está bien: te está diciendo que ese idioma no se escribe así.

2.3 · AND, OR y NOT

Las condiciones se combinan como en lenguajes de programación. La precedencia es NOT, después AND, después OR. Cuando dudes, usa paréntesis: no cuestan nada y evitan el error más caro de un filtro.

sql — combinar condiciones 
-- Sensores baratos que todavía hay en stock
SELECT nombre, precio, stock
FROM productos
WHERE categoria = 'sensores'
  AND precio < 50000
  AND stock > 0;

-- O bien barato, o bien con muchas unidades (el paréntesis importa)
SELECT nombre, precio, stock
FROM productos
WHERE (precio < 30000 OR stock > 20)
  AND activo = true;
Precisión — precio < 30000 OR stock > 20 AND activo

Sin paréntesis, AND se evalúa antes que OR, así que esa consulta significa «barato, o bien (con stock y activo)». Si querías «(barato o con stock) y activo», el resultado sería distinto. Cuando una consulta mezcle AND y OR, escribe los paréntesis aunque creas que sobran.

2.4 · LIKE, IN y BETWEEN

Tres atajos que evitan condiciones interminables y que se leen mejor que la alternativa.

sql — patrones, listas y rangos 
-- LIKE: % es «da igual lo que haya»; _ es «un carácter»
SELECT nombre FROM productos
WHERE nombre LIKE 'Sensor%';

SELECT nombre FROM productos
WHERE nombre LIKE '%ultrasónico%';

-- IN: un valor de una lista (mucho más claro que tres OR)
SELECT nombre, categoria FROM productos
WHERE categoria IN ('sensores', 'placas', 'kits');

-- BETWEEN: rango inclusivo en los dos extremos
SELECT nombre, precio FROM productos
WHERE precio BETWEEN 30000 AND 80000;
Nota — ILIKE ignora mayúsculas y minúsculas

LIKE distingue sensor de Sensor. En PostgreSQL, ILIKE no. Para un buscador de catálogo, casi siempre quieres ILIKE: quien escribe «sensor» espera encontrar «Sensor ultrasónico».

2.5 · NULL: el valor que no es un valor

NULL no es cero ni es «vacío». Es la ausencia de valor: se ignora el precio, o se ignora el stock. Y con él, la lógica de tres estados se vuelve obligatoria.

Cómo se comporta NULL en un WHERE
Expresión¿Pasa la fila?Por qué
stock = NULLNuncaLa comparación con NULL no es ni verdadera ni falsa: es desconocida
stock IS NULLSi el stock es nuloLa única forma correcta de preguntar por la ausencia

Advertencia — el bug silencioso de los NULL

Es el filtro que «no funciona» y no da error: devuelve menos filas de las que esperabas, y el culpable es un campo nulo que nadie miró. Antes de culpar al WHERE, comprueba si la columna puede ser nula y si tu condición sobrevive a un NULL.

2.6 · Parámetros: $1, $2…

La consulta de la clase 8 ya lo usaba, y ahora toca entender por qué. Un parámetro es un hueco en el SQL que se rellena después, de forma que el valor del usuario nunca llega a formar parte del texto de la consulta.

consultas.py — filtro parametrizado con asyncpg 
async def productos_de_categoria(conn, categoria: str) -> list[dict]:
    """Los productos activos de una categoría, por precio."""
    filas = await conn.fetch(
        """
        SELECT id, nombre, precio, stock
        FROM productos
        WHERE categoria = $1
          AND activo = true
        ORDER BY precio
        """,
        categoria,
    )
    return [dict(f) for f in filas]
consultas.py — lo que jamás se escribe 
# NUNCA. Ni en un taller, ni en una broma, ni «solo para probar».
sql = f"SELECT * FROM productos WHERE categoria = '{categoria}'"
await conn.fetch(sql)   # inyección SQL, en dos líneas
Distinción — el valor no es código

Con $1, lo que el usuario escriba es un dato: se compara como texto, se trata como texto y no puede cambiar la consulta. Con f-strings, lo que escriba es código SQL: si escribe x' OR '1'='1, la consulta devuelve la tabla entera. La diferencia entre las dos líneas de arriba es la diferencia entre una API segura y una noticia de seguridad.

2.7 · Práctica guiada: cuatro filtros

  1. Los productos de la categoría 'kits' con stock positivo.
  2. Los productos cuyo nombre empieza por 'Sensor' (con LIKE).
  3. Los productos con precio entre 30 000 y 80 000, o con stock mayor que 20.
  4. La misma consulta del punto 1, pero como función con un parámetro $1.
sql y python — cuatro filtros 
-- 1. Categoría y stock
SELECT nombre, stock FROM productos
WHERE categoria = 'kits' AND stock > 0;

-- 2. Prefijo
SELECT nombre FROM productos
WHERE nombre LIKE 'Sensor%';

-- 3. Rango o stock alto
SELECT nombre, precio, stock FROM productos
WHERE (precio BETWEEN 30000 AND 80000) OR stock > 20;

-- 4. Con parámetro
await conn.fetch(
    "SELECT nombre, stock FROM productos WHERE categoria = $1 AND stock > 0",
    categoria,
)

Unidad 03 · El orden y el resumen

Ordenar, limitar y resumir

Ya eliges columnas y filas. Falta decidir el orden en que salen, cuántas salen, y cómo condensar mil filas en cinco números que se puedan leer de un vistazo.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: resumen por categoría

3.1 · ORDER BY: el orden no es gratis, pero es obligatorio

Una tabla relacional no garantiza orden. Sin ORDER BY, las filas llegan en el orden que le convenga al planificador de PostgreSQL: casi siempre el de inserción en tablas pequeñas, y otro cualquiera en tablas con índices o actualizaciones. Si la pantalla necesita un orden, dilo en el SQL.

sql — orden por una y por dos columnas 
-- Del más barato al más caro
SELECT nombre, precio
FROM productos
ORDER BY precio ASC;

-- Categoría alfabética, y dentro de cada una, el más caro primero
SELECT categoria, nombre, precio
FROM productos
ORDER BY categoria ASC, precio DESC;
Detalles de ORDER BY que se olvidan
DetalleComportamiento
ASC / DESCAscendente es el orden por defecto; DESC invierte solo esa columna
Varias columnasSe aplican en el orden en que se escriben: primero la categoría, después el precio
Por número de posiciónORDER BY 2 ordena por la segunda columna del SELECT
NULLS FIRST / LASTDecide dónde caen los nulos; por defecto, al final en ASC

3.2 · OFFSET y LIMIT: acotar la respuesta

Ninguna pantalla útil muestra mil filas de golpe. LIMIT corta el resultado; OFFSET salta las primeras filas. Juntos forman la paginación más simple que existe.

sql — top 3 y página 2 
-- Los tres más caros
SELECT nombre, precio
FROM productos
ORDER BY precio DESC
LIMIT 3;

-- Página 2 de 10 en 10 (filas 11 a 20)
SELECT id, nombre
FROM productos
ORDER BY nombre
LIMIT 10 OFFSET 10;
Advertencia — LIMIT sin ORDER BY es una ruleta

Si preguntas «los 10 productos» sin decir el orden, PostgreSQL te da diez productos, sí, pero no tienes ninguna garantía de cuáles ni de que sean los mismos la próxima vez. En una paginación, eso significa productos que se repiten o que se saltan entre una página y la siguiente. Ordena siempre que limits.

3.3 · Funciones de agregado: de mil filas a un número

Un agregado colapsa varias filas en un valor. No devuelve una fila por producto: devuelve un número. Y esa diferencia se nota en lo que se puede poner a su lado.

Los cinco agregados que usarás siempre
FunciónQué calculaEjemplo
COUNT(*)Número de filasSELECT COUNT(*) FROM productos
SUM(precio)SumaValor total del catálogo
AVG(precio)Media aritméticaPrecio medio
MIN / MAXExtremosProducto más barato y más caro
COUNT(col)Valores no nulosDiferente de COUNT(*) si hay nulos
sql — el resumen del catálogo 
SELECT
  COUNT(*)                AS productos,
  SUM(stock)             AS unidades,
  ROUND(AVG(precio))     AS precio_medio,
  MIN(precio)            AS mas_barato,
  MAX(precio)            AS mas_caro
FROM productos
WHERE activo = true;

3.4 · GROUP BY y HAVING

«El resumen del catálogo» es un número. «El resumen por categoría» es una fila por categoría. Ese agrupamiento se escribe con GROUP BY, y el filtro después de agrupar se llama HAVING.

sql — resumen por categoría 
SELECT
  categoria,
  COUNT(*)                 AS productos,
  SUM(stock)              AS unidades,
  ROUND(AVG(precio))      AS precio_medio
FROM productos
WHERE activo = true
GROUP BY categoria
HAVING COUNT(*) >= 2
ORDER BY precio_medio DESC;
Distinción — WHERE filtra filas; HAVING filtra grupos

El orden de ejecución es: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Por eso WHERE activo se aplica antes de contar, y HAVING COUNT(*) >= 2 se aplica después. Si pones el conteo en un WHERE, PostgreSQL te dirá que no existe esa columna todavía: tiene razón.

Nota — lo que se puede listar junto a un agregado

En un SELECT con agregados, cada columna que no sea agregada debe aparecer en el GROUP BY. SELECT categoria, COUNT(*) funciona porque categoria está agrupada. SELECT nombre, COUNT(*) sin agrupar por nombre es un error de SQL, y está bien que lo sea: la pregunta no tiene sentido.

3.5 · Práctica guiada: el resumen de la semana

  1. Los cinco productos más baratos, del más barato al quinto.
  2. Cuántos productos hay en cada categoría (incluidas las categorías con un solo producto).
  3. Las categorías con más de 20 unidades en stock sumadas.
  4. El precio medio por categoría, solo de productos activos, del más alto al más bajo.
sql — resumen de la semana 
-- 1. Cinco más baratos
SELECT nombre, precio FROM productos
ORDER BY precio ASC LIMIT 5;

-- 2. Productos por categoría
SELECT categoria, COUNT(*) AS productos
FROM productos GROUP BY categoria ORDER BY categoria;

-- 3. Categorías con stock total alto
SELECT categoria, SUM(stock) AS unidades
FROM productos
GROUP BY categoria
HAVING SUM(stock) > 20;

-- 4. Precio medio por categoría, activos
SELECT categoria, ROUND(AVG(precio)) AS precio_medio
FROM productos
WHERE activo = true
GROUP BY categoria
ORDER BY precio_medio DESC;

El nombre con el que una columna o expresión sale en el resultado.
Agregado
Función que colapsa varias filas en un valor: COUNT, SUM, AVG.
Parámetro
Hueco $1, $2… que se rellena con un dato, nunca con código SQL.
JSON
Formato de texto para estructuras de datos. El idioma en que la API le habla al navegador.
Escape
Convertir <, > y & en entidades para que un texto no se interprete como HTML.

Actividad 5.1 · De la consulta a la ruta

El SQL ya sabe responder. Ahora hay que colgarlo de una URL de FastAPI para que cualquiera pueda preguntar desde el navegador o desde curl, con filtros opcionales.

5.1 · El enunciado

Actividad

La ruta consultora del catálogo

La tienda necesita una URL que devuelva productos como JSON, con filtros opcionales por categoría, precio máximo y búsqueda de texto. La consulta debe vivir en un módulo aparte, usar parámetros y devolver una lista siempre —también cuando no hay resultados—.

Ficha del sistema

Entrada GET /productos?categoria=sensores&precio_max=50000&q=sensor (todo opcional)
Salida 200 con una lista JSON de productos, o [] si no hay coincidencias
Restricción Toda la consulta con $1, $2…; ningún valor pegado al SQL
Restricción La SQL vive en consultas.py; la ruta solo la invoca y formatea
Restricción Orden estable: ORDER BY precio, id

5.2 · Tres formas de leer: fetch, fetchrow, fetchval

asyncpg no devuelve «un resultado». Devuelve el resultado con la forma que pediste. Elegir bien la variante evita convertir a mano y evita errores tontos.

Qué método usar según lo que necesites
MétodoDevuelveCuándo
conn.fetch(sql, …)Lista de Record (filas)Listados, tablas, el caso normal de un SELECT
conn.fetchrow(sql, …)Una fila o NoneDetalle por id, «el producto 7»
conn.fetchval(sql, …)La primera columna de la primera filaCOUNT, AVG, un solo número
consultas.py — las tres variantes 
from typing import Any

async def listar_productos(
    conn,
    categoria: str | None = None,
    precio_max: int | None = None,
    q: str | None = None,
) -> list[dict[str, Any]]:
    """Productos con filtros opcionales. Nunca devuelve None: siempre lista."""
    condiciones: list[str] = ["activo = true"]
    valores: list[Any] = []

    if categoria is not None:
        valores.append(categoria)
        condiciones.append(f"categoria = ${len(valores)}")

    if precio_max is not None:
        valores.append(precio_max)
        condiciones.append(f"precio <= ${len(valores)}")

    if q:
        valores.append(f"%{q}%")
        condiciones.append(f"nombre ILIKE ${len(valores)}")

    sql = f"""
        SELECT id, nombre, categoria, precio, stock
        FROM productos
        WHERE {" AND ".join(condiciones)}
        ORDER BY precio, id
    """

    filas = await conn.fetch(sql, *valores)
    return [dict(f) for f in filas]


async def contar_productos(conn) -> int:
    """Un solo número: cuántos productos activos hay."""
    return await conn.fetchval(
        "SELECT COUNT(*) FROM productos WHERE activo = true"
    )
Precisión — len(valores) construye el hueco correcto

Cada filtro añade un valor y, con él, el siguiente hueco: $1, $2, $3. El texto del SQL se arma con el número del hueco, no con el valor. El valor viaja aparte, en *valores. Esa separación es exactamente lo que impide la inyección.

5.3 · La ruta FastAPI

La ruta recibe los parámetros de la query string como opcionales, llama a la consulta y devuelve la lista. Nada más. Sin formatear HTML aquí: eso es trabajo del navegador.

main.py — GET /productos 
from fastapi import Depends, Query
from database import ConnectionDep
import consultas

@app.get("/productos")
async def listar_productos(
    conn: ConnectionDep,
    categoria: str | None = Query(None),
    precio_max: int | None = Query(None, ge=0),
    q: str | None = Query(None, min_length=1, max_length=60),
):
    return await consultas.listar_productos(
        conn, categoria=categoria, precio_max=precio_max, q=q
    )
Nota — Query(...) también valida

ge=0 rechaza precios negativos y min_length/max_length acotan el buscador. La validación vive en la frontera: lo que entra de la red se comprueba antes de tocar la base de datos.

5.4 · Probar con curl antes de dibujar nada

Si la ruta no devuelve bien el JSON, la tabla nunca se verá bien. Comprueba el contrato en la terminal; es más rápido que abrir el navegador con las herramientas de desarrollo.

terminal — tres casos 
# 1. Sin filtros: el catálogo entero
curl -s http://localhost:8000/productos | python -m json.tool

# 2. Con filtros
curl -s "http://localhost:8000/productos?categoria=sensores&precio_max=50000"

# 3. Sin resultados: debe devolver [], no un error
curl -s "http://localhost:8000/productos?categoria=drones"
Advertencia — [] es un éxito, no un fallo

Una consulta correcta que no encuentra filas no es un error. Si la ruta devuelve 404 porque no hay coincidencias, el navegador dibujará un error donde debería dibujar «no hay productos». Reserva 404 para el recurso que no existe (un producto concreto), no para el listado vacío.

6.2 · Dibujar una tabla con JavaScript

El navegador no «entiende» JSON: recibe texto, lo parsea y tú decides cómo se pinta. La forma más clara de pintar una tabla es crear los elementos uno a uno y asignar el texto con textContent.

static/catalogo.js — pintar la tabla 
async function cargarCatalogo(params = '') {
  const tabla = document.querySelector('#tabla-productos');
  const estado = document.querySelector('#estado');

  estado.textContent = 'Cargando…';
  tabla.innerHTML = '';

  try {
    const res = await fetch(`/productos${params}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);

    const productos = await res.json();

    if (productos.length === 0) {
      estado.textContent = 'No hay productos con esos filtros.';
      return;
    }

    const columnas = ['nombre', 'categoria', 'precio', 'stock'];
    const thead = document.createElement('thead');
    const trH = document.createElement('tr');
    columnas.forEach(c => {
      const th = document.createElement('th');
      th.textContent = c;          // texto, no HTML
      trH.appendChild(th);
    });
    thead.appendChild(trH);
    tabla.appendChild(thead);

    const tbody = document.createElement('tbody');
    productos.forEach(p => {
      const tr = document.createElement('tr');
      columnas.forEach(c => {
        const td = document.createElement('td');
        td.textContent = p[c];
        tr.appendChild(td);
      });
      tbody.appendChild(tr);
    });
    tabla.appendChild(tbody);
    estado.textContent = `${productos.length} productos`;
  } catch (err) {
    estado.textContent = 'No se pudo cargar el catálogo. Revisa el servidor.';
  }
}

6.3 · Escape: el dato que no es HTML

Si alguna vez se te ocurre escribir td.innerHTML = p.nombre, deja de leer y cambia a textContent. No es estética: es seguridad.

javascript — la diferencia que importa 
// Un producto con nombre hostil
const p = { nombre: '<img src=x onerror=alert(1)>' };

td.innerHTML = p.nombre;    // el navegador ejecuta el script  ← XSS
td.textContent = p.nombre;  // se ve el texto literal      ← correcto
Advertencia — XSS: el script que se cuela por un nombre de producto

Si el nombre de un producto puede escribirlo un usuario y tú lo insertas con innerHTML, esa persona (o quien haya comprometido la base) puede ejecutar JavaScript en el navegador de todo el que abra el catálogo. textContent convierte el valor en texto y el navegador lo dibuja tal cual. Es una línea de código y cierra el agujero.

6.4 · Los tres estados que siempre se pintan

Una tabla sin estados es una tabla a medias
EstadoCuándoQué debe ver el usuario
CargandoEntre el fetch y la respuesta«Cargando…» o un esqueleto de tabla
Vacío200 con []«No hay productos con esos filtros.»
ErrorRed caída, 500, 503«No se pudo cargar. Revisa el servidor.»
Con datosUna o más filasLa tabla y el conteo de filas

6.5 · Tres puertas: JavaScript, HTMX o Jinja2

html — HTMX: la tabla que se actualiza sin escribir JS 
<form hx-get="/productos" hx-target="#tabla" hx-trigger="change">
  <select name="categoria">
    <option value="">Todas</option>
    <option value="sensores">Sensores</option>
  </select>
</form>

<div id="tabla">
  <!-- el servidor devuelve solo el fragmento de tabla -->
</div>
Distinción — JSON + JS, HTMX o Jinja: tres contratos distintos

Con JSON + JavaScript, el servidor devuelve datos y el cliente dibuja: máximo control, más código en el navegador. Con HTMX, el servidor devuelve fragmentos HTML y el cliente solo los inserta: menos JS, más HTML en el servidor. Con Jinja2, el servidor devuelve la página entera: la opción más simple y la menos interactiva. Elige por quién mantendrá la pantalla, no por moda.

async def resumen_por_categoria(conn) -> list[dict]:
    """Un renglón por categoría: productos, unidades y precio medio."""
    filas = await conn.fetch(
        """
        SELECT
          categoria,
          COUNT(*)            AS productos,
          SUM(stock)          AS unidades,
          ROUND(AVG(precio))  AS precio_medio
        FROM productos
        WHERE activo = true
        GROUP BY categoria
        ORDER BY unidades DESC
        """
    )
    return [dict(f) for f in filas]

  


  
7.3 · Las tres reglas que este taller no negocia


  

    Regla 1 — nada de SELECT * en una ruta pública
    

      Nombrar columnas es la forma más barata de no filtrar datos sensibles y de no romper el
      contrato del JSON cuando la tabla cambie. Si necesitas otra columna, la añades a la consulta
      y al modelo a la vez.
    

  


  

    Regla 2 — ningún valor del usuario se pega al SQL
    

      Ni con f-strings, ni con format, ni «solo esta vez». El hueco es
      $n; el valor viaja aparte. Si un filtro es opcional, se añade la condición al
      SQL y el valor a la lista, como en la unidad 5.
    

  


  

    Regla 3 — ningún dato se inserta como HTML
    

      textContent para pintar, o escape explícito si usas plantillas. Un nombre de
      producto con <script> debe verse como texto, no ejecutarse. Y los tres
      estados de la tabla —cargando, vacío, error— se implementan, no se dejan «para después».

7.5 · Síntesis: siete ideas para llevarse


  

    

      
01

      
Un SELECT es una pregunta: la proyección elige el ancho, el WHERE elige las filas.

    

    

      
02

      
SELECT * es cómodo en la consola y una fuga de datos en una API. Nombra las columnas.

    

    

      
03

      
Los parámetros $1, $2 separan el dato del código. Esa separación es la seguridad.

    

    

      
04

      
Los NULL no son cero: IS NULL es la única pregunta que los encuentra.

    

    

      
05

      
Ordena siempre que limits. Sin ORDER BY, la paginación es una ruleta.

    

    

      
06

      
WHERE filtra filas; HAVING filtra grupos. El orden de ejecución lo decide el motor.

    

    

      
07

      
La cadena es SQL → JSON → HTML. Pinta con textContent y no olvides los estados vacío y error.
