Unidad 00 · Apertura

La máquina del tiempo de tu código

Git guarda fotos de tu proyecto para que puedas volver, comparar y trabajar en paralelo sin pisar a nadie. Esta clase te da el flujo mínimo que se usa todos los días —iniciar, preparar, confirmar, ramificar, fusionar y deshacer— con los comandos actuales de Git 2.56.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: el mapa de las tres zonas

0.1 · Tres accidentes que Git evita

Son las 11:40 y entrega es a las 12:00. Dañas app.py con un cambio que no entiendes, el último commit tiene un mensaje que dice «asdf», y ya subiste a la nube un cambio que rompió la página. Sin Git, los tres problemas se resuelven con copias llamadas app_final_bueno_ahora_si.py. Con Git, se resuelven con seis comandos que vas a aprender en esta clase.

Git no es solo «subir código a GitHub». Es un historial local de fotos de tu proyecto. Cada foto —un commit— guarda qué cambió, quién lo cambió y por qué. A partir de ese historial puedes volver atrás, probar una idea en una rama y deshacer un error sin perder el trabajo de los demás.

Distinción — guardar el archivo no es guardar la foto

Guardar en el editor escribe el archivo en el disco. Un commit es distinto: congela una versión del proyecto en el historial. Puedes tener el archivo guardado y, aun así, no tener ningún commit. Y puedes tener un commit sin haber subido nada a internet: Git trabaja primero en tu computadora.

Una rama es un nombre que apunta a un commit. Cuando haces un commit nuevo en main, el nombre main avanza. Si creas feature/saludo y haces commits allí, main se queda donde estaba. Esa es toda la magia: trabajar en paralelo sin copiar carpetas.

0.3 · Git moderno: los comandos que sí se usan hoy

Esta clase se apoya en Git 2.56.0, publicado el 28 de septiembre de 2026 según la documentación oficial. Los comandos de abajo existen desde Git 2.23 o antes, así que funcionan en cualquier Git actual.

Lo viejo y lo claro
Se usabaHoy es más claroPor qué
git checkout ramagit switch ramaswitch solo cambia de rama; no toca archivos
git checkout -b ramagit switch -c ramaCrea y se mueve en un solo paso, sin ambigüedad
git checkout -- app.pygit restore app.pyrestore solo restaura archivos
git reset HEAD app.pygit restore --staged app.pySaca del staging sin tocar el archivo
Precisión — checkout no está «deprecado»

Git sigue manteniendo git checkout y no planea eliminarlo. Lo que cambió es la recomendación: switch y restore separan dos acciones que checkout mezclaba —cambiar de rama y restaurar archivos—. En documentación vieja y en tutoriales de internet lo vas a encontrar; para tu trabajo diario, usa los comandos claros.

Unidad 01 · El origen

Iniciar el repositorio y ponerle main

Antes del primer commit hay que crear el repositorio, configurar tu identidad y decidir cómo se llama la rama principal. Git ya no te obliga a llamarla master: el estándar actual es main, y se puede elegir al iniciar o renombrar después.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: repositorio con primer commit en main

1.1 · Comprobar Git y configurar tu identidad

Git firma cada commit con un nombre y un correo. Si no los configuras, el commit falla o queda con una identidad inventada. Hazlo una vez por computadora con --global.

terminal — versión e identidad 
git --version

git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"

# La rama inicial de todos los repos nuevos será main
git config --global init.defaultBranch main

git config --global --list
user.name
El nombre que aparecerá como autor de cada commit. No tiene que ser tu nombre legal; usa el que quieras que vea tu equipo.
user.email
El correo asociado a los commits. En GitHub conviene que coincida con el de tu cuenta para que te atribuya la autoría.
init.defaultBranch main
Hace que git init cree main en lugar de master. Es una preferencia local; no cambia repos que ya existen.
--global
Aplica a todos tus repositorios. Sin --global, el ajuste vale solo para el repositorio actual.

1.2 · Crear el repositorio con main desde el inicio

git init -b main crea el repositorio y le pone main a la rama inicial en un solo paso. Es la forma recomendada desde Git 2.28; no hace falta iniciar con master y renombrar después.

terminal — iniciar un repositorio nuevo 
mkdir bitacora-git
cd bitacora-git

git init -b main
git status
salida esperada (tu Git puede estar en español) 
Initialized empty Git repository in /ruta/bitacora-git/.git/
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
Nota — qué es esa carpeta .git

git init crea una carpeta oculta .git/ con todo el historial y la configuración del repositorio. No la borres, no la edites a mano y no la copies dentro de otra carpeta como si fuera un archivo normal. Si ves .git, estás dentro de un repositorio.

1.3 · El primer archivo y el primer commit

Crea app.py, míralo con git status, prepáralo con git add y confírmalo con git commit. El primer commit es la foto base de tu proyecto.

terminal — del archivo al primer commit 
printf 'def saludar():\n    return "Hola"\n' > app.py

git status -sb
# ?? app.py

git add app.py
git status -sb
# A  app.py

git commit -m "crear el archivo inicial de la aplicación"
git log --oneline --decorate

1.4 · El .gitignore desde el primer día

No todo lo que hay en la carpeta debe entrar al historial. Los archivos temporales, las dependencias y los secretos se excluyen con .gitignore. Ese archivo sí se versiona; lo que contiene son patrones.

.gitignore — un ejemplo para Python 
__pycache__/
*.pyc
.venv/
.env
.vscode/
.DS_Store
Advertencia — si ya lo preparaste, .gitignore no lo saca

.gitignore evita que Git vea archivos nuevos, pero no elimina del staging uno que ya agregaste. Si un archivo prohibido ya está preparado, sácalo con git restore --staged archivo y confirma el .gitignore. Si ya está en un commit, hay que sacarlo del historial con más cuidado.

1.5 · Renombrar master a main

Si tu repositorio ya existe y su rama principal se llama master, se renombra con git branch -m. Esto cambia el nombre local; no reescribe commits ni borra nada.

terminal — renombrar la rama principal 
# Ver cómo se llama la rama actual
git branch

# Renombrar master a main (solo local)
git branch -m master main

# Confirmar
git branch
git status -sb

Si el repositorio ya tiene un remoto —por ejemplo, GitHub con origin— hay que publicar la rama nueva, cambiar la rama predeterminada en la plataforma y recién entonces borrar la vieja. No borres master del remoto antes de cambiar la predeterminada: dejarías el repositorio apuntando a una rama que ya no existe.

terminal — renombrar con remoto (opcional) 
# 1. Renombrar en local
git branch -m master main

# 2. Subir main y dejarla como upstream
git push -u origin main

# 3. En GitHub: Settings → Branches → cambiar la default a main

# 4. Recién ahora borrar la rama vieja del remoto
git push origin --delete master
Precisión — el nombre no cambia el historial

git branch -m master main mueve la etiqueta main al mismo commit donde estaba master. Los commits, sus hashes y sus fechas no cambian. Lo que cambia es el nombre de la rama y, si tienes remoto, la referencia que hay que volver a publicar.

1.6 · Verificar antes de seguir

terminal — checklist del repositorio 
git status -sb          # debe decir: ## main
git log --oneline       # debe mostrar tu primer commit
git branch              # debe mostrar * main
git remote -v           # vacío si es local; origin si ya lo subiste

Unidad 02 · La foto

Stage y commits: elegir qué entra en la foto

Un commit no debería ser «todo lo que cambié hoy». Debería ser una unidad con sentido: un arreglo, una función, un documento. El staging existe para que elijas exactamente qué entra en cada foto, aunque tengas diez archivos modificados.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: commits atómicos y legibles

2.1 · Mirar antes de preparar

git status es el GPS: dice en qué rama estás y qué archivos cambiaron. Pero no muestra el contenido del cambio. Para eso están git diff —lo que aún no está preparado— y git diff --staged —lo que ya está en el staging—.

terminal — los tres diagnósticos 
git status -sb          # rama y archivos, en formato corto
git diff                # cambios en la carpeta que NO están preparados
git diff --staged       # cambios que SÍ están preparados para el commit
Nota — git diff no muestra archivos nuevos

Un archivo que Git todavía no conoce aparece como ?? en git status, pero git diff no lo muestra: no hay versión anterior con la que compararlo. Para verlo, prepáralo con git add y usa git diff --staged.

2.2 · Preparar archivos

Formas de preparar cambios
ComandoQué preparaCuándo usarlo
git add app.pyEse archivo completoEl caso normal y más seguro
git add app.py estilos.cssVarios archivos concretosCuando el commit toca esos dos
git add .Todo lo nuevo o modificado desde la carpeta actualCuidado: puede incluir archivos que no querías
git add -p app.pySolo algunos fragmentos del archivoCuando hay dos cambios distintos en el mismo archivo
git restore --staged app.pySaca el archivo del staging sin tocar su contenidoTe arrepentiste de prepararlo
Advertencia — git add . no es pecado, pero sí una decisión

git add . es cómodo y en un proyecto pequeño suele estar bien. El problema es que también prepara archivos temporales, capturas o credenciales que olvidaste ignorar. Antes de usarlo, mira git status; si hay algo que no debe entrar, agrégalo a .gitignore o prepáralo archivo por archivo.

2.3 · El mensaje del commit

El mensaje no es un trámite: es lo que vas a leer dentro de seis meses cuando algo falle. La convención más extendida es una primera línea corta, en imperativo, que complete la frase «Este commit va a…»; si hace falta, una línea en blanco y un cuerpo que explique el porqué.

Mensajes que ayudan y mensajes que estorban
BuenoMaloPor qué
validar el correo antes de guardarcambiosDice qué hace y en qué parte
corregir el cálculo del IVAfixSe entiende sin abrir el diff
agregar la pantalla de reportesasdfNo hay que adivinar
documentar cómo arrancar el proyectoupdate READMEExplica el para qué, no solo el archivo
terminal — commit con título y cuerpo 
git add app.py validaciones.py
git commit -m "validar el correo antes de guardar" -m "Rechaza direcciones sin @ y muestra el error junto al campo."

# Una sola línea también es válida
git add README.md
git commit -m "documentar cómo arrancar el proyecto"
Precisión — git commit -am solo mira archivos ya seguidos

git commit -am "..." prepara y confirma los archivos que Git ya conoce, pero no incluye archivos nuevos. Es cómodo para un cambio pequeño en un archivo existente; no reemplaza a git add cuando hay archivos nuevos o cambios que quieres separar.

2.4 · Commits atómicos, no un revoltijo

Un commit atómico hace una sola cosa. Si el commit arregla el precio y además cambia el color del botón, no puedes revertir el precio sin revertir el color. Separar en dos commits no es burocracia: es lo que hace que deshacer sea fácil.

Commit 1
validar el correo

Un archivo, una intención. Se puede revertir sin tocar el diseño.

──▶ luego
Commit 2
cambiar el color del botón

Otro archivo, otra intención. Se puede revertir por separado.

──▶ luego
Commit 3
documentar el cambio

El README explica lo anterior; no mezcla código con documentación.

2.5 · El historial

terminal — leer el álbum 
git log --oneline --decorate
git log --oneline --graph --decorate --all
git show HEAD
git show HEAD~1:app.py
HEAD
El commit donde estás ahora. Normalmente es la punta de la rama actual.
HEAD~1
El commit anterior a HEAD. HEAD~2 es dos atrás, y así.
--oneline
Una línea por commit: hash corto y mensaje. Es la vista más útil para el día a día.
--graph
Dibuja las ramas y fusiones con caracteres. Se entiende mejor junto a --all.
--decorate
Muestra los nombres de ramas y etiquetas junto a los commits.

 Unidad 03 · Los caminos

    
Ramas: trabajar en paralelo y volver

    

      Una rama es una línea de trabajo independiente. Puedes crear una para probar una idea,
      cambiar de rama para revisar main, y fusionar cuando la idea esté lista. Si algo
      sale mal, la rama se borra y main nunca se enteró.
    

    

      ⏱ 30 minutos
      📄 Lectura y práctica
      🧭 Producto: una rama creada, recorrida y fusionada
    

  


  
3.1 · Una rama es un nombre que apunta a un commit


  

    Cuando creas una rama, Git no copia la carpeta ni duplica los archivos. Solo crea un nombre
    nuevo que apunta al mismo commit donde estás. A partir de ahí, los commits que hagas en esa
    rama mueven ese nombre, no el de main.
  


  

    

      
main

      
commit A

      
La base estable. main apunta aquí.

    

    

      ──▶
      git switch -c
feature
    

    

      
feature

      
commit B

      
Tu idea nueva. feature avanza; main sigue en A.

    

    

      ──▶
      git merge
feature
    

    

      
main

      
commit A + B

      
La idea ya está en main. La rama se puede borrar.

    

  


  

    

      

        

        terminal — crear, listar y cambiar de rama
      

      
    


git branch                      # lista ramas; * marca la actual
git switch -c feature/saludo    # crea Y se mueve a la rama nueva
git branch                      # * feature/saludo, main

git switch main                 # vuelve a main
git switch -                    # vuelve a la rama anterior
git switch feature/saludo       # va a una rama que ya existe


  


  

    

      
git switch -c nombre

      
Crea la rama y te mueve a ella en un solo paso. Es el reemplazo claro de git checkout -b.

    

    

      
git switch nombre

      
Cambia a una rama existente. Conserva tus cambios sin confirmar si no chocan con la rama de destino.

    

    

      
git switch -

      
Vuelve a la rama en la que estabas antes. Muy útil para ir y volver entre dos ramas.

    

    

      
git branch -d nombre

      
Borra una rama ya fusionada. Si no está fusionada, Git se niega; -D fuerza el borrado y puede perder commits.

    

  


  

    Advertencia — cambiar de rama no es magia si tienes cambios sin confirmar
    

      Si tienes archivos modificados que chocan con la rama de destino, Git no te deja cambiar y te
      pide confirmar o guardar esos cambios. No uses --discard-changes para «salir del
      paso»: eso descarta tu trabajo. Confirma en un commit o guarda con git stash.
    

  


  
3.2 · Crear la rama, trabajar y fusionar


  

    El flujo diario tiene cuatro momentos: crear la rama, hacer commits allí, volver a
    main y fusionar. Si main no avanzó mientras trabajabas, el merge es
    fast-forward: Git solo mueve el nombre hacia adelante, sin crear un commit extra.
  


  

    

      

        

        terminal — el ciclo completo
      

      
    


# 1. Crear la rama y moverse a ella
git switch -c feature/saludo

# 2. Trabajar y confirmar en la rama
printf 'def saludar():\n    return "Hola, mundo"\n' > app.py
git add app.py
git commit -m "saludar con el nombre del mundo"

# 3. Volver a main
git switch main

# 4. Fusionar la rama en main
git merge feature/saludo

# 5. Si ya está fusionada, borrar la rama local
git branch -d feature/saludo


  


  

    

      

        

        salida típica del merge
      

      
    


Updating a1b2c3d..d4e5f6a
Fast-forward
 app.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

  


  

    Si quieres que quede un commit de merge explícito —aunque el merge pudiera ser
    fast-forward— usa --no-ff. Sirve para conservar en el historial el momento en que
    se integró la rama.
  


  

    

      

        

        terminal — merge con commit explícito
      

      
    


git switch main
git merge --no-ff feature/saludo -m "integrar la rama de saludo"


  


  

    

      Fast-forward o merge commit
      
        
TipoCuándo ocurreQué ves en el historial

      
      
        
Fast-forwardmain no avanzó desde que creaste la ramaUna línea recta; no hay commit de merge

        
Merge commitmain y la rama avanzaron por separado, o usas --no-ffUn commit con dos padres y un mensaje de integración

      
    

  


  
3.3 · Navegar y ver el mapa


  

    

      

        

        terminal — el mapa de ramas
      

      
    


git branch -a                   # locales y remotas
git log --oneline --graph --decorate --all
git switch -                    # alterna entre las dos últimas ramas


  


  

    

      

        

        cómo se ve un merge en el grafo
      

      
    


*   c68bda2 (HEAD -> main) integrar la rama de saludo
|\
| * fada89b (feature/saludo) saludar con el nombre del mundo
|/
* ceb9f25 crear el archivo inicial de la aplicación

  


  

    La línea vertical de la izquierda es la rama que se separó; la diagonal es el momento en que se
    integró. No necesitas memorizar el dibujo: con git log --graph --all puedes
    reconstruir qué pasó antes de borrar una rama.
  


  
3.4 · Cuando las dos ramas tocan la misma línea


  

    Un merge automático funciona si los cambios están en archivos o líneas distintas. Si las dos
    ramas modificaron la misma línea, Git no adivina: marca el conflicto y te pide decidir. No es un
    error de Git; es una decisión humana.
  


  

    

      

        

        terminal — el merge se detiene
      

      
    


git switch main
git merge feature/precio
# CONFLICT (content): Merge conflict in app.py
# Automatic merge failed; fix conflicts and then commit the result.

git status
# both modified: app.py


  


  

    

      

        

        app.py — las marcas del conflicto
      

      
    


def precio_final(precio):
<<<<<<< HEAD
    return precio * 1.19
=======
    return precio * 1.21
>>>>>>> feature/precio


  


  

    El bloque entre <<<<<<< HEAD y ======= es lo que
    hay en tu rama actual; el bloque entre ======= y
    >>>>>>> es lo que trae la otra rama. Edita el archivo, deja la
    versión correcta, borra las tres marcas, prepara y confirma.
  


  

    

      

        

        terminal — resolver y cerrar el merge
      

      
    


# Después de editar app.py y quitar las marcas:
git add app.py
git commit -m "resolver el conflicto del precio final"

# Si te arrepientes antes de terminar:
git merge --abort


  


  

    Nota — git merge --continue también existe
    

      En un conflicto, Git deja el merge «a medias». git commit lo cierra con el
      mensaje de merge; git merge --continue hace lo mismo y es más explícito.
      git merge --abort vuelve al estado anterior al merge y no conserva la resolución
      a medias.
    

  


  
3.5 · Borrar la rama sin perder la foto


  

    Una rama fusionada se puede borrar con git branch -d: sus commits ya están en
    main, así que no se pierde nada. Si la rama no está fusionada, Git se niega para
    protegerte. -D fuerza el borrado y puede dejar commits inalcanzables; si de verdad
    quieres descartarla, hazlo con intención, no por costumbre.

4.2 · Vocabulario del taller


  

    

      
Working tree

      
Los archivos de tu carpeta tal como están ahora, con o sin cambios guardados.

    

    

      
Staging area

      
La bandeja de cambios elegidos para el próximo commit.

    

    

      
Commit

      
Una foto del proyecto con un hash, un autor, una fecha y un mensaje.

    

    

      
HEAD

      
El commit o la rama donde estás ahora. Es el «tú estás aquí» del historial.

    

    

      
Rama

      
Un nombre que apunta a un commit; permite líneas de trabajo paralelas.

    

    

      
Fast-forward

      
Un merge que solo adelanta la rama, sin crear un commit de fusión.

    

    

      
Conflicto

      
Dos ramas modificaron la misma zona; Git pide una decisión humana.

    

    

      
restore

      
Restaura archivos desde el staging o desde un commit; no cambia de rama.

    

    

      
revert

      
Crea un commit nuevo que deshace otro, sin reescribir el historial compartido.

    

    

      
reflog

      
El registro local de todo lo que movió HEAD; sirve para rescatar commits.

    

  


  

    
    
  








  

    
 Unidad 05 · La red de seguridad

    
Deshacer sin miedo: cada desastre tiene su comando

    

      La pregunta no es «¿cómo borro el último commit?», sino «¿qué quiero conservar?». Esta unidad
      ordena las seis situaciones más comunes del día a día y te da el comando moderno, lo que
      conserva y el riesgo de cada uno.
    

    

      ⏱ 35 minutos
      📄 Lectura y práctica
      🧭 Producto: la tabla de decisiones interiorizada
    

  


  
5.1 · La tabla que resuelve el 90 %


  

    

      Seis situaciones, seis comandos
      
        
SituaciónComandoQué conservaRiesgo

      
      
        

          «Dañé app.py y quiero volver a la última foto»
          git restore app.py
          La versión del staging (normalmente el último commit); descarta lo no confirmado
          Alto: los cambios sin guardar desaparecen
        

        

          «Agregué al staging algo que no era»
          git restore --staged app.py
          Tu cambio en la carpeta; solo lo saca de la bandeja
          Bajo: no borra el trabajo
        

        

          «El commit quedó con un mensaje feo»
          git commit --amend -m "nuevo"
          El contenido; reescribe el último commit
          Medio: no lo uses si ya lo compartiste
        

        

          «Me sobró el último commit (aún no lo he compartido)»
          git reset --soft HEAD~1
          Los cambios, en el staging, intactos
          Medio: reescribe el historial local
        

        

          «Hay que deshacer un commit que ya compartieron»
          git revert <hash>
          El historial completo; crea un commit inverso
          Bajo para el equipo; puede pedir resolver conflictos
        

        

          «Hice algo horrible y no sé qué»
          git reflog
          El registro de dónde estabas; permite volver
          El reflog es local y no es eterno
        

      
    

  


  

    Distinción — local y compartido no se deshacen igual
    

      Un commit que solo existe en tu computadora se puede reescribir con amend o
      reset. Un commit que ya está en la rama compartida no se reescribe: se deshace
      hacia adelante con revert. La regla es simple: si alguien más pudo descargarlo,
      no cambies su historia; agrega un commit nuevo.
    

  


  
5.2 · Situación por situación


  
1. Descartar cambios de un archivo: git restore


  

    git restore app.py copia la versión que está en el staging sobre tu archivo de
    trabajo. Si no habías preparado nada, esa versión es la del último commit. Es la forma moderna
    de git checkout -- app.py.
  


  

    

      

        

        terminal — descartar lo no confirmado
      

      
    


git status -sb
#  M app.py

git restore app.py
git status -sb
# (sin cambios)

# Si quieres recuperar la versión de un commit concreto:
git restore --source=HEAD~1 app.py


  


  

    Advertencia — restore no pregunta
    

      Los cambios que no están en un commit ni en el staging se sobrescriben sin confirmación. Si
      no estás seguro, antes de restaurar copia el archivo a otro nombre o crea un commit temporal.
      Git no puede recuperar lo que nunca guardó.
    

  


  
2. Sacar algo del staging: git restore --staged


  

    Este comando saca el archivo del staging sin tocar su contenido. Si era un archivo existente,
    vuelve a «modificado»; si era nuevo, vuelve a «sin seguimiento». Es el backspace del staging: el
    archivo sigue en tu carpeta, con tu cambio intacto.
  


  

    

      

        

        terminal — despreparar sin borrar
      

      
    


git add app.py
git status -sb
# M  app.py

git restore --staged app.py
git status -sb
#  M app.py


  


  
3. Corregir el último mensaje: git commit --amend


  

    --amend reemplaza el último commit por uno nuevo. Si solo cambias el mensaje,
    usas -m; si además quieres incluir un archivo que olvidaste, lo preparas antes y
    usas --amend --no-edit.
  


  

    

      

        

        terminal — rehacer el último commit
      

      
    


# Solo cambiar el mensaje
git commit --amend -m "validar el correo antes de guardar"

# Agregar un archivo olvidado, sin cambiar el mensaje
git add validaciones.py
git commit --amend --no-edit


  


  

    Advertencia — amend cambia el hash
    

      El commit corregido es un commit distinto, con otro hash. Si ya lo habías subido, tu rama
      local y la remota dejan de coincidir. No uses push --force para tapar eso sin
      coordinar: quien haya descargado el commit viejo tendrá problemas. Si ya es público, deja el
      mensaje feo y sigue; o usa una corrección coordinada.
    

  


  
4. Deshacer el último commit local: git reset --soft


  

    git reset --soft HEAD~1 mueve la rama un commit hacia atrás, pero deja los cambios
    de ese commit en el staging. El commit desaparece del historial y el trabajo sigue ahí, listo
    para volver a confirmarlo con otro mensaje o en otro commit.
  


  

    

      

        

        terminal — sacar la última foto sin perder el contenido
      

      
    


git reset --soft HEAD~1
git status
# Changes to be committed:
#        modified:   app.py

git commit -m "mensaje mejor pensado"


  


  

    Precisión — --soft, --mixed y --hard
    

      --soft deja los cambios en el staging; --mixed (el modo por
      defecto) los deja en la carpeta sin preparar; --hard los borra. Para «me sobró el
      commit pero quiero el trabajo», usa --soft. --hard es para cuando
      de verdad quieres descartar todo.
    

  


  
5. Deshacer un commit compartido: git revert


  

    git revert <hash> no borra el commit: crea uno nuevo que aplica los cambios
    inversos. El historial sigue completo y quien ya descargó el commit original no pierde nada.
    Es la opción correcta cuando el commit ya está en una rama compartida.
  


  

    

      

        

        terminal — revertir hacia adelante
      

      
    


git log --oneline
# d4e5f6a cambiar el precio del teclado
# a1b2c3d crear la pantalla de inicio

git revert d4e5f6a
# Abre el editor con el mensaje "Revert ..."; guarda y cierra.

git log --oneline
# 9f2d1c4 Revert "cambiar el precio del teclado"
# d4e5f6a cambiar el precio del teclado


  


  

    Si el commit es un merge, revert necesita saber cuál de los dos padres invertir:
    git revert -m 1 <hash>. Es un caso menos frecuente; lo importante es no
    borrar el merge a la fuerza.
  


  
6. «Hice algo horrible»: git reflog


  

    El reflog es el historial de todo lo que movió HEAD, incluso cosas que ya no están
    en ninguna rama: commits, cambios de rama, resets. Si hiciste un reset --hard por
    error, ahí puedes encontrar el commit perdido.
  


  

    

      

        

        terminal — encontrar y rescatar
      

      
    


git reflog
# 9f2d1c4 HEAD@{0}: reset: moving to HEAD~1
# a1b2c3d HEAD@{1}: commit: agregar el botón de guardar
# 7e4f2a1 HEAD@{2}: commit: crear la pantalla de inicio

# Opción segura: crear una rama en el commit perdido
git switch -c rescate HEAD@{1}

# Opción directa: mover la rama actual (descarta lo no confirmado)
git reset --hard HEAD@{1}


  


  

    Nota — el reflog es local y caduca
    

      El reflog vive en tu repositorio, no se sube a GitHub y Git lo va limpiando con el tiempo
      (por defecto, 90 días para entradas alcanzables y 30 para las que no). No es una copia de
      seguridad eterna: si el proyecto es importante, además de Git conviene un respaldo real.

01

02

6.1 · git status es el GPS


  

    Antes de cualquier comando, mira dónde estás y qué cambió. git status -sb te da la
    rama y los archivos en dos columnas; git log --oneline --decorate -5 te dice si tus
    últimos commits son los que esperabas. Con esas dos fotos evitas el 80 % de los errores.
  


  

    

      

        

        terminal — la rutina de cada día
      

      
    


git status -sb
git log --oneline --decorate -5

# Trabajar en una rama, no directamente en main
git switch main
git pull --ff-only
git switch -c feature/mi-cambio

# Editar, revisar y confirmar
git diff
git add app.py
git commit -m "describir el cambio en imperativo"

# Integrar y publicar
git switch main
git merge feature/mi-cambio
git push -u origin main


  


  

    Nota — pull --ff-only evita merges sorpresa
    

      git pull --ff-only solo avanza si tu rama puede adelantarse sin crear un merge.
      Si hay divergencia, te avisa y decides: git pull --rebase para reaplicar tus
      commits encima, o un merge explícito. Es más predecible que un pull que a veces
      crea un commit de merge sin que lo pidas.

6.3 · Errores que se arreglan con calma


  
Commit en la rama equivocada


  

    Hiciste un commit en main que debía ir en una rama. No hace falta borrar nada:
    crea la rama en ese commit, vuelve a main y retrocede un paso. El commit queda en
    la rama nueva.
  


  

    

      

        

        terminal — mover el commit a una rama
      

      
    


# El commit está en main, pero debía estar en una rama
git switch -c feature/mi-cambio   # crea la rama apuntando al commit actual
git switch main
git reset --hard HEAD~1            # mueve main un commit atrás

# El commit sigue vivo en feature/mi-cambio


  


  

    Advertencia — reset --hard borra cambios no confirmados
    

      En el paso anterior, --hard descarta lo que tengas sin confirmar en
      main. Si hay trabajo suelto, confírmalo o guárdalo con git stash
      antes. Para mover la rama sin tocar archivos, puedes usar git reset --soft HEAD~1
      y luego limpiar el staging.
    

  


  
Guardar cambios sin confirmar: git stash


  

    Si necesitas cambiar de rama y no quieres confirmar todavía, guarda el trabajo en un cajón
    temporal y recógelo después. No es un commit y no aparece en el historial de la rama.
  


  

    

      

        

        terminal — el cajón temporal
      

      
    


git stash push -m "cambio a medias"
git switch main
# ...haces lo que necesitas...
git switch feature/mi-cambio
git stash pop

git stash list


  


  
Archivos que no deben entrar


  

    

      Qué ignorar y qué nunca confirmar
      
        
ArchivoPor quéQué hacer

      
      
        
__pycache__/, *.pycSe regeneran solosAgregar a .gitignore

        
.venv/, node_modules/Dependencias pesadas y reproduciblesIgnorar; documentar cómo instalarlas

        
.env, claves, tokensSecretos: no deben quedar en el historialIgnorar y usar variables de entorno

        
Capturas, videos, binarios grandesAumentan mucho el tamaño del repositorioGuardar fuera o usar almacenamiento aparte

Parte C — Las seis prácticas


  

    

      

        

        terminal — practicar sin miedo (en el repo del taller)
      

      
    


# 1. restore: dañar app.py y volver al último commit
printf 'esto no era\n' > app.py
git status -sb
git restore app.py
git status -sb

# 2. restore --staged: preparar y despreparar
printf '# nota temporal\n' >> README.md
git add README.md
git status -sb
git restore --staged README.md
git status -sb
git restore README.md

# 3. amend: corregir el último mensaje
git commit --amend -m "ignorar archivos temporales de Python y caché"

# 4. reset --soft: deshacer el último commit conservando el cambio
git reset --soft HEAD~1
git status -sb
git commit -m "ignorar archivos temporales de Python"

# 5. revert: deshacer un commit que ya está en main
printf 'version temporal\n' >> README.md
git add README.md
git commit -m "agregar una nota temporal"
git revert --no-edit HEAD

# 6. reflog: rescatar el commit antes del revert
git reflog -5
git switch -c rescate HEAD@{1}
git log --oneline -3


  


  

    Advertencia — el taller es un laboratorio, no producción
    

      Aquí puedes usar --soft, revert y reflog sin miedo
      porque el repositorio es tuyo y no lo compartiste. En un proyecto real, antes de un
      reset o un amend verifica que el commit no esté en la rama
      compartida. La regla de oro no cambia: si ya lo tienen otros, revert.

7.5 · Síntesis: siete ideas para llevarse


  

    

      
01

      
Git guarda fotos, no solo archivos: un commit es una unidad con mensaje, autor y fecha.

    

    

      
02

      
git add elige qué entra en la foto; git commit la guarda. No son lo mismo.

    

    

      
03

      
Una rama es un nombre que apunta a un commit; cambiar de rama no copia la carpeta.

    

    

      
04

      
switch y restore separan dos acciones que checkout mezclaba; son los comandos claros de hoy.

    

    

      
05

      
Si el commit es local, amend o reset --soft; si ya es público, revert.

    

    

      
06

7.6 · Puente hacia la próxima etapa


  

    Ya tienes el flujo local de Git. El siguiente paso natural es compartirlo: un remoto en GitHub,
    push y pull, ramas remotas y revisión de cambios con Pull Requests.
    Ese tema se trabaja por separado; aquí lo importante es que el historial local sea claro antes
    de subirlo.
  


  

    Antes de cerrar
    

      Deja el repositorio del taller con git status limpio, al menos tres commits, una
      rama fusionada y un revert visible. Si algo salió mal, no borres la carpeta:
      usa git reflog y vuelve a intentarlo. Ese es exactamente el hábito que esta clase
      quiere dejarte.
    

  


  

    
Fin de la Clase 16

    

      Git no es un conjunto de comandos para memorizar: es un historial que puedes leer, ramificar y
      deshacer. Con init -b main, add, commit,
      switch, merge, restore, revert y
      reflog tienes lo necesario para trabajar todos los días sin miedo a romper algo
      que no puedas recuperar.
