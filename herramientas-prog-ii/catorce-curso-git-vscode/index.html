🖥️ El mismo Git, con botones

En la clase 12 aprendiste a hablarle a Git en la terminal. Buenas noticias: VS Code ya hablaba ese idioma por ti. Su integración con Git es tan completa que puedes hacer el 90% del trabajo diario — commits, ramas, conflictos, sincronización — sin escribir un solo comando. Pero ojo: la meta de hoy no es "olvidar la terminal", sino algo más valioso: saber qué comando ejecuta cada botón que presionas. Porque quien entiende el botón, nunca le tiene miedo al clic.

La idea que sostiene toda la clase

La documentación oficial de VS Code lo dice sin rodeos: "el editor y Git en la línea de comandos usan el mismo repositorio; puedes trabajar en cualquiera de las dos interfaces sin importar ni sincronizar nada entre ellas". Es decir: no hay "un Git de botones" y "un Git de terminal". Hay un álbum (la carpeta .git/) y dos formas de conversar con él. Cuando haces clic en Stage Changes, VS Code ejecuta git add detrás de la cortina. Y cuando escribes git commit en la terminal, el panel de VS Code se actualiza al instante. Mismo álbum, dos idiomas — y hoy aprendes el segundo con el primero de traductor.

🦹 Los villanos de hoy (todos tienen forma de botón)

El clic 🗑️ sin leer la confirmación — el botón Discard descarta tu trabajo para siempre (es un git restore sin deshacer). El "Commit & Sync" elegido por accidente — cuando solo querías commit, y terminas publicando en la nube sin haberlo decidido. El "hago clic hasta que algo pase" — el método del pánico: funciona hasta que no funciona. Y el más sutil: la confianza ciega en "Accept Both Changes" — que verás en el módulo de conflictos. La vacuna contra los cuatro es la misma, y es la regla de oro de la clase:

🌳 Regla de oro: nunca presiones un botón de Git cuyo comando equivalente no puedas decir en voz alta.

🌿 El panel Source Control: el centro de mando

⏱️ 35 minutos · "El mismo git status de siempre, pero pintado bonito"

🧠 La idea central

El panel Source Control (SCM) es, literalmente, tu git status convertido en una aplicación: te dice qué cambió (lista de archivos), qué está preparado (Staged Changes) y qué historias nuevas hay (incoming/outgoing si hay remoto). La diferencia es que en vez de texto plano, cada archivo trae botones de acción al pasar el cursor — y cada botón es un comando de la clase 12 con otro traje. Ábrelo con Ctrl+Shift+G y vamos pieza por pieza.

🔧 Anatomía del panel, pieza por pieza

lo que ves al abrir el panel (con un cambio de ejemplo)

│  SOURCE CONTROL                                    ⋯     │
│ ┌────────────────────────────────────────────────────┐ │
│ │  "Mensaje del commit…" ← LA CAJA: lo que irá en el -m    │ │
│ └────────────────────────────────────────────────────┘ │
│  [ ✓ Commit  ▾ ]   ← EL BOTÓN: toma la foto (▾ = variantes)│
│                                                          │
│  ▾ CHANGES                    ← sin preparar (= git diff) │

🖱️ El clic que toma la foto (y sus variantes)

Escribes el mensaje en la caja y presionas el botón ✓ Commit (o Ctrl+Enter desde la caja). Eso es un git commit -m "…" exacto. Pero el botón trae un pequeño ▾ con variantes que hay que conocer antes de presionarlas sin querer:

Opción del botón ✓Qué hace por debajoCuándo usarla
Commitgit commit -m "…"La de siempre: la foto queda en tu compu
Commit & Pushcommit + git pushTerminaste y quieres publicar de una vez
Commit & Synccommit + git pull + git pushTrabajo en equipo: bajarte lo nuevo y subir tu foto en un solo clic

🦹 Villano: el ▾ que nadie abre

VS Code recuerda la última variante que usaste: si ayer terminaste en "Commit & Push", hoy el botón principal puede decir eso mismo, y un Ctrl+Enter distraído publica en la nube lo que creías solo local. No es peligroso (publicar nunca lo es, con el .gitignore bien puesto), pero es exactamente el tipo de clic que rompe la regla de oro. Costumbre sana: lee la etiqueta del botón antes de presionarlo — si dice algo que no quieres hoy, ábrelo con el ▾ y elige "Commit" a secas.

💡 Dos detalles que ahorran sustos

  • El asterisco junto a la rama (main*) en la barra de estado significa "tienes cambios sin commitear". Es el recordatorio permanente de que hay una foto pendiente.
  • ¿Varios archivos con cambios y quieres prepararlos todos de un golpe? El título CHANGES también reacciona al cursor: su botón + prepara todo — es el git add . de siempre, con un solo clic más grande.

🔄 Actividad en pareja — 5 minutos

  1. Cada uno cambia algo pequeño en su biblioteca/ (añade un comentario, toca un título) y abre el panel SCM con Ctrl+Shift+G. ¿Qué letra apareció? ¿De qué color? Explíquense la letra en voz alta: ¿U o M? ¿Por qué?
  2. Creen un archivo nuevo notas.txt con una línea cualquiera. ¿Dónde aparece? Ahora compárenlo con el archivo modificado: ¿cuál es U y cuál es M?
  3. Sin commitear nada todavía: presionen + sobre cada archivo y miren cómo la lista se reorganiza en STAGED CHANGES. ¿Qué comando acaban de ejecutar? (Díganlo en voz alta — regla de oro).

👀 Diffs, staging fino y el botón que hay que respetar

⏱️ 35 minutos · "El +, el −, el 🗑️… y el staging por líneas"

🧠 La idea central

Al hacer clic en un archivo del panel SCM, VS Code no lo abre normal: abre el editor de diffs — el antes y el después, lado a lado, con las líneas nuevas en verde y las borradas en rojo. Es el git diff de la clase 12, pero con cursor: puedes navegarlo, editarlo y, sobre todo, preparar cambios con precisión quirúrgica. Hoy verás que se puede preparar para la foto media función cuando en la terminal eso requiere un comando (git add -p) que casi nadie domina. Los botones lo vuelven humano.

👀 Leer un diff sin comandos

clic en el archivo M → el editor de diffs 
│ dominio/servicios.py (lado IZQUIERDO = la última foto)      │
│                                                          │
│  TARIFA_POR_DIA = 500                          ← rojo: salió │
│  TARIFA_POR_DIA = 800                          ← verde: entró │
│                                                          │
│ ┌──────────────────────┐ ┌──────────────────────┐     │
│ │ (botón ↻: lado a lado)│ │ (botón ▤: inline)    │     │
│ └──────────────────────┘ └──────────────────────┘     │
# · Izquierda: cómo estaba en la última foto (read only)
# · Derecha:   cómo está ahora — y se puede seguir editando
# · Arriba a la derecha: alterna "lado a lado" ↔ "en línea"

🖱️ Los tres botones del cursor (y su comando secreto)

Al pasar el cursor sobre un archivo en el panel…BotónComando que ejecuta
En CHANGES+ (Open / Stage Changes)git add archivo
En CHANGES↩ / 🗑️ (Discard Changes)git restore archivo ⚠️ sin deshacer
En STAGED CHANGES− (Unstage Changes)git restore --staged archivo
En cualquier lista+ sobre el título CHANGESgit add . (prepara todo)

🦹 El villano vive aquí: el botón 🗑️ (Discard Changes)

Es el único botón de la clase que borra trabajo de verdad: descarta los cambios del archivo y lo devuelve a como estaba en la última foto — un git restore que no tiene deshacer. Por eso VS Code te pregunta con una ventana de confirmación que menciona el archivo exacto. Lee el nombre del archivo en esa ventana: es tu última oportunidad. Y una costumbre que evita el 90% de las tragedias: commit temprano, commit seguido — con la foto tomada, el 🗑️ vuelve a ser inofensivo (solo descartaría cambios nuevos).

✂️ El superpoder: staging por líneas

Modificaste dos cosas distintas en el mismo archivo — el título y la tarifa — y quieres que cada una viva en su propio commit. En la terminal eso es git add -p (pantalla críptica, miedo escénico). En VS Code es un clic junto a la línea:

stage solo lo que quieres que entre en la foto 
# 1. Abre el diff del archivo (clic sobre él en el panel SCM).
# 2. Pasa el cursor por el canal IZQUIERDO de cada cambio (gutter):
#    aparece un signo + que abarca exactamente esas líneas.

# 3. Clic en el +  →  SOLO ese pedazo pasa a STAGED CHANGES.
#    El resto de los cambios del archivo siguen en CHANGES.

# 4. Caja de mensaje → ✓ Commit  →  foto 1: solo el título.
# 5. Ahora prepara lo que falta (el + de las otras líneas o el +
#    del archivo entero) → foto 2: la tarifa.

# Resultado: dos commits que cuentan dos historias distintas,
# del mismo archivo, sin un solo comando. 🎯

💡 Detalles que hacen la vida más fácil

  • El diff de un archivo en STAGED muestra lo que entrará en la próxima foto — es el git diff --staged de siempre.
  • Si el diff se te hace pequeño, el botón de vista inline (arriba a la derecha del diff) pone el antes y el después en una sola columna, más fácil de leer en portátiles chicos.
  • El panel SCM también tiene un buscador: si tu proyecto tiene muchos cambios, filtra por nombre de archivo en vez de navegar a mano.

🔄 Actividad en pareja — 8 minutos

  1. Cada uno modifica dos cosas distintas de un mismo archivo (por ejemplo: un comentario arriba y una línea en medio).
  2. Logren juntos el staging fino: un commit solo con el comentario y otro solo con la línea. Verifiquen en el historial (módulo 5 o git log --oneline) que las dos fotos existen y son distintas.
  3. El juego de la valentía (controlada): uno provoca un cambio tonto, el otro presiona 🗑️ leyendo la confirmación en voz alta antes de aceptar. ¿Qué comando se ejecutó? ¿Qué se perdió? ¿Qué NO se perdió? (Pista: lo que ya estaba en el álbum, sigue en el álbum).
  4. Rematen el traductor de arriba: cada uno responde 3 situaciones seguidas sin fallar. Copiloto con derecho a risa.

📊 La barra de estado: el velocímetro del repositorio

⏱️ 35 minutos · "Ramas, ↓↑ y sincronizar — todo en una franja de un centímetro"

🧠 La idea central

La franja inferior de VS Code es el lugar más denso del editor: en unos centímetros conviven la rama actual (clic → todas tus ramas), el estado de sincronización (↓n ↑n → cuánto debes bajar y subir) y el botón que en la clase 13 escribiste con manos temblorosas: publicar al remoto. Y cuando algo no tiene botón directo — como el merge — está la llave maestra: la paleta de comandos (Ctrl+Shift+P), que conoce TODO lo que Git sabe hacer, con nombres en español. Hoy la barra de estado deja de ser decoración: es tu tablero de vuelo.

🔧 Anatomía de la franja

abajo a la izquierda, de izq. a derecha 
┌────────────────────────────────────────────────────────────┐
│  🌿 main*        ↓0 ↑2       ↻  Synchronize Changes  ⚠ 0  │
└────────────────────────────────────────────────────────────┘
     │            │            │                │
     │            │            │                └ problemas del proyecto
     │            │            └ el botón que hace pull+push
     │            └ ahead/behind: 2 para subir, 0 para bajar
     └ rama actual · el * = "tienes cambios sin commitear"
Lo que vesTraducción de la clase 12/13El clic que lo resuelve
main* (asterisco)"Hay cambios sin commitear" (git status)Al panel SCM, caja + ✓ Commit
↑2 (flecha arriba)"Ahead: 2 commits tuyos sin subir"↻ Synchronize Changes (= pull + push)
↓1 (flecha abajo)"Behind: 1 commit en la nube que te falta" (lo subió otra persona)El mismo ↻ — o git pull en terminal

🌿 Ramas con clics (crear, cambiar, fusionar)

el ciclo completo de una rama, sin terminal 
# 1. CREAR: clic en el nombre de la rama (main) en la barra de estado
#    → aparece la lista de ramas + arriba "+ Create new branch…"
#    → escribe:  feature/reportes
#    → Enter. Ya estás EN la rama nueva (un solo paso: = git switch -c)

# 2. CAMBIAR: clic en la rama otra vez → elige de la lista.
#    (cambiar de rama con archivos sucios: VS Code te avisa si
#    algo se rompería, y ofrece "stash" — lo dejamos de bonus)

# 3. FUSIONAR: no hay botón visible… pero está la llave maestra:
#    Ctrl+Shift+P → escribe "merge" → "Git: Merge Branch…"
#    → elige feature/reportes → el mismo merge de la clase 12.

# 4. BORRAR la rama ya fusionada: en la lista de ramas,
#    pasa el cursor sobre la rama → 🗑️ (git branch -d).

🦹 Villano: "no encuentro el botón" no significa "no existe"

La interfaz cubre el 90% del día a día, pero la paleta de comandos cubre el 100%: presiona Ctrl+Shift+P y escribe git — aparecerán todos: Git: Commit, Git: Push, Git: Pull, Git: Merge Branch…, Git: Undo Last Commit, Git: Show Git Output… Cada uno con su nombre en español y funcionando sin instalar nada. La costumbre pro no es memorizar menús: es saber el verbo ("merge", "push", "undo") y dejar que la paleta complete la frase. La terminal sigue ahí para el resto — y sigue siendo tu red de seguridad.

💡 Sync vs. el orden manual

El ↻ hace pull y luego push — exactamente el orden que aprendimos en la clase 13 ("bajar antes de subir"). Si el pull trae un conflicto, el sync se detiene con el icono de advertencia y el archivo marcado con !: es la señal de pasar al módulo 5. Y si solo quieres una de las dos mitades: el ▾ junto al ↻ (o el menú ⋯ del panel) tiene Push y Pull por separado. Sincronizar es un atajo sano — pero saber qué contiene el atajo es la diferencia entre usarlo y depender de él.

  3. Fusionen con Ctrl+Shift+P → "Git: Merge Branch…" y borren la rama con el 🗑️ de la lista. ¿Qué dijo la barra de estado en cada paso?

⚔️ Conflictos: las marcas se vuelven botones

⏱️ 35 minutos · "Accept Current, Accept Incoming… ¿y yo qué acepto?"

🧠 La idea central

En la clase 12, un conflicto te dejaba marcas crípticas en el archivo (<<<<<<<, =======, >>>>>>>) y la resolución era manual: elegir la línea, borrar las marcas, commitear. En VS Code el proceso es el mismo — pero las marcas vienen con botones arriba: Accept Current Change, Accept Incoming Change, Accept Both Changes, Compare Changes. Un clic, y las líneas quedan como elegiste, sin marcas que borrar. La parte difícil no desaparece: sigue siendo tuya la decisión de qué versión queda. Los botones solo ejecutan tu decisión más rápido.

⚔️ El conflicto, como lo ves ahora

así abre VS Code un archivo en conflicto 
# Tras un merge con conflicto, el editor muestra sobre la zona:
| Accept Current Change | Accept Incoming Change | Accept Both Changes | Compare Changes |

TARIFA_POR_DIA = 800          # ← CURRENT (HEAD): tu versión de main
TARIFA_POR_DIA = 500          # ← INCOMING: la versión de la otra rama

# · Accept Current:    se queda la tuya (main)
# · Accept Incoming:    se queda la de la otra rama
# · Accept Both:        se quedan las dos líneas ⚠️ (¡leer la caja villano!)
# · Compare Changes:    abre el diff de 3 versiones para decidir con calma

# Después de aceptar: el archivo queda SIN marcas, la letra !
# cambia a M… y el resto del ritual es el de siempre:
#   + (stage) → mensaje → ✓ Commit  →  conflicto resuelto. 🎉
BotónQué elige por tiCuándo es EL botón correcto
Accept CurrentLa versión de la rama donde estás (HEAD)Sabes que tu versión es la buena (o la última decisión)
Accept IncomingLa versión de la rama que llegaLa otra persona ya resolvió lo que tú no sabías
Accept BothDeja las dos líneas, una tras otra⚠️ Casi nunca: solo cuando las dos líneas son complementarias (y no dos versiones de lo mismo)
Compare ChangesAbre la vista de 3 versionesNo estás segur@: mira antes de decidir

🦹 Villano: "Accept Both Changes" con fe ciega

"Both" suena a diplomacia, pero en un conflicto de dos versiones de la misma línea produce código roto: TARIFA = 800 y TARIFA = 500 una debajo de la otra, las dos activas — un bug silencioso que la última línea gana. Acepta Both solo cuando las dos líneas son cosas distintas (por ejemplo, dos imports que ambos agregaron). Ante la duda, la secuencia profesional es: Compare Changes → leer las tres versiones → decidir → luego el botón. Y siempre, SIEMPRE: después de aceptar, lee el resultado en el editor antes del commit — los botones hacen lo que dicen, no lo que soñaste.

💡 El resto del ritual no cambió en nada

  • El archivo en conflicto aparece con ! y en una sección propia MERGE CHANGES del panel.
  • Tras aceptar, lo preparas con + — y cuando todos los ! desaparecen, el ✓ Commit cierra el merge (VS Code ya escribe el mensaje por ti).
  • ¿Te arrepientes a mitad de camino? La paleta: Ctrl+Shift+P → "Git: Abort Merge". Vuelve todo como antes de empezar — es el merge --abort de la clase 12.

🔄 Actividad en pareja — 10 minutos

Provocar y resolver, con botones de principio a fin:

  1. En main, cambia la primera línea de tu README.md (título) y haz commit con el panel.
  2. Crea la rama fix/conflicto-ui desde la barra de estado y, en ella, cambia la misma línea a otra cosa. Commit.
  3. Vuelve a main y fusiona con la paleta ("Git: Merge Branch…"). El panel debería mostrar el !.
  4. Abre el archivo: usen Compare Changes primero para decidir con calma, acepten una versión y completen el commit del merge. Repitan una vez más con Accept Incoming para sentir la diferencia.

🕰️ El historial, hecho visible (y Git Output: el puente)

⏱️ 35 minutos · "Graph, Timeline… y ver los comandos que esconden tus clics"

🧠 La idea central

El álbum de la clase 12 se leía con git log. VS Code lo pinta entero en dos vistas: el Source Control Graph (la gráfica de commits y ramas de TODO el repositorio — la línea del tiempo con sus universos paralelos) y el Timeline (la historia de UN archivo, abajo del Explorer). Y para cerrar la clase con broche, existe una vista secreta que conecta los dos mundos del curso: Git Output, el registro donde VS Code anota el comando exacto que ejecutó cada clic tuyo. Spoiler: es la clase 12 entera, en streaming.

🚀 Publicar a GitHub desde el editor (bonus de la clase 13)

Si tu proyecto aún no tiene remoto, el panel SCM muestra un botón "Publish to GitHub": un clic, eliges público o privado, y VS Code crea el repo en tu cuenta y hace el push inicial — el ciclo completo de la clase 13 sin abrir el navegador. Para crear y revisar Pull Requests desde el editor existe la extensión GitHub Pull Requests and Issues: la dejamos como exploración en casa — en el colegio trabajamos con lo integrado, que ya lo es casi todo.

🦹 Villano: la fe en la vista bonita

El Graph y el Timeline son vistas de solo lectura: mirar no cambia nada — perfecto. Pero ojo con la trampa inversa: ver el historial bonito no es entenderlo. Un repo puede tener una gráfica preciosa y mensajes tipo "cambios" por todas partes: la vista no perdona lo que el historial dice. El diagnóstico de calidad sigue siendo el de siempre: lee los mensajes de la gráfica como si fuera la autobiografía del proyecto — porque lo es.

💡 ¿Y el "blame"? (exploración en casa)

El comando git blame — saber quién escribió cada línea y en qué commit — no viene integrado en VS Code de fábrica: lo trae la extensión GitLens, la más famosa del ecosistema Git. Si te pica la curiosidad, instálala en tu compu (Extensions → buscar "GitLens"): añade el autor con colorcitos al lado de cada línea. Pero nota la ironía: para ESTA clase no la necesitas — ya sabes hacer el 90% del trabajo diario sin instalar absolutamente nada.

🦹 Reflexión final

Empezaste el módulo de Git escribiendo comandos letra por letra; terminaste haciendo lo mismo con botones que entiendes por dentro. Esa es exactamente la diferencia entre "usar una interfaz" y saber Git: los botones son rápidos, pero el mapa mental es tuyo. La terminal queda para siempre como tu red de seguridad — para el día que un botón no exista, para el script que automatiza, para el SSH de una empresa — y el editor queda como tu rutina diaria. Dos idiomas, un álbum. 🎛️
