Unidad 00 · Apertura

Borrar no tiene deshacer

Crear y editar se pueden corregir. Borrar, no: una vez ejecutado el DELETE, el registro no está. Por eso esta operación necesita tres cosas que las anteriores no tenían: una confirmación, un identificador inequívoco y un control de integridad.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: el mapa de un borrado seguro

0.1 · El producto que desapareció sin querer

En TechStore, el botón Eliminar estaba al lado de Editar. Un vendedor quiso corregir un precio, pulsó el botón equivocado y confirmó sin leer. El producto desapareció de la tabla y de la base. No había copia, no había historial y el cliente que lo estaba mirando ya no pudo comprarlo.

La aplicación no falló: hizo exactamente lo que le pidieron. El problema es que una operación destructiva no puede tener la misma fricción que una lectura. Necesita una pausa, una pregunta clara y un servidor que se niegue a borrar cuando hacerlo rompería algo más.

Distinción — borrar no es «editar a vacío»

Un UPDATE deja una fila con otros valores. Un DELETE elimina la fila. La diferencia importa porque las relaciones con otras tablas —pedidos, autores, auditorías— apuntan a esa fila. Si desaparece, esas referencias quedan huérfanas o el motor rechaza la operación. El borrado no es una edición: es una operación con reglas propias.

Unidad 01 · La pausa

Confirmar antes de borrar: la petición que no sale

La confirmación no es un adorno: es la única barrera entre un clic accidental y una pérdida irreversible. Esta unidad explica cómo HTMX la implementa, qué pasa cuando el usuario cancela y por qué cancelar debe significar cero peticiones al servidor.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: botón de borrado con confirmación

1.1 · El botón del repositorio

En la tabla de productos, cada fila tiene un botón Eliminar. HTMX intercepta el clic, muestra una confirmación del navegador y, solo si el usuario acepta, envía un DELETE a /productos/{id}. La respuesta reemplaza únicamente el tbody de esa fila.

fila_producto.html — el botón Eliminar 
<button class="eliminar"
        hx-delete="/productos/{{ producto.id }}"
        hx-confirm="¿Eliminar el producto «{{ producto.nombre }}»? Esta acción no se puede deshacer."
        hx-target="#producto-{{ producto.id }}"
        hx-swap="outerHTML">
  Eliminar
</button>
hx-delete
La ruta que se llamará con el método HTTP DELETE. No es un POST disfrazado: el método importa y el servidor lo declara con @router.delete.
hx-confirm
El texto que HTMX muestra en un cuadro de confirmación del navegador antes de enviar. Si el usuario cancela, no se envía nada.
hx-target
El tbody de esa fila. La respuesta del servidor se inserta ahí, no en toda la tabla.
hx-swap
outerHTML reemplaza el tbody completo. La fila desaparece o se convierte en el aviso de error.
El nombre en el mensaje
Incluye producto.nombre para que el usuario sepa exactamente qué está a punto de borrar. «¿Eliminar este producto?» no es suficiente.

1.2 · Cancelar significa cero peticiones

La confirmación ocurre en el navegador, antes de que HTMX construya la petición. Si el usuario pulsa «Cancelar», el servidor no recibe nada: no hay DELETE, no hay fila borrada y no hay nada que deshacer. Esa es la diferencia entre una confirmación real y un aviso que se muestra después de borrar.

Qué ocurre en cada decisión

El usuario aceptaEnvía DELETE /productos/5Ejecuta la rutaDELETE 1
El producto ya no existeEnvía la peticiónResponde 404DELETE 0
Otra tabla depende del productoEnvía la peticiónResponde 409La base rechaza el borrado
Advertencia — hx-confirm no reemplaza la validación del servidor

La confirmación vive en el navegador y se puede desactivar con DevTools o con curl. El servidor no puede confiar en que el usuario confirmó: debe verificar el id, aplicar las reglas de integridad y responder correctamente. La confirmación es una ayuda para el usuario, no un control de seguridad.

Nota — confirmación nativa o modal propio

hx-confirm usa el cuadro del navegador: es rápido, accesible y no requiere JavaScript propio. Un modal propio permite más contexto —mostrar la ficha del producto, pedir el nombre para confirmar— pero hay que cuidar el foco, Esc, el fondo y la navegación por teclado. Para esta clase, la confirmación nativa es suficiente y más segura que un modal mal hecho.

1.5 · Doble clic, doble borrado

Si el usuario pulsa dos veces rápido, HTMX puede enviar dos peticiones. La primera borra; la segunda llega cuando la fila ya no existe y responde 404. El resultado no es catastrófico, pero la interfaz muestra un error después de un éxito. Deshabilitar el botón mientras se envía evita esa carrera.

HTMX — deshabilitar el botón durante la petición 
<button class="eliminar"
        hx-delete="/productos/5"
        hx-confirm="¿Eliminar el producto?"
        hx-disabled-elt="this"
        hx-target="#producto-5"
        hx-swap="outerHTML">
  Eliminar
</button>
Precisión — hx-disabled-elt no cancela la petición

Deshabilitar el botón impide un segundo clic, pero no cancela la primera petición. Si el usuario quiere cancelar una operación ya enviada, necesita otra herramienta —un hx-preserve, un AbortController o un flujo de borrado lógico—. Para esta clase, lo importante es que el doble clic no produzca dos borrados.

Unidad 02 · La sentencia

El DELETE seguro: una fila, un id, un resultado

Un borrado seguro no adivina: recibe la clave primaria, ejecuta un DELETE parametrizado y comprueba cuántas filas eliminó. Esta unidad escribe la consulta, la ruta y el fragmento que reemplaza la fila, y explica por qué «DELETE 0» nunca puede mostrarse como éxito.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: DELETE parametrizado y fragmento de éxito

2.1 · La función del repositorio

La función recibe la conexión y el id. El WHERE usa un parámetro posicional; no se concatena nada. conn.execute devuelve una cadena que dice cuántas filas se eliminaron: "DELETE 1" o "DELETE 0".

repositorio.py — eliminar_producto() 
async def eliminar_producto(conn, producto_id: int) -> bool:
    """Elimina un producto por su clave primaria.

    Devuelve True si borró una fila, False si el id no existía.
    """
    resultado = await conn.execute(
        """
        DELETE FROM productos
         WHERE id = $1
        """,
        producto_id,
    )
    return resultado == "DELETE 1"
WHERE id = $1
La única condición. El id es la clave primaria; no se borra por nombre porque puede haber dos productos con el mismo nombre.
execute
Ejecuta una sentencia que no devuelve filas. En un DELETE, el texto de retorno empieza por "DELETE" y termina con el número de filas afectadas.
"DELETE 1"
Se eliminó exactamente una fila. Es el único caso de éxito.
"DELETE 0"
No se eliminó nada: el id no existía o ya había sido borrado. No es un éxito.
bool
La función traduce la cadena a un valor que la ruta puede usar sin conocer los detalles de asyncpg.
Advertencia — DELETE 0 no es un error de SQL

PostgreSQL no lanza una excepción cuando el WHERE no encuentra filas. La sentencia termina bien con "DELETE 0". Si la ruta no comprueba ese valor, va a responder 200 y a mostrar «Producto eliminado» aunque no se haya borrado nada. Ese es el falso éxito que esta clase quiere evitar.

2.2 · La ruta que responde con un fragmento

vistas.py — DELETE /productos/{id} 
@router.delete("/productos/{producto_id}")
async def eliminar_producto_vista(
    request: Request,
    conn: ConnectionDep,
    producto_id: int,
):
    eliminado = await eliminar_producto(conn, producto_id)
    if not eliminado:
        return producto_no_encontrado(request, producto_id)

    return templates.TemplateResponse(
        request=request,
        name="componentes/fila_eliminada.html",
        context={"producto_id": producto_id},
    )
Precisión — DELETE es idempotente, pero el resultado no es el mismo

Repetir un DELETE no borra dos filas: la segunda vez ya no hay nada que borrar. Por eso se dice que el método es idempotente en su efecto. El código de la segunda respuesta puede ser 404 (esta clase) o 204 (un cliente que considera que el recurso ya está ausente). Lo importante es que la interfaz no muestre «eliminado» la segunda vez si no se eliminó nada.

2.4 · La variante con RETURNING

Si además del éxito quieres mostrar el nombre del producto borrado o guardarlo en una auditoría, puedes usar DELETE ... RETURNING. La consulta devuelve la fila que acaba de desaparecer.

repositorio.py — borrar y devolver la fila 
async def eliminar_producto(conn, producto_id: int) -> dict | None:
    fila = await conn.fetchrow(
        """
        DELETE FROM productos
         WHERE id = $1
        RETURNING id, nombre, precio, cantidad, descripcion
        """,
        producto_id,
    )
    return dict(fila) if fila is not None else None
Nota — dos formas, el mismo resultado

execute + comparar "DELETE 1" es suficiente cuando solo necesitas saber si borraste. fetchrow + RETURNING es mejor cuando necesitas los datos del registro eliminado, por ejemplo para escribir una auditoría o para mostrar «Se eliminó Teclado mecánico». No uses las dos a la vez: elige la que cuente la historia que necesitas.

2.5 · Nunca por nombre

la diferencia entre borrar uno y borrar varios 
-- MAL: si hay dos productos con ese nombre, borra los dos
DELETE FROM productos WHERE nombre = 'Teclado mecánico';

-- BIEN: la clave primaria identifica una sola fila
DELETE FROM productos WHERE id = $1;
Distinción — el nombre no es una clave

En TechStore puede haber dos productos llamados «Teclado mecánico» de distinto proveedor. El nombre es un dato descriptivo; el id es la identidad. Borrar por nombre es una operación de varios registros disfrazada de una: afecta a filas que el usuario no eligió.

Unidad 03 · La integridad

Cuando el producto todavía importa: referencias y borrado lógico

No todos los registros se pueden borrar: un producto con pedidos, un autor con libros o una cuenta con movimientos. Esta unidad explica cómo PostgreSQL rechaza esos borrados, cómo se responde con 409 y cuándo conviene archivar en vez de eliminar.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: 409 por integridad y borrado lógico

3.1 · La clave foránea que protege el historial

En una tienda real, un producto puede aparecer en pedidos. Si borras el producto, los pedidos quedan apuntando a una fila que ya no existe. PostgreSQL lo impide con una clave foránea: la tabla pedidos declara que su producto_id debe existir en productos.

SQL — un pedido que referencia un producto 
CREATE TABLE pedidos (
    id          BIGSERIAL PRIMARY KEY,
    producto_id INTEGER NOT NULL
        REFERENCES productos(id) ON DELETE RESTRICT,
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0)
);

Al intentar borrar un producto que tiene pedidos, PostgreSQL rechaza la operación. Con ON DELETE RESTRICT lanza RestrictViolationError (SQLSTATE 23001); con el valor por defecto NO ACTION lanza ForeignKeyViolationError (SQLSTATE 23503). La aplicación debe capturar los dos y explicar por qué no se puede borrar.

Qué hace cada acción al borrar el producto padre
AcciónQué pasa con los pedidosCuándo usarla
ON DELETE RESTRICTEl borrado falla si hay pedidosCuando el historial es valioso y no debe perderse
ON DELETE CASCADESe borran también los pedidosCuando los hijos no tienen sentido sin el padre
ON DELETE SET NULLEl pedido queda sin productoCuando el pedido debe sobrevivir, pero sin referencia
Sin clave foráneaQuedan referencias huérfanasNunca en un modelo relacional serio
Advertencia — CASCADE no es una solución mágica

ON DELETE CASCADE hace que el borrado funcione, pero puede borrar mucho más de lo que el usuario cree. Si un producto tiene cien pedidos, borrar el producto borra los cien pedidos. La pregunta no es «¿cómo hago que el borrado no falle?», sino «¿qué historial quiero conservar?».

3.2 · Convertir la violación en un 409

vistas.py — capturar la referencia 
import asyncpg

3.3 · Borrado lógico: archivar en vez de borrar

Si el negocio necesita conservar el historial, el borrado físico no es la herramienta. Se agrega una columna deleted_at: el registro sigue en la tabla, pero las consultas lo ignoran. «Borrar» se convierte en un UPDATE.

SQL — borrado lógico 
ALTER TABLE productos
    ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMPTZ;

-- «Borrar» es archivar:
UPDATE productos
   SET deleted_at = now()
 WHERE id = $1 AND deleted_at IS NULL;

-- Las consultas del catálogo filtran los archivados:
SELECT id, nombre, precio, cantidad, descripcion
  FROM productos
 WHERE deleted_at IS NULL
 ORDER BY nombre;
Borrado físico frente a borrado lógico
Físico (DELETE)Lógico (deleted_at)
El dato desapareceSíNo: queda archivado
Se puede recuperarNo, salvo un respaldoSí, con otro UPDATE
El id se puede reutilizarNoNo, mientras la fila exista
ConsultasNo necesitan filtroTodas deben filtrar deleted_at IS NULL
UnicidadEl nombre queda libreEl nombre sigue ocupado salvo un índice parcial
Uso típicoDatos de prueba, registros sin historialProductos, usuarios, cuentas con auditoría
Precisión — el borrado lógico no es gratis

Cada consulta del catálogo tiene que recordar el filtro deleted_at IS NULL. Si una vista lo olvida, el producto archivado reaparece. Además, un índice UNIQUE sobre el nombre impide crear un producto nuevo con el mismo nombre mientras el archivado siga en la tabla. Se resuelve con un índice parcial: CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL. Es potente, pero exige disciplina.

3.4 · Auditoría del borrado

Si el borrado es físico y el negocio necesita saber qué se borró, guarda una fila en una tabla de archivo antes de eliminar. Hazlo en la misma transacción: o se guarda el archivo y se borra, o no ocurre ninguna de las dos cosas.

repositorio.py — archivar y borrar en una transacción 
async with conn.transaction():
    fila = await conn.fetchrow(
        "DELETE FROM productos WHERE id = $1 RETURNING *",
        producto_id,
    )
    if fila is not None:
        await conn.execute(
            """
            INSERT INTO productos_eliminados
                (producto_id, nombre, precio, cantidad)
            VALUES ($1, $2, $3, $4)
            """,
            fila["id"],
            fila["nombre"],
            fila["precio"],
            fila["cantidad"],
        )
Nota — borrar también es un permiso

En una aplicación real, no cualquier usuario puede eliminar. El borrado se protege con autenticación y roles: un vendedor quizá pueda archivar, pero solo un administrador puede borrar definitivamente. La clase no implementa login, pero el diseño debe dejar claro dónde iría esa comprobación.

4.2 · Vocabulario del taller

Operación destructiva
Una acción que elimina datos y no se puede deshacer con un UPDATE.
hx-confirm
La confirmación nativa de HTMX. Si el usuario cancela, la petición no sale.
DELETE 1
Se borró exactamente una fila.
DELETE 0
Ninguna fila coincidió; el producto no existe o ya fue borrado.
Clave foránea
Una columna que referencia la clave primaria de otra tabla y protege la integridad.
ON DELETE RESTRICT
Impide borrar el padre mientras existan hijos que lo referencian.
ON DELETE CASCADE
Borra los hijos cuando se borra el padre. Es potente y peligroso.
deleted_at
La columna del borrado lógico: si tiene fecha, la fila está archivada.
Auditoría
El registro de qué se borró y cuándo, guardado antes o después del borrado.
Falso éxito
Responder 200 y «eliminado» cuando la base no borró nada.

5.1 · El enunciado

Actividad

El botón que pregunta antes de borrar

La tabla de productos ya permite listar y editar. Agrega el borrado: cada fila debe tener un botón Eliminar, la confirmación debe mostrar el nombre del producto y el servidor debe ejecutar un DELETE por id. Si el producto ya no existe, la fila debe mostrar un aviso con 404; si tiene pedidos, un 409. Nunca debe mostrarse «eliminado» cuando la base no cambió.

No existe 404 con el fragmento de no encontrado
Conflicto de integridad 409 con un aviso de pedidos asociados
Restricción DELETE FROM productos WHERE id = $1, nunca por nombre
Restricción Si el usuario cancela, no se envía ninguna petición

5.3 · Paso 2: la función y la ruta

repositorio.py — el DELETE 
async def eliminar_producto(conn, producto_id: int) -> bool:
    resultado = await conn.execute(
        "DELETE FROM productos WHERE id = $1",
        producto_id,
    )
    return resultado == "DELETE 1"
vistas.py — la ruta con tres salidas 
@router.delete("/productos/{producto_id}")
async def eliminar_producto_vista(
    request: Request,
    conn: ConnectionDep,
    producto_id: int,
):
    try:
        eliminado = await eliminar_producto(conn, producto_id)
    except (asyncpg.RestrictViolationError, asyncpg.ForeignKeyViolationError):
        return templates.TemplateResponse(
            request=request,
            name="componentes/producto_con_pedidos.html",
            context={"producto_id": producto_id},
            status_code=409,
        )

    if not eliminado:
        return producto_no_encontrado(request, producto_id)

    return templates.TemplateResponse(
        request=request,
        name="componentes/fila_eliminada.html",
        context={"producto_id": producto_id},
    )

5.5 · Paso 4: mostrar también el 409

La configuración de HTMX del proyecto habilita el intercambio de 404 y 422, pero no de 409. Si no la amplías, el aviso de «tiene pedidos» no se verá en la fila. Agrega la entrada de 409 a responseHandling.

base.html — habilitar el swap de 409 
<meta name="htmx-config" content='{
  "responseHandling": [
    {"code": "204", "swap": false},
    {"code": "[23]..", "swap": true},
    {"code": "404", "swap": true},
    {"code": "409", "swap": true},
    {"code": "422", "swap": true},
    {"code": "[45]..", "swap": false, "error": true}
  ]
}'>
Advertencia — el 409 también puede ser JSON

Si la ruta devuelve un fragmento HTML, HTMX lo inserta en la fila. Si devuelve JSON, no hay nada que insertar. Para esta actividad, el 409 debe ser el fragmento producto_con_pedidos.html, no un JSONResponse. La API JSON y la interfaz HTML pueden compartir la lógica, pero no el formato de respuesta.

Unidad 06 · La respuesta

Errores y confirmaciones: nunca un éxito falso

El error más grave de un borrado no es un 500: es un 200 que dice «eliminado» cuando la fila sigue ahí. Esta unidad ordena los estados, las confirmaciones y los mensajes para que la interfaz cuente siempre lo que pasó.

6.1 · El mapa de errores de un borrado

Qué puede fallar y qué debería responder la API
SituaciónQué ocurrióEstadoQué ve el usuario
Producto existenteDELETE 1200«Producto eliminado correctamente»
Producto ya borradoDELETE 0404«No se encontró el producto con id N»
Producto con pedidosRestrictViolationError (23001) o ForeignKeyViolationError (23503)409«No se puede eliminar: tiene pedidos»
id no numérico en la URLFastAPI no convierte el parámetro422Mensaje de ruta inválida
Tabla o columna inexistenteError de SQL500Mensaje genérico; detalle en el log
Base caída o pool no listoError de conexión503«Intenta de nuevo en unos segundos»
Distinción — 404 no es un fallo del servidor

Que un producto ya no exista es un resultado normal de un borrado repetido o de un enlace viejo. No es un 500. El 404 le dice al usuario que el recurso no está; el 500 le dice que el servidor falló. Confundirlos hace que el usuario reintente cuando no debe o que el equipo busque un bug que no existe.

6.2 · El falso éxito

El error más peligroso es el que no parece un error. Si la ruta ignora el valor de retorno de eliminar_producto y siempre devuelve el fragmento de éxito, el usuario ve «Producto eliminado» aunque la base no haya borrado nada.

la diferencia entre un borrado honesto y uno falso 
# MAL: siempre responde éxito, aunque no se haya borrado nada
await eliminar_producto(conn, producto_id)
return templates.TemplateResponse(
    request=request,
    name="componentes/fila_eliminada.html",
    context={"producto_id": producto_id},
)

# BIEN: el resultado decide la respuesta
eliminado = await eliminar_producto(conn, producto_id)
if not eliminado:
    return producto_no_encontrado(request, producto_id)
Advertencia — el 200 no se elige por costumbre

Un 200 significa «la operación se realizó». Si el DELETE afectó cero filas, la operación no se realizó. Usar 200 porque «es más fácil para HTMX» es una decisión de interfaz que miente sobre el resultado. HTMX puede intercambiar 404 y 409 si se configura; no hay que falsear el estado.

6.3 · HTMX 2 y el intercambio de errores

HTMX 2 no inserta por defecto las respuestas 4xx. El proyecto lo resuelve con <meta name="htmx-config"> y una lista de responseHandling. Para que el aviso de 409 se vea, esa lista debe incluir el código.

base.html — la lista completa 
<meta name="htmx-config" content='{
  "responseHandling": [
    {"code": "204", "swap": false},
    {"code": "[23]..", "swap": true},
    {"code": "404", "swap": true},
    {"code": "409", "swap": true},
    {"code": "422", "swap": true},
    {"code": "[45]..", "swap": false, "error": true}
  ]
}'>
Nota — HTMX 4.0 cambia la regla

En HTMX 4.0, las respuestas 4xx se intercambian por defecto, salvo 204 y 304. Si actualizas el proyecto, la configuración de responseHandling deja de ser necesaria para 404/409, pero no está de más documentar qué se espera. El proyecto de esta clase usa HTMX 2.0.4 y necesita la lista.

6.4 · Doble clic, doble petición

Sin protección, un doble clic puede enviar dos DELETE. El primero responde 200; el segundo, 404. La fila muestra un error después de un éxito y el usuario no entiende qué pasó. Deshabilitar el botón durante la petición evita la carrera.

hx-disabled-elt — un clic, una petición 
<button hx-delete="/productos/5"
        hx-confirm="¿Eliminar el producto?"
        hx-disabled-elt="this"
        hx-target="#producto-5"
        hx-swap="outerHTML">
  Eliminar
</button>

Nota — qué registrar en un borrado

Un log útil dice: id borrado, resultado (DELETE 1/DELETE 0), SQLSTATE si hubo error y usuario que lo solicitó. No hace falta guardar el nombre o la descripción: para depurar el borrado bastan el id y el resultado. Si el negocio necesita el dato, va en la tabla de auditoría, no en el log.

7.2 · Las pruebas

terminal — instalar y ejecutar

test_borrado.py — éxito, repetición y ruta inválida 
import os
import re

import pytest
from fastapi.testclient import TestClient

pytestmark = pytest.mark.skipif(
    not os.getenv("DATABASE_URL"),
    reason="Requiere PostgreSQL y DATABASE_URL definida",
)


def primer_producto(cliente):
    html = cliente.get("/productos").text
    coincidencia = re.search(r'id="producto-(\d+)"', html)
    if coincidencia is None:
        pytest.skip("No hay productos en la base")
    return coincidencia.group(1)


def test_borrar_producto_existente():
    from main import app

    with TestClient(app) as cliente:
        producto_id = primer_producto(cliente)
        respuesta = cliente.delete(f"/productos/{producto_id}")
        assert respuesta.status_code == 200
        assert "Producto eliminado correctamente" in respuesta.text


def test_borrar_dos_veces_devuelve_404():
    from main import app

    with TestClient(app) as cliente:
        producto_id = primer_producto(cliente)
        primera = cliente.delete(f"/productos/{producto_id}")
        assert primera.status_code == 200

        segunda = cliente.delete(f"/productos/{producto_id}")
        assert segunda.status_code == 404
        assert "No se encontró" in segunda.text


def test_id_invalido_devuelve_422():
    from main import app

    with TestClient(app) as cliente:
        respuesta = cliente.delete("/productos/abc")
        assert respuesta.status_code == 422
Advertencia — el producto de prueba tiene que ser borrable

Si el primer producto de la lista tiene pedidos, la prueba de borrado exitoso recibirá 409 y fallará. Usa un producto sin pedidos o prepara datos de prueba limpios antes de ejecutar la suite. La prueba de conflicto se hace aparte, creando un pedido para un producto concreto.

Precisión — la prueba no puede usar el mismo producto dos veces

test_borrar_producto_existente y test_borrar_dos_veces toman el primer producto de la lista. Si se ejecutan en orden, el primero borra el producto y el segundo toma otro. Si la base se queda sin productos, las pruebas se saltan con un mensaje claro. En un proyecto real se crearían productos de prueba en una transacción y se revertirían al final.

Nota — la confirmación no se prueba con TestClient

hx-confirm vive en el navegador. TestClient no muestra el cuadro ni puede simular que el usuario cancela: envía la petición directamente. La confirmación se verifica manualmente en la pestaña Network. Lo que sí se prueba en el servidor es que un DELETE sin fila responde 404 y no un falso éxito.

7.4 · Síntesis: siete ideas para llevarse

01

Borrar es la única operación del CRUD que no se puede corregir con otra operación: la confirmación es parte del diseño.

02

hx-confirm pregunta en el navegador; si el usuario cancela, el servidor no recibe nada.

03

El DELETE se identifica por la clave primaria y usa $1; nunca por el nombre ni por concatenación.

04

DELETE 1 es éxito; DELETE 0 es 404. Responder 200 a los dos es un falso éxito.

05

Las claves foráneas protegen el historial; una violación se traduce en 409, no en 500.

06

Si el historial importa, se archiva con deleted_at o con una tabla de auditoría antes de borrar.

07

La interfaz debe contar lo que pasó: éxito solo si se borró, 404 si no estaba y 409 si dependía de otro registro.
