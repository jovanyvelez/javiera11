Unidad 00 · Apertura

Un autor nuevo, tres filtros

La aplicación Escritores tiene un formulario para crear autores y una tabla que se actualiza sin recargar la página. Detrás de ese botón «Crear» hay tres filtros: el navegador, Pydantic y PostgreSQL. Si uno falla, el dato no entra. Hoy vas a aprender a construir y a leer esos tres filtros.

0.2 · El formulario que acepta demasiado

El modelo actual del proyecto es este:

esquemas.py — el modelo actual del repositorio 
from pydantic import BaseModel, Field


class AutorCrear(BaseModel):
    nombre: str = Field(min_length=1)
    pais: str | None = None
    nacimiento: int | None = Field(default=None, ge=0)

Con este modelo, un nombre de una sola letra es válido, un año 3000 es válido y dos autores pueden llamarse igual. El formulario tampoco tiene required ni maxlength. La aplicación funciona, pero acepta datos que después son difíciles de corregir. Esa es la diferencia entre «guardar» y insertar con criterio.

Distinción — insertar no es escribir una fila: es aceptar un dato

Un INSERT guarda lo que le des. Una inserción bien hecha decide antes si el dato merece entrar y después si la base lo aceptó. Esas dos decisiones viven en lugares distintos: Pydantic y PostgreSQL. El navegador ayuda a escribirlo, pero no decide.

0.3 · Las tres capas de una inserción

Qué atrapa cada capa
CapaQué compruebaQué error produce¿Se puede saltar?
Navegadorrequired, tipos de input, longitudesUn globo del navegador; no envíaSí: DevTools, curl o novalidate
PydanticTipos, límites, valores, normalizaciónValidationError → 422No: está en el servidor
PostgreSQLNOT NULL, UNIQUE, CHECK, claves foráneasasyncpg exceptions → 409/500No: está en la base

Las tres capas no son redundantes: atrapan cosas distintas. El navegador evita un viaje inútil. Pydantic convierte y valida la forma. PostgreSQL protege la integridad incluso si dos peticiones llegan al mismo tiempo. Si eliminas una, las otras dos siguen ahí; si eliminas la última, no hay red.

Precisión — la validación de Pydantic no consulta la base

Pydantic puede comprobar que un nombre tiene dos caracteres y que el año no es futuro. No puede saber si ese nombre ya existe: para eso necesitaría una consulta, y una consulta antes del INSERT no es una garantía. Dos peticiones simultáneas pueden pasar la consulta y luego insertar las dos. La garantía real es una restricción UNIQUE en PostgreSQL. Esa es la idea central de la unidad 3.

Unidad 01 · La entrada

El formulario y el POST: de una caja de texto a un parámetro

El formulario de Escritores tiene tres campos y un botón. Cuando lo envías, HTMX manda un POST y el servidor recibe tres textos. Esta unidad explica cómo se conectan el HTML, la ruta y la tabla, y por qué el nombre del campo tiene que coincidir con el nombre del parámetro.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: formulario y ruta conectados

1.1 · El formulario real

Este es el formulario del repositorio. Está dentro de una tarjeta de Bootstrap y usa atributos hx-* para que HTMX haga el envío. Los tres campos tienen name; sin ese atributo, el servidor no recibiría nada.

hx-post="/autores"
HTMX intercepta el envío y manda un POST a esa URL. Sin HTMX, el formulario necesitaría action="/autores" y method="post".
hx-target="#autores"
El fragmento que devuelva el servidor se inserta en el contenedor con ese id, no en toda la página.
hx-swap="outerHTML"
Reemplaza el contenedor completo, no solo su contenido. Así la tabla se vuelve a pintar con el autor nuevo.
hx-select="#autores"
Del HTML que responde el servidor, toma solo el fragmento #autores. El servidor puede devolver la página completa y HTMX recorta la parte útil.
name
La clave con la que viaja el valor. Si el campo se llama nombre en el HTML y la ruta espera nombre, se encuentran; si no, llega missing.
Precisión — HTMX 4.0 también intercambia respuestas 4xx

En versiones anteriores de HTMX, una respuesta 422 no se insertaba por defecto y el formulario se quedaba como estaba. HTMX 4.0 cambia el contenido para todas las respuestas salvo 204 y 304, incluidas las de error. Por eso el 422 con el formulario vuelve a la pantalla y los mensajes se ven. Si usas una versión anterior, tendrías que escuchar htmx:beforeSwap o devolver 200 con el formulario.

1.2 · Qué viaja en el cuerpo

Con un formulario HTML sin archivos, el cuerpo viaja como application/x-www-form-urlencoded. Todos los valores son texto, aunque el input sea de tipo number.

el cuerpo de un envío real 
nombre=Gabriel+Garc%C3%ADa+M%C3%A1rquez&pais=Colombia&nacimiento=1927

+ es un espacio y %C3%AD es la í en UTF-8. El campo nacimiento viaja como "1927", no como el número 1927. Convertirlo es trabajo del servidor.

Unidad 02 · El filtro

Validaciones previas: que el dato malo no llegue al INSERT

El modelo actual del proyecto acepta un nombre de una letra y un año 3000. Esta unidad lo convierte en un contrato: longitudes, rango de años, país opcional y mensajes que se pueden mostrar. Todo ocurre antes de tocar la base de datos.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: AutorCrear con límites y normalización

2.1 · El modelo actual no es un contrato

El repositorio usa nombre: str = Field(min_length=1), pais libre y nacimiento con ge=0. Es un buen comienzo, pero deja pasar cosas que el negocio no quiere: un nombre de una letra, un país de 300 caracteres, un año 3000 o un año negativo distinto de cero. La validación previa consiste en escribir esas reglas en el modelo, no en confiar en que el formulario las ponga.

2.2 · El modelo propuesto

esquemas.py — un contrato para el autor 
from datetime import date

from pydantic import BaseModel, ConfigDict, Field, field_validator


class AutorCrear(BaseModel):
    """Datos que acepta el formulario de creación de autores."""

    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")

    nombre: str = Field(min_length=2, max_length=80)
    pais: str | None = Field(default=None, max_length=60)
    nacimiento: int | None = Field(
        default=None,
        ge=1000,
        le=date.today().year,
    )

    @field_validator("pais", mode="before")
    @classmethod
    def pais_vacio(cls, valor: str | None) -> str | None:
        """Un país vacío se guarda como NULL, no como cadena vacía."""
        if isinstance(valor, str) and not valor.strip():
            return None
        return valor
str_strip_whitespace=True
Recorta los espacios de los extremos antes de medir. " Ana " se valida como "Ana"; sin esto, tres espacios pasarían un mínimo de dos.
extra="forbid"
Rechaza campos que el modelo no declara. En un formulario con Form() por campo no es lo que más se nota, pero protege el modelo cuando se reutiliza con JSON.
Field(min_length=2, max_length=80)
El nombre tiene un mínimo y un máximo. El mínimo evita iniciales; el máximo evita textos que no caben en la tabla ni en la pantalla.
ge=1000, le=date.today().year
El año está en un rango razonable y no puede ser futuro. date.today().year se evalúa al importar el módulo; si la app vive varios años sin reiniciar, el máximo se queda viejo.
pais_vacio
Convierte "" y los espacios en None. Así la base guarda NULL, que significa «no se sabe», y no una cadena vacía que significa otra cosa.
Nota — validar no es lo mismo que normalizar

Validar decide si el dato se acepta. Normalizar lo convierte a una forma canónica antes de guardarlo. Recortar espacios y convertir un país vacío en NULL son normalizaciones; rechazar un nombre de una letra es una validación. Pydantic hace las dos, en ese orden: primero normaliza, después mide.

2.3 · El formulario también ayuda (pero no decide)

El formulario del repositorio no tiene required, ni maxlength, ni un rango de año. Añadir esas restricciones mejora la experiencia y evita peticiones inútiles, pero no sustituye al modelo. Esta es la versión con las tres capas en su sitio:

formulario_autor.html — restricciones del navegador 
<input type="text" class="form-control" id="nombre" name="nombre"
       placeholder="Nombre del autor" value="{{ nombre or '' }}"
       required minlength="2" maxlength="80" autocomplete="name">

<input type="text" class="form-control" id="pais" name="pais"
       placeholder="País" value="{{ pais or '' }}"
       maxlength="60" autocomplete="country-name">

<input type="number" class="form-control" id="nacimiento" name="nacimiento"
       placeholder="Año" value="{{ nacimiento or '' }}"
       min="1000" max="2026" inputmode="numeric">

El max="2026" del HTML es una ayuda para el navegador; el servidor usa date.today().year, que es la fuente de verdad. Si cambias de año, actualiza el atributo o pásalo desde la plantilla; la validación de Pydantic no depende de él.

Advertencia — el globo del navegador no es tu mensaje

required y min muestran un aviso del navegador, en su idioma y con su diseño. No puedes cambiar el texto ni el estilo. Para mensajes propios y accesibles, el servidor tiene que devolver el formulario con sus errores; el navegador solo evita el viaje más obvio.

2.4 · Validar antes del INSERT

La ruta del repositorio construye el modelo dentro de un try. Si Pydantic lanza ValidationError, la ruta no llama al repositorio: vuelve a pintar el formulario con los valores y los errores.

vistas.py — validar antes de insertar 
from pydantic import ValidationError

from esquemas import AutorCrear


@router.post("/autores")
async def crear_autor_vista(
    request: Request,
    conn: ConnectionDep,
    nombre: Annotated[str | None, Form()] = None,
    pais: Annotated[str | None, Form()] = None,
    nacimiento: Annotated[str | None, Form()] = None,
):
    try:
        autor = AutorCrear(
            nombre=nombre,
            pais=pais,
            nacimiento=nacimiento,
        )
    except ValidationError as e:
        autores = await obtener_autores(conn)
        return templates.TemplateResponse(
            request=request,
            name="autores.html",
            context={
                "autores": autores,
                "nombre": nombre,
                "pais": pais,
                "nacimiento": nacimiento,
                "errors": errores_por_campo(e),

            status_code=422,
        )

    await crear_autor(conn, autor.nombre, autor.pais, autor.nacimiento)

Precisión — nacimiento como str para controlar el mensaje

En este bloque la ruta recibe nacimiento como str | None, no como int. Así, si el usuario escribe abc, FastAPI no responde antes de entrar: el valor llega a Pydantic, que lanza int_parsing y permite devolver un mensaje en español. Es un cambio pequeño con una consecuencia grande en la experiencia.

2.5 · De la lista de errores a un diccionario por campo

e.errors() devuelve una lista de diccionarios con type, loc, msg e input. La plantilla del repositorio la recorre y compara error.loc.0 con el nombre del campo. Funciona, pero es más limpio convertirla en un diccionario campo → mensaje antes de pasarla a Jinja2.

vistas.py — traducir los errores de Pydantic 
from pydantic import ValidationError

TRADUCCIONES = {
    "missing": "Este campo es obligatorio.",
    "string_too_short": "El texto es demasiado corto.",
    "string_too_long": "El texto es demasiado largo.",
    "int_parsing": "El año debe ser un número entero.",
    "greater_than_equal": "El año no puede ser anterior a 1000.",
    "less_than_equal": "El año no puede estar en el futuro.",
}


def errores_por_campo(exc: ValidationError) -> dict[str, str]:
    """Convierte la lista de Pydantic en {campo: mensaje}."""
    errores: dict[str, str] = {}
    for error in exc.errors():
        campo = str(error["loc"][0])
        errores.setdefault(
            campo,
            TRADUCCIONES.get(error["type"], "Revisa este campo."),
        )
    return errores
error["loc"][0]
El primer elemento de la ruta del error. En un modelo plano es el nombre del campo: nombre, pais o nacimiento.
error["type"]
El identificador estable del error: string_too_short, int_parsing, greater_than_equal. Se traduce por tipo, no por el texto en inglés.
setdefault
Guarda el primer mensaje de cada campo y descarta los siguientes. Mostrar tres errores apilados bajo el mismo input confunde más de lo que ayuda.
La plantilla
Con un diccionario, cada campo pregunta errores.get('nombre') y decide si pinta el mensaje. No recorre la lista ni depende de la forma de loc.

2.6 · Lo que Pydantic no puede validar

El modelo puede comprobar la forma del dato, pero no su relación con la base. Estas reglas necesitan una consulta o una restricción:

Fuera del alcance de Pydantic
Regla¿Por qué no cabe en Pydantic?Dónde vive
El nombre ya existeRequiere consultar la tabla; además, otra petición puede insertar entre la consulta y el INSERTUNIQUE en PostgreSQL
El país es un código ISO válidoNecesita una lista oficial o una tabla de paísesUn Literal o una tabla de referencia
El autor tiene al menos un libroDepende de otras filas y del momentoRegla de negocio o consulta posterior
El id no se repiteLo genera la baseIDENTITY / secuencia
Aplicación — validar antes ahorra transacciones

Cada ValidationError evita un viaje a PostgreSQL. En un formulario con cien envíos por minuto, eso es tiempo y conexiones. Pero la razón principal no es el rendimiento: es que el repositorio solo recibe objetos que ya cumplen el contrato. La función que inserta no tiene que preguntarse si el nombre está vacío.

Unidad 03 · La escritura

Inserción segura: INSERT, RETURNING y UNIQUE

El modelo ya acepta solo datos con forma. Ahora hay que escribirlos sin abrir la puerta a la inyección SQL, recuperar el id que genera PostgreSQL y dejar que una restricción —no una consulta previa— impida los duplicados.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: INSERT parametrizado con RETURNING

3.1 · La función que inserta

En el repositorio, crear_autor recibe la conexión y los tres valores, ejecuta un INSERT y devuelve la fila creada. El RETURNING * es la pieza que evita una segunda consulta: PostgreSQL devuelve el id y los valores tal como quedaron guardados.

repositorio.py — crear_autor() 
async def crear_autor(
    conn,
    nombre: str,
    pais: str | None,
    nacimiento: int | None,
) -> dict:
    row = await conn.fetchrow(
        """
        INSERT INTO autores (nombre, pais, nacimiento)
        VALUES ($1, $2, $3)
        RETURNING *
        """,
        nombre,
        pais,
        nacimiento,
    )
    return dict(row)
$1, $2, $3
Marcadores de parámetro. Los valores viajan aparte y PostgreSQL los trata como datos, no como código. Es la defensa contra la inyección SQL.
RETURNING *
Devuelve la fila insertada, incluido el id generado por la base. Sin esto, habría que hacer un SELECT extra o confiar en un id calculado por el cliente.
fetchrow
Devuelve una fila (Record) o None. En un INSERT ... RETURNING siempre hay una fila si la inserción tuvo éxito.
dict(row)
Convierte el Record de asyncpg en un diccionario que Jinja2 y Pydantic pueden usar.
Advertencia — nunca armes el INSERT con f-string

f"INSERT ... VALUES ('{nombre}')" convierte el nombre en parte del SQL. Un nombre como '; DROP TABLE autores; -- puede cambiar la consulta entera. Con $1, ese texto se guarda como texto y no se ejecuta. La única parte del SQL que se puede interpolar es una lista blanca de nombres de tabla o columnas, nunca un valor.

3.2 · La tabla y la restricción que faltan

El esquema del proyecto define autores con id, nombre, pais y nacimiento. El nombre es NOT NULL, pero no es único: dos autores pueden llamarse igual. Para que la base sea la última defensa, añade un índice único sobre el nombre normalizado.

docs/tablas_bd.md — tabla e índice único 
CREATE TABLE autores (
    id         INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre     TEXT    NOT NULL,
    pais       TEXT,
    nacimiento INTEGER
);

-- Unicidad sin distinguir mayúsculas ni espacios extremos:
-- "Gabriel García Márquez" y "  gabriel garcía márquez  "
-- se consideran el mismo autor.
CREATE UNIQUE INDEX IF NOT EXISTS autores_nombre_unico
    ON autores (lower(btrim(nombre)));
Precisión — el índice es sobre una expresión

lower(btrim(nombre)) normaliza el nombre para comparar. El índice no cambia el valor guardado; solo define qué se considera duplicado. Si ya hay autores repetidos, la creación del índice fallará: primero hay que limpiar o fusionar los duplicados. Esa limpieza es una decisión de datos, no un detalle de SQL.

SQL — encontrar duplicados antes de crear el índice 
SELECT lower(btrim(nombre)) AS nombre_normalizado,
       count(*) AS veces
FROM autores
GROUP BY 1
HAVING count(*) > 1
ORDER BY veces DESC;
Nota — no todas las reglas se duplican en la base

El rango del año y el largo del nombre son reglas de negocio que Pydantic aplica antes del INSERT. La base repite las restricciones que protegen la integridad estructural: NOT NULL y UNIQUE. Si un INSERT manual pudiera saltarse el año, se añadiría un CHECK o un trigger; para el flujo de la aplicación, Pydantic ya lo cubre.

3.3 · Por qué una consulta previa no basta

La tentación es hacer SELECT ... WHERE nombre = $1 y, si no hay filas, insertar. Funciona en una demostración y falla en producción. Dos peticiones pueden ejecutar el SELECT al mismo tiempo, las dos ver que no existe y las dos insertar.

La carrera entre dos peticiones
MomentoPetición APetición BBase de datos
1SELECT: no existe—Sin filas
2—SELECT: no existeSin filas
3INSERT—Una fila
4—INSERTDos filas idénticas
5——La consulta previa no sirvió
Distinción — la restricción es la garantía; la consulta es una cortesía

La consulta previa puede servir para dar un mensaje más rápido en el caso normal, pero no es una garantía. La garantía es el índice UNIQUE: si dos INSERT llegan a la vez, PostgreSQL deja pasar uno y rechaza el otro con UniqueViolationError (SQLSTATE 23505). El servidor captura ese error y responde 409.

3.4 · La alternativa ON CONFLICT

PostgreSQL permite decirle al INSERT qué hacer si el valor ya existe. En vez de lanzar una excepción, puede no insertar y devolver cero filas. Es útil cuando el conflicto es esperado y no necesita un error.

INSERT ... ON CONFLICT DO NOTHING 
row = await conn.fetchrow(
    """
    INSERT INTO autores (nombre, pais, nacimiento)
    VALUES ($1, $2, $3)
    ON CONFLICT (lower(btrim(nombre))) DO NOTHING
    RETURNING *
    """,
    nombre,
    pais,
    nacimiento,
)
if row is None:
    # No se insertó porque ya existía; la ruta puede responder 409.
    ...
Nota — el objetivo del conflicto debe coincidir con el índice

ON CONFLICT (lower(btrim(nombre))) solo funciona si existe un índice único con exactamente esa expresión. Si el índice es UNIQUE (nombre), el objetivo debe ser (nombre). Si no coincide, PostgreSQL responde con un error de «no existe una restricción de exclusión». Para esta clase usamos la excepción, que es más explícita y permite responder 409 sin confundir «no inserté» con «la base falló».

3.5 · Transacciones: una inserción no siempre es una fila

Un autor solo es una fila y un INSERT ya es atómico. Pero si la creación incluye una auditoría, una relación con un libro o un contador, las operaciones tienen que ir juntas. Para eso está la transacción.

una inserción con auditoría en la misma transacción 
async with conn.transaction():
    autor = await crear_autor(conn, datos.nombre, datos.pais, datos.nacimiento)
    await conn.execute(
        "INSERT INTO auditoria (tabla, accion, registro_id) VALUES ($1, $2, $3)",
        "autores",
        "crear",
        autor["id"],
    )
Advertencia — no dejes una transacción abierta esperando al usuario

Una transacción mantiene bloqueos y una conexión ocupada. Si dentro de ella esperas una respuesta externa o una confirmación del usuario, el pool se agota y otros inserts esperan. Abre la transacción cuando ya tienes todos los datos y ciérrala lo antes posible.

Unidad 06 · La respuesta

Control de errores: 422, 409 y mensajes que se entienden

Una inserción puede fallar por el formulario, por Pydantic, por una restricción de la base o porque la base no está. Cada fallo necesita un código y un mensaje distintos. Esta unidad separa los caminos y evita el error más común: responder 500 a todo.

La ruta de la actividad captura dos cosas: ValidationError antes del INSERT y UniqueViolationError durante el INSERT. Cada una vuelve al formulario con un estado distinto.

422 con el formulario
El dato no tiene la forma correcta. Se vuelve a pintar el formulario con los valores y los mensajes; HTMX 4.0 intercambia la respuesta aunque sea 4xx.
409 con el formulario
El dato tiene forma correcta, pero choca con una regla de unicidad. El usuario puede cambiar el nombre y reintentar.
Por qué no 400
400 se reserva para una petición mal formada (por ejemplo, un JSON inválido). Aquí la petición está bien formada; lo que falla es el contenido.
Por qué no 500
Un 500 dice «el servidor falló». Un nombre corto no es un fallo del servidor: es un dato que el usuario puede corregir.

6.3 · Los errores que no captura la ruta

Si la tabla no existe, si la conexión se cae o si otra ruta intenta insertar un duplicado, la ruta no lo captura. Para esos casos se registran manejadores globales en main.py.

main.py — manejadores globales 
import asyncpg
from fastapi import Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from loguru import logger


@app.exception_handler(asyncpg.UniqueViolationError)
async def nombre_duplicado(
    request: Request, exc: asyncpg.UniqueViolationError
) -> JSONResponse:
    logger.warning("Conflicto de unicidad: {}", exc.constraint_name)
    return JSONResponse(
        {"detail": "Ya existe un autor con ese nombre."},
        status_code=409,
    )


@app.exception_handler(RequestValidationError)
async def error_de_fastapi(
    request: Request, exc: RequestValidationError
) -> JSONResponse:
    logger.warning("Validación de FastAPI: {}", exc.errors())
    return JSONResponse(
        {"detail": "Revisa los datos enviados."},
        status_code=422,
    )


@app.exception_handler(asyncpg.PostgresError)
async def error_postgres(
    request: Request, exc: asyncpg.PostgresError
) -> JSONResponse:
    logger.error("PostgreSQL {}: {}", exc.sqlstate, exc)
    return JSONResponse(
        {"detail": "Error al guardar los datos."},
        status_code=500,
    )
Advertencia — el manejador global no reemplaza al de la ruta

El manejador de UniqueViolationError devuelve JSON, no el formulario. Sirve para otras rutas o para un cliente de API, pero la ruta de autores captura el error antes y devuelve HTML. Si quitas el except de la ruta, el usuario vería un JSON en medio de la página. Cada camino tiene su formato.

Precisión — RequestValidationError ocurre antes de tu función

Si un parámetro anotado como int recibe abc, FastAPI lanza RequestValidationError y no entra a la ruta. El manejador global puede responder 422, pero no tiene los valores del formulario para volver a pintarlo. Por eso la ruta de autores recibe nacimiento como texto y deja que Pydantic lo valide dentro: así puede devolver el formulario completo.

test_autores.py — los tres caminos y el duplicado 
import os
from uuid import uuid4

import pytest
from fastapi.testclient import TestClient

pytestmark = pytest.mark.skipif(
    not os.getenv("DATABASE_URL"),
    reason="Requiere PostgreSQL y DATABASE_URL definida",
)


def test_crear_autor_valido():
    from main import app

    nombre = f"Autor {uuid4().hex[:8]}"
    with TestClient(app) as cliente:
        respuesta = cliente.post(
            "/autores",
            data={"nombre": nombre, "pais": "Colombia", "nacimiento": "1990"},
        )
        assert respuesta.status_code == 200
        assert nombre in respuesta.text


def test_nombre_corto_devuelve_422():
    from main import app

    with TestClient(app) as cliente:
        respuesta = cliente.post(
            "/autores",
            data={"nombre": "A", "pais": "Colombia", "nacimiento": "1990"},
        )
        assert respuesta.status_code == 422
        assert "demasiado corto" in respuesta.text


def test_anio_futuro_devuelve_422():
    from main import app

    with TestClient(app) as cliente:
        respuesta = cliente.post(
            "/autores",
            data={"nombre": "Autor Futuro", "pais": "Colombia", "nacimiento": "3000"},
        )
        assert respuesta.status_code == 422
        assert "futuro" in respuesta.text


def test_nombre_duplicado_devuelve_409():
    from main import app

    nombre = f"Autor {uuid4().hex[:8]}"
    with TestClient(app) as cliente:
        primero = cliente.post(
            "/autores",
            data={"nombre": nombre, "pais": "Colombia", "nacimiento": "1990"},
        )
        assert primero.status_code == 200

        repetido = cliente.post(
            "/autores",
            data={"nombre": nombre, "pais": "Colombia", "nacimiento": "1990"},
        )
        assert repetido.status_code == 409
        assert "Ya existe" in repetido.text
Precisión — with TestClient(app) ejecuta el lifespan

Sin el with, el pool no se abre y la ruta falla con PoolNotReadyError. Con el with, FastAPI arranca, conecta la base, corre la prueba y cierra el pool. Cada prueba abre y cierra su propio cliente; es más lento que un cliente compartido, pero aísla el estado y demuestra el ciclo de vida real.

Nota — nombres únicos para pruebas repetibles

La tabla tiene un índice único sobre el nombre. Si todas las pruebas usaran «Autor de prueba», la segunda corrida chocaría con la primera. uuid4().hex[:8] genera un sufijo distinto y permite ejecutar la suite muchas veces sin limpiar la base. En un proyecto real, además, habría una transacción de prueba que se revierte al final.

7.4 · Síntesis: siete ideas para llevarse

01

Insertar no es escribir una fila: es aceptar un dato después de tres filtros. El navegador ayuda, Pydantic decide la forma y PostgreSQL protege la integridad.

02

El name del HTML, el parámetro de la ruta y el campo del modelo tienen que llamarse igual. La mayoría de los «no llega» empieza ahí.

03

Validar antes del INSERT evita transacciones y da mensajes por campo. Normalizar antes de medir evita que tres espacios pasen como un nombre.

04

El INSERT usa $1, $2, $3 y RETURNING: los valores no se concatenan y el id lo genera la base.

05

Un SELECT previo no impide duplicados: dos peticiones pueden consultar antes de que cualquiera inserte. La garantía es el índice UNIQUE.

06

422 es un error del dato, 409 es un conflicto, 503 es temporal y 500 es un fallo interno. El estado comunica la categoría.

07

El mensaje público dice qué corregir; el log guarda el SQLSTATE y la restricción. Nunca se devuelve exc.detail al usuario.

7.5 · Puente hacia la próxima clase

Tu formulario ya inserta con criterio. Lo que sigue es hacer que el esquema evolucione sin romper lo que ya está guardado, y que la inserción siga siendo segura cuando el proyecto crezca.

  1. Migraciones. El índice único no debería crearse a mano en producción: se versiona con una migración (Alembic) que se aplica en orden y se puede revertir.
  2. Repositorio y pruebas. La ruta no debería saber SQL; el repositorio no debería saber HTTP. Separarlos permite probar la inserción sin levantar FastAPI y cambiar de base sin tocar las vistas.
  3. Auditoría y concurrencia. Cuando la inserción forme parte de un proceso más grande —crear un autor y asociarlo a un libro— la transacción y el registro de auditoría entran en juego. Es el tema de las próximas clases.
