0.1 · El formulario que aceptaba todo

El club de robótica del colegio abrió un formulario para recibir inscripciones. La primera semana llegaron cuarenta mensajes. La segunda, tres mil. Alguien descubrió que el campo nombre aceptaba ocho mil caracteres, que el campo correo aceptaba cualquier cosa y que el botón de enviar no tenía ningún límite. La bandeja se llenó de basura y el mensaje de un estudiante real se perdió entre dos mil novecientos noventa y nueve mensajes automáticos.

El formulario no estaba roto: estaba abierto. Aceptaba todo lo que le llegara, y todo lo que le llegaba era tratado como si fuera verdad. Ninguna de las dos cosas es un detalle de estilo: son la diferencia entre un sistema que sirve y un sistema que se puede llenar de basura en una tarde.

Distinción — un formulario no es una página: es un contrato

Una página se mira. Un formulario se cumple. Sus campos, sus tipos y sus límites son las cláusulas de un contrato entre quien escribe y quien recibe. Si el contrato dice «nombre de 3 a 60 caracteres», el servidor tiene que poder demostrar que se cumplió. El navegador ayuda a redactarlo, pero no es el notario.

0.2 · Las dos validaciones

«Validar el formulario» suena a una sola cosa. Son dos, con trabajos distintos, y confundirlas es el error que produce la mayoría de los formularios inseguros.

La del navegador es una cortesía: hace que la experiencia sea agradable. La del servidor es una garantía: es la única que se cumple siempre. Un formulario sin validación del navegador es incómodo; un formulario sin validación del servidor es una puerta abierta. En esta clase vas a construir las dos, y vas a comprobar con tus propias manos que la primera se puede saltar.

0.3 · El formulario que no valida nada

Este es el punto de partida. La ruta compila, responde 200 y acepta un mensaje de ochocientos mil caracteres. El problema no es la sintaxis: es que no hay ninguna regla.

main.py — la puerta abierta 
from typing import Annotated

from fastapi import FastAPI, Form

app = FastAPI()


@app.post("/contacto")
def recibir(
    nombre: Annotated[str, Form()],
    mensaje: Annotated[str, Form()],
) -> dict[str, str]:
    return {"recibido": mensaje}

Form() hace que el campo sea obligatorio: si no llega, la petición se rechaza. Pero un campo obligatorio no es un campo válido. Un nombre vacío llega, un correo inventado llega, un mensaje de ocho mil caracteres llega. La diferencia entre «está» y «sirve» es exactamente el tema de esta clase.

El viaje del dato: de una caja de texto a un objeto Python

Cuando pulsas «Enviar» ocurren seis cosas en menos de un segundo. Entender ese recorrido es lo que permite responder la pregunta más útil del desarrollo web: «¿en qué punto se perdió mi dato?».

1.1 · Los seis pasos de un envío

Pydantic convierte y valida; tu ruta recibe un objeto y responde con una página o un error.

El paso 1 es el que más se olvida. El navegador no envía «el formulario»: envía una lista de parejas. Si un control no tiene name, no existe para el servidor. Si está deshabilitado, no existe. Si es un checkbox sin marcar, no existe. Esa lista tiene un nombre técnico: los controles exitosos (successful controls).

Precisión — el atributo que manda es name

id sirve para el for de la etiqueta, para el CSS y para el JavaScript. name sirve para el servidor. Un campo puede tener id="correo" y name="email": el servidor recibirá email. Cuando un formulario «no manda nada», la primera revisión es siempre la misma: ¿tiene name? ¿coincide con lo que espera la ruta?

Si pones method="get" en el formulario de contacto, el mensaje completo terminará en la barra de direcciones, en el historial del navegador y en los registros del servidor. Además, si el texto es largo, la URL se corta o el servidor la rechaza. Para enviar información usa POST; para consultar información usa GET.

1.3 · Qué hay dentro del cuerpo

Con method="post" y sin archivos, el navegador envía el cuerpo con el tipo application/x-www-form-urlencoded. Es una sola línea de parejas separadas por &, con los caracteres especiales codificados.

el cuerpo real de un envío 
nombre=Ana+Torres&correo=ana%40colegio.edu.co&asunto=consulta&mensaje=Hola%2C+quiero+inscribirme.
+
Un espacio. En este formato, el espacio se codifica como + para no romper la línea.
%40
El carácter @, escrito en hexadecimal. %2C es la coma y %C3%B1 sería la ñ en UTF-8.
&
El separador entre parejas. Si un valor contuviera un & sin codificar, el servidor creería que empieza otro campo.
multipart/form-data
El otro formato, obligatorio cuando el formulario sube archivos. Lleva cada campo en su propia «parte», con nombre y tipo.

1.4 · Del cuerpo al parámetro: Form()

FastAPI hace la traducción. Le dices el nombre del campo y el tipo que esperas, y él busca ese nombre en el formulario, lo convierte y te lo entrega. El nombre del parámetro de Python tiene que coincidir con el name del HTML.

main.py — el formulario mínimo 
from typing import Annotated

from fastapi import FastAPI, Form
from fastapi.responses import HTMLResponse

app = FastAPI()


@app.get("/", response_class=HTMLResponse)
def mostrar_formulario() -> str:
    return """
    <form method="post" action="/saludo">
      <label for="nombre">Tu nombre</label>
      <input id="nombre" name="nombre" type="text" required>
      <button type="submit">Saludar</button>
    </form>
    """


@app.post("/saludo")
def saludar(nombre: Annotated[str, Form()]) -> dict[str, str]:
    return {"mensaje": f"Hola, {nombre}"}

1.6 · La variante dinámica: request.form()

Cuando los campos no se conocen de antemano —una encuesta que cambia, un formulario que el usuario construye— no se puede declarar un parámetro por campo. Ahí se lee el formulario completo como un diccionario.

main.py — leer todos los campos 
from fastapi import FastAPI, Request

app = FastAPI()


@app.post("/contacto")
async def recibir_cualquier_campo(request: Request) -> dict[str, str]:
    formulario = await request.form()
    return {
        "campos": ", ".join(formulario.keys()),
        "mensaje": str(formulario.get("mensaje", "")),
    }
Advertencia — dinámico no significa sin reglas

request.form() entrega exactamente lo que llegó, sin validar nada. Si el formulario es dinámico, la validación se escribe a mano: lista de campos permitidos, longitud máxima por campo, tipos y valores aceptados. «No sé qué campos vendrán» no es una excusa para aceptar cualquier cosa; es una razón para tener una lista blanca.

2.4 · Accesibilidad: el formulario también se escucha

Un formulario no se usa solo con el ratón. Se usa con el teclado, con un lector de pantalla, con el zoom al 200 % y con el dedo en una pantalla pequeña. Cuatro decisiones resuelven casi todos los problemas.

Una etiqueta por campo
Cada <input> tiene su <label for="id">. Al pulsar la etiqueta, el cursor salta al campo; el lector de pantalla anuncia el nombre. Un placeholder no sustituye a la etiqueta: desaparece al escribir y suele tener poco contraste.
Los grupos, con fieldset
Un grupo de radios o de checkboxes relacionados va dentro de <fieldset> con un <legend>. Así se anuncia «Asunto: consulta, soporte o sugerencia» como una sola pregunta.
El error, en texto
El color rojo no es un mensaje. El error se escribe, se asocia al campo con aria-describedby y se marca el campo con aria-invalid="true".
El foco, visible
Nunca se quita el contorno del foco sin poner otro. Quien navega con Tab necesita saber dónde está.

3.1 · La frontera de confianza

Imagina que el formulario es la ventanilla de una oficina. La ventanilla sirve para ordenar la fila y para que la gente sepa qué papeles traer. Pero el funcionario que recibe los papeles no puede fiarse de que estén completos solo porque hay un cartel que lo dice: tiene que revisarlos uno por uno. El servidor es ese funcionario.

En seguridad informática, esa línea se llama frontera de confianza. Todo lo que está por fuera —el navegador, la red, el formulario, el JavaScript, curl— es territorio no confiable. Todo lo que está por dentro —tu código Python— es lo único que puedes dar por cierto. La validación del servidor es la aduana que cruza esa línea.

Aplicación — la misma regla en cualquier lenguaje

Esto no es una costumbre de FastAPI. Cualquier servidor —Django, Express, Spring, Laravel— recibe texto sin validar y tiene que convertirlo en un dato seguro. Cambia la herramienta, no la obligación. Aprender a pensar en «qué entra» y «qué se guarda» vale más que memorizar un decorador.

3.2 · El modelo Contacto

Un modelo Pydantic es una clase que describe un dato válido. Cada atributo es un campo; cada tipo es una regla; cada Field o StringConstraints es un límite. Si el dato no cumple, el modelo no se construye y FastAPI responde 422.

modelos.py — el contrato del contacto 
"""Modelos de validación del formulario de contacto."""

from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, EmailStr, StringConstraints, field_validator


class Contacto(BaseModel):
    """Datos que acepta el formulario de contacto del club."""

    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")

    nombre: Annotated[str, StringConstraints(min_length=3, max_length=60)]
    correo: EmailStr
    asunto: Literal["consulta", "soporte", "sugerencia"]
    mensaje: Annotated[str, StringConstraints(min_length=20, max_length=800)]
    acepta: bool
    sitio: str = ""

    @field_validator("acepta")
    @classmethod
    def debe_aceptar(cls, valor: bool) -> bool:
        """La casilla de consentimiento no es opcional."""
        if not valor:
            raise ValueError("Debes aceptar para enviar el mensaje.")
        return valor

    @field_validator("mensaje")
    @classmethod
    def sin_enlaces(cls, valor: str) -> str:
        """Un formulario de contacto no necesita enlaces en el primer mensaje."""
        if "http://" in valor or "https://" in valor:
            raise ValueError("El mensaje no puede contener enlaces.")
        return valor

    @field_validator("sitio")
    @classmethod
    def trampa_vacia(cls, valor: str) -> str:
        """El campo invisible debe llegar vacío: si trae algo, es un robot."""
        if valor:
            raise ValueError("El campo invisible debe estar vacío.")
        return valor

Hay seis decisiones importantes en esas pocas líneas. Vale la pena leerlas despacio.

str_strip_whitespace=True
Recorta los espacios de los extremos antes de medir. Un nombre " Ana " se valida como "Ana". Sin esto, un texto de tres espacios pasaría un mínimo de tres y llegaría a la base de datos como basura.
extra="forbid"
Si el formulario trae un campo que el modelo no declara, la petición se rechaza. Es una defensa contra campos inesperados y contra la tentación de aceptar «cualquier cosa extra».
StringConstraints(min_length=3, max_length=60)
El límite vive junto al tipo, no en un if suelto. Se documenta solo en /docs y se prueba solo.
EmailStr
Valida la forma del correo con email-validator. No comprueba que el buzón exista: eso solo se sabe enviando un correo. fastapi[standard] ya trae la dependencia.
Literal[...]
El asunto solo puede ser uno de tres valores. No es una sugerencia del select: es una lista cerrada en el servidor.
field_validator
Una regla que no cabe en un tipo: el consentimiento tiene que ser verdadero, el mensaje no puede llevar enlaces, el campo trampa tiene que estar vacío. Si falla, se lanza ValueError y FastAPI lo convierte en 422.

Desde FastAPI 0.113, un modelo Pydantic se puede declarar directamente como formulario con Annotated[Contacto, Form()]. FastAPI extrae cada campo del cuerpo, lo valida y te entrega un objeto Contacto ya construido.

detail
La lista de errores. Cada elemento es un campo que no cumplió una regla.
loc
La ruta del campo dentro de la petición. ["body", "nombre"] significa «en el cuerpo, el campo nombre». El último elemento es el nombre que usarás para pintar el error junto al campo.
type
El identificador estable del error: string_too_short, literal_error, value_error, missing. Es lo que se traduce a un mensaje en español sin depender del texto en inglés.
msg
El mensaje en inglés que genera Pydantic. Es útil para depurar, pero no es lo que se le muestra al usuario final.
input
El valor que llegó. Nunca se debe devolver tal cual en una página sin escapar: es dato del usuario.

3.6 · Validadores: reglas que no caben en un tipo

Un validador es una función que recibe el valor ya convertido y lo devuelve, o lanza ValueError si no cumple. Se declara con @field_validator("campo") y @classmethod. El valor que recibe ya pasó por el tipo, así que acepta llega como bool, no como el texto "true".

modelos.py — tres validadores con propósitos distintos 
@field_validator("acepta")
@classmethod
def debe_aceptar(cls, valor: bool) -> bool:
    if not valor:
        raise ValueError("Debes aceptar para enviar el mensaje.")
    return valor


@field_validator("mensaje")
@classmethod
def sin_enlaces(cls, valor: str) -> str:
    if "http://" in valor or "https://" in valor:
        raise ValueError("El mensaje no puede contener enlaces.")
    return valor


@field_validator("sitio")
@classmethod
def trampa_vacia(cls, valor: str) -> str:
    if valor:
        raise ValueError("El campo invisible debe estar vacío.")
    return valor
Nota — no lances HTTPException dentro de un validador

Dentro de un validador, la forma correcta de fallar es raise ValueError(...). Pydantic lo recoge, lo convierte en un error de validación y FastAPI responde 422 como con cualquier otra regla. Si lanzas HTTPException, rompes esa cadena y el error sale por un camino que no es el de los demás campos.

Un campo que el navegador incluye en el envío: tiene name, no está deshabilitado y, si es una casilla, está marcado.

Un campo invisible para las personas y visible para los robots. Si llega relleno, la petición se rechaza.
Sanitización
Neutralizar el contenido peligroso antes de mostrarlo o guardarlo. En HTML, la herramienta principal es escapar la salida, no borrar caracteres a mano.

"""Formulario de contacto del Club de Robótica."""

from typing import Annotated

from fastapi import FastAPI, Form, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import HTMLResponse, RedirectResponse
from fastapi.templating import Jinja2Templates

from modelos import Contacto

app = FastAPI(title="Contacto del Club de Robótica")
templates = Jinja2Templates(directory="plantillas")

TRADUCCIONES = {
    "missing": "Este campo es obligatorio.",
    "string_too_short": "El texto es demasiado corto.",
    "string_too_long": "El texto es demasiado largo.",
    "string_type": "Escribe un texto válido.",
    "value_error": "El valor no es válido.",
    "literal_error": "Elige una de las opciones disponibles.",
    "bool_parsing": "Marca la casilla para continuar.",
    "extra_forbidden": "El formulario contiene un campo no permitido.",
}


@app.get("/", response_class=HTMLResponse)
def mostrar_formulario(request: Request) -> HTMLResponse:
    """Pinta el formulario vacío."""
    return templates.TemplateResponse(
        request=request,
        name="contacto.html",
        context={"errores": {}, "valores": {}},
    )


@app.post("/contacto")
def recibir_contacto(datos: Annotated[Contacto, Form()]) -> RedirectResponse:
    """Valida, atiende y redirige (patrón POST-Redirect-GET)."""
    print(f"Contacto recibido: asunto={datos.asunto}")
    return RedirectResponse(url="/gracias", status_code=303)


@app.get("/gracias", response_class=HTMLResponse)
def mostrar_gracias(request: Request) -> HTMLResponse:
    """Página de confirmación, ya sin datos del formulario."""
    return templates.TemplateResponse(request=request, name="gracias.html")


@app.exception_handler(RequestValidationError)
async def errores_de_validacion(
    request: Request, exc: RequestValidationError
) -> HTMLResponse:
    """Devuelve el formulario con los valores y los errores en español."""
    errores: dict[str, str] = {}
    for error in exc.errors():
        campo = str(error["loc"][-1])
        if campo == "correo":
            errores[campo] = "Escribe un correo válido, por ejemplo ana@colegio.edu.co."
        elif campo == "acepta":
            errores[campo] = "Debes aceptar para enviar el mensaje."
        elif campo == "sitio":
            errores[campo] = "El formulario no pasó la comprobación antispam."
        else:
            errores[campo] = TRADUCCIONES.get(error["type"], "Revisa este campo.")

    formulario = await request.form()
    return templates.TemplateResponse(
        request=request,
        name="contacto.html",
        context={"errores": errores, "valores": formulario},
        status_code=422,
    )
Precisión — await request.form() dentro del manejador

El manejador necesita los valores que el usuario escribió para volver a pintarlos. Starlette guarda el formulario ya leído en la petición, así que await request.form() los devuelve sin consumir el cuerpo otra vez. El resultado es un FormData que se comporta como un diccionario: en la plantilla se usa valores.get("nombre", "").

5.9 · Antes de dar la actividad por terminada

  1. El formulario se abre en / y llega a /contacto con POST.
  2. Un envío válido responde 303 y muestra /gracias.
  3. Un envío inválido responde 422 y vuelve a pintar el formulario con los valores.
  4. Los mensajes de error están en español y aparecen junto al campo que falló.
  5. El campo sitio existe, está oculto y no se puede ver con Tab.
  6. La consola del servidor registra el asunto, no el contenido del mensaje.
Advertencia — los tres fallos más comunes de esta actividad

Uno: el campo del HTML se llama correo y el modelo espera email; el 422 dice «missing» y el formulario parece roto. Dos: el formulario no tiene enctype y se intenta subir un archivo; el archivo llega como texto. Unidad 06 · La respuesta

Errores que se entienden y éxito que no se repite

Un 422 en inglés es una prueba de que el servidor está funcionando. También es una mala experiencia. Esta unidad traduce los errores, los coloca junto al campo que falló y convierte el éxito en una redirección que no reenvía el mensaje al recargar.

6.1 · El mensaje que ve el usuario no es el 422

El cuerpo de errores de FastAPI está diseñado para quien programa: tiene type, loc, msg e input. Un estudiante de once que escribe su nombre con dos letras no necesita saber que el tipo es string_too_short; necesita leer «El nombre debe tener al menos 3 caracteres» debajo del campo.

El mismo error, contado para dos públicos
Para quien programaPara quien escribe
{"type": "string_too_short", "loc": ["body", "nombre"], "ctx": {"min_length": 3}} «El nombre debe tener al menos 3 caracteres.»
{"type": "value_error", "loc": ["body", "correo"]} «Escribe un correo válido, por ejemplo ana@colegio.edu.co.»
{"type": "literal_error", "loc": ["body", "asunto"]} «Elige una de las opciones disponibles.»
Distinción — traducir no es ocultar

Un mensaje claro dice qué pasó y cómo corregirlo. No dice «error de validación» ni «datos inválidos»: eso no ayuda a nadie. Tampoco revela detalles internos como el nombre de la columna de la base de datos o la ruta del archivo. La regla es sencilla: lo suficiente para corregir, nada más de lo necesario.

6.2 · El manejador, línea por línea

El manejador de la unidad 5 es corto, pero cada línea tiene una razón. Esta es la versión comentada.

main.py — el manejador de errores explicado 
@app.exception_handler(RequestValidationError)
async def errores_de_validacion(
    request: Request, exc: RequestValidationError
) -> HTMLResponse:
    """Devuelve el formulario con los valores y los errores en español."""

    # 1. Un diccionario campo -> mensaje. La plantilla lo consulta por nombre.
    errores: dict[str, str] = {}

    # 2. exc.errors() trae un error por cada regla incumplida.
    for error in exc.errors():
        # 3. loc es ("body", "nombre"); el último elemento es el campo.
        campo = str(error["loc"][-1])

        # 4. Los mensajes se eligen por campo y por tipo, no por el texto en inglés.
        if campo == "correo":
            errores[campo] = "Escribe un correo válido, por ejemplo ana@colegio.edu.co."
        elif campo == "acepta":
            errores[campo] = "Debes aceptar para enviar el mensaje."
        elif campo == "sitio":
            errores[campo] = "El formulario no pasó la comprobación antispam."
        else:
            errores[campo] = TRADUCCIONES.get(error["type"], "Revisa este campo.")

    # 5. Los valores que el usuario escribió, para no perderlos.
    formulario = await request.form()

    # 6. Se vuelve a pintar el formulario, con 422, no con 200.
    return templates.TemplateResponse(
        request=request,
        name="contacto.html",
        context={"errores": errores, "valores": formulario},
        status_code=422,
    )
Por qué loc[-1]
La ruta completa es ["body", "nombre"]. El último elemento es el nombre del campo, que es lo que la plantilla usa para decidir dónde pintar el error. Si algún día hay modelos anidados, la ruta puede ser más larga; el último elemento sigue siendo el campo.
Por qué un diccionario
La plantilla necesita responder «¿hay error en correo?». Un diccionario lo responde en una línea; una lista obligaría a recorrerla en cada campo.
Por qué TRADUCCIONES.get(...)
El tipo es un identificador estable; el texto en inglés puede cambiar entre versiones de Pydantic. Traducir por tipo es más robusto que buscar frases.
Por qué 422
La petición está bien construida, pero su contenido no se puede procesar. 400 se reserva para peticiones mal formadas; 422 comunica «entiendo la forma, pero los datos no cumplen».

La plantilla de la actividad ya hace lo importante: conserva el valor, marca el campo y pinta el mensaje. Estas son las tres piezas que hay que mirar con lupa.

Devuelve al usuario lo que escribió. Sin esto, un error en el último campo obliga a reescribir todo el formulario, que es la forma más rápida de perder un mensaje.
aria-invalid="true"
Le dice al lector de pantalla que el campo tiene un problema. No cambia el aspecto por sí solo; el CSS puede usar [aria-invalid="true"] para resaltarlo.
aria-describedby="error-correo"
Asocia el campo con el texto del error. Al enfocar el campo, el lector anuncia también el mensaje. El id del span tiene que coincidir exactamente.
role="alert"
Hace que el mensaje se anuncie en cuanto aparece. Se usa con moderación: si hay diez alertas a la vez, el lector se vuelve un ruido.

6.5 · El patrón PRG: éxito sin reenvíos

Después de un POST exitoso, la respuesta no es una página: es una redirección. El navegador hace un GET a /gracias y la barra de direcciones cambia. Si el usuario recarga, recarga el GET, no el POST. El mensaje no se envía dos veces.

Advertencia — no redirijas cuando hay errores

Una tentación frecuente es redirigir siempre y mostrar los errores con un mensaje flash. Para un formulario pequeño es peor: el usuario pierde lo que escribió y el error queda lejos del campo. La regla es: éxito redirige, error vuelve a pintar. El código 422 es parte de la respuesta del formulario, no una página aparte.

6.6 · Seguridad y privacidad en el formulario

Escapar la salida
Jinja2 escapa por defecto en las plantillas .html. No uses |safe con datos del usuario: un mensaje con <script> se ejecutaría en el navegador de quien lo lea. Escapar es la defensa principal contra XSS.
Limitar la entrada
Un máximo de 800 caracteres no es una molestia: es una defensa contra el agotamiento de memoria y contra mensajes imposibles de moderar. El límite se pone en el modelo, no solo en el HTML.
No registrar de más
El asunto basta para saber que llegó un contacto. Guardar el mensaje completo en los registros del servidor es un riesgo de privacidad y no ayuda a depurar. Si se guarda, que sea en la base de datos y con acceso restringido.
Honeypot y ritmo
Un campo invisible y un límite de envíos por minuto reducen el spam. El honeypot se implementa en el modelo; el límite de ritmo se hace en el servidor o en un proxy, y se estudia más adelante.
CSRF, cuando hay sesión
Si el formulario viaja con una cookie de sesión, otro sitio podría enviarlo en nombre del usuario. Ahí hace falta un token CSRF. Un formulario público de contacto no tiene ese problema, pero conviene saber que existe.
EmailStr no verifica el buzón
Comprueba la forma, no la existencia. La única prueba de que el correo funciona es enviar un mensaje de confirmación. No prometas en la página que el correo «es válido»: promete que tiene forma de correo.

Precisión — follow_redirects=False

Por defecto, TestClient sigue las redirecciones y la prueba vería el 200 de /gracias, no el 303. Con follow_redirects=False se comprueba el código real y la cabecera Location. Es la diferencia entre probar «la página final» y probar «la decisión del servidor».

7.3 · El registro que no guarda el mensaje

En la actividad se usa un print para ver que la ruta se ejecutó. En el taller se cambia por el módulo logging, que permite niveles y destinos. Lo importante no es la herramienta: es qué se escribe. El asunto sirve para saber que llegó un contacto; el mensaje y el correo son datos de una persona.

main.py — un registro útil y discreto 
import logging

logger = logging.getLogger("contacto")


@app.post("/contacto")
def recibir_contacto(datos: Annotated[Contacto, Form()]) -> RedirectResponse:
    # Sirve para saber que llegó un contacto sin guardar datos personales.
    logger.info("Contacto recibido: asunto=%s", datos.asunto)
    return RedirectResponse(url="/gracias", status_code=303)
Advertencia — print no es un registro

print escribe en la salida estándar y desaparece cuando el servidor corre como servicio. logging permite niveles, formato y destino. Pero el cambio no es solo técnico: un print(f"{datos.nombre}: {datos.mensaje}") deja el mensaje completo en los registros, donde cualquiera con acceso al servidor puede leerlo. El asunto es suficiente.

7.5 · Síntesis: siete ideas para llevarse

01

Un formulario es una frontera: todo lo que entra por él es texto, es opcional y es sospechoso hasta que el servidor lo demuestra.

02

El atributo name es el que viaja; el id solo sirve para la etiqueta y el CSS. Un campo sin name no existe para el servidor.

03

La validación del navegador es una cortesía; la del servidor es una garantía. Las dos se escriben, pero solo una decide.

04

422 no es un error del programa: es la respuesta correcta cuando el contenido no cumple el contrato.

05

Un buen error dice qué pasó y cómo corregirlo, aparece junto al campo y conserva lo que la persona ya había escrito.

06

Después de un POST exitoso, redirigir con 303 evita que recargar envíe el mensaje dos veces.

07

Las pruebas con TestClient convierten las reglas del formulario en algo que se puede comprobar en segundos, no en una promesa.
