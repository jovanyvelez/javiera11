Unidad 01 · La pieza nueva

El modelo que también es la tabla

Hasta ahora, un modelo de Pydantic era un validador: comprobaba que el formulario viniera bien. A partir de ahora será algo más: la definición de la tabla. Una sola clase describirá las columnas, los tipos y la clave primaria.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: un modelo con table=True

1.1 · La clase que lo cambia todo

Mira las dos definiciones de la clase 10, la que usabas para validar el formulario de alta. Ahora la misma, con una palabra de diferencia.

ejemplo — el mismo modelo, dos veces 
# ANTES (clase 10): un modelo que valida el formulario
class ProductoActualizar(BaseModel):
    nombre: str = Field(min_length=1, max_length=100)
    precio: float = Field(gt=0)
    cantidad: int = Field(ge=0)


# AHORA: el mismo modelo, y además la tabla
class Producto(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True, min_length=1, max_length=100)
    precio: float = Field(gt=0)
    cantidad: int = Field(ge=0)
    descripcion: str | None = None

Lo único que ha cambiado es la base: SQLModel en vez de BaseModel, y el table=True detrás. Con eso, esa clase deja de ser «un validador» y pasa a ser «la tabla productos».

Qué significa cada palabra nueva
Se escribeLe dice a la base de datosPor qué importa
table=True «Esta clase es una tabla» Sin esto, la clase solo valida; con esto, define las columnas
primary_key=True «Esta columna es la clave primaria» La columna que identifica cada fila y no se repite
index=True «Pon un índice en esta columna» Buscar por nombre o por id será rápido en vez de un barrido entero
default=None «Esta columna puede venir vacía» Necesario para el id: lo pone la base de datos

1.2 · El id que pone la base de datos

Precisión — por qué int | None y no int

La clave primaria se declara como int | None, no como int. Parece un detalle tipográfico, pero es una decisión de diseño: en Python puedes crear el objeto sin id, porque en ese momento todavía no existe. Se lo inventa la base de datos al guardarlo.

SQLModel lo entiende y además define la columna como un entero que no puede ser nulo en la tabla: puede faltar en Python, pero una vez guardado, siempre tiene valor.

ejemplo — el id se inventa al guardar, no antes 
from sqlmodel import Session, SQLModel

producto = Producto(nombre="Teclado mecánico", precio=189900, cantidad=7)
print(producto.id)      # None: todavía no existe

with Session(engine) as session:
    session.add(producto)
    session.commit()
    session.refresh(producto)

print(producto.id)      # 1: ahora sí, y lo puso la base de datos

1.3 · Lo que el modelo le dice a la tabla

Con el modelo escrito, la tabla se describe sola. Puedes ver exactamente qué columnas habrá y de qué tipo, sin adivinar:

ejemplo — el esquema que sale del modelo 
CREATE TABLE producto (
    id          INTEGER NOT NULL PRIMARY KEY,
    nombre      VARCHAR NOT NULL,
    precio      FLOAT NOT NULL,
    cantidad    INTEGER NOT NULL,
    descripcion VARCHAR
)
CREATE INDEX ix_producto_nombre ON producto (nombre)
Aplicación — por qué esto no es «magia»

No adivinas: traducen. El str se vuelve VARCHAR, el float se vuelve FLOAT, el int | None con primary_key=True se vuelve INTEGER NOT NULL PRIMARY KEY. La diferencia con la clase 8 es que allí escribías el CREATE TABLE a mano y el modelo por separado: dos fuentes de verdad que se podían desincronizar. Aquí hay una sola.

Advertencia — «el esquema nace del código» no significa «el esquema no cambia»

Si mañana añades una columna al modelo, create_all() no la añade a una tabla que ya existe: solo crea las tablas que faltan. Cambiar el esquema de una base de datos que ya tiene datos es un problema aparte, y tiene nombre: migraciones. Lo veremos en la clase 19; el tutorial oficial también las aplaza y las mentions como el paso siguiente.

Unidad 02 · La conexión

El motor y las tablas

El motor es el objeto que sabe cómo hablar con la base de datos. En la clase 8 lo llamaste «pool de conexiones»; aquí tiene un nombre propio y una diferencia importante: un motor no guarda conexiones, las fabrica.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: un motor y las tablas creadas al arrancar

2.1 · El motor

El motor se crea con create_engine(). Necesita dos cosas: la URL de la base de datos y, en el caso de SQLite, un ajuste que evita un error muy confuso.

ejemplo — el motor 
from sqlmodel import create_engine

# SQLite es un solo archivo: no hay servidor que levantar
sqlite_file_name = "database.db"
sqlite_url = f"sqlite:///{sqlite_file_name}"

# Esta línea solo hace falta con SQLite.
connect_args = {"check_same_thread": False}

engine = create_engine(sqlite_url, connect_args=connect_args)
Precisión — qué es check_same_thread

Por defecto, SQLite dice: «una conexión no se puede usar desde dos hilos a la vez». En FastAPI, una sola petición puede tocar la base de datos desde más de un hilo (por ejemplo, si una dependencia y la ruta usan la misma conexión). Con False se levanta esa prohibición.

Y aquí está la buena noticia: esa línea desaparece con PostgreSQL. No es una peculiaridad de FastAPI, es una peculiaridad de SQLite, que es un motor de un solo archivo pensado para uso local. En cuanto passes a un servidor de verdad, se borra.

2.2 · Crear las tablas

Con el motor listo, las tablas se crean a partir de los modelos. Una sola función se encarga:

ejemplo — crear las tablas 
def create_db_and_tables() -> None:
    """Crea las tablas de todos los modelos de tabla."""
    SQLModel.metadata.create_all(engine)

SQLModel.metadata es el registro donde SQLModel guarda todos los modelos que llevan table=True. create_all() recorre ese registro y crea en la base de datos las tablas que falten. Si la tabla ya existe, no hace nada.

2.3 · Cuándo crearlas: al arrancar la aplicación

Las tablas tienen que existir antes de la primera petición. El sitio para hacerlo es el arranque de la aplicación, y el curso ya te enseñó cómo: con lifespan.

ejemplo — el arranque 
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Al arrancar la aplicación se crean las tablas.
    create_db_and_tables()
    yield
    # Al apagarla, aquí se cerraría el pool. Con SQLite no hace falta.


app = FastAPI(title="TechStore", lifespan=lifespan)
Nota — el tutorial oficial usa otra cosa

El tutorial de FastAPI crea las tablas con @app.on_event("startup"). En nuestra clase 8 ya aprendiste que ese patrón está de salida: la forma moderna es lifespan, que además permite cerrar cosas al apagar. Lo que ves aquí es el tutorial actualizado, no el publicado.

2.4 · Cambiar de SQLite a PostgreSQL

Cuando la tienda crezca de verdad, el archivo database.db se quedará corto. El cambio completo son tres líneas:

ejemplo — el mismo motor, otro motor de base de datos 
# ANTES (SQLite, un archivo)
sqlite_url = "sqlite:///database.db"
connect_args = {"check_same_thread": False}
engine = create_engine(sqlite_url, connect_args=connect_args)

# DESPUÉS (PostgreSQL, un servidor)
postgresql_url = "postgresql://usuario:clave@localhost:5432/techstore"
engine = create_engine(postgresql_url, pool_pre_ping=True)
Aplicación — la primera ventaja del ORM

Compáralo con la clase 8: allí el cambio de motor significaba reescribir el DSN, revisar los tipos de columna y tocar el código de la conexión. Aquí el ORM ya traduce los tipos de Python a los de cada motor: str es VARCHAR en los dos, pero el Decimal de los precios se traduce solo. El modelo es el mismo; el motor se decide en un archivo.

Unidad 03 · La idea central

La sesión: la unidad de trabajo

Una conexión abre la puerta a la base de datos. Una sesión es el espacio de trabajo: recuerda lo que has cambiado, y decide si eso se guarda o se tira. Es el concepto más importante del ORM y el que más cuesta hasta que «suena» la explicación.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el simulador de la sesión, funcionando

3.1 · La diferencia entre conexión y sesión

Con asyncpg (clase 8) tenías una conexión: un canal por el que mandabas consultas. Con el ORM tienes una sesión, que es una conexión con memoria. En esa sesión viven los objetos que has tocado, y hay tres palabras que deciden qué pasa con ellos.

Las tres palabras de la sesión
PalabraQué haceSi no la escribes
add() Deja el objeto pendiente dentro de la sesión El objeto se queda en memoria y se pierde al cerrar
commit() Escribe de verdad en la base de datos Nada se guarda: el cambio se pierde
refresh() Relee el objeto desde la base de datos El objeto en memoria puede quedar desfasado
Precisión — por qué hace falta refresh()

Porque la base de datos puede hacer cosas que tú no pediste. El caso típico: tú creas un producto sin id y la base de datos le asigna el 1. Tu objeto en memoria sigue con id=None, porque nadie le ha dicho que la base de datos decidió. refresh() es esa llamada: «vuelve a leerlo y actualiza el objeto».

3.2 · La dependencia que abre la sesión

La sesión se abre y se cierra sola, una por petición. En FastAPI eso es una dependencia con yield, y el curso ya te enseñó la forma exacta en la clase 8:

ejemplo — la dependencia de sesión 
from typing import Annotated

from fastapi import Depends
from sqlmodel import Session


def get_session():
    """Abre una sesión, la cede y la cierra al terminar la petición."""
    with Session(engine) as session:
        yield session


SessionDep = Annotated[Session, Depends(get_session)]

El with es la clave: si la petición termina bien, la sesión se cierra; si falla a mitad, el with deshace lo que no se había confirmado. Es el rollback implícito, y por eso es imposible dejar la base de datos a medias.

Aplicación — el mismo yield de la clase 8

Fíjate: es exactamente el mismo patrón que aprendiste en la clase 8 con get_connection(). Cambia lo que se cede (una conexión frente a una sesión) y nada más. Esa es una de las razones por las que el curso empieza por la conexión y no por el ORM: la forma ya la conoces.

3.3 · Laboratorio: la máquina de la sesión

Antes de leer más código, recorre una petición real. Pulsa Avanzar para ver cómo la sesión va guardando el trabajo, y pulsa Forzar un fallo para ver qué pasa cuando algo se rompe antes del commit.

Laboratorio

La máquina de la sesión

Cada petición abre una sesión, la llena de cambios y decide si se confirman. Avanza paso a paso, o inyecta un fallo antes del commit para ver el rollback.

Nota — lo que tienes que salir sabiendo

Tres cosas: que add() no guarda nada; que commit() es el punto sin retorno; y que si algo falla antes del commit, la base de datos ni se entera. Ese último punto es el que hace que una API sea fiable: un error a mitad de una petición nunca deja datos a medias.

5.1 · El enunciado

Ejercicio

Las cuatro operaciones, sin SQL

Escribe la aplicación del CRUD con el ORM. Tienes el motor, el modelo y la dependencia de sesión de las unidades anteriores: solo faltan las rutas.

Ficha del sistema

Entrada Un cuerpo JSON con nombre, precio, cantidad y descripcion
Salida JSON con los datos del producto y su id
Restricción Ninguna ruta escribe SQL: todo pasa por la sesión
Restricción Una sola sesión por petición, entregada por SessionDep
Restricción Si el id no existe, la respuesta es un error 404

Requisitos

  1. POST /productos/: crea el producto, lo guarda con add + commit + refresh, y lo devuelve.
  2. GET /productos/: devuelve la lista, con offset y limit como en la clase 9.
  3. GET /productos/{producto_id}: devuelve uno, o un error 404 con el mensaje «Producto no encontrado».
  4. DELETE /productos/{producto_id}: lo borra y devuelve {"ok": true}.
  5. Que el id lo ponga la base de datos: si el cuerpo no trae id, la respuesta trae el que la base de datos generó.
  6. Que el orden de las operaciones sea siempre el mismo: add → commit → refresh. Nunca al revés.

Modelo de respuesta

La diferencia con las clases 9 a 13 está en qué se le pide a la base de datos. Ya no escribes la consulta: describes qué quieres y el ORM la traduce.

app.py — las cuatro rutas con ORM 
from typing import Annotated

from fastapi import FastAPI, HTTPException, Query
from sqlmodel import select

from modelos import Producto
from dependencias import SessionDep

app = FastAPI(title="TechStore")


@app.post("/productos/")
def crear_producto(producto: Producto, session: SessionDep) -> Producto:
    """Crea un producto y lo guarda."""
    session.add(producto)
    session.commit()
    session.refresh(producto)
    return producto


@app.get("/productos/")
def leer_productos(
    session: SessionDep,
    offset: int = 0,
    limit: Annotated[int, Query(le=100)] = 100,
) -> list[Producto]:
    """Devuelve la lista de productos."""
    productos = session.exec(select(Producto).offset(offset).limit(limit)).all()
    return productos


@app.get("/productos/{producto_id}")
def leer_producto(producto_id: int, session: SessionDep) -> Producto:
    """Devuelve un producto, o un 404 si no existe."""
    producto = session.get(Producto, producto_id)
    if not producto:
        raise HTTPException(status_code=404, detail="Producto no encontrado")
    return producto


@app.delete("/productos/{producto_id}")
def borrar_producto(producto_id: int, session: SessionDep):
    """Borra un producto."""
    producto = session.get(Producto, producto_id)
    if not producto:
        raise HTTPException(status_code=404, detail="Producto no encontrado")
    session.delete(producto)
    session.commit()
    return {"ok": True}

La línea que más se olvida es session.get(Producto, producto_id): es el equivalente exacto de SELECT ... WHERE id = $1 de la clase 9. Y el if not producto es el 404: la clase 12 ya te enseñó a distinguir «no existe» de «hay un problema».

Mira la última línea: el esquema de Producto incluye id. Como el POST usa ese mismo modelo, el cliente puede mandar un id… y sobrescribir un producto que ya existe. Y como el modelo también incluye los campos internos, el cliente ve todo lo guardado.

La API funciona. Pero tiene una puerta abierta de par en par, y el ejercicio 7 y la clase 19 van a cerrarla.

Aplicación — lo que es una API

Una API es un contrato: esto es lo que acepto, esto es lo que devuelvo, y esto es lo que pasa cuando te equivocas. La documentación de /docs no es un adorno: es el contrato escrito y actualizado por el propio código. Si cambias el modelo, la documentación cambia sola. Nadie tiene que acordarse de actualizar un Word.

las seis comprobaciones del taller

7.3 · Síntesis: siete ideas para llevarse

01

Un table=True convierte una clase en la definición de una tabla: el esquema nace del código.

02

El id se declara int | None porque lo inventa la base de datos al guardar, no el programa al crear.

03

El motor sabe fabricar conexiones; la sesión es una conexión con memoria de lo que has cambiado.

04

add() no guarda nada: commit() es el punto sin retorno, y refresh() pone al día el objeto.

05

Una sesión por petición, entregada por una dependencia: si algo falla, se deshace sola.

06

El 404 lo escribes tú; el 422 lo genera FastAPI. No todos los errores se escriben igual.

07

Una API es un contrato, y la documentación se escribe sola a partir del código. Pero un solo modelo deja puertas abiertas.

7.4 · Puente hacia la próxima clase

Tu API funciona: crea, lista, lee y borra. Y funciona de la manera más simple posible: con un solo modelo para todo.

Ese modelo único tiene dos agujeros abiertos, y los dos son de seguridad:

  1. El id lo puede elegir el cliente. Si alguien manda id=99 al crear, puede sobrescribir el producto que ya tiene ese identificador.
  2. Todos los campos guardados se devuelven. Hoy no hay ningún campo interno, así que no se nota. En cuanto lo haya —el precio de compra, la nota interna, el proveedor— saldrá en la respuesta.

La próxima clase arregla las dos cosas separando lo que entra de lo que sale. Y para eso hay una herramienta que no conocías: la herencia de modelos.
