0.2 · El problema no es el código: es dónde vive

Distinción — un archivo largo no es lo mismo que un código malo

El código de tu main.py es correcto. Funciona, pasa las comprobaciones y no tiene un solo error. El problema es otro: cuando todo vive en el mismo sitio, cualquier cambio toca el mismo archivo.

Concretamente: para corregir el precio de un producto tienes que abrir doscientas líneas, encontrar la función correcta entre once, y rezar por no pisar la de al lado. Para saber qué hace la aplicación entera, hay que leerla entera. Y para que otra persona toque el repositorio sin romperte las rutas, no hay manera: todo está en el mismo archivo y todo es el mismo problema.

0.4 · La idea central de la clase

La idea cabe en una frase: un router por archivo, y una aplicación que solo sabe unirlos. Ni más ni menos. Todo lo demás —las carpetas, los prefijos, las dependencias— son consecuencia de esa frase.

ejemplo — el antes y el después de la misma aplicación 
# ANTES: un archivo, seis responsabilidades
main.py  "(213 líneas: config, base de datos, modelos, consultas, rutas…)"

# DESPUÉS: cada archivo con una responsabilidad, y uno que solo las une
app/
├── main.py            # 12 líneas: crea FastAPI e incluye los routers
├── config.py          # la configuración
├── database.py        # el pool de conexiones
├── esquemas.py        # los modelos
├── repositorio.py     # las consultas
├── dependencias.py    # las dependencias compartidas
└── routers/
    └── productos.py   # las rutas de productos
Nota — esto no es «programación modular» abstracta

Hay una diferencia entre esto y el tema teórico de los módulos. Aquí no se trata de que el código «sea más elegante», sino de algo muy concreto: tus rutas dejan de poder romper tu repositorio, y tú puedes cambiar el pool de conexiones sin tocar una sola línea de las rutas. Esa es la prueba de que la separación sirve.

Unidad 01 · La pieza nueva

El APIRouter: un router por archivo

La herramienta que hace posible toda la clase cabe en dos palabras: APIRouter. Es un grupo de rutas con nombre propio, que vive en un archivo propio y que después la aplicación principal incluye. Esta unidad la presenta y muestra el cambio exacto que produce.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: un router propio y la app que lo incluye

1.1 · Qué es un APIRouter

FastAPI tiene dos cosas que se parecen mucho: la aplicación app y el router router. Los dos se declaran igual, con una línea:

ejemplo — la misma línea, dos objetos distintos 
from fastapi import APIRouter, FastAPI

app = FastAPI(title="TechStore")   # la aplicación completa
router = APIRouter()                          # un grupo de rutas
La diferencia entre la aplicación y el router
FastAPI()APIRouter()
Es La aplicación que se arranca Un trozo de la aplicación
Vive en app/main.py, normalmente Un archivo por módulo, dentro de routers/
Se usa con uvicorn app.main:app app.include_router(router)
Declara rutas con @app.get(...) @router.get(...)
Se puede incluir en Nada: es la raíz Una aplicación y otro APIRouter

1.2 · El cambio: de @app.get a @router.get

Pasar de un archivo gigante a un proyecto con carpetas empieza con un cambio de tres caracteres. En cada archivo de rutas, se sustituye @app por @router:

ejemplo — app/routers/productos.py 
from fastapi import APIRouter, Request
from fastapi.templating import Jinja2Templates

from ..dependencias import ConnectionDep
from ..repositorio import obtener_productos

# El router se declara una vez, con su nombre
router = APIRouter()
templates = Jinja2Templates(directory="templates")


@router.get("/productos")
async def listar_productos(request: Request, conn: ConnectionDep):
    """Muestra la página con la lista de productos."""
    productos = await obtener_productos(conn)
    return templates.TemplateResponse(
        request=request,
        name="productos.html",
        context={"productos": productos},
    )
Precisión — el router no es un archivo, es un objeto

Fíjate en que router = APIRouter() es una variable que vive en el módulo. Eso no es un detalle: es lo que permite que el archivo del router sea importado y que su router se pase a la aplicación. Es el mismo mecanismo que en la clase 6, cuando una función devolvía un valor y quien la llamaba decidía qué hacer con él.

1.3 · La aplicación que solo arma

Y el main.py nuevo se queda con muy poco:

ejemplo — app/main.py 
from fastapi import FastAPI

from .routers import productos

app = FastAPI(title="TechStore")

# Una línea por router: aquí solo se une, no se programa
app.include_router(productos.router, prefix="/api", tags=["productos"])
Aplicación — el archivo que se lee en diez segundos

Un main.py de doce líneas se lee entero y se entiende entero: esto es la aplicación, esto es lo que incluye. Si mañana hay diez módulos más, serán diez líneas más. Ese es el objetivo: que el archivo de arranque no crezca con el proyecto, sino que siga siendo una lista de piezas.

1.4 · Qué gana y qué cuesta

El balance honesto de dividir el archivo
Se ganaSe cuesta
Cada archivo se puede leer solo Hay que escribir imports y acordarse de la ruta
Un error en las consultas no tumba las rutas Un error de import sí tumba el arranque
Dos personas pueden tocar archivos distintos Hay que pactar qué archivo hace qué
El repositorio se puede probar sin el servidor Las rutas pierden acceso directo a las variables de su archivo
La documentación se separa por router Hay que recordar include_router al añadir un módulo
Advertencia — la respuesta de un import

En un solo archivo, una función puede usar cualquier variable que haya arriba. Al dividir, eso deja de ser automático: si productos.py usa templates y no lo importa, el error aparece al arrancar, no al escribir. Es el precio de la separación, y se paga una sola vez: en la primera clase, cuando el ImportError te enseñe exactamente qué falta.

Qué archivo va en cada carpeta

Un APIRouter por archivo no basta: si los archivos se nombran al azar, el proyecto sigue siendo ilegible. Esta unidad define tres responsabilidades y muestra a qué archivo corresponde cada cosa, más la regla que decide qué archivos pueden importarse entre sí.

2.2 · Las tres responsabilidades

Siete archivos, pero solo tres preguntas. Y cada archivo responde a una:

Las tres responsabilidades y sus archivos
ResponsabilidadLa pregunta que respondeArchivos
Las rutas «¿Qué pasa cuando alguien pide esta URL?» routers/productos.py
La lógica «¿Qué reglas se aplican a los datos y cómo se guardan?» esquemas.py, repositorio.py
La infraestructura «¿De dónde sale la conexión y de dónde la configuración?» config.py, database.py, dependencias.py
Nota — por qué «routers» y no «productos»

La carpeta se llama routers/ y no productos/ porque lo que agrupa sus archivos no es la entidad, sino el tipo de cosa que hacen. Dentro de routers/ puede haber productos.py, ventas.py, usuarios.py… y todos son rutas. Si la carpeta se llamara productos/, el día que llegue ventas tendrías que crear una carpeta con el mismo nombre y acabarías con productos/productos.py.

2.3 · La regla de las importaciones

La estructura no es solo dónde va cada archivo: es hacia dónde puede mirar cada archivo. Y esa regla es una pirámide, no una red.

Capa 3
La infraestructura

config.py, database.py y dependencias.py no saben nada del dominio.

Advertencia — el import que rompe la pirámide

La forma más común de arruinar la estructura es que repositorio.py importe de routers/productos.py: «es que necesito la plantilla de aquí». En ese momento las dos capas quedan atadas, el repositorio deja de poder probarse solo y el día que quieras reutilizarlo en otro proyecto no podrás.

La salida es siempre la misma: copia el dato que necesitas hacia abajo, no lo que necesitas hacia arriba. Si el repositorio necesita la plantilla, lo que necesita es el contenido, no el archivo que lo pinta.

2.4 · __init__.py: el detalle que lo hace posible

En Python, una carpeta no es un paquete automáticamente: necesita un archivo __init__.py dentro. Puede estar vacío.

ejemplo — las dos formas de importar 
# Desde app/main.py: el punto significa «dentro de mi paquete»
from .routers import productos

# Desde app/routers/productos.py: dos puntos para subir un nivel
from ..dependencias import ConnectionDep
from ..repositorio import obtener_productos

# Con el punto inicial, el proyecto se puede mover a cualquier carpeta
# y seguir funcionando. Sin él, solo funciona desde la raíz.
Precisión — el error que da el tutorial cuando falta

Si olvidas el __init__.py en app/routers/, el from .routers import productos falla con un ModuleNotFoundError: No module named 'app.routers'. El mensaje parece encryption, pero la causa es una: una carpeta sin __init__.py no es un paquete, y sin paquete no hay import que valga.

Unidad 03 · La unión

Unir las piezas con include_router

Ya tienes las piezas en sus archivos. Falta la pieza que las une y decide cómo se llaman por fuera. Esta unidad muestra las cuatro cosas que puedes decidir al incluir un router — prefijo, tags, dependencias y respuestas— y termina con un laboratorio donde repartes tú los archivos.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el organizador de archivos funcionando

3.1 · El prefijo: la dirección pública de tus rutas

En el router, la ruta se escribe sin prefijo: @router.get("/productos"). El prefijo lo decide quien incluye el router. Esto tiene una ventaja práctica: el archivo del router no sabe si sus rutas se van a servir en /productos o en /api/v1/productos.

ejemplo — el prefijo lo pone el que incluye 
# app/routers/productos.py — el archivo no menciona ningún prefijo
@router.get("/productos")
async def listar_productos(request, conn): ...

# app/main.py — aquí se decide cómo se llaman por fuera
app.include_router(productos.router, prefix="/api")

# El resultado: GET /api/productos
terminal — el esquema de la API, que es la prueba
curl http://127.0.0.1:8000/openapi.json | grep -A 1 '"/api/productos"'
"/api/productos": {
"get": { "tags": ["productos"], ... }
 
curl http://127.0.0.1:8000/api/productos -o /dev/null -w '%{http_code}\n'
200

3.2 · Los tags: la documentación se ordena sola

El tag no cambia lo que hace la ruta: cambia cómo aparece en la documentación automática de FastAPI (/docs). Es la manera de que, con veinte rutas, la página siga siendo legible: cada router es un grupo.

Aplicación — el tag es una decisión de arquitectura

Cuando defines los tags por router (tags=["productos"]), el grupo de la documentación coincide con el grupo de archivos. Eso no es casualidad: significa que quien lee /docs y quien abre app/routers/ ven las mismas cosas. Si el tag fuera "API v1" o "datos", esa correspondencia se pierde.

3.3 · Las dependencias: una regla para todo un router

La cuarta pieza es la más útil en la práctica. Puedes colgar una dependencia al incluir el router, y se aplicará a todas sus rutas sin tocar ni una de ellas.

ejemplo — incluir con prefijo, tag, dependencia y respuestas 
from fastapi import Depends, FastAPI

from .dependencias import get_token_header
from .routers import productos

app = FastAPI(title="TechStore")

app.include_router(productos.router, prefix="/api", tags=["productos"])

app.include_router(
    admin.router,
    prefix="/admin",
    tags=["admin"],
    dependencies=[Depends(get_token_header)],
    responses={404: {"description": "No encontrado"}},
)
Las cuatro decisiones que se toman al incluir un router
ParámetroQué decideEjemplo
prefixPor dónde empiezan las rutas/api
tagsEn qué grupo salen en la documentación["productos"]
dependenciesQué se ejecuta antes de cada ruta[Depends(get_token_header)]
responsesQué errores se documentan{404: {...}}
Nota — el mismo router, dos veces

Como include_router no modifica el router original, puedes incluirlo dos veces con prefijos distintos: una para la versión pública y otra para la interna. Es un uso avanzado, pero sirve para entender que el router es un objeto y no una lista fija de rutas.

3.5 · El entrypoint: dónde está tu aplicación

Con la aplicación en app/main.py, el comando de arranque tiene que saber dónde buscarla. Se le dice una sola vez, en pyproject.toml:

ejemplo — pyproject.toml 
[project]
name = "techstore"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = ["fastapi[standard]", "asyncpg", "jinja2"]

[tool.fastapi]
entrypoint = "app.main:app"
Precisión — qué significa app.main:app

Es una ruta de importación con dos partes: app.main es el módulo (el archivo app/main.py dentro del paquete app) y app es el objeto que se busca dentro de él (la variable app = FastAPI()). El equivalente escrito a mano sería from app.main import app. Es exactamente la misma idea que include_router, pero en la otra dirección: en vez de incluir un router en la app, la app se encuentra a partir de su ruta.

4.2 · Vocabulario del taller

Estas siete palabras aparecerán en el taller final. Léelas ahora; las definiciones son aproximadas y se afinarán en las unidades siguientes.

Router
Un grupo de rutas con nombre propio: router = APIRouter(). Se declara en un archivo y se incluye en la aplicación.
Prefijo
La parte de la URL que se antepone a todas las rutas de un router: /api.
Tag
La etiqueta que agrupa las rutas en la documentación automática de FastAPI.
Dependencia
Una función que se ejecuta antes de la ruta y que le entrega algo: una conexión, un usuario, un token.
Paquete
Una carpeta con __init__.py. Es lo que hace posible importar de dentro de ella.
Import relativo
Importar usando puntos: . es el paquete actual, .. es el de arriba.
Entrypoint
La ruta donde está tu aplicación: app.main:app en pyproject.toml.

app/main.py — la aplicación entera 
from contextlib import asynccontextmanager

from fastapi import FastAPI

from .config import DATABASE_URL
from .database import db
from .routers import productos


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Al arrancar la aplicación se crea el pool de conexiones.
    await db.connect(DATABASE_URL)
    yield
    # Al apagar la aplicación, el pool se cierra.
    await db.close()


app = FastAPI(title="TechStore", lifespan=lifespan)

# Una línea por router: aquí solo se une, no se programa
app.include_router(productos.router, prefix="/api", tags=["productos"])

Y el database.py también cambia un detalle: ahora importa la configuración con from .config import DATABASE_URL, en vez de leer os.environ en el sitio. La infraestructura habla con la infraestructura; nadie más lee el entorno.

5.2 · La comprobación que importa

Advertencia — si el comportamiento cambia, la repartición está mal

Repartir el código no puede cambiar lo que hace la aplicación. Si antes de repartir tenías GET /productos y después de repartir tienes GET /api/productos, has introducido un cambio de comportamiento sin querer. Y lo mismo con los códigos de respuesta y con el contenido del HTML.

La forma de comprobarlo no es «a ver si funciona»: es comparar el esquema de la API antes y después. Es un archivo JSON que FastAPI genera solo, y que te dice exactamente qué rutas tienes y con qué forma.

Unidad 06 · Taller de aplicación

Ejercicio 6.1 · Prefijos, tags y dependencias

Los archivos ya están repartidos. Ahora decides cómo se ven por fuera: qué prefijo tienen las rutas, en qué grupo salen en la documentación y qué tiene que pasar antes de que una ruta pueda ejecutarse. En 35 minutos le pones las tres cosas a tu proyecto.

⏱ 35 minutos 💻 Ejercicio de desarrollo 🧭 Producto: las rutas bajo /api y con su documentación

6.1 · El enunciado

Ejercicio

La API pública de la tienda

Añade a tu proyecto un segundo router y configura las decisiones de la unidad 3. El objetivo no es «que funcione»: es que la documentación automática de FastAPI (/docs) muestre las rutas agrupadas y con su prefijo, sin tocar una sola línea de las vistas.

Ficha del sistema

Entrada El proyecto estructurado del ejercicio anterior
Salida Dos routers con prefijos y tags distintos, y una dependencia compartida
Restricción Las decisiones se toman en main.py, no dentro del router
Restricción El router nuevo no puede importar nada de main.py: la pirámide manda
Restricción La dependencia se ejecuta antes de la ruta y le entrega un valor

Requisitos

  1. El router de productos incluido con prefix="/api" y tags=["productos"].
  2. Un segundo router en app/routers/ventas.py, con su propio APIRouter y al menos una ruta.
  3. El prefijo /admin para ese segundo router, con su propio tag, sin tocar el archivo del router.
  4. Una dependencia compartida en app/dependencias.py que se aplique a todas las rutas del router de administración.
  5. Las respuestas documentadas: al menos un código de error en el responses del router.
  6. La comprobación: que /openapi.json muestre las dos secciones, con sus prefijos y sus tags.
Pista — el error de la pirámide

Si al crear app/routers/ventas.py te appetitece importar from ..main import app para registrar la ruta ahí, no lo hagas: eso es un círculo. El router se registra en main.py, y en ningún otro sitio. Si necesitas datos de la app, pásalos por una dependencia.

Modelo de respuesta

La respuesta son tres archivos. Y fíjate en que main.py es el único que decide: los routers no saben con qué prefijo se van a servir.

app/routers/ventas.py — el segundo router 
from fastapi import APIRouter

from ..dependencias import AdminDep

router = APIRouter()


@router.get("/ventas")
async def listar_ventas(admin: AdminDep):
    """Muestra las ventas. Solo un administrador puede verlo."""
    return {"ventas": [], "quien_lo_pide": admin}
app/dependencias.py — la dependencia compartida 
from typing import Annotated

from fastapi import Depends, Header, HTTPException

async def get_admin(x_token: str = Header(alias="X-Token")) -> str:
    """Exige un token de administrador y devuelve quién es."""
    if x_token != "secreto-admin":
        raise HTTPException(status_code=403, detail="No autorizado")
    return "la administradora"


AdminDep = Annotated[str, Depends(get_admin)]
app/main.py — donde se toman las decisiones 
from fastapi import Depends, FastAPI

from .dependencias import get_admin
from .routers import productos, ventas

app = FastAPI(title="TechStore")

app.include_router(
    productos.router,
    prefix="/api",
    tags=["productos"],
)

app.include_router(
    ventas.router,
    prefix="/admin",
    tags=["administración"],
    dependencies=[Depends(get_admin)],
    responses={403: {"description": "Se necesita un token de administrador"}},
)

Fíjate en el detalle final: la dependencia aparece dos veces, y con dos propósitos distintos. En ventas.py la ruta la pide para usar el valor (y por eso el parámetro admin); en main.py la dependency se cuelga al router para que se ejecute en todas sus rutas. La primera usa el valor; la segunda lo exige.

Aplicación — la dependencia hace el trabajo invisible

Modelo de respuesta

El párrafo del entregable 5 es donde se demuestra que la clase valió la pena. No es una descripción: es un pronóstico. Si puedes decir «cambiaré este archivo y solo este» y es verdad, la estructura está bien.

prueba_repositorio.py — la prueba de independencia 
"""Este archivo no importa FastAPI: solo el repositorio."""

import asyncio

from app.repositorio import obtener_productos


async def main() -> None:
    # Una conexión falsa: el repositorio no sabe de dónde viene.
    class ConexionFalsa:
        async def fetch(self, consulta, *args):
            return [{"id": 1, "nombre": "Teclado mecánico", "precio": 189900, "cantidad": 7, "descripcion": ""}]

    productos = await obtener_productos(ConexionFalsa())
    print(productos)


if __name__ == "__main__":
    asyncio.run(main())

Ese archivo es la mejor prueba de la clase: el repositorio se usa sin FastAPI, sin servidor y sin base de datos. Antes de dividir, eso era imposible: la función de consultas estaba enterrada en un archivo que, al importarse, arrancaba la aplicación entera.

7.3 · Síntesis: siete ideas para llevarse

01

Un APIRouter es un grupo de rutas con nombre propio. Cambiar @app.get por @router.get es todo el truco.

02

La aplicación deja de programar y pasa a unir: un main.py de doce líneas que se lee entero.

03

Las carpetas son por responsabilidad —rutas, lógica, infraestructura— y no por entidad ni por persona.

04

Las importaciones van en una sola dirección: hacia abajo. Un círculo entre capas destruye la reutilización.

05

Un __init__.py vacío convierte una carpeta en un paquete. Sin él, no hay import que valga.

06

El prefijo, el tag y la dependencia se deciden al incluir el router: el archivo de rutas no sabe cómo se llama por fuera.

07

La prueba de que la estructura funciona es poder cambiar una pieza sin tocar las demás. Si no puedes, todavía no está estructurado.

7.4 · Puente: qué sigue después del CRUD

Tu CRUD está completo y, por fin, ordenado: las cuatro operaciones están repartidas en archivos con nombre, la aplicación solo las une y la documentación automática las muestra agrupadas. Ese era el objetivo de las últimas seis clases.

Pero hay algo que sigue pendiente, y es lo que convierte un proyecto escolar en algo que se puede volver a abrir dentro de seis meses:

  1. Un historial de cambios. Ahora mismo, si rompes algo, no hay forma de volver atrás: el único «deshacer» es volver a escribir el archivo a mano. La herramienta para eso la tienes vista en la clase 16: Git.
  2. Un commit que explique cada cambio. «Arreglado» no sirve de nada dentro de seis meses; «muevo el pool a database.py para poder cambiar de motor» sí.
  3. Pruebas que no dependan del navegador. La prueba de la unidad 7 —un archivo que usa el repositorio sin importar FastAPI— es el primer paso. A partir de ahí, la ruta siguiente es automatizar esas pruebas para que se ejecuten solas en cada commit.
Antes de cerrar el curso

Guarda este proyecto completo en un repositorio de Git, con un commit por cada unidad de la clase: uno para la repartición en routers, otro para los prefijos y las dependencias. La clase 16 explica Git en detalle; lo único que necesitas ahora es tener el proyecto en un repositorio y dos commits con mensajes claros.
