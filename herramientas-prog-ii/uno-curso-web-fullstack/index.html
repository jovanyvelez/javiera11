Unidad 00 · Apertura

Por qué una aplicación web es, ante todo, un problema de arquitectura

Esta clase abre el módulo de Herramientas de Programación II. Su propósito no es enseñarte a escribir código, sino darte el marco conceptual que hace legible todo lo que escribirás después: por qué existe un servidor, qué viaja por la red, qué significa «full stack» y dónde termina tu trabajo y empieza el de tu compañero de equipo.

⏱ 20 minutos 📄 Lectura 🧭 Sin entregable

0.1 · El problema de fondo

Abre cualquier aplicación que uses a diario —un messenger, una red social, un sistema de notas— y observarás una sola cosa: una pantalla. Todo lo demás está oculto. Pero detrás de esa pantalla hay, como mínimo, dos equipos distintos que se comunican, un protocolo que fija las reglas de esa comunicación, un proceso en el servidor que decide qué mostrar, y muy probablemente una base de datos donde vive la información.

La distancia entre lo que el usuario ve y lo que realmente ocurre es enorme, y esa distancia es precisamente el objeto de estudio de esta clase. Un estudiante que entiende qué pasa entre el instante en que presiona Enter y el instante en que aparece la respuesta ya no programa «a ciegas»: sabe en qué máquina está el problema, qué capa puede tocar y qué contrato debe respetar.

Nota de encuadre

La arquitectura cliente-servidor no es una invención reciente ni un capricho de las redes sociales. Es la forma en que se organizaron los primeros sistemas de información conectados, y sigue siendo —con variantes— la arquitectura de casi todo lo que usas hoy. Entenderla no te ata a una tecnología: te da el marco para entender cualquier tecnología.

0.2 · Propósito, alcance y límites

Lo que sí estudiamos
El modelo cliente-servidor como forma de organizar un sistema distribuido; la estructura por capas de un servidor; el protocolo HTTP y el ciclo completo de una petición; la frontera de responsabilidades entre frontend y backend.
Lo que dejamos para después
La sintaxis de Python, las rutas de FastAPI, los modelos de Pydantic y el acceso a bases de datos. Nada de eso se entiende sin este marco, y por eso va después.
El supuesto de trabajo
Suponemos que ya sabes lo que es una variable, un tipo de dato, una función y una estructura condicional. Todo lo demás se explica aquí.

Unidad 01 · Marco conceptual

La arquitectura cliente-servidor

Un modelo es una forma de simplificar la realidad sin perder lo esencial. Esta unidad construye el modelo que usaremos durante todo el módulo: qué roles existen, cómo se relacionan y qué propiedades los definen.

⏱ 30 minutos 📄 Lectura y análisis 🧭 Producto: diagrama anotado

1.1 · Por qué hace falta un modelo

Un sistema conectado por red es, por definición, un sistema distribuido: el trabajo se reparte entre máquinas que no comparten memoria, no comparten reloj y, en muchos casos, no están ni en el mismo edificio. Programar así sin un modelo mental es como construir una casa sin planos: se puede hacer, pero cada error cuesta el doble.

El modelo cliente-servidor es la manera más antigua y más extendida de organizar esa distribución. Su intuición central es simple: alguien pide, alguien responde. A partir de ahí, todo lo demás son refinamientos.

1.2 · Las cuatro piezas del modelo

Cliente
El proceso que inicia una interacción esperando un resultado. No produce datos: los solicita. Puede ser un navegador, una aplicación móvil, otro servidor o incluso una línea de comandos.
Servidor
El proceso que atiende solicitudes y produce respuestas. Varias instancias del mismo servidor pueden atender en paralelo. Su trabajo es responder, no decidir quién pregunta.
Red
El medio físico y lógico que transporta los mensajes. Es inherentemente no confiable: los paquetes pueden perderse, llegar duplicados o llegar en desorden. Los protocolos de aplicación existen para sortear esa incertidumbre.
Protocolo
El conjunto de reglas que ambos extremos respetan: qué significa cada mensaje, qué se puede pedir, en qué formato viaja la información y qué hacer cuando algo falla. HTTP es el protocolo que estudiaremos.

1.3 · Una analogía y sus límites

La analogía clásica es la de un restaurante. El cliente es el comensal que se sienta y hace un pedido; el servidor es la cocina que prepara y entrega; el mesero (la red) transporta la comanda y el plato; y el menú (el protocolo) es el acuerdo sobre qué se puede pedir y en qué formato.

Precisión sobre la analogía

La analogía es útil hasta un punto y luego empieza a mentir. Dos diferencias importan: en un restaurante la cocina es una sola y atiende en fila, mientras que un servidor real puede tener muchas instancias trabajando en paralelo; y el mesero nunca pierde una comanda, mientras que la red sí pierde paquetes. Usaremos la analogía para introducir las ideas, no para razonar sobre los detalles.

1.4 · Cuatro propiedades que definen el modelo

Asincronía
El cliente no necesita estar frente al servidor mientras este trabaja: emite la petición, continúa haciendo otras cosas y recibe la respuesta cuando llegue. En un navegador esto significa que la interfaz puede seguir respondiendo mientras una imagen carga.
Ausencia de estado
El servidor no recuerda peticiones anteriores por sí solo. Cada petición es completa en sí misma. Quien necesita recordar algo —el usuario que ha iniciado sesión— debe enviarlo en cada petición, normalmente en una cabecera o en un token.
Direccionalidad
La comunicación se inicia siempre desde el cliente. El servidor nunca toma la iniciativa de hablar por su cuenta en el modelo HTTP clásico; si quiere avisar algo, el cliente debe preguntar (o el servidor debe usar un canal aparte, como las websockets).
Petición / respuesta
Cada interacción tiene la misma estructura: una petición con una intención y una respuesta con un resultado y un estado. Todo lo demás —streaming, websockets, pub-sub— son variantes que reorganizan estas dos piezas.
Nota

«Sin estado» (stateless) no significa que el servidor no pueda tener memoria. Significa que no debe depender de ella para responder correctamente. Un servidor con caché o con sesiones sigue siendo «sin estado» en términos de HTTP, siempre que pueda reconstruir el contexto a partir de lo que el cliente envía.

1.5 · Los roles son relativos, no permanentes

«Servidor» no es una propiedad de una máquina, es un rol dentro de una interacción. Tu navegador es cliente del servidor de la biblioteca. Pero ese mismo servidor, para obtener la lista de libros, es cliente de la base de datos. Y esa base de datos, a su vez, es cliente del servidor de archivos donde se guardan las portadas.

Esta relatividad es la razón por la que «full stack» no significa «programador que sabe todos los idiomas». Significa que entiendes cómo encajan las piezas de ambos lados de la frontera y puedes moverte con soltura entre ellas.

Ejemplo guiado 1.1 — Descomponer una interacción real 6 min

El enunciado es: «Un estudiante escribe https://biblioteca.colegio.edu.co/api/libros en la barra del navegador y presiona Enter. Describe, en orden, quién actúa en cada momento.»

1
El estudiante actúa, no el servidor

Es el único humano en el proceso, y su única acción relevante es iniciar. A partir de aquí todo ocurre entre procesos. Anota esto: el usuario no «entra» a la página; dispara una petición.

2
El navegador actúa como cliente

Interpreta la URL, resuelve el nombre del dominio a una dirección IP, abre una conexión y escribe una petición HTTP. Nótese que el navegador es un programa genérico: no sabe nada de libros. Solo sabe hablar HTTP.

3
La red transporta

Los bytes viajan en paquetes que pueden perderse, duplicarse o llegar desordenados. El protocolo de transporte (TCP) se encarga de reordenarlos y entregarlos íntegros; HTTP, en cambio, no se ocupa de eso: asume que debajo hay un transporte confiable.

4
El servidor recibe y decide

Un servidor web acepta la conexión, lee la petición, la enruta a la función que corresponde y ejecuta la lógica de negocio. En nuestro caso, esa función consulta la base de datos.

Observa: el servidor también es cliente de la base de datos. La cadena de roles no termina en el servidor: continúa.

5
La respuesta vuelve y el navegador la consume

El servidor devuelve un código de estado, unas cabeceras y un cuerpo con los datos en JSON. El navegador recibe ese texto y lo convierte en datos que el JavaScript del frontend puede usar para pintar la lista de libros.

Pregunta de control: ¿en qué momento el estudiante ve por primera vez un libro en pantalla? Razonar esa respuesta ya es trabajo de frontend y lo veremos en la unidad 6.

Aplicación

Escribe en tu cuaderno una tabla de dos columnas con el encabezado «Momento» / «Quién actúa y por qué» y llénala con al menos seis filas a partir de los cinco pasos anteriores. Añade una fila final: «¿qué pasaría si el servidor no respondiera?».

Unidad 02 · Marco conceptual

El servidor y su estructura por capas

En la unidad 1 vimos los dos extremos de la interacción. Ahora abrimos el servidor por dentro: de qué está hecho, en qué capas se organiza y qué ocurre exactamente entre que llega una petición y sale una respuesta.

⏱ 30 minutos 📄 Lectura y análisis 🧭 Producto: traza interna

2.1 · Tres sentidos de la palabra «servidor»

Cuando se dice «el servidor», muchas veces se mezclan tres cosas distintas. Conviene separarlas, porque cada una falla de manera diferente y se repara de manera diferente.

Servidor (equipo)
La máquina física: un computador con CPU, memoria, disco y tarjeta de red. En un centro de datos puede haber miles,worked en conjunto.
Servidor (software)
El programa que atiende peticiones. Hay de distintos tipos: servidores web (Nginx, Apache), servidores de aplicaciones (Uvicorn, Gunicorn), servidores de bases de datos (PostgreSQL).
Servidor (proceso en ejecución)
La instancia concreta del software, corriendo y escuchando en un puerto. Puedes tener varias instancias del mismo software en la misma máquina, cada una en un puerto distinto.
Distinción

«El servidor está caído» puede significar tres cosas distintas: la máquina no está encendida, el software falló al arrancar, o el proceso está vivo pero nadie le está escuchando en el puerto. Diagnosticar bien un sitio web caído empieza por decidir en cuál de las tres capas está el fallo.

2.2 · Las cuatro capas de un servidor de aplicaciones

Un servidor web moderno no es un bloque monolítico: es una pila de capas, cada una con una responsabilidad y una herramienta propia. Entender la pila explica por qué existen tantas piezas distintas en un proyecto real.

Nota

La capa de datos es a su vez un servidor: habla SQL, que es otro protocolo, sobre otro socket, con otras reglas. Ilustra por qué el modelo cliente-servidor se repite: la base de datos es cliente del servidor de archivos que guarda sus datos.

2.3 · Servidor estático y servidor dinámico

La distinción operativa más importante de esta unidad es la que separa un servidor que entrega archivos de uno que produce respuestas.

Aplicación

La página de inicio de un portal educativo puede ser estática y servir muy bien a 800 estudiantes a la vez. En cambio, la pantalla que lista los préstamos de cada estudiante no puede ser estática: depende de quién pregunta. En la práctica, casi todas las aplicaciones reales son mezclas: el frontend se sirve como archivos estáticos y los datos pedidos por JavaScript los produce un servidor dinámico.

2.4 · Qué ocurre dentro del servidor

Cuando una petición llega a la aplicación, se ejecuta siempre una secuencia parecida. Conocerla permite localizar un error con precisión: no todo está en el mismo sitio.

1 EnrutamientoLa aplicación decide qué función corresponde a esa ruta y ese método. «GET /api/libros → listar_libros()».
2 Validación de la entradaSe comprueba que los datos recibidos tengan la forma y el tipo correctos, y se rechazan los que no.
3 Lógica de negocioLas reglas del dominio: ¿puede este estudiante pedir este libro? ¿hay días de retraso?
4 Acceso a datosSe consulta (o se modifica) la base de datos. Ojo: esto es SQL, y SQL no viaja al navegador.
5 Serialización y respuestaLos datos se convierten a JSON, se les asigna un código de estado y se devuelve la respuesta HTTP.
Ejemplo guiado 2.1 — Rastrear una petición dentro del servidor 8 min

Seguimos la petición del ejemplo 1.1, esta vez desde que entra al servidor hasta que sale. Cada paso indica en qué capa ocurre, porque esa es la información que te permitirá diagnosticar.

1
Capa de aplicación — enrutamiento

Llega GET /api/libros. El router de FastAPI busca la función registrada para esa ruta y ese método. Si no encuentra ninguna, la respuesta será un 404; si encuentra la ruta pero no el método, un 405.

Diagnóstico: un 404 con la URL correcta significa, casi siempre, un problema de enrutamiento.

2
Capa de aplicación — validación

La petición es un GET sin cuerpo, así que no hay mucho que validar. Pero imaginemos que fuera POST /api/prestamos: el cuerpo llega como texto JSON y la aplicación comprueba que tenga libro_id, estudiante y dias, y que los tipos sean correctos. Si no lo son, la respuesta es 422.

Diagnóstico: un 422 significa que el problema está en los datos que envió el cliente, no en el servidor.

3
Capa de lógica de negocio

Antes de tocar la base de datos, el código aplica las reglas: «¿el libro está disponible?», «¿el student's penalty no supera el límite?». Estas reglas sólo pueden vivir en el servidor, porque el cliente no es confiable.

4
Capa de datos

La aplicación abre una conexión, ejecuta SELECT * FROM libros WHERE disponible = true y recibe filas. Si la base de datos está caída o la consulta está mal escrita, aquí es donde falla, y el servidor devolverá un 500.

Diagnóstico: un 500 con la base de datos caída es un problema de datos, no de lógica.

5
Capa de serialización

Las filas (que son diccionarios con tipos de SQL) se convierten a JSON, se añade la cabecera Content-Type: application/json y se responde 200 OK. El navegador recibe texto; el JavaScript del frontend lo convierte en objetos con JSON.parse().

Aplicación

Repite el ejercicio con una petición distinta: POST /api/prestamos con un cuerpo JSON. Escribe en una tabla las cuatro diferencias entre ambos recorridos (qué se valida, qué se escribe, qué código de estado se devuelve, qué método SQL se usa).

2.5 · Desarrollo y producción no son lo mismo

Durante el desarrollo, FastAPI se ejecuta en tu computador y escucha en el puerto 8000. Eso significa que la dirección http://localhost:8000 apunta a tu propia máquina. Para que alguien más pueda verlo, hace falta una dirección pública, un nombre de dominio y una cadena de capas (servidor web, aplicación, base de datos) desplegadas por separado.

Precisión

«Localhost» no es una dirección de internet: significa «esta misma máquina». Es el nombre que el sistema le da a la computadora donde estás. Por eso una aplicación que funciona en localhost puede no funcionar en un servidor, y viceversa: casi siempre la diferencia está en la configuración (variables de entorno, rutas de base de datos, puertos).

Unidad 03 · El protocolo

HTTP: la gramática del intercambio

Un protocolo es un acuerdo sobre la forma de los mensajes. Esta unidad abre HTTP y examina su estructura real: qué contiene una petición, qué contiene una respuesta, qué significan los métodos y los códigos de estado, y por qué esa estructura es la que permite que dos programas escritos por personas distintas se entiendan.

⏱ 30 minutos 📄 Lectura y análisis 🧭 Producto: petición anotada

3.1 · Qué es un protocolo

Un protocolo es una especificación: un documento que dice exactamente qué mensajes se pueden intercambiar, qué estructura tienen y qué significa cada parte. Su valor no está en lo que permite hacer, sino en que cualquier implementación que lo respete puede interoperar con cualquier otra. Un navegador y un servidor escritos por personas que nunca se conocieron se entienden porque ambos respetan HTTP.

HTTP (Hypertext Transfer Protocol) nació en 1989, diseñado por Tim Berners-Lee en el CERN para compartir documentos entre investigadores. Su nombre original habla de «hipertexto» porque los documentos contenían enlaces a otros documentos; la idea de fondo era la misma que hoy: recursos identificados por direcciones, transferidos mediante peticiones y respuestas.

Nota

HTTP es un protocolo de aplicación: usa TCP (o QUIC) por debajo. Es decir, HTTP define qué significan los bytes, no cómo viajan. Por eso el mismo HTTP funciona sobre una red de fibra y sobre una conexión móvil inestable: el transporte inferior se encarga de que los bytes lleguen.

3.2 · La anatomía de una petición

Una petición HTTP tiene tres partes: una línea de petición, un conjunto de cabeceras y, opcionalmente, un cuerpo.

petición HTTP — GET /api/libros 
GET /api/libros HTTP/1.1
Host: biblioteca.colegio.edu.co
Accept: application/json
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Connection: keep-alive


(no hay cuerpo: un GET no lleva datos)
Las tres partes de una petición
ParteEjemploFunción
Línea de peticiónGET /api/libros HTTP/1.1Método, ruta de destino y versión del protocolo
CabecerasAccept: application/jsonMetadatos del mensaje: qué formatos se aceptan, quién pregunta, autenticación
CuerpoausenteLos datos que se envían (típicamente en POST, PUT o PATCH)
Precisión sobre la ruta

La ruta de la petición (/api/libros) no es necesariamente la URL completa que escribió el usuario: normalmente es la parte posterior al dominio. Y no tiene por qué corresponder a un archivo en disco. Es un identificador de recurso que el servidor traduce a una función mediante el enrutamiento.

3.3 · Los métodos: verbos con intención

El método expresa qué se quiere hacer con el recurso. No es decorativo: el servidor usa el método para decidir si ejecuta una consulta o una modificación, y los intermediarios de la red usan el método para decidir si pueden cachear la respuesta.

Distinción: idempotente ≠ «no se repite»

Un método es idempotente cuando repetir la misma petición varias veces produce el mismo efecto final que repetirla una. Un GET es idempotente: leer diez veces el mismo recurso no lo altera. Un POST no lo es: diez POST crean diez préstamos. Por eso, si una petición se pierde por el camino, un GET puede repetirse sin riesgo, y un POST no.

3.4 · La anatomía de una respuesta

Una respuesta tiene la misma estructura: línea de estado, cabeceras y cuerpo.

respuesta HTTP — 200 OK 
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 96
Date: Tue, 21 Oct 2026 14:03:21 GMT
Server: uvicorn


{"id": 1, "titulo": "Cien años de soledad", "disponible": false}

Códigos de estado: la primera cifra ya dice mucho

Familias de códigos de estado
FamiliaSignificadoCódigos frecuentesQué revisar
2xxÉxito200, 201, 204Todo salió bien
3xxRedirección301, 302, 304El recurso está en otra parte
4xxError del cliente400, 401, 403, 404, 422La petición está mal o no está autorizada

Aplicación — leer el código antes de leer el mensaje

Cuando una web falla, el código de estado te dice en qué lado está el problema: un 4xx significa que el cliente pidió algo incorrecto o no permitido (revisar la URL, los datos enviados, los permisos); un 5xx significa que el servidor falló (revisar logs, base de datos, dependencias). Este es el primer paso del diagnóstico y es un hábito que te va a ahorrar horas.

3.5 · Las cabeceras que siempre aparecen

Content-Type
El formato del cuerpo. application/json, text/html, image/png. Si falta o es incorrecta, el cliente no sabrá cómo interpretar los datos.
Accept
Los formatos que el cliente está dispuesto a recibir. El servidor puede responder con otro si no tiene el pedido (negociación de contenido).
Authorization
Credenciales o token de acceso. Es el mecanismo por el que un servidor «sin estado» sabe quién es el usuario que pregunta.
Cache-Control
Cuánto tiempo (y bajo qué condiciones) se puede guardar la respuesta en memoria intermedia. Una de las palancas más efectivas de rendimiento web.
Set-Cookie
La instrucción para que el cliente guarde una cookie: un pequeño fragmento de datos que el navegador enviará en las peticiones siguientes.

3.6 · Versiones del protocolo

Evolución de HTTP

Ejemplo guiado 3.1 — Pedir y leer una respuesta real 9 min

La herramienta más directa para ver HTTP en crudo es curl, disponible en Windows 10, macOS y Linux. Con -i (o --include) muestra también las cabeceras de la respuesta, no solo el cuerpo.

terminal — curl 
# Ver la respuesta completa, con cabeceras
curl -i https://biblioteca.colegio.edu.co/api/libros

# Enviar datos: aquí nace un POST
curl -i -X POST https://biblioteca.colegio.edu.co/api/prestamos \
  -H "Content-Type: application/json" \
  -d '{"libro_id": 1, "estudiante": "Ana Torres", "dias": 7}'
1
Ejecuta el primer comando y localiza la línea de estado

En la primera línea de la respuesta verás HTTP/1.1 200 OK. Esa línea se compone de la versión del protocolo, el código de estado y una frase corta que explica el código en palabras.

2
Localiza las cabeceras y el cuerpo

Las cabeceras aparecen hasta que hay una línea en blanco. Después de esa línea en blanco empieza el cuerpo. Content-Type: application/json te dice que lo que sigue puede interpretarse como JSON.

Observa: la línea en blanco entre cabeceras y cuerpo es un separador del protocolo, no un adorno. Todo lo que está por encima son metadatos; todo lo que está por debajo son datos.

3
Ejecuta el segundo comando y compara

Ahora hay una línea de petición con POST, una cabecera Content-Type y un cuerpo con los datos en JSON. La respuesta probablemente sea 201 Created, con una cabecera Location que apunta al recurso recién creado.

Observa: el \ al final de una línea indica «continúa en la siguiente línea». Es de la terminal, no de HTTP.

4
Provoca un error y obsérvalo

Repite el primer comando cambiando la ruta a algo inexistente: curl -i https://biblioteca.colegio.edu.co/api/no-existe. Ahora la línea de estado dirá 404 Not Found. Anota la diferencia entre la respuesta exitosa y la fallida: el formato es el mismo, lo que cambia es el código y el cuerpo.

Observa: las cabeceras de error suelen añadir Content-Type: text/html cuando el servidor genera una página de error. No todos los errores son JSON.

Aplicación

Unidad 05 · El ciclo completo

El viaje de una petición, fase por fase

Ahora se arma todo lo anterior en una sola secuencia. Esta unidad describe las siete fases que ocurren entre que el usuario presiona Enter y que la página aparece, y enseña a observar ese viaje con las herramientas del navegador.

⏱ 35 minutos 🖥 Práctica guiada 🧭 Producto: lectura de tiempos

5.1 · Las siete fases

Una petición HTTP completa no es un instante: es una secuencia de fases, cada una a cargo de un actor distinto y con un costo de tiempo propio. Conocer la secuencia es lo que te permite decir «el problema está aquí» en lugar de «la página va lenta».

1 El usuario dispara la petición · ClienteEscribe una URL (o hace clic en un enlace) y el navegador decide qué recurso quiere obtener.
2 Resolución del nombre · RedEl nombre de dominio se traduce a una dirección IP consultando un servidor DNS. Es la primera ida y vuelta de la red.
3 Apertura de la conexión · RedSe abre un canal TCP y, si el sitio usa HTTPS, se negocia el cifrado TLS. A partir de aquí, los dos extremos pueden hablar.
4 Envío de la petición · Cliente → ServidorEl navegador escribe la petición HTTP: método, ruta, cabeceras y, si hace falta, cuerpo.
5 Procesamiento · ServidorEnrutamiento, validación, lógica de negocio, consulta a la base de datos y construcción de la respuesta.
6 Envío de la respuesta · Servidor → ClienteEl servidor devuelve la línea de estado, las cabeceras y el cuerpo con los datos.
7 Construcción de la página · ClienteEl navegador interpreta el HTML, descarga el CSS y el JavaScript, ejecuta el código y por fin muestra el resultado. A partir de aquí puede haber más peticiones.
Distinción

Las fases 1 a 7 ocurren una sola vez por recurso. Pero una página real dispara muchas peticiones: el documento HTML, sus hojas de estilo, sus scripts, sus imágenes, y las llamadas a APIs que hace el JavaScript. La fase 7 es, de hecho, el comienzo de otra ronda de peticiones.

5.2 · Trazador interactivo

Recorre las fases del ciclo. En cada panel aparece lo que el actor correspondiente está haciendo y qué se ve en el cable.

Traza de una petición · GET /api/libros
1 · Usuario 2 · DNS 3 · Conexión 4 · Petición 5 · Servidor 6 · Respuesta 7 · Render

Fase 1 · El usuario dispara la petición

El estudiante escribe la URL y presiona Enter. Todavía no ha ocurrido ninguna comunicación: solo se ha registrado la intención. El navegador toma la decisión de qué recurso pedir y con qué cabeceras. 

dirección:  https://biblioteca.colegio.edu.co/api/libros
acción:    Enter
estado:    nada ha salido del equipo todavía

Fase 2 · Resolución del nombre (DNS)

El nombre biblioteca.colegio.edu.co no es una dirección que la red entienda. Se consulta a un servidor DNS, que devuelve una dirección IP. Es una ida y vuelta completa antes de que pueda enviarse la petición. 

pregunta:  ¿qué IP corresponde a biblioteca.colegio.edu.co?
respuesta: 190.12.44.7
tiempo típico: 10 – 80 ms   (se cachea en el navegador y en el sistema)

Fase 3 · Apertura de la conexión

Se abre un canal TCP con un saludo de tres pasos. Si el sitio usa HTTPS, se negocia TLS y se establece una clave de cifrado simétrica. A partir de aquí, todo lo que viaje es indescifrable para un intermediario. 

TCP:   SYN  →  SYN-ACK  →  ACK
TLS:   ClientHello  →  ServerHello  →  certificado  →  clave de sesión
tiempo típico: 30 – 150 ms en una conexión nueva

Fase 4 · Envío de la petición

El navegador escribe la petición y la entrega al canal. La primera línea es la más importante: método, ruta y versión. Las cabeceras que siguen transportan metadatos y, en este caso, la información de quién es el usuario. 

GET /api/libros HTTP/1.1
Host: biblioteca.colegio.edu.co
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Connection: keep-alive

Fase 5 · Procesamiento en el servidor

El servidor web recibe la petición y la entrega a la aplicación, que enruta, valida, aplica las reglas de negocio y consulta la base de datos. El tiempo que se tarda aquí se conoce como TTFB (Time To First Byte): es el tiempo que el usuario percibe como «espera». 

enrutamiento  →  validación  →  lógica de negocio  →  SELECT ...
                                                       ↓
                                              filas en memoria
tiempo típico: 20 – 300 ms (más si la consulta es lenta o la base está lejos)

Fase 6 · Envío de la respuesta

El servidor responde con un código, unas cabeceras y el cuerpo. El código 200 confirma que todo salió bien; el Content-Type le dice al navegador cómo leer lo que viene. 

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 96
Server: uvicorn

[{"id": 1, "titulo": "Cien años de soledad", "disponible": false}]

Fase 7 · Construcción de la página

El navegador interpreta el contenido, descarga el resto de recursos y ejecuta el JavaScript. Si la página es una aplicación de una sola página, este JavaScript hace una nueva petición a la API y reemplaza el contenido sin recargar la página. 

HTML recibido  →  parseo  →  construcción del DOM
                 →  GET /estilos.css
                 →  GET /app.js
                 →  ejecución del JS  →  GET /api/libros  (otra vez, vía fetch)
                 →  pintado final de la lista

5.3 · La cascada de tiempos: leer el diagrama

La pestaña Network no solo muestra qué se pidió: muestra cuándo. El diagrama de tiempos descompone cada petición en fases, y cada fase tiene un significado distinto.

Aplicación — dos síntomas distintos, dos causas distintas

Si el TTFB es alto, el problema está en el servidor (o en la red hasta él): una consulta lenta, una base de datos saturada, un servidor sin recursos. Si el Content Download es alto y el tamaño de la respuesta es enorme, el problema es de peso de la respuesta, y la solución pasa por la caché o por enviar menos datos. Confundir ambos casos lleva a optimizar lo que no importa.

Unidad 06 · La frontera

Frontend y backend: dos responsabilidades, un contrato

Con el mapa completo de la petición, esta unidad delimita las dos mitades del desarrollo web: qué corresponde a cada una, cómo se comunican y por qué esa separación es una decisión de diseño, no una casualidad histórica.

⏱ 35 minutos 🧪 Práctica guiada 🧭 Producto: clasificación razonada

6.1 · Una frontera, dos ambientes

«Frontend» y «backend» no son dos programas que se hablan: son dos ambientes de ejecución, en dos máquinas (generalmente distintas), que se comunican únicamente mediante el protocolo HTTP. Todo lo que uno necesita saber del otro está en el contrato: la lista de operaciones, sus parámetros y sus respuestas.

Frontend
La capa de presentación e interacción. Se ejecuta en el dispositivo del usuario. Recibe eventos (clics, escritura, scroll), mantiene el estado visual de la interfaz y pide datos al backend cuando los necesita. Puede existir sin backend (una web estática), pero no puede decidir por sí mismo nada que dependa de los datos del negocio.
Backend
La capa de lógica de negocio y datos. Se ejecuta en el servidor. Valida las entradas de verdad, aplica las reglas, accede a la base de datos, decide qué se puede ver y qué no, y devuelve resultados. Puede existir sin frontend (una API consumida por una app móvil), pero no tiene sentido sin datos que proteger.
API
La superficie de contacto del backend: el conjunto de operaciones que ofrece y que otros programas pueden invocar siguiendo el contrato. En este curso, siempre vía HTTP.

6.3 · Por qué la frontera importa: tres razones

Razón 1 — Seguridad

Todo lo que se ejecuta en el navegador es visible y modificable por el usuario. Si el frontend decide si un estudiante puede ver el carnet de otro, basta con abrir la consola y saltarse la comprobación. La única verificación que no se puede evadir es la que hace el servidor.

Razón 2 — Integridad de los datos

El navegador puede estar desactualizado, tener una caché vieja o estar manipulado. Si el precio de un producto se calcula en el cliente, alguien puede enviar un precio distinto. Las reglas que afectan a los datos deben ejecutarse donde los datos viven.

Razón 3 — Escala y mantenimiento

Separar las capas permite que cada una crezca a su ritmo: se pueden añadir servidores de aplicación sin tocar la interfaz, y rediseñar la interfaz sin tocar la lógica. Además, cada equipo puede trabajar en paralelo sobre un contrato estable.

Precisión

«Las reglas no van en el frontend» no significa «el frontend nunca valida nada». El frontend sí debe validar para dar experiencia de usuario: avisar de inmediato que el correo está mal escrito, sin molestar al servidor. La diferencia es que esa validación es una comodidad, y la del servidor es una garantía. Ambas coexisten.

6.4 · El contrato: endpoints, métodos y JSON

La forma más común de contractualizar el backend es una lista de endpoints. Cada endpoint es un par método + ruta que corresponde a una operación del negocio, y su contrato especifica qué datos exige y qué devuelve.

Contrato de ejemplo: API de la biblioteca

Nota — las dos familias de estilos de API

Las APIs orientadas a recursos (como la de arriba) organizan todo alrededor de nouns —/libros, /prestamos— y dejan la intención en el método HTTP. Las APIs orientadas a acciones usan verbos en la ruta (/prestamos/crear). Las primeras son más idiomáticas en HTTP y permiten usar la caché del navegador; las segundas a veces son más explícitas. Ambas son válidas si el contrato es claro.

Distinción — REST no es lo mismo que «API JSON»

REST es un estilo arquitectónico con criterios más específicos: recursos identificables, interfaces uniformes, ausencia de estado, caché negociable y un modelo jerárquico de recursos. Una API puede usar JSON y HTTP sin ser REST, y puede ser REST sin usar JSON. Conocer los criterios permite evaluar bien un contrato, pero en este módulo trabajaremos con APIs HTTP que usan JSON.

  6. Frontend. El frontend ya recibió la lista como JSON en el paso anterior; solo tiene que dibujarla.
  7. Backend. Escribir en la base de datos es, por definición, tarea del servidor.
  8. Frontend. El frontend recibe la respuesta con su código de estado y decide qué mostrar. Detectar el 404 no es una regla de negocio, es una reacción a la respuesta.

Patrón que resume el ejercicio: la pregunta que decide la capa no es «¿qué código escribo?» sino «¿esta tarea necesita datos que solo el servidor tiene, o protege una regla que no puede confiarse del cliente?».

Ejemplo guiado 6.1 — El viaje de un dato 10 min

Sigamos un dato concreto —«¿cuántos préstamos tiene Ana Torres?»— a través de las dos capas. Es el ejercicio que une todo lo studied en las seis unidades anteriores.

1
El frontend decide que necesita el dato

La interfaz tiene un botón «Ver mis préstamos». Al pulsarlo, el JavaScript llama a fetch('/api/prestamos?estudiante=ana'). Esa llamada es una petición HTTP ordinary: mismo protocolo, mismo formato, mismas reglas que las que estudiaste en la unidad 3.

Observa: el frontend no sabe de dónde sale el dato ni qué reglas se aplican. Solo conoce la ruta.

2
El backend recibe, valida y autoriza

La ruta /api/prestamos se enruta a su función. Se comprueba quién es el usuario (token), se valida el parámetro estudiante y se decide si esa persona puede ver ese dato. Aquí es donde un 403 o un 401 detienen la operación.

3
El backend consulta y aplica las reglas

Se ejecuta una consulta SQL con un filtro por estudiante, y se calculan datos derivados (¿multa por retraso?, ¿días pendientes?). Estas preguntas de negocio no se pueden responder en el navegador: necesitarían todos los préstamos, no solo los de esa persona.

4
El backend responde con un contrato fijo

Serializa a JSON, elige el código de estado (200) y devuelve. El contrato garantiza una forma estable: una lista de objetos con las mismas claves, siempre.

Observa: si mañana el backend cambia la base de datos y la
consulta, el frontend no se entera: siempre recibe el mismo JSON.

5
El frontend recibe y presenta

response.json() convierte el texto en objetos, y el código dibuja la lista en el DOM. Si la respuesta fue un error, el frontend muestra un mensaje adecuado en lugar de una pantalla rota.

Observa: la responsabilidad del frontend termina en presentar la respuesta. No la interpreta: la recibe.

Aplicación

Dibuja este recorrido en una sola tira horizontal de cinco casillas, y escribe bajo cada casilla qué actor actúa, qué protocolo usa y qué datos viajan. Luego señala con una flecha en qué punto exacto un usuario malintencionado intentaría saltarse una regla, y explica por qué no puede.

2. ¿Por qué el frontend puede validar los datos aunque no sea la única validación?

3. En una API orientada a recursos, ¿qué expresa el método de una petición?

Modelo de respuesta (extracto)

A. Inventario de componentes

  • Navegador (frontend): catálogo, formularios, sesión del usuario. Comunica con la API por HTTP/JSON.
  • API Python/FastAPI (backend): reglas de préstamo, autorización, cálculo de multas. Es cliente de PostgreSQL por SQL.
  • PostgreSQL: libros, ejemplares, préstamos, estudiantes.

Justificación de negocio: la restricción «un estudiante no puede ver el historial de otro» solo puede garantizarse en el servidor, porque el navegador es propiedad del usuario y su código es modificable.

B. Contrato de la API (extracto)

  • GET /api/libros → lista de libros disponibles. 200.
  • GET /api/prestamos?estudiante=… → préstamos del estudiante indicado. 200 si es el propio, 403 si es otro y no es coordinador.
  • POST /api/prestamos → registra un préstamo. Cuerpo JSON. 201, o 422 si el cuerpo no cumple el contrato, o 409 si no hay ejemplares disponibles.
  • POST /api/prestamos/{id}/devolucion → registra la devolución y recalcula multas.

C. Traza de «Pedir un libro»

  1. Cliente: el estudiante pulsa «Pedir»; el JavaScript envía un POST con el cuerpo JSON.
  2. Red: resolución DNS y apertura de conexión (ya abierta, por lo general).
  3. Cliente → Servidor: llega la petición HTTP con la cabecera de autenticación.
  4. Servidor: enrutamiento, validación del cuerpo, verificación de la sesión y de las reglas de préstamo.
  5. Servidor → datos: se ejecuta un SELECT de ejemplares disponibles y un INSERT del préstamo.
  6. Servidor → Cliente: 201 Created con el préstamo en JSON y la cabecera Location.
  7. Cliente: el JavaScript muestra la confirmación y actualiza la lista.

D. Decisión de diseño

Decisión: SSR para el catálogo y CSR para el panel de préstamos. Motivo: el catálogo cambia poco y debe ser visible para quien busca; el panel es personalised y exige interacción. Consecuencia: dos mecanismos de renderizado que mantener. Alternativa descartada: CSR para todo, descartada porque el catálogo perdería visibilidad en buscadores y tardaría más en mostrar.

7.2 · Síntesis: siete ideas para llevarse

Si tu documento quedó sólido, es porque estas siete ideas están detrás. Consérvalas: son el andamiaje conceptual sobre el que se construyen las trece clases restantes del módulo.

01

Todo sistema conectado se organiza como una interacción entre quien pide y quien responde.

02

El papel de servidor es relativo: cada proceso puede ser cliente de otro y servidor de otro.

03

Un servidor real son capas: red, servidor web, aplicación y datos.

04

HTTP es un contrato: línea de petición, cabeceras y cuerpo; y su respuesta tiene la misma forma.

05

El código de estado dice en qué lado está el problema: 4xx es del cliente, 5xx es del servidor.

06

Entre la pulsación del usuario y la página hay siete fases; medir es el primer paso para diagnosticar.

07

La frontera entre frontend y backend protege los datos: las reglas se aplican donde los datos viven.
