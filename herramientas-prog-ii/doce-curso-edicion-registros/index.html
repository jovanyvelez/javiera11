Unidad 00 · Apertura

El editor que pisa al otro

En la clase 11 aprendiste a cargar un producto en un formulario y a guardarlo con un UPDATE. Hoy aparece el problema que ese primer editor no resuelve: dos personas abren el mismo producto, las dos guardan y la segunda borra el cambio de la primera. Vas a aprender a editar sin perder cambios ajenos.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: el mapa de una edición concurrente

0.1 · Dos personas, un mismo producto

Ana abre el producto «Teclado mecánico» para subirle el precio. Bruno abre el mismo producto para corregir la cantidad. Ana guarda primero: el precio queda actualizado. Bruno, que tenía el formulario cargado con los valores viejos, guarda después. Su UPDATE escribe todas las columnas, incluido el precio viejo. El cambio de Ana desaparece.

No hubo ningún error: las dos peticiones fueron válidas. El problema es de concurrencia. Un UPDATE que escribe todos los campos a partir de una copia vieja se llama lost update: una actualización legítima se pierde porque otra llegó después con datos desactualizados.

Distinción — guardar no es lo mismo que actualizar sin pisar

Guardar es ejecutar un UPDATE. Actualizar sin pisar es ejecutar un UPDATE que solo tenga efecto si el registro sigue siendo el que el usuario vio. La diferencia es una condición en el WHERE y una columna de versión. Es el tema de esta clase.

0.5 · El esquema que vas a necesitar

La tabla del repositorio tiene id, nombre, precio, cantidad y descripcion. Para detectar cambios ajenos hacen falta dos columnas nuevas: una versión que sube en cada edición y una marca de tiempo de la última actualización.

SQL — columnas para editar con versión 
ALTER TABLE productos
    ADD COLUMN IF NOT EXISTS version INTEGER NOT NULL DEFAULT 1,
    ADD COLUMN IF NOT EXISTS actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now();
Precisión — la versión no es el id

El id identifica el producto; la versión identifica qué copia del producto está viendo el usuario. El primero no cambia nunca; la segunda sube con cada actualización. Son dos números distintos y cumplen dos funciones distintas.

Unidad 01 · La carga

Cargar el registro: el formulario que recuerda

Un formulario de edición no empieza vacío: empieza con los valores actuales y con la versión que el usuario está viendo. Esta unidad recorre el GET, el contexto de Jinja2 y los detalles que hacen que un campo vuelva con el dato correcto, incluido NULL.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: formulario de edición precargado

1.1 · El GET que pide el formulario

Cuando el usuario pulsa Editar, HTMX pide GET /productos/5/editar. La ruta busca el producto por su clave primaria y devuelve el fragmento fila_editar.html con los valores actuales. Si el producto no existe, devuelve un aviso con 404 en lugar de un error del servidor.

vistas.py — cargar el formulario 
@router.get("/productos/{producto_id}/editar")
async def editar_producto_vista(
    request: Request,
    conn: ConnectionDep,
    producto_id: int,
):
    producto = await obtener_producto(conn, producto_id)
    if producto is None:
        return producto_no_encontrado(request, producto_id)

    return templates.TemplateResponse(
        request=request,
        name="componentes/fila_editar.html",
        context={
            "producto": producto,
            "nombre": producto["nombre"],
            "precio": producto["precio"],
            "cantidad": producto["cantidad"],
            "descripcion": producto["descripcion"] or "",
            "version": producto["version"],
            "errores": {},
        },
    )
producto_id: int
La clave primaria viaja en la URL. Si no es un entero, FastAPI responde 422 antes de entrar a la función.
obtener_producto
Un SELECT ... WHERE id = $1. Devuelve un diccionario o None; el None es el caso «no existe».
producto["descripcion"] or ""
Un NULL de la base se convierte en cadena vacía para el <textarea>. Si no, Jinja2 escribiría «None» dentro del campo.
version
La copia que el usuario está viendo. Viaja al formulario en un campo oculto y volverá en el POST.
Advertencia — el SELECT tiene que traer la versión

Si obtener_producto sigue seleccionando solo las columnas antiguas, el formulario recibe version = None y el campo oculto queda vacío. Actualiza la consulta antes de continuar.

repositorio.py — obtener_producto con versión 
async def obtener_producto(conn, producto_id: int) -> dict | None:
    fila = await conn.fetchrow(
        """
        SELECT id, nombre, precio, cantidad, descripcion,
               version, actualizado_en
          FROM productos
         WHERE id = $1
        """,
        producto_id,
    )
    return dict(fila) if fila is not None else None

Advertencia — el campo oculto se puede manipular

version viaja en un <input type="hidden">, y un usuario con DevTools puede cambiarlo. Por eso el servidor no confía en él: lo valida como entero y lo usa como condición del UPDATE. Si alguien envía una versión inventada, la condición no coincide y el servidor responde 409; no se escribe nada.

1.3 · Por qué cada fila es su propio tbody

La tabla de productos envuelve cada fila en un <tbody id="producto-5">. HTMX reemplaza ese tbody completo con el formulario, la fila actualizada o el aviso de error. Si todas las filas compartieran un contenedor, editar una borraría o duplicaría las demás.

Nota — cargar no es copiar a mano

El formulario no debería pedirle al usuario que vuelva a escribir los datos. La ruta los consulta, los pasa al contexto y la plantilla los coloca en value y en el contenido del textarea. Si un campo llega vacío, el usuario no debería tener que adivinar si el dato era NULL o si la carga falló: la ruta debe distinguir entre «no existe el producto» (404) y «el campo está vacío» (valor vacío legítimo).

1.4 · El producto que ya no está

Si el usuario abre un enlace viejo o el producto fue eliminado, el GET devuelve un fragmento de aviso con 404. No es un error del servidor: es un recurso que ya no existe. La interfaz lo muestra en la misma fila, sin romper la tabla.

Precisión — el 404 también necesita una configuración de HTMX

Por defecto, HTMX 2 no inserta las respuestas 4xx. El proyecto incluye un <meta name="htmx-config"> que habilita el intercambio para 404 y 422. HTMX 4.0 ya intercambia esos códigos por defecto. Si el aviso no aparece, revisa la versión de HTMX y esa configuración.

Unidad 02 · El filtro

Validar la edición sin perder lo escrito

La validación de una edición es la misma de una inserción, con una regla adicional: el formulario tiene que volver con lo que el usuario escribió, no con los valores originales. Esta unidad conecta Pydantic, los mensajes por campo y la versión que se está editando.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: ProductoActualizar con versión

2.1 · El modelo de la edición

El modelo del repositorio ya valida nombre, precio y cantidad. Para editarlo con seguridad hay que añadir la versión: el número de copia que el usuario recibió al cargar el formulario. Si no coincide con la de la base, la actualización no se ejecuta.

esquemas.py — ProductoActualizar con versión 
from pydantic import BaseModel, ConfigDict, Field


class ProductoActualizar(BaseModel):
    """Datos que se aceptan al editar un producto."""

    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")

    nombre: str = Field(min_length=1, max_length=100)
    precio: float = Field(gt=0)
    cantidad: int = Field(ge=0)
    descripcion: str | None = Field(default=None, max_length=500)
    version: int = Field(ge=1)
nombre
Obligatorio, entre 1 y 100 caracteres. Se recorta antes de medir.
precio
Número mayor que cero. Un precio cero o negativo es un error de captura, no una oferta.
cantidad
Entero mayor o igual que cero. Una cantidad negativa no existe en el inventario.
descripcion
Opcional, hasta 500 caracteres. Si llega vacía, la ruta la guarda como NULL.
version
Entero mayor o igual que 1. No se guarda como dato del producto: se usa como condición del UPDATE.
Precisión — la versión también se valida

Si el campo oculto llega 0 o negativo, Pydantic rechaza el modelo antes del UPDATE. Si llega "abc" o vacío, FastAPI no puede convertirlo a int y responde 422 antes de entrar a la función. Para devolver el formulario con un mensaje propio en ese caso, recibe version como str y deja que Pydantic lo convierta, igual que hicimos con el año en la clase 10. La versión es parte del contrato, no un adorno del formulario.

Advertencia — no recargues el formulario con los valores originales

Si el usuario escribió un precio nuevo y la cantidad era inválida, el formulario debe volver con el precio nuevo y el mensaje de cantidad. Volver a los valores de la base borra el trabajo del usuario y es la causa más común de abandono en un formulario de edición.

2.3 · Los mensajes por campo

vistas.py — traducir los errores 
from pydantic import ValidationError

MENSAJES_ERROR = {
    "nombre": "El nombre es obligatorio (entre 1 y 100 caracteres).",
    "precio": "El precio debe ser un número mayor que cero.",
    "cantidad": "La cantidad debe ser un número entero mayor o igual que cero.",
    "descripcion": "La descripción no puede superar los 500 caracteres.",
    "version": "La versión del registro no es válida.",
}


def errores_de_validacion(exc: ValidationError) -> dict[str, str]:
    """Convierte la lista de Pydantic en {campo: mensaje}."""
    errores: dict[str, str] = {}
    for error in exc.errors():
        campo = str(error["loc"][0])
        errores.setdefault(
            campo,
            MENSAJES_ERROR.get(campo, "Revisa este campo."),
        )
    return errores

La plantilla consulta el diccionario por campo y pinta el mensaje debajo. También marca el campo con aria-invalid y aria-describedby para que el error no sea solo un color.

fila_editar.html — campo con error 
<div>
  <label>Precio:
    <input type="text" name="precio" value="{{ precio }}"
           inputmode="decimal"
           {% if errores.get('precio') %}aria-invalid="true" aria-describedby="error-precio"{% endif %}>
  </label>
  {% if errores.get('precio') %}
  <p class="error" id="error-precio" role="alert">{{ errores['precio'] }}</p>
  {% endif %}
</div>
Nota — el 422 debe volver a la fila, no a una página aparte

El formulario vive dentro de un tbody. Si la validación falla, la respuesta tiene que ser el mismo fragmento con los valores y los errores; HTMX lo inserta en esa fila. Si la ruta devolviera la página completa o un JSON, el usuario perdería el contexto y la tabla quedaría rota.

Unidad 03 · La escritura

Actualizar sin pisar: el UPDATE condicional

El UPDATE de una edición concurrente no es «escribe estas columnas en este id». Es «escribe estas columnas en este id solo si la versión sigue siendo la que el usuario vio». Esa condición es la que evita el lost update.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: UPDATE con versión y RETURNING

3.1 · La función del repositorio

La función recibe el id, la versión esperada y los datos validados. El WHERE combina las dos condiciones; el RETURNING devuelve la fila nueva con la versión incrementada. Si no hay fila, devuelve None.

repositorio.py — actualizar_producto() 
async def actualizar_producto(conn, producto_id: int, datos) -> dict | None:
    fila = await conn.fetchrow(
        """
        UPDATE productos
           SET nombre = $3,
               precio = $4,
               cantidad = $5,
               descripcion = $6,
               version = version + 1,
               actualizado_en = now()
         WHERE id = $1 AND version = $2
        RETURNING id, nombre, precio, cantidad, descripcion,
                  version, actualizado_en
        """,
        producto_id,
        datos.version,
        datos.nombre,
        datos.precio,
        datos.cantidad,
        datos.descripcion,
    )
    return dict(fila) if fila is not None else None
WHERE id = $1 AND version = $2
Las dos condiciones. El id elige la fila; la versión elige la copia. Si alguien guardó antes, la versión ya no coincide y el UPDATE no toca nada.
version = version + 1
La versión sube en la misma sentencia. No hay una lectura intermedia que otra petición pueda pisar.
actualizado_en = now()
La marca de tiempo se escribe en la base, no en Python. Así no depende de la zona horaria del servidor de aplicaciones.
RETURNING
Devuelve la fila actualizada, incluida la versión nueva. La plantilla puede mostrar el resultado sin una segunda consulta.
fetchrow → None
No hubo filas afectadas. La ruta debe averiguar si fue porque el producto no existe o porque la versión cambió.

3.2 · La ruta que distingue 404 de 409

Distinción — 404 es «no existe»; 409 es «cambió debajo de ti»

Los dos casos producen UPDATE 0, pero significan cosas distintas. Si el producto no existe, el recurso desapareció: 404. Si existe pero la versión no coincide, el recurso sigue ahí y el usuario puede reconciliarse con los valores actuales: 409 Conflict. Responder 404 al conflicto oculta el problema; responder 409 al producto borrado confunde al usuario.

Advertencia — la comprobación de existencia no puede ir antes del UPDATE

Si primero haces SELECT y después UPDATE, entre las dos consultas otra petición puede borrar el producto o cambiar su versión. La condición del WHERE es la que decide en el mismo instante de la escritura. El SELECT posterior solo sirve para explicar por qué no se actualizó.

3.4 · Historial y auditoría

Una edición con versión ya evita perder cambios, pero no dice quién cambió qué. Si el producto es parte de un negocio, conviene guardar un historial en la misma transacción que el UPDATE.

SQL — tabla de historial 
CREATE TABLE IF NOT EXISTS historial_productos (
    id          BIGSERIAL PRIMARY KEY,
    producto_id INTEGER NOT NULL REFERENCES productos(id) ON DELETE CASCADE,
    version     INTEGER NOT NULL,
    cambiado_en TIMESTAMPTZ NOT NULL DEFAULT now()
);
repositorio.py — UPDATE e historial en una transacción 
async with conn.transaction():
    fila = await conn.fetchrow(sql_update, producto_id, datos.version, ...)
    if fila is not None:
        await conn.execute(
            "INSERT INTO historial_productos (producto_id, version) VALUES ($1, $2)",
            producto_id,
            fila["version"],
        )
return dict(fila) if fila is not None else None
Nota — la transacción no reemplaza la condición de versión

Una transacción garantiza que el UPDATE y el historial se guarden juntos; no evita que dos usuarios editen a la vez. La condición version = $2 sigue siendo la que decide si la edición es válida. Son dos herramientas para dos problemas distintos.

4.2 · Vocabulario del taller

Lost update
Una actualización válida que se pierde porque otra petición escribe después con datos viejos.
Bloqueo optimista
No se bloquea la fila al leerla; al escribir se comprueba que la versión siga siendo la misma. Si cambió, se rechaza.
Versión
Un entero que sube en cada actualización y representa la copia que el usuario está viendo.
UPDATE condicional
Un UPDATE cuyo WHERE incluye el id y la versión esperada.
RETURNING
La cláusula que devuelve la fila actualizada, incluida la versión nueva.
409 Conflict
El estado que indica que el recurso cambió desde que se cargó; el usuario debe reconciliarse con los valores actuales.
actualizado_en
La marca de tiempo de la última escritura. Se calcula en la base con now().
Auditoría
El registro de qué cambió y cuándo, guardado en una tabla aparte dentro de la misma transacción.
Formulario precargado
Un formulario que llega con los valores actuales y la versión, no vacío.
Reconciliación
El proceso de mostrar al usuario los valores actuales después de un conflicto para que decida cómo continuar.

5.3 · Paso 2: el repositorio

Reemplaza la función actualizar_producto para que reciba el modelo validado y devuelva la fila nueva o None. La clave está en el WHERE de dos condiciones y en el RETURNING.

repositorio.py — actualizar solo si la versión coincide 
async def actualizar_producto(conn, producto_id: int, datos) -> dict | None:
    fila = await conn.fetchrow(
        """
        UPDATE productos
           SET nombre = $3,
               precio = $4,
               cantidad = $5,
               descripcion = $6,
               version = version + 1,
               actualizado_en = now()
         WHERE id = $1 AND version = $2
        RETURNING id, nombre, precio, cantidad, descripcion,
                  version, actualizado_en
        """,
        producto_id,
        datos.version,
        datos.nombre,
        datos.precio,
        datos.cantidad,
        datos.descripcion,
    )
    return dict(fila) if fila is not None else None

Unidad 06 · La respuesta

Conflictos y errores: decir la verdad al usuario

Una edición puede fallar por datos inválidos, por un producto que ya no existe o por una versión que cambió. Cada caso tiene un código distinto y una acción distinta para el usuario. Esta unidad ordena esos caminos y evita el error más caro: decir «guardado» cuando la base no cambió.

Distinción — 409 no es un error del usuario

Un 422 dice «lo que escribiste no cumple las reglas». Un 409 dice «lo que escribiste era válido, pero el mundo cambió mientras editabas». Son dos acciones distintas: en el primer caso el usuario corrige el campo; en el segundo revisa los valores actuales y decide si quiere guardar encima.

6.2 · La respuesta de conflicto que se puede reconciliar

El 409 no debe ser una página en blanco ni un JSON técnico. La mejor respuesta es el mismo formulario con los valores actuales, la versión actual y un aviso. Así el usuario ve qué cambió y puede volver a guardar con la versión correcta.

Advertencia — no devuelvas la versión vieja en el conflicto

Si el formulario de conflicto conserva la versión que el usuario envió, el siguiente intento volverá a fallar con 409. El formulario debe construirse con la versión actual de la base. Es la única forma de que el usuario pueda reconciliarse y guardar.

La petición está bien formada, pero los datos no cumplen el modelo. Se corrige en el formulario.
404
El recurso no existe. No tiene sentido reintentar con los mismos datos.
409

500
Fallo interno. El cliente recibe un mensaje neutro; el equipo recibe el SQLSTATE y el stack trace en el log.
503
Fallo temporal de disponibilidad. Se puede reintentar después.

def primer_producto(cliente):

01

Guardar no es actualizar sin pisar: un UPDATE normal puede borrar el cambio de otra persona.

02

La versión representa la copia que el usuario está viendo; el id representa el producto.

03

El formulario se carga con los valores actuales y la versión; nunca empieza vacío.

Pydantic valida la forma y la versión antes de tocar la base; si falla, se conserva lo escrito.
