La analogía de la clase

Git es el álbum de fotos que ya armaste en la clase 12. El álbum funciona sin red social… pero la red social no funciona sin álbum. Por eso esta clase viene después de la 12.

🐙 El remoto: la dirección de tu álbum en la nube

⏱️ 35 minutos · "origin es solo un apodo para una URL"

🧠 La idea central

Un remoto es simplemente una dirección donde hay otra copia del álbum — en la nube. Git la guarda con un apodo; por tradición mundial, ese apodo es origin. Los dos comandos del día: git push — "envía mis commits nuevos a la nube" — y git pull — "tráeme los commits que hay allá y que a mí me faltan". Nada más. Con eso, tu proyecto pasa de existir en un disco a existir en dos lugares — y esa copia extra es respaldo, visibilidad y colaboración a la vez.

🚶‍♀️ El viaje de un commit: del disco a la nube

Recorre las seis paradas con los botones. Este es el mapa mental de toda la clase: si entiendes este viaje, el resto son detalles.

Parada 1 de 6
Parada 1 · Tu computador — Git
biblioteca/.git/ — el álbum local
Todo lo de la clase 12 ya ocurrió aquí: tus commits con hash, autoría y mensaje viven en la carpeta .git/. Aún nadie más en el mundo puede verlos: son tuyos y de tu disco.
lo que ya sabes hacer
git log --oneline
#    9f3c2b1 (HEAD -> main) Resolver conflicto de título en README
#    4a8e7d2 Agregar página de préstamos
#    c1d9f3e Primer commit: proyecto biblioteca
Por qué importa: el viaje SIEMPRE empieza con un commit local. Sin fotos en el álbum no hay nada que subir.
Parada 2 · La dirección — el remote
git remote add origin https://github.com/tuusuario/biblioteca.git
Le dices a Git: "hay otro álbum en esta dirección, y le pondré el apodo origin a esa dirección". Es guardar un contacto en el celular: lo haces una vez y queda para siempre en la configuración del repo.
registrar la dirección y verificarla
git remote add origin https://github.com/tuusuario/biblioteca.git

git remote -v          # -v de "verbose": muestra la lista de remotos
#    origin  https://github.com/tuusuario/biblioteca.git (push)
#    origin  https://github.com/tuusuario/biblioteca.git (pull)
Por qué "origin": es solo el apodo tradicional. Podrías llamarlo mi-nube y todo funcionaría igual… pero el mundo dice origin, y el mundo conviene seguirlo.
Parada 3 · El viaje por internet — git push
git push -u origin main
Empacas los commits que la nube no tiene y los envías a la dirección de origin, a la rama main de allá. La primera vez, GitHub te pide identificarte (tu navegador se abre y listo: el Git Credential Manager de Windows recuerda la sesión).
la salida real de tu primer push
git push -u origin main
#    Enumerating objects: 42, done.
#    Writing objects: 100% (42/42), 21.3 KiB | 7.10 MiB/s, done.
#    To https://github.com/tuusuario/biblioteca.git
#     * [new branch]      main -> main
#    branch 'main' set up to track 'origin/main'.
Qué es ese -u: "upstream". Conecta tu main local con el origin/main de la nube, para siempre. A partir de ahí, subir es solo escribir git push a secas. Se hace una vez por rama.
Parada 4 · GitHub recibe — github.com/tuusuario/biblioteca
El navegador — tu repo en la web
Abre la URL de tu repo. Ahí está tu mismo álbum, en la web: cada commit con su mensaje y su autora, tus archivos navegables con colores, tu historial como gráfica. Y de regalo: cualquier persona del planeta puede verlo, clonarlo o proponer cambios.
lo que verás en la web
//  tuusuario / biblioteca            ← tu repo, con tu nombre 😍
//  📁 dominio/  📁 nucleo/  📁 presentacion/  📄 main.py  📄 README.md
//  ───────────────────────────────────────────────────────
//  9f3c2b1  Resolver conflicto de título en README    · hace 2 minutos
//  4a8e7d2  Agregar página de préstamos              · hace 1 hora
//  c1d9f3e  Primer commit: proyecto biblioteca        · ayer
El respaldo ya existe: si mañana tu compu se muere, tu proyecto completo —archivos E historial— vive en la nube. Villano 1 de la clase: muerto.
Parada 5 · Otras personas entran — clone y pull
git clone URL — y luego git pull
Tu compañera ejecuta git clone https://github.com/tuusuario/biblioteca.git y obtiene el proyecto completo con todo el historial en su compu (no un zip: un álbum vivo, listo para recibir y proponer fotos). Si ya lo tenía clonado, git pull le trae solo lo nuevo.
del lado de quien recibe
# primera vez en la vida con tu proyecto:
git clone https://github.com/tuusuario/biblioteca.git
#    Cloning into 'biblioteca'...
#    remote: Enumerating objects: 42, done.
#    Receiving objects: 100% (42/42), done.

# días después, para actualizarse con tus cambios:
git pull
#    Already up to date.   (o la lista de lo nuevo que llegó)
Por eso Git es "distribuido": no hay "el servidor manda": hay copias completas del álbum que se sincronizan entre iguales. GitHub es solo la copia más popular del vecindario.
Parada 6 · El círculo se cierra — pull → commit → push
la rutina diaria de toda persona que programa
Este es el flujo de trabajo permanente: al empezar el día, git pull (¿qué hay nuevo en la nube?); durante el día, editar + commit como en la clase 12; al terminar, git push (mis fotos nuevas, a la nube). Tres verbos, en orden, todos los días, por el resto de tu carrera.
el ciclo, resumido
#   ┌──► git pull      (bajar lo nuevo de la nube)
#   │        │
#   │        ▼
#   │   editar + git add + git commit   (la clase 12)
#   │        │
#   │        ▼
#   └──  git push     (subir tus fotos nuevas) ♻️
Y cuando dos personas suben a la vez… aparece el rechazo amable (fetch first), que es el villano del módulo 2 — y tu mejor amigo disfrazado.

🚀 El primer push: de la teoría a tu URL pública

⏱️ 35 minutos · "Crear el repo, conectarlo y subir el álbum completo"

🧠 La idea central

El push del módulo 1 fue el mapa; ahora el camino real. Son dos pasos que se hacen una sola vez: crear el repositorio vacío en github.com y conectar tu repo local con git remote add. Después de eso, tu vida es el ciclo de siempre — pull, editar, add, commit, push — y Git mismo te dice en git status cuántos commits te faltan por subir. El detalle que salva la clase: el repo de la web se crea VACÍO, sin README ni licencia inicial, para que tu historial local sea el que manda.

paso 1 — crear el repo en la web (hazlo con tu cuenta ya creada) 
// 1. Entra a github.com con tu cuenta → botón verde "+ " (arriba a la derecha)
//    → "New repository".
// 2. Repository name:  biblioteca
// 3. Visibility: Public   ← el mundo lo verá (eso queremos: es tu portafolio)
// 4. ⚠️ CRÍTICO — DEJA TODO LO DEMÁS DESMARCADO:
//      ❌ sin "Add a README file"   ❌ sin .gitignore   ❌ sin licencia
//    ¿Por qué? Esos archivos crearían commits allá que tú no tienes aquí,
//    y las dos historias chocarían en el primer push. El repo nace VACÍO.
// 5. Botón verde "Create repository".
// 6. GitHub te muestra la URL: cópiala (botón de copiar del cuadrito HTTPS):
//      https://github.com/tuusuario/biblioteca.git
paso 2 — conectar y subir (en la terminal, en tu biblioteca/) 
# 1. Registrar la dirección (una sola vez en la vida de este repo):
git remote add origin https://github.com/tuusuario/biblioteca.git
git remote -v                     # verificar: debe listar origin

# 2. Que tu rama se llame main, como en la nube (por si nació como "master"):
git branch -M main

# 3. El primer empujón — el -u conecta main con origin/main para siempre:
git push -u origin main
#    Enumerating objects: 42, done.
#    To https://github.com/tuusuario/biblioteca.git
#     * [new branch]      main -> main

# 4. Abre la URL en el navegador y DISFRUTA:
#    https://github.com/tuusuario/biblioteca  ← tu proyecto, publicado 🎉
HTTPSSSH

📅 El día a día: Git te avisa solo

A partir de ahora, tu git status de siempre tiene una línea nueva: la relación entre tu compu y la nube. Aprende a leerla — es el velocímetro del push.

git status, ahora bilingüe: local + nube 
# Hiciste 2 commits hoy y aún no subes. El status te lo recuerda:
git status
#    On branch main
#    Your branch is ahead of 'origin/main' by 2 commits.
#      (use "git push" to publish your local commits)
#    → "vas GANANDO por 2 commits": súbelos con git push

# Un compañero subió cambios y tú los necesitas:
#    Your branch is behind 'origin/main' by 3 commits.
#    → "vas PERDIENDO por 3": bájalos con git pull

# Todo sincronizado:
#    Your branch is up to date with 'origin/main'.
#    → nirvana. ♻️

🦹 Villano: ! [rejected] — el susto del primer equipo

Trabajando con otra persona, esto va a pasar (es una certeza, no una posibilidad):

git push
#    To https://github.com/equipo/biblioteca.git
#     ! [rejected]        main -> main (fetch first)
#    error: failed to push some refs to 'https://github.com/…'

No es un error. Es Git protegiendo el álbum común. Significa: "en la nube hay commits que tú no tienes (los subió tu compañero) y no voy a dejar que los tapes". La solución es la rutina completa, en orden: git pull (bajas lo nuevo; si ambos tocaron lo mismo, aparece un conflicto como en la clase 12 — se resuelve igual), y recién entonces git push. El rechazo es la red de seguridad trabajando: un día le agradecerás.

💡 ¿Y eso de "local" y "remoto" en VS Code?

VS Code trae Git integrado: el panel Source Control (el ícono de la ramita 🌿 en la barra izquierda) hace add y commit con clics, y muestra los archivos modificados con colores. Ahora sabes qué hace por debajo: exactamente lo mismo que escribiste en la terminal. En este curso seguimos con la terminal — saber qué pasa por debajo es lo que te permite usar cualquier herramienta después. Pero siéntete libres de explorar el panel: ya no tiene secretos para ti.

📄 El README: la vitrina de tu proyecto

⏱️ 35 minutos · "El archivo más importante del repo no es código"

🧠 La idea central

Cuando alguien entra a tu repo en GitHub —una compañera, un profe, una futura jefa— lo primero que ve no es tu código: es tu README. GitHub lo pinta automáticamente en la portada del repo. Un proyecto brillante sin README parece abandonado; un proyecto mediano con un README claro parece profesional. La buena noticia: se escribe en Markdown, el mismo formato que conoces de las clases de documentación. Hoy le pones vitrina a tu biblioteca y de paso, tu README de perfil: el escaparate de tu cuenta completa.

🦹 El villano del repo fantasma

El repo sin README, con nombres como proyecto-final o prueba2 y sin una línea de descripción, da la impresión exacta de estar abandonado — aunque el código adentro sea brillante. En GitHub la primera impresión es digital: quien entra, decide en 10 segundos si sigue leyendo o cierra la pestaña. El README es tu embajador: trabaja por ti las 24 horas. Además: en la página del repo, el ícono de ⚙️ te deja poner una descripción de una línea y temas (topics: fastapi, python, postgresql) — dos detalles que multiplican la seriedad del repo.

💡 La licencia MIT: "puedes usar esto, dame crédito"

Un repo sin licencia es técnicamente "todos los derechos reservados": nadie debería copiarlo. Los repos de estudiantes usan la licencia MIT: permiso libre de usar y modificar, con crédito. En la web: botón Add file → Create new file → nómbralo LICENSE → GitHub te ofrece la plantilla → eliges MIT → commit. Un archivo, cero drama legal, seriedad instantánea.

GitHub no nació para empresas: nació en 2008 como una startup de tres personas, y su primer usuario famoso fue… el propio Linus Torvalds subiendo el kernel de Linux (bueno, casi: primero fue el proyecto Ruby on Rails). En 2018 Microsoft lo compró por 7.500 millones de dólares — y para entonces ya era la casa de más de 80 millones de repos. Hoy, cuando alguien dice "mándame el código", en el 90% del planeta la respuesta es una URL de GitHub. Y desde hoy, tú tienes la tuya. 🐙

🤝 Colaborar: Pull Requests, el arte de proponer

⏱️ 35 minutos · "Mira mis cambios y, si te gustan, únelos"

🧠 La idea central

Todo lo de la clase 12 (ramas) y el push de hoy se combinan en el flujo colaborativo estándar del planeta: en vez de escribir directo en main, cada cambio viaja en una rama propia que subes a GitHub con git push. Ahí abres un Pull Request (PR): una página que dice "así quedaría mi cambio sobre tu proyecto — revísalo y decide", con el diff pintado de colores, espacio para comentarios y un botón verde de merge. Es el chat donde el código discute antes de entrar a main. El mismo mecanismo sirve para equipos de 2 personas y para equipos de 2.000 — solo cambia quién aprueba el botón verde.

el flujo completo de un Pull Request — hazlo sobre tu propio repo 
# 1. Rama nueva para la misión (la clase 12, nivel pro):
git switch -c fix/titulo-inicio
# …edita algo pequeño, add, commit…
git add .
git commit -m "Corregir acentos del título de inicio"

# 2. Subir la RAMA a la nube (la primera vez lleva -u):
git push -u origin fix/titulo-inicio
#    remote: Create a pull request for 'fix/titulo-inicio' on GitHub by visiting:
#    remote:      https://github.com/tuusuario/biblioteca/pull/new/fix/titulo-inicio
#    ← ¡GitHub te da el link del PR! Es que quiere que lo abras. 😄

# 3. Abre ese link (o entra al repo: aparece un botón verde
#    "Compare & pull request"). Escribe título y descripción y "Create".

# 4. En la pestaña "Files changed" revisa tu propio diff con calma.

# 5. Botón verde "Merge pull request" → "Confirm merge".
#    El cambio entra a main EN LA NUBE. El PR queda cerrado y archivado.

# 6. Vuelve a tu compu y bájate el main actualizado:
git switch main
git pull
git branch -d fix/titulo-inicio      # la misión terminó: rama local fuera

🚀 Directo a main

Aceptable cuando trabajas sol@ en un proyecto chico: commit a main, push, listo. Rápido, sin ceremonia.

🤝 Vía Pull Request

Para equipo (o para ti del futuro): otra persona revisa el diff, comenta, aprueba. main queda protegida de errores ajenos — y de los propios: la semana que viene, ese "revisor" que te salva de un bug serás tú mirando tu propio PR con ojos frescos.

🐞 Issues: la sala de pendientes del repo

Un issue es la conversación de "esto está mal / falta": un pendiente con dueño, descripción y comentarios. Es donde los usuarios reportan bugs y donde el equipo organiza el trabajo.

cómo se escribe un issue que da vergüenza no leer 
// Repo → pestaña Issues → botón verde "New issue".
// Un issue amable y útil tiene 4 partes:

Título: La página de libros muestra "Sin libros" aunque sí hay

Pasos para reproducirlo:
1. Entrar a /libros
2. Registrar un autor con libros

Qué esperaba: Ver la lista de libros del autor
Qué pasa en realidad: "Sin libros" (y la consola muestra un error 500)

// ❌ NO: "no funciona" / "está dañado" / "urgente!!!"
// ✅ SÍ: pasos concretos + esperado + real. El que lee, entiende.

🦹 Villano: el push directo a main en equipo

Dos personas empujando directo a main todo el día es el clásico "¿por qué mi código que funcionaba ya no funciona?" — con la agravante de que nadie sabe quién rompió qué ni por qué. El PR no es burocracia: es el cinturón de seguridad del equipo. main queda intocada sin revisión, cada cambio tiene una página con su historia y su discusión, y el blame (sí, Git sabe quién escribió cada línea, con git blame) deja de ser un dedo apuntador: todo pasó por un PR visible.

💡 El jardín verde: tu marcador de videojuego

En tu perfil, la grilla de cuadritos es el gráfico de contribuciones: cada cuadro es un día, cada cuadrito verde un repo con commits tuyos. A los 16-17 años puede parecer un juego sin importancia… pero cuando apliques a una beca o a un primer trabajo tech, esa grilla verde y continua vale más que cualquier certificado: es evidencia pública de constancia, con fecha. Empieza a regarla hoy: cada push la riega.

🔄 Actividad en pareja — 10 minutos

Colaboración real de ida y vuelta, cada uno en el repo del otro:

  1. Tu compañero/a te agrega como colaboradora: en su repo web → Settings → Collaborators → "Add people" → tu username (aceptan la invitación desde su correo). Haz lo mismo en sentido contrario.
  2. Clona el repo del otro y propón una mejora pequeñita vía rama + push… pero NO hagas merge tú: ábrele el Pull Request.
  3. Cada uno revisa el PR que le llegó: mira el diff con "Files changed", escribe un comentario (algo amable y útil) y recién ahí hace el merge.
  4. Abranse un issue mutuo con un "bug" inventado pero bien escrito (título + pasos + esperado + real).

🧙 Buenas prácticas: GitHub como portafolio

⏱️ 35 minutos · "Tu historial habla por ti antes de que tú puedas"

🧠 La idea central

Con lo que ya sabes, publicar es fácil. La diferencia entre "subir archivos a internet" y tener un portafolio está en las costumbres: commits que cuentan historias, README que recibe visitas, secretos blindados, historial limpio y constancia. Estas prácticas no son para engañar a nadie: son la disciplina con la que el mundo real trabaja, y además — casualidad o no — son exactamente las cosas que una futura empresa, universidad o beca revisa cuando busca a alguien que sepa trabajar en equipo.

Práctica 😎Por qué
Commits pequeños y frecuentes (no el commit-montaña de 47 archivos)Cada foto cuenta una sola historia: se puede leer, revertir o revisar con precisión
Mensajes que dicen QUÉ y POR QUÉEl git log es la autobiografía del proyecto: "cambios" no le cuenta nada a nadie (ni a ti en 3 meses)
push diario = respaldo diarioUn commit sin subir NO está respaldado: la nube solo guarda lo que le empujas
.gitignore blindado desde el inicioLos secretos en el historial no se borran con borrar el archivo (módulo 3 de la clase 12)
README + descripción + topics en cada repoRepo fantasma vs repo estrella: la diferencia es de 10 minutos de escritura
PR e issues educadosLos PRs con buena descripción y los issues con pasos concretos son el reflejo de cómo trabajas con otros
cheat sheet — tu rutina de GitHub en una tarjeta 
# ── AL EMPEZAR EL DÍA ──────────────────────────────
git pull                          # ¿qué hay nuevo en la nube?

# ── DURANTE EL DÍA (cada cambio, 4 líneas) ──────────
git switch -c feature/lo-nuevo    # o quedo en main si soy sol@ y es chico
# …editar, guardar…
git diff                          # releer lo que hice, en serio
git add .
git commit -m "Qué hice y por qué, en una frase"

# ── AL TERMINAR ────────────────────────────────────
git push                          # respaldo activado. Jardin regado. ♻️

# ── COLABORANDO (equipo) ───────────────────────────
git push -u origin feature/lo-nuevo   # subir la RAMA
# → abrir PR en la web → revisión → merge → pull

👻 El proyecto fantasma

Un zip subido como "proyecto"… digo, un repo sin README, sin descripción, con 2 commits: "init" y "cambios" (ambos de hace 3 meses). Sin historial, sin constancia, sin autoría visible. Nadie — nadie — se detiene a excavar ahí.

⭐ El proyecto estrella

README con qué/cómo/estructura, descripción y topics, licencia MIT, 40 commits con mensajes legibles a lo largo de semanas, ramas feature/ fusionadas vía PR, issues resueltos. Mismo código, otra reputación. Y sí: tus proyectos de clase pueden ser exactamente esto.

🦹 El villano del commit gigante

Subir 3 semanas de trabajo en un commit titulado "avances" con 47 archivos cambiados es como empacar toda tu casa en una sola caja cuando te mudas: nadie puede revisarla, nadie puede encontrar nada, y si algo se rompió, no sabes ni en qué capa estaba. La costumbre profesional: un commit = una historia ("Corregir cálculo de multa con días negativos"), y push con frecuencia. Si llevas 3 días sin subir, tu respaldo lleva 3 días desactualizado y tu jardín verde, 3 días seco.

💡 Bonus: GitHub Pages — tu HTML en internet, gratis

¿Recuerdas el index.html del currículo? GitHub puede publicar HTML estático gratis: en tu repo, Settings → Pages → Branch: main, folder / (root) → Save. Minutos después tu index.html vive en https://tuusuario.github.io/nombre-del-repo/. Es el mismo truco con el que millones de personas publican sus páginas sin pagar un servidor. Si tu repo tiene HTML/CSS/JS puro (¡como este currículo!), pruébalo: tu primera web pública está a tres clics.

  3. Pregunta seria para los dos: si una beca les pidiera HOY "envía el link de un proyecto tuyo", ¿cuál envían? ¿Ese repo está a la altura? ¿Qué le falta?

🧠 Reto 3 — Blindaje de secretos (la prueba de fuego)

Demuestra que tu .gitignore hace su trabajo: en la web, entra a la lista de archivos del repo y busca (el buscador de la web, o simplemente recorre el árbol): .env y __pycache__/ NO deben existir allá. Si aparecen, para todo, llama a tu profe y arreglen el historial antes de seguir — este es el error más grave que puede tener un repo público.

🧠 Reto 4 — Tu primer Pull Request (a tu propio repo)

Haz el flujo completo del módulo 5 en tu repo: rama fix/detalles-readme con una mejora real al README, push de la rama, abre el PR con buena descripción, revísalo tú mism@ en "Files changed", mérgelo, y actualiza tu main local con pull. Tu repo queda con su primer PR archivado — exactamente como los proyectos grandes.

🧠 Reto 5 — Perfil y feria de repos 🎪

Crea el repo tuusuario/tuusuario con tu README de perfil (foto, nombre, bio, tus proyectos con enlaces). Luego, la feria: el profe proyecta o comparte los links, y cada estudiante visita los repos de 3 compañeros, les pone ⭐ a los que le parezcan serios y les abre 1 issue educado a uno de ellos (una sugerencia o un "bug" amable, con la plantilla del módulo 5). Nótese: las estrellas se ganan con vitrina — el Reto 2 trabajando para ti.
