Unidad 00 · Apertura

El mismo resultado, otra manera

La clase pasada escribiste el enlace a mano: ponías editorial_id y pedías las dos tablas con un JOIN. Hoy el ORM se encarga: la relación pasa a ser un atributo del modelo, y mover un libro actualiza las dos caras solo.

⏱ 20 minutos 📄 Lectura y comparación 🧭 Producto: las dos maneras, comparadas

0.1 · Lo que hiciste la clase pasada, en dos frases

Para conectar un libro con una editorial escribiste editorial_id=planeta.id, y para leerlos escribiste select(Libro, Editorial).where(...). Funciona, y es exactamente lo que hace SQL. Pero obliga a acordarte de dos cosas en cada operación: qué columna apunta a quién, y qué se escribe en el otro lado cuando mueves un libro.

ejemplo — la manera de la clase 20 
# A mano: yo me acuerdo de la columna y de la dirección
libro.editorial_id = oceano.id
session.add(libro)
session.commit()

for libro, editorial in session.exec(select(Libro, Editorial).where(Libro.editorial_id == Editorial.id)):
    print(libro.titulo, editorial.nombre)

0.2 · Lo que vas a aprender a hacer

ejemplo — la manera de esta clase 
# Con el ORM: la relación es un atributo del modelo
libro.editorial = oceano
session.add(libro)
session.commit()

for libro in session.exec(select(Libro)).all():
    print(libro.titulo, libro.editorial.nombre)
Nota — no es magia, es que el ORM conoce el esquema

Cuando declaras foreign_key="editorial.id", el ORM sabe que la columna editorial_id de libro apunta a editorial.id. Con esa información puede escribir la columna por ti cuando le das un objeto entero, y puede leerla y buscar el objeto cuando le pides la editorial. Eso es todo: el ORM no adivina, usa lo que le declaraste.

Unidad 01 · La pieza nueva

El atributo que habla

La clase 20 usó la clave foránea como lo que es: una columna. Esta clase le añade un atributo con el mismo nombre y otra intención: el que te deja recorrer la relación como si los objetos estuvieran unidos de verdad.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: los dos modelos con la relación declarada

1.1 · Las dos cosas que tiene el modelo

El modelo de Libro sigue teniendo su columna editorial_id —esa es la que se guarda en la base de datos— y además gana un atributo editorial, que es la que te permite trabajar con objetos.

ejemplo — la columna y el atributo 
class Editorial(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True)


class Libro(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    titulo: str = Field(index=True)
    anio: int

    # La COLUMNA: lo que se guarda en la tabla.
    editorial_id: int | None = Field(default=None, foreign_key="editorial.id")

    # El ATRIBUTO: lo que te permite recorrer la relación.
    editorial: Editorial | None = Relationship(back_populates="libros")
Precisión — las dos cosas se complementan

No se sustituyen: editorial_id es lo que se guarda, editorial es lo que se usa. El ORM mantiene las dos en coherencia: si le das un objeto editorial, escribe su id en la columna; si lees la columna, te da el objeto.

Por eso en la tabla solo hay una columna nueva. La relación no ocupa sitio en la base de datos: ocupa una línea en el modelo.

1.2 · Crear con la relación, sin tocar la columna

ejemplo — crear pasando el objeto 
planeta = Editorial(nombre="Planeta")
session.add(planeta)
session.commit()

# Se pasa el objeto, no el id. El ORM escribe el id en la columna.
amor = Libro(titulo="El amor en los tiempos del cólera", anio=1985, editorial=planeta)
session.add(amor)
session.commit()
session.refresh(amor)

print(amor.editorial.nombre)   # Planeta
Aplicación — por qué esto es mejor que el id a mano

Fíjate en lo que desaparece: el planeta.id ya no aparece en la línea de creación. ¿Y si el modelo del ORM lo escribiera mal? No puedes: el id lo pone la base de datos, y el ORM lo lee. Con el id a mano dependías de acordarte de hacer el commit en el momento exacto.

1.3 · La anotación de tipo: la flecha hacia adelante

Hay un detalle en el modelo de Editorial que parece un error y no lo es:

ejemplo — la referencia hacia adelante 
class Editorial(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True)

    # "Libro" entre comillas: la clase todavía no existe aquí.
    libros: list["Libro"] = Relationship(back_populates="editorial")

Las comillas no son un descuido: son la forma que tiene Python de decir «esta clase aún no está definida, pero lo estará». Sin ellas, Python intentaría resolver Libro al llegar a esa línea y fallaría, porque Libro está debajo en el archivo. Con ellas, la referencia se resuelve más tarde, cuando ya existen las dos clases.

Unidad 02 · Las dos caras

El espejo: back_populates

Una relación no tiene un solo sentido. Si un libro sabe su editorial, la editorial debería saber sus libros. back_populates es la línea que convierte dos atributos sueltos en un enlace de ida y vuelta.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el espejo funcionando en las dos direcciones

2.1 · Los dos lados de la misma puerta

Sin back_populates, cada relación va en un solo sentido: el libro sabe su editorial, pero la editorial no sabe sus libros. Con él, cada lado nombra al otro.

ejemplo — los dos lados, nombrándose 
class Editorial(SQLModel, table=True):
    ...
    # "libros" es el nombre del atributo del OTRO lado.
    libros: list["Libro"] = Relationship(back_populates="editorial")


class Libro(SQLModel, table=True):
    ...
    # "editorial" es el nombre del atributo del OTRO lado.
    editorial: Editorial | None = Relationship(back_populates="libros")
Precisión — el nombre es el del otro lado

En Editorial, back_populates="editorial": «el atributo que me corresponde en el otro lado se llama editorial». En Libro, back_populates="libros": «el mío se llama libros». Si los dos nombres no coinciden, SQLModel avisa al arrancar con un error que dice exactamente eso.

2.2 · El espejo, en movimiento

ejemplo — mover un libro actualiza las dos caras 
with Session(engine) as session:
    planeta = session.exec(select(Editorial).where(Editorial.nombre == "Planeta")).one()
    viento = session.exec(select(Libro).where(Libro.titulo == "La sombra del viento")).one()

    # Una sola línea: el libro pasa a Planeta.
    viento.editorial = planeta
    session.add(viento)
    session.commit()
    session.refresh(viento)

    print(viento.editorial.nombre)
    print([x.titulo for x in planeta.libros])
terminal — las dos caras, después de mover un libro
== UPDATE de la relación ==
La sombra del viento -> Planeta
planeta.libros = ['El amor en los tiempos del cólera', 'Cien años de soledad', 'La sombra del viento']
oceano.libros = []

Eso es el espejo: una sola línea de código, y las dos listas se actualizan. En la clase 20, para mover un libro tenías que acordarte de que la editorial vieja lo soltaba. Aquí no hay nada que recordar: el ORM mantiene la coherencia porque sabe que son dos caras de la misma puerta.

Unidad 03 · Las operaciones

Crear, leer y cortar una relación

Las cuatro operaciones de la clase 20, pero en el idioma del ORM. La diferencia no está en el código: está en que ya no teequivocas de dirección, porque el enlace tiene las dos puntas.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: las cuatro operaciones con objetos

3.1 · Leer: el ORM trae el objeto

Con la clase 20, para saber de qué editorial es un libro había que hacer un JOIN y emparejar los resultados. Con el atributo, el ORM hace la consulta por ti cuando le pides la editorial.

ejemplo — leer la relación 
with Session(engine) as session:
    editorial = session.exec(select(Editorial).where(Editorial.nombre == "Planeta")).one()

    # Los libros de la editorial: ya no hay que emparejar nada.
    print([x.titulo for x in editorial.libros])
terminal — leer la relación
== LECTURA por relación ==
libros de Planeta: ['El amor en los tiempos del cólera', 'Cien años de soledad']

3.2 · Cortar: poner la relación a None

ejemplo — cortar la relación 
viento.editorial = None
session.add(viento)
session.commit()
session.refresh(viento)

print(viento.editorial)                        # None
print([x.titulo for x in planeta.libros])
terminal — el resultado de cortar
== REMOVE de la relación ==
La sombra del viento -> None
planeta.libros = ['El amor en los tiempos del cólera', 'Cien años de soledad']
Advertencia — cortar no es borrar, ni al revés

Poner libro.editorial = None deja el libro en la tabla y su editorial_id a nulo. Borrar el libro es session.delete(libro). Son dos cosas distintas, igual que en la clase 20, pero aquí el ORM se encarga de que no se te olvide de ninguna.

3.3 · Lo que sigue sin resolver

Una relación que va y vuelve es cómoda, pero deja una pregunta: si borro una editorial, ¿qué pasa con sus libros? La clave foránea de la clase 20 solo comprueba al escribir. No dice nada de lo que ocurre al borrar. Y esa es la unidad siguiente.

Nota — dos preguntas, dos respuestas

Cuando borras una editorial, puedes decidir que pasa con sus libros de dos maneras:

  • Que no se pueda borrar mientras tenga libros (lo restringe: no hay libros sin editorial).
  • Que los libros se queden sin editorial (lo permite: habrá libros huérfanos, y hay que asumirlos).

Decidirlo es parte del trabajo, no un detalle que se deje para luego.

5.1 · El enunciado

Ejercicio

El enlace que se mantiene solo

Ficha del sistema

EntradaLos dos modelos con Relationship() y back_populates

Requisitos

  2. leer_desde_la_editorial(): los libros de una editorial, sin JOIN.
  3. mover(): cambia libro.editorial y comprueba las dos listas.

Modelo de respuesta

La diferencia se ve en cuanto comparas las dos versiones: la de la clase 20 tenía que acordarse de la columna editorial_id y de que la editorial vieja soltara al libro. Esta no se acuerda de nada.

las cuatro operaciones con el ORM 
def crear() -> None:
    """1. CREAR: se pasa el objeto editorial, no su id."""
    with Session(engine) as session:
        planeta = Editorial(nombre="Planeta")
        oceano = Editorial(nombre="Océano")
        session.add(planeta)
        session.add(oceano)
        session.commit()

        libros = [
            Libro(titulo="El amor en los tiempos del cólera", anio=1985, editorial=planeta),
            Libro(titulo="Cien años de soledad", anio=1967, editorial=planeta),
            Libro(titulo="La sombra del viento", anio=2001, editorial=oceano),
        ]
        for libro in libros:
            session.add(libro)
        session.commit()


def leer_desde_la_editorial(nombre: str) -> None:
    """2. LEER: el ORM carga la relación por nosotros."""
    with Session(engine) as session:
        editorial = session.exec(select(Editorial).where(Editorial.nombre == nombre)).one()
        print([x.titulo for x in editorial.libros])


def mover(titulo: str, editorial_nombre: str) -> None:
    """3. MOVER: una línea, y las dos caras se actualizan."""
    with Session(engine) as session:
        libro = session.exec(select(Libro).where(Libro.titulo == titulo)).one()
        editorial = session.exec(select(Editorial).where(Editorial.nombre == editorial_nombre)).one()

        libro.editorial = editorial
        session.add(libro)
        session.commit()
        session.refresh(libro)
        print(f"{libro.titulo} -> {libro.editorial.nombre}")


def cortar(titulo: str) -> None:
    """4. CORTAR: el libro sigue, pero ya no cuelga de ninguna editorial."""
    with Session(engine) as session:
        libro = session.exec(select(Libro).where(Libro.titulo == titulo)).one()
        libro.editorial = None
        session.add(libro)
        session.commit()
        session.refresh(libro)
        print(f"{libro.titulo} -> {libro.editorial}")

Fíjate en que mover y cortar ya no tocan ninguna columna. El ORM escribe el editorial_id por su cuenta a partir de la relación que le diste.

Aplicación — la comparación que pide el ejercicio

La versión de la clase 20 tenía cinco responsabilidades repartidas entre tú y la base de datos: elegir la columna, acertar con el orden de los commit(), emparejar los resultados del JOIN, acordarte de soltar el libro de la editorial vieja, y no dejar libros con ids que ya no existen. La de hoy tiene una: escribir qué editorial es. El resto lo hace el ORM, que para eso conoce el esquema.

6.1 · El enunciado

Ejercicio

Decidir qué pasa al borrar

Implementa las dos reglas posibles de borrado y decide cuál usa tu biblioteca. No es un ejercicio de escribir código: es de elegir una regla y sostenerla.

Ficha del sistema

EntradaUna editorial con dos libros, y el intento de borrarla
SalidaUna de las dos reglas, aplicada y comprobada
RestricciónLa regla se escribe en el modelo, no en la ruta
RestricciónCon SQLite, las claves foráneas tienen que estar activadas

Requisitos

  1. Regla A — no se puede borrar: la editorial con libros no se borra. (Con la base de datos: ondelete="RESTRICT".)
  2. Regla B — los libros se quedan sin editorial: la editorial se borra y sus libros quedan con la editorial a nulo. (Con la base de datos: ondelete="SET NULL".)
  3. El modelo con la regla elegida, y el passive_deletes="all" que le corresponde.
  4. La prueba: borrar la editorial y comprobar qué quedó en la tabla de libros.
  5. Un párrafo: por qué elegiste esa regla y qué tendrías que revisar en la interfaz si hubieras elegido la otra.

Modelo de respuesta

La regla B es la más cómoda para empezar, y la que se usa en la mayoría de los sistemas reales: un libro puede quedarse sin editorial durante un tiempo, y la aplicación lo refleja con un null.

el modelo con la regla B 
class Editorial(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True)

    # "all": que la base de datos borre, y no el ORM carga uno a uno.
    libros: list["Libro"] = Relationship(back_populates="editorial", passive_deletes="all")


class Libro(SQLModel, table=True):
    ...
    # Al borrar la editorial, la columna del libro se pone a nulo.
    editorial_id: int | None = Field(
        default=None, foreign_key="editorial.id", ondelete="SET NULL"
    )
    editorial: Editorial | None = Relationship(back_populates="libros")
la prueba del borrado 
with Session(engine) as session:
    planeta = session.exec(select(Editorial).where(Editorial.nombre == "Planeta")).one()
    libros = session.exec(select(Libro)).all()

    session.delete(planeta)
    session.commit()

    for libro in libros:
        session.refresh(libro)
        print(f"{libro.titulo}  editorial_id={libro.editorial_id}  editorial={libro.editorial}")

    print("libros que quedan:", len(session.exec(select(Libro)).all()))
terminal — el resultado real de borrar la editorial
== antes de borrar la editorial ==
planeta.libros = ['Cien años de soledad', 'El amor en los tiempos del cólera']
== al borrar la editorial, los libros quedan, pero sin editorial ==
Cien años de soledad editorial_id=None editorial=None
El amor en los tiempos del cólera editorial_id=None editorial=None
libros que quedan: 2
Advertencia — sin el PRAGMA, esto no pasa

La salida de arriba es con las claves foráneas activadas. Si ejecutas el mismo programa sin el PRAGMA foreign_keys=ON de la unidad 1, la editorial se borra y los libros se quedan con un editorial_id que ya no apunta a nadie: el libro fantasma. La base de datos no avisa, porque en SQLite no le importa. Por eso el PRAGMA no es un detalle: es la diferencia entre una regla y una casualidad.

Precisión — qué hace passive_deletes="all"

Cuando borras una editorial, el ORM tiene dos opciones: cargar todos sus libros en memoria y ponerles la editorial a nulo uno por uno (lo que se llama una cascada en Python), o dejar que lo haga la base de datos con su regla ondelete. Con passive_deletes="all" le dices al ORM que no se encargue: que lo haga la base de datos, que lo hace en una sola operación y no se equivoca.

7.3 · Síntesis: siete ideas para llevarse

01

La columna y el atributo son dos caras de lo mismo: una se guarda, la otra se usa.

02

back_populates convierte dos atributos en una relación de ida y vuelta: mover un lado mueve el otro.

03

Al pedir un atributo de relación, el ORM hace la consulta por ti: el JOIN ya no se escribe.

04

list["Libro"] con comillas es una referencia hacia adelante: la clase se definirá más abajo.

05

Cortar una relación no borra nada: el registro sigue existiendo, solo que ya no apunta a nadie.

06

La clave foránea comprueba al escribir, pero no decide al borrar: esa regla la escribes tú.

07

Un ORM no es una caja negra: es la capa que usa el esquema que tú declaraste. Sin esquema, no hay magia.

7.4 · Puente hacia la próxima clase

Ya sabes conectar dos tablas de una a muchos. Pero hay relaciones que no caben en ese molde: un libro puede tener varios autores, y un autor varios libros. Ninguna de las dos columnas puede ser la clave foránea de la otra, porque ninguna es «la principal».

La solución es una tercera tabla: la tabla intermedia. Y con ella llega el último caso: la relación que no solo guarda quién está conectado con quién, sino también cómo.
