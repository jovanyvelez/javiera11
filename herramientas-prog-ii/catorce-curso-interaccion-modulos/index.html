Unidad 00 · Apertura

El sistema que no conversa

Ya sabes consultar, insertar, editar y borrar. Lo que falta es que esas piezas trabajen juntas: que un botón de la lista lleve al formulario, que guardar devuelva la fila actualizada, y que volver no deje a nadie perdido. Hoy estudias la interacción entre módulos y el flujo de acciones del sistema.

⏱ 20 minutos 📄 Lectura y preparación 🧭 Producto: el mapa de módulos y el flujo dibujado

0.1 · La app que funciona a pedazos

Imagina una biblioteca digital. Hay una lista de autores, un botón para editar cada uno, un formulario para crear y otro para borrar. Cada pieza, por separado, funciona: la lista muestra filas, el formulario guarda, el botón de borrar borra. Pero cuando las juntas, algo falla. El usuario edita, guarda y la fila queda en blanco. O pulsa «Volver» y el navegador le pregunta si quiere recargar. O crea un autor y la tabla no se actualiza hasta que recarga a mano.

El problema no es el SQL. Ni siquiera es el framework. Es que ninguno de los módulos sabe qué espera el otro. Hoy abrimos la app Escritores —una biblioteca hecha con FastAPI, Jinja2, htmx y PostgreSQL— y trazamos el camino completo de cada acción.

Distinción — una función hace algo; un flujo lleva a alguien a algún sitio

actualizar_autor() es una función: recibe datos y escribe una fila. «Editar → Guardar → ver la fila actualizada» es un flujo: un camino que el usuario recorre, con un principio, un medio y un regreso. Las funciones se prueban solas; los flujos solo se entienden viendo cómo se encadenan.

Lo que se ve al abrir la app y lo que hay debajo
En la pantallaEn el sistema
ListarUna tabla con autoresGET /autores → consulta → página
EditarLa fila se convierte en formularioGET /autores/{id}/editar → pieza editable

0.2 · Qué es un «módulo» en este sistema

En esta clase, un módulo no es un paquete de Python ni un componente de React. Es una responsabilidad con su propio archivo. Cada uno sabe hacer una cosa, y se comunica con los demás a través de un contrato estrecho: una función que devuelve datos, una ruta que devuelve HTML, una plantilla que rellena huecos.

escritores/ — los módulos del sistema 
escritores/
├── main.py            la app: lifespan, pool, include del router
├── vistas.py          las rutas: cada endpoint pide datos y devuelve HTML
├── repositorio.py     el acceso a datos: SQL plano sobre asyncpg
├── esquemas.py        los modelos Pydantic de validación
├── dependencias.py    ConnectionDep: la conexión del pool por petición
├── database.py        el pool asyncpg (crear, adquirir, cerrar)
└── templates/         las plantillas Jinja2 (base, páginas, componentes)
Precisión — los módulos no son iguales entre sí

database.py no sabe que existe una tabla de autores. repositorio.py no sabe qué es HTML. vistas.py no escribe SQL. templates/ no decide nada: solo dibuja. Esa separación es lo que permite cambiar la pantalla sin tocar la base, o cambiar la base sin reescribir las plantillas.

0.3 · El flujo que vamos a trazar

El flujo central de esta clase tiene cuatro pasos. Es el mismo en cualquier sistema de administración: una lista, un modo edición, un guardado y un regreso.

Listar
Ver las piezas que hay. Es el estado de partida de casi todos los flujos.
Editar
Convertir una pieza en formulario. No cambia nada todavía: solo la vista.
Guardar
Enviar los cambios al servidor y ver la pieza actualizada.
Volver
Salir del modo edición sin guardar. La pieza vuelve a su estado normal.

1.1 · La dirección de las dependencias

Los módulos se llaman entre sí, pero no en cualquier dirección. La regla es simple: lo de arriba conoce lo de abajo; lo de abajo no conoce lo de arriba. Las vistas llaman al repositorio; el repositorio no llama a las vistas. Las plantillas reciben datos; no los buscan.

cadena de dependencias — de arriba abajo 
templates/     ← dibuja; no decide
    ↑
vistas.py      ← orquesta: pide datos, elige plantilla, responde
    ↑
repositorio.py ← consulta y escribe; no sabe qué es HTML
    ↑
database.py    ← presta conexiones; no sabe qué hay en ellas
Advertencia — el atajo que rompe el sistema

Si desde una plantilla llamas a una función del repositorio, o si desde el repositorio importas una plantilla, has roto la dirección. Hoy parece un atajo útil; en tres semanas, cuando cambies la base de datos, tendrás que reescribir las plantillas. La dirección de las dependencias no es estética: es lo que hace posible el cambio.

1.2 · Ficha de cada módulo

1.3 · Un ejemplo de contrato: la conexión

El contrato más limpio de Escritores es el que presta la conexión. La vista no crea conexiones ni las cierra: pide una al sistema de dependencias y la usa.

dependencias.py — el contrato de la conexión 
from typing import Annotated, AsyncIterator
from fastapi import Depends
import asyncpg
from database import pool

async def get_connection() -> AsyncIterator[asyncpg.Connection]:
    async with pool.acquire() as conn:
        yield conn

ConnectionDep = Annotated[asyncpg.Connection, Depends(get_connection)]
vistas.py — la vista que la usa sin conocerla 
@router.get("/autores")
async def listar_autores_vista(conn: ConnectionDep):
    autores = await repositorio.obtener_autores(conn)
    return templates.TemplateResponse(
        request, "autores.html", {"autores": autores}
    )
Nota — el tipo ConnectionDep es el contrato

La vista declara conn: ConnectionDep y ya está. No sabe si la conexión viene de un pool, de un mock en las pruebas o de un contenedor. Si mañana cambias asyncpg por otro driver, tocas database.py y dependencias.py; las vistas no se mueven.

Unidad 02 · El camino

El flujo de acciones

Listar, editar, guardar, volver. Cuatro acciones que, encadenadas, forman el camino más común de cualquier sistema de administración. Esta unidad las descompone en su cadena completa: botón, petición, ruta, repositorio, pieza.

⏱ 30 minutos 📄 Lectura y demo 🧭 Producto: cadena botón → pieza de cada acción

2.1 · La metáfora del rompecabezas

Piensa en la tabla de autores como un rompecabezas armado sobre la mesa. El marco es el contenedor de la tabla; cada fila es una pieza. Sin un mecanismo de actualización parcial, cualquier acción obligaría a tirar el rompecabezas al suelo y armarlo de nuevo: la página entera se recarga para cambiar una fila.

La idea de este flujo es lo contrario: cambiar solo la pieza que tocó. Y cada pieza tiene varios estados —normal, en edición, expandida— entre los que se mueve sin desmontar el resto del tablero.

estados de una pieza — la misma fila, tres versiones 
fila_autor.html          Gabo · Colombia · 1927    [Editar] [Borrar] [Libros]
        ↓ Editar
fila_editar_autor.html   [Gabo____] [Colombia__] [1927]  [Guardar] [Cancelar]
        ↓ Guardar                          o bien ↓ Cancelar
fila_autor.html          Gabo · Colombia · 1927    [Editar] [Borrar] [Libros]
Precisión — «Editar» no escribe nada en la base

Pasar de fila normal a fila en edición es un cambio de vista, no de datos. Por eso se responde con un GET: solo se pide la otra versión de la pieza. Si «Editar» hiciera un PUT, cada clic de edición modificaría la base, y «Cancelar» ya no podría ser un simple «vuelve a pedir».

2.2 · El ciclo de seis pasos

Todas las acciones —crear, editar, guardar, borrar, ver libros— siguen el mismo ciclo. Aprender el ciclo una vez sirve para todas.

El ciclo que se repite en cada clic
PasoQuiénQué hace
1NavegadorEl usuario pulsa un botón; se dispara la petición hx-*
2vistas.pyLa ruta recibe la petición y llama al repositorio
3repositorio.pyEjecuta SQL en PostgreSQL
4PostgreSQLDevuelve filas (o un error)
5vistas.pyRenderiza la pieza con Jinja2
6Navegadorhtmx encaja la pieza en el lugar indicado por hx-target
Distinción — el servidor fabrica piezas; el navegador las encaja

El servidor no «actualiza la página». Devuelve un fragmento de HTML y se olvida. El navegador es quien decide dónde ponerlo, según lo que digan hx-target y hx-swap. Esa división es la que permite que el mismo servidor sirva una fila, un formulario o la página entera sin cambiar de lógica.

2.3 · Las cuatro acciones, en cadena

Abajo tienes el trazador del flujo. Cada botón muestra la cadena completa de esa acción: el atributo htmx, la ruta, la función del repositorio, la pieza que sale y los estados por los que pasa la fila. Úsalo para asociar el clic con el recorrido.

    Unidad 03 · Los acuerdos

    Contratos entre módulos

    Cada paso del flujo es un intercambio: un módulo pide, otro responde. Esta unidad define qué se pide, qué se devuelve y qué se garantiza en cada intercambio — incluido el caso de error.

    ⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: tabla de peticiones y respuestas

    3.1 · El contrato de cada petición

    Un contrato no es un documento aparte: es lo que el receptor puede dar por supuesto. Si la vista llama a obtener_autor(conn, id) y espera una fila o None, eso es el contrato. Si la plantilla recibe autor.nombre, espera que ese campo exista.

    Qué se garantiza en cada intercambio
    De → aSe pideSe devuelveGarantía
    Vista → Repo Una conexión y parámetros ya validados Filas, una fila, None o un número SQL parametrizado; nunca texto pegado
    Repo → PostgreSQL SQL con huecos $n Registros tipados Los valores viajan aparte del texto
    Vista → Plantilla Un nombre de plantilla y un contexto HTML de la pieza La plantilla no consulta la base
    htmx → Vista Un verbo, una URL y (a veces) un formulario HTML de una pieza o de una sección Éxito y error devuelven la misma forma

    3.2 · Pieza, sección o página

    No toda respuesta es igual de grande. Elegir el tamaño correcto es parte del contrato: si devuelves de más, el navegador encaja basura; si devuelves de menos, la pantalla queda a medias.

    Tres tamaños de respuesta y cuándo usar cada uno
    TamañoCuándoEjemplo
    Pieza Cuando solo cambia una fila Editar, Guardar, Cancelar, Ver libros
    Sección Cuando cambian varias piezas o hay errores de formulario Crear (tabla + formulario con errores)
    Página Cuando se entra al módulo o se navega entre módulos GET /autores, GET /libros
    componentes/fila_autor.html — el contrato de una pieza

  <td>{{ autor.pais }}</td>

  </td>

    3.3 · Los atributos htmx como contrato

    Los atributos hx-* no son «magia de front-end». Son la cláusula del contrato que el navegador se compromete a cumplir: a quién se le pide, con qué verbo, qué datos van y dónde se encaja la respuesta.

    Los atributos que cierran el contrato
    AtributoSe lee como…Ejemplo
    hx-get / hx-post / hx-put / hx-delete«Al pulsar, pide esta URL con este verbo»hx-put="/autores/3"
    hx-target«…y la respuesta va a esta pieza»hx-target="closest tr"
    hx-swap«…y reemplázala así»hx-swap="outerHTML"
    hx-include«…enviando también estos datos»hx-include="closest tr"
    hx-select«…y de la respuesta, quédate solo con este trozo»hx-select="#autores"
    hx-confirm«…preguntando antes»hx-confirm="¿Borrar?"
    Advertencia — hx-include es el olvido más caro

    Al guardar una fila en edición, los datos viven en los <input> de esa fila. Sin hx-include="closest tr", htmx no los recolecta y el PUT llega vacío: la fila «se guarda» en blanco. Es el error que más tiempo roba en este flujo, y se detecta mirando la petición en las herramientas de desarrollo.

    3.4 · El contrato de error: misma forma, distinto estado

    La regla más elegante de este sistema: éxito y error devuelven la misma pieza. Si falta el nombre al crear un autor, la ruta responde la misma sección con status 422, los mensajes de error bajo cada campo y lo que el usuario escribió todavía en los inputs. Para htmx es indiferente: recibe HTML y lo encaja.

    vistas.py — éxito y error, la misma forma 
    @router.post("/autores")
async def crear_autor_vista(
    request: Request,
    conn: ConnectionDep,
    nombre: str = Form(...),
    pais: str = Form(""),
    nacimiento: int | None = Form(None),
):
    errores = {}
    try:
        datos = esquemas.AutorCrear(nombre=nombre, pais=pais, nacimiento=nacimiento)
    except ValidationError as e:
        errores = errores_por_campo(e)
        datos = None

    if datos:
        await repositorio.crear_autor(conn, datos)
        status = 200
    else:
        status = 422

    autores = await repositorio.obtener_autores(conn)
    return templates.TemplateResponse(
        request, "autores.html",
        {"autores": autores, "errores": errores,
         "valores": {"nombre": nombre, "pais": pais}},
        status_code=status,
    )
    Nota — htmx 4 intercambia también los 4xx

    htmx solo ignora 204 y 304. Una respuesta 422 con HTML se encaja igual que un 200. Por eso el error se comunica con la misma pieza, no con una página de error aparte que dejaría al usuario en otro módulo.

    1. Para «Editar»: qué recibe la ruta, qué pide al repositorio y qué devuelve a htmx.
    2. Para «Guardar»: qué datos viajan, dónde se validan y qué pasa si falla la validación.
    3. Para «Volver»: qué se lee, qué se escribe (nada) y qué pieza sale.
    4. Un caso de error propio: un 409 por nombre duplicado. ¿Qué pieza devuelves?

    2. Dos fichas más: Crear y Borrar, con su tamaño de respuesta justificado.
    3. Una captura de la pestaña Red mostrando el PUT de guardar, con su carga útil.
    4. Un párrafo (~80 palabras): qué se rompería si «Guardar» devolviera la página entera en lugar de la fila.

    5.2 · Paso 1: abrir el expediente

    Antes de hacer clic, prepara el terreno. Abre la consola de red, filtra por Fetch/XHR —o por el dominio— y deja la tabla de autores a la vista. Todo lo que hagas a partir de ahora debe verse ahí.

    checklist — lo que hay que mirar en cada clic 
    [ ] Verbo HTTP          GET / POST / PUT / DELETE
[ ] URL                 /autores/3/editar
[ ] Cuerpo              nombre=Gabo&pais=Colombia&nacimiento=1927
[ ] Status              200 / 422 / 409
[ ] Trozo HTML          <tr>…</tr>  o  <div id="autores">…</div>
[ ] Destino             la fila, la sección, la tabla

    5.3 · Paso 2: trazar las cuatro acciones

    Usa el trazador de la unidad 2 como plantilla y completa cada ficha con lo que veas en la red. La ficha de «Guardar» es la más rica: lleva cuerpo, validación y pieza de vuelta.

    ficha modelo — Guardar 
    Acción:     Guardar
Botón:      <button hx-put="/autores/3" hx-include="closest tr"
                   hx-target="closest tr" hx-swap="outerHTML">Guardar</button>
Petición:   PUT /autores/3
Cuerpo:     nombre=Gabo&pais=Colombia&nacimiento=1927
Ruta:       vistas.py → actualizar_autor_vista(conn, id=3, …)
Repositorio: actualizar_autor(conn, id=3, datos)
              → UPDATE autores SET … WHERE id = $1 RETURNING *
Éxito:      200 · fila_autor.html · se encaja en closest tr
Error:      422 · fila_editar_autor.html con errores · se encaja en closest tr
Estados:    fila en edición → fila normal   |   fila en edición → fila con errores
    Precisión — una ficha sin URL ni verbo no es una ficha

    Es fácil redactar «se guarda el autor» y creer que ya está. El valor del trazado está en los datos concretos: la URL exacta, el verbo, el campo del cuerpo, el nombre de la función. Si una ficha no puede citarlos, todavía no has trazado el flujo: solo lo has narrado.

    5.4 · Paso 3: el caso de error

    Ahora rompe la validación a propósito. Deja el nombre vacío, o pon un año imposible, y guarda. Observa: la petición sale igual, el status cambia y la pieza que vuelve trae errores.

    Advertencia — un error que devuelve HTML vacío es un error peor

    Si la ruta responde 422 sin cuerpo, htmx encaja nada y la fila se desvanece. El usuario se queda sin formulario, sin errores y sin lo que había escrito. La regla del contrato —misma forma, distinto estado— no es opcional.

    Unidad 06 · El regreso

    Volver, cancelar y estados

    Ir a algún sitio es fácil. Lo difícil es volver sin perderse y sin dejar la base a medias. Esta unidad cierra el flujo con el regreso y con la máquina de estados de una pieza.

    ⏱ 35 minutos 📄 Lectura y práctica 🧭 Producto: máquina de estados de una fila

    6.1 · «Volver» no es «deshacer»

    Cuando el usuario pulsa «Cancelar» en una fila en edición, espera dos cosas: dejar de ver el formulario y que no se haya guardado nada. El mecanismo más limpio no es «deshacer los cambios»: es volver a pedir la pieza normal, que la base nunca dejó de tener.

    vistas.py — cancelar no escribe nada 
    @router.get("/autores/{autor_id}/cancelar")
async def cancelar_autor_vista(conn: ConnectionDep, autor_id: int):
    autor = await repositorio.obtener_autor(conn, autor_id)
    return templates.TemplateResponse(
        request, "componentes/fila_autor.html", {"autor": autor}
    )
    Distinción — cancelar una vista vs. deshacer un cambio

    Cancelar una vista es barato y seguro: se pide otra vez el HTML del estado anterior y ya está. Deshacer un cambio es caro y propenso a errores: hay que saber qué se cambió, revertirlo y confirmar que funcionó. Si no se ha escrito nada, cancelar siempre debe ser lo primero.

    6.2 · La máquina de estados de una fila

    Una fila de autor tiene tres estados y cuatro transiciones. Dibujarlos evita que el flujo se rompa en un camino que nadie probó.

    máquina de estados — una fila de autor 
            ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
   ┌─────────┐   Editar    ┌──────────┐   Guardar  │
   │ normal  │ ──────────► │ edición  │ ──────────┘
   └─────────┘             └──────────┘   (o Cancelar)
        │                        │
        │ Libros                 │ Cancelar
        ▼                        │
   ┌──────────┐                  │
   │expandida │ ◄────────────────┘
   └──────────┘   (Cerrar → normal)
    Transiciones y su contrato
    TransiciónDisparadorPeticiónResultado
    normal → ediciónEditarGET …/editarfila editable
    edición → normalGuardarPUT …fila con datos nuevos
    edición → normalCancelarGET …/cancelarfila sin cambios
    edición → ediciónGuardar con errorPUT … → 422fila editable con errores
    normal → expandidaLibrosGET …/librosfila con la lista
    expandida → normalCerrarGET …/cancelarfila normal
    Nota — «Cerrar» reutiliza el endpoint de cancelar

    El botón «Cerrar» de la fila expandida llama al mismo GET /autores/{id}/cancelar. No hay un endpoint «cerrar». Esa reutilización es parte del diseño: el contrato solo dice «dame la pieza normal de este autor», y da igual desde qué estado la pidas.

    6.3 · Volver entre módulos

    Hay dos tipos de «volver» en un sistema como este, y confundirlos es la raíz de muchas pantallas rotas.

    Dos «volver» distintos
    TipoQué cambiaCómo se haceEjemplo
    Volver de una pieza Una fila, un fragmento hx-get de la pieza normal Cancelar, Cerrar
    Volver de un módulo La página entera Enlace normal, GET de otra URL De libros a autores
    Advertencia — el botón «Atrás» del navegador

    Si la edición de una fila se hace sin cambiar la URL, el botón «Atrás» del navegador no vuelve de la edición: sale del módulo entero. Para flujos largos —un formulario de una página— conviene que cada paso tenga su URL (por ejemplo /autores/3/editar como página). Para una fila de tabla, el intercambio de piezas es suficiente; solo no finjas que «Atrás» hará algo que no hará.

    6.4 · El estado vacío también es un estado

    La máquina de estados no termina en la fila. La tabla entera tiene su propio estado: con filas, vacía, cargando, con error. Diseñarlos es parte del flujo, no un extra.

    Estados de la tabla de autores
    EstadoCuándoQué ve el usuario

    VacíaLa lista viene []«Todavía no hay autores» y el formulario de crear
    Error de redEl servidor no responde«No se pudo cargar. Reintenta.»

    7.1 · El encargo

    Encargo

    La sección de libros de la biblioteca

    La biblioteca ya administra autores. Falta la sección de libros, con el mismo flujo y los mismos contratos. Debe listar los libros, permitir editar cada uno en su fila, guardar los cambios, cancelar sin escribir, y mostrar los autores de cada libro — el momento donde aparece el JOIN por la tabla intermedia.

    Ficha del sistema

    Contenido Rutas, repositorio, esquemas y plantillas de la entidad libros

    repositorio.py — el JOIN que asoma en el flujo 
    async def obtener_autores_de_libro(conn, libro_id: int) -> list[dict]:
    """Los autores de un libro, por la tabla intermedia autoria."""
    filas = await conn.fetch(
        """
        SELECT a.id, a.nombre, a.pais
        FROM autores a
        JOIN autoria au ON au.autor_id = a.id
        WHERE au.libro_id = $1
        ORDER BY a.nombre
        """,
        libro_id,
    )
    return [dict(f) for f in filas]

    7.3 · Las tres reglas que este taller no negocia

    Regla 1 — la dirección de las dependencias se mantiene

    Las plantillas no importan el repositorio. El repositorio no importa las plantillas. Si necesitas un dato en una plantilla, la vista se lo pasa en el contexto. Es la única forma de que la sección de libros se pueda probar, cambiar o reescribir sin arrastrar el resto.

    Regla 2 — éxito y error devuelven la misma forma

    Un 422 sin HTML deja la fila en blanco. Un 500 con stack trace filtra información del servidor. En ambos casos, la respuesta correcta es la pieza (o la sección) con el estado que toque: datos, o datos con errores.

    Regla 3 — cada acción tiene su tamaño de respuesta

    Editar y Cancelar devuelven una pieza. Crear devuelve la sección. Listar devuelve la página. Mezclar los tamaños —devolver la página donde se esperaba una fila— es el bug que más se ve en este flujo, y el más fácil de prevenir decidiéndolo antes de escribir la ruta.

    7.5 · Síntesis: siete ideas para llevarse

    01

    Un módulo es una responsabilidad con un contrato; la dirección de dependencias es lo que hace posible el cambio.

    02

    El flujo listar → editar → guardar → volver es el camino mínimo de cualquier sistema de administración.

    03

    Editar no escribe: es pedir la otra versión de la misma pieza. Guardar escribe y devuelve la pieza normal.

    04

    El ciclo es siempre el mismo: botón → ruta → repositorio → plantilla → encaje en el navegador.

    05

    Éxito y error devuelven la misma forma. Un error sin HTML deja la pantalla peor que antes.

    06

    Volver no es deshacer: es pedir otra vez la pieza normal. Si no se escribió nada, es gratis.

    07

    El tamaño de la respuesta —pieza, sección o página— se decide antes de escribir la ruta, no después.
