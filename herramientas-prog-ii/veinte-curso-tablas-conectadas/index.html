0.2 · El problema que resuelve el enlace

Sin clave foránea, el editorial_id de cada libro sería un número suelto. Y un número suelto se equivoca. Hoy laeditorial 3 es «Planeta»; mañana será «Océano» porque insertaste una editorial en medio, y todos los libros que apuntaban al 3RBON suddenly pertenecen a otra casa. En una biblioteca real, eso es un desastre silencioso.

Advertencia — el error que la clave foránea evita

Con la clave foránea, la base de datos se niega a guardar un editorial_id que no existe en la tabla editorial. No es una convención: es una regla que la base de datos hace cumplir. Por eso el orden de la clase 8 («conectar» antes de «usar») importa: primero las editoriales, después los libros.

Unidad 01 · La pieza nueva

La clave foránea

Una clave foránea no es un invento de SQLModel: es una columna normal que además dice «este valor tiene que existir en aquella otra tabla». Declararla es una línea; entender lo que implica es la unidad entera.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el esquema con su clave foránea

1.1 · Qué es una clave foránea

Es una columna cuyo valor no puede ser un valor inventado: o está vacía, o es el id de una fila que existe en la otra tabla. La regla la pone la base de datos, no tu código.

ejemplo — las dos tablas y su enlace 
class Editorial(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nombre: str = Field(index=True)


class Libro(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    titulo: str = Field(index=True)
    anio: int

    # La clave foránea: el id de una editorial, o nada.
    editorial_id: int | None = Field(default=None, foreign_key="editorial.id")
Precisión — «editorial.id», con punto y no con guion

El valor de foreign_key es el nombre de la tabla y el nombre de la columna, separados por un punto. La tabla se llama editorial (en minúsculas, como SQLModel las crea) y la columna se llama id. Escribir "editorial-id" o "Editorial.id" falla al arrancar, con un error que menciona «no such table».

1.2 · El esquema que sale de ahí

Con el modelo escrito, la base de datos refleja el enlace. Esto no es el CREATE TABLE de la clase 8: es lo que la base de datos dice que hay después de crear las tablas.

terminal — el esquema real de las dos tablas
editorial
id INTEGER
nombre VARCHAR
libro
id INTEGER
titulo VARCHAR
anio INTEGER
editorial_id INTEGER REFERENCES editorial.id

La última línea es el enlace. Fíjate en que editorial_id es una columna normal: puedes leerla, escribirla, indexarla. Lo único especial es la regla que la acompaña.

Advertencia — SQLite no aplica las claves foráneas por defecto

Este es uno de los Tricks que más sorprenden: SQLite ignora las claves foráneas salvo que se lo digas. Con la base de datos de la clase 8 (PostgreSQL) la regla se cumple sola; con el archivo .db de esta clase, no.

ejemplo — cómo activar las claves foráneas en SQLite 
from sqlalchemy import event


def activar_claves_foraneas(dbapi_con, con_record):
    # Se ejecuta en cada conexión nueva del pool.
    dbapi_con.execute("PRAGMA foreign_keys=ON")


engine = create_engine(sqlite_url, connect_args=connect_args)
event.listen(engine, "connect", activar_claves_foraneas)
Aplicación — por qué el curso usa PostgreSQL en la clase 8

Ahora se entiende por qué la clase 8 te pidió levantar un PostgreSQL con Docker: en PostgreSQL las claves foráneas siempre están activas. SQLite es cómodo para una clase de 4 horas (un archivo, cero instalación), pero tiene esta trampa. No es un defecto de SQLite: es que cada motor decide sus valores por defecto, y hay que conocerlos.

1.3 · Lo que la clave foránea NO hace

Lo que sí hace y lo que no hace una clave foránea
La clave foránea……impide esto…NO impide esto
Comprueba que el id exista Guardar un libro con editorial_id=99 si no hay editorial 99 Que el libro se guarde sin editorial (NULL es válido)
Se fija al borrar la editorial — Que el borrado de la editorial se lleve por delante sus libros

Unidad 02 · El orden

Crear filas conectadas

Conectar dos filas es fácil; conectarlas en el orden correcto es lo que cuesta. Esta unidad es corta y mecánica, y justo por eso se equivoca tanto: aquí se aprende el orden que hay que respetarlo siempre.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: padre e hijo, en orden

2.1 · El orden importa: primero el padre

Para meter un libro en la editorial «Planeta» necesitas el id de la editorial, y ese id no existe hasta que la editorial se guarda. Así que: primero la editorial, luego el libro.

ejemplo — guardar el padre y luego el hijo 
with Session(engine) as session:
    # 1. El padre. Todavía no tiene id.
    planeta = Editorial(nombre="Planeta")
    oceano = Editorial(nombre="Océano")
    session.add(planeta)
    session.add(oceano)
    session.commit()

    # 2. Ahora sí: el commit le ha dado los ids.
    amor = Libro(titulo="El amor en los tiempos del cólera", anio=1985, editorial_id=planeta.id)
    soledad = Libro(titulo="Cien años de soledad", anio=1967, editorial_id=planeta.id)
    viento = Libro(titulo="La sombra del viento", anio=2001, editorial_id=oceano.id)
    paramo = Libro(titulo="Pedro Páramo", anio=1955, editorial_id=None)

    for libro in (amor, soledad, viento, paramo):
        session.add(libro)
    session.commit()
terminal — lo que queda guardado
== CREADOS ==
1 El amor en los tiempos del cólera (1985) editorial_id=1
2 Cien años de soledad (1967) editorial_id=1
3 La sombra del viento (2001) editorial_id=2
4 Pedro Páramo (1955) editorial_id=None
Advertencia — el error de «guardar el hijo antes que el padre»

Si añades el libro antes de hacer el commit() del padre, su editorial_id valdrá None: el id de la editorial todavía no existe. El libro se guarda, pero sin editorial, y no hay ningún error que te avise. Es el mismo tipo de fallo silencioso que el formulario vacío de la clase 11: el programa «funciona» y el dato está mal.

Precisión — por qué el commit() va en medio

El commit() de la clase 18 tenía una sola misión: escribir. Aquí tiene una segunda: es el punto en que la base de datos genera los ids. Hasta que no haya un commit(), el planeta.id es None. Por eso los dos commit() —uno para los padres y otro para los hijos— no son un descuido de estilo: son la mitad del trabajo.

2.2 · La conexión también se puede romper

Con las claves foráneas activadas, esta llamada no se guarda:

ejemplo — el error que la base de datos sí avisa 
fantasma = Libro(titulo="Un libro que no existe", anio=2020, editorial_id=99)
session.add(fantasma)
session.commit()
# IntegrityError: FOREIGN KEY constraint failed

Este error es una buena noticia: la base de datos te ha parado. Compáralo con la clase 10, donde un formulario mal enviado se guardaba sin quejarse. La clave foránea es una red de seguridad debajo de la validación.

Unidad 03 · La lectura

Leer lo conectado: el JOIN

Crear el enlace era la mitad. La otra mitad es leerlo: traer el libro y su editorial en la misma respuesta. Eso es el JOIN, y en SQLModel se escribe con dos modelos en el select.

⏱ 30 minutos 📄 Lectura y práctica 🧭 Producto: el tablero de relaciones, funcionando

3.1 · Dos tablas, una consulta

La consulta de la clase 9 pedía un modelo: select(Libro). Para traer también la editorial, se piden los dos y se dice cómo se conectan:

ejemplo — el JOIN con SQLModel 
from sqlmodel import select

with Session(engine) as session:
    statement = select(Libro, Editorial).where(Libro.editorial_id == Editorial.id)
    for libro, editorial in session.exec(statement):
        print(f"{libro.titulo}  ->  {editorial.nombre}")
terminal — el resultado del JOIN
== JOIN: cada libro con su editorial ==
El amor en los tiempos del cólera -> Planeta
Cien años de soledad -> Planeta
La sombra del viento -> Océano
Advertencia — el JOIN se traga los libros sin editorial

«Pedro Páramo» no aparece en la lista, y no es un fallo: no tiene editorial, así que la condición Libro.editorial_id == Editorial.id no se cumple. Un JOIN normal (INNER JOIN) devuelve solo las filas que tienen pareja en las dos tablas.

Para traer también los libros sueltos se necesita un LEFT JOIN, que dice «incluye los libros aunque no tengan editorial». En SQLModel se hace con isouter=True.

4.2 · Vocabulario del taller

Estas siete palabras aparecerán en el taller final. Léelas ahora.

Clave foránea
Columna que apunta a otra tabla y no puede contener un valor que no exista allí.
Tabla referenciada
La tabla «padre»: la que contiene los valores a los que se puede apuntar.
Tabla que referencia
La tabla «hija»: la que tiene la columna con la clave foránea.
Cardinalidad
Cuántas filas de una tabla se corresponden con una de la otra: una a una, una a muchas o muchas a muchas.
JOIN
Consulta que trae columnas de dos tablas a la vez, uniendo por la clave foránea.
INNER JOIN
El JOIN normal: solo devuelve las filas que tienen pareja en las dos tablas.
LEFT JOIN
El JOIN que además trae las filas de la izquierda que no tienen pareja.

Ejercicio 5.1 · Las cuatro operaciones sobre el enlace

Conectar, leer, cambiar y desconectar. Son cuatro operaciones, y en una base de datos real son cuatro operaciones distintas que se confunden todo el tiempo. En 35 minutos las escribes las cuatro y compruebas que ninguna rompe lo anterior.

⏱ 35 minutos 💻 Ejercicio de desarrollo 🧭 Producto: las cuatro operaciones funcionando

5.1 · El enunciado

Ejercicio

Conectar, leer, mover y soltar

Escribe un programa que haga las cuatro operaciones sobre el enlace entre editorial y libro. Cada una va en su propia función, y cada una dice qué ha hecho.

Ficha del sistema

EntradaDos tablas: editorial y libro, unidas por editorial_id
SalidaCuatro funciones que operan sobre el enlace
RestricciónNinguna función escribe SQL: todo se hace con modelos y sesión
RestricciónDesconectar no es borrar: el libro sigue existiendo
RestricciónCon las claves foráneas activadas, guardar un editorial_id inexistente debe fallar

Requisitos

  1. crear_editoriales(): dos editoriales y cuatro libros, con el orden correcto.
  2. leer_con_join(): la consulta que trae libro y editorial juntos.
  3. mover_libro(): cambia el editorial_id de un libro.
  4. desconectar_libro(): pone el editorial_id a None sin borrar el libro.
  5. La comprobación de las cuatro: que cada función imprima lo que ha hecho y que los datos sigan siendo coherentes.

Modelo de respuesta

La parte que más cuesta no es el código: es entender que desconectar y borrar son cosas distintas, y que el JOIN no ve lo que no tiene pareja.

las cuatro operaciones 
def crear_editoriales() -> None:
    """1. CONECTAR: primero los padres, luego los hijos."""
    with Session(engine) as session:
        planeta = Editorial(nombre="Planeta")
        oceano = Editorial(nombre="Océano")
        session.add(planeta)
        session.add(oceano)
        session.commit()

        libros = [
            Libro(titulo="El amor en los tiempos del cólera", anio=1985, editorial_id=planeta.id),
            Libro(titulo="Cien años de soledad", anio=1967, editorial_id=planeta.id),
            Libro(titulo="La sombra del viento", anio=2001, editorial_id=oceano.id),
            Libro(titulo="Pedro Páramo", anio=1955, editorial_id=None),
        ]
        for libro in libros:
            session.add(libro)
        session.commit()


def leer_con_join() -> None:
    """2. LEER: el libro y su editorial en la misma fila."""
    with Session(engine) as session:
        statement = select(Libro, Editorial).where(Libro.editorial_id == Editorial.id)
        for libro, editorial in session.exec(statement):
            print(f"{libro.titulo}  ->  {editorial.nombre}")


def mover_libro(titulo: str, editorial_id: int) -> None:
    """3. MOVER: cambiar a qué editorial apunta un libro."""
    with Session(engine) as session:
        libro = session.exec(select(Libro).where(Libro.titulo == titulo)).one()
        libro.editorial_id = editorial_id
        session.add(libro)
        session.commit()
        session.refresh(libro)
        print(f"{libro.titulo} ahora editorial_id={libro.editorial_id}")


def desconectar_libro(titulo: str) -> None:
    """4. DESCONECTAR: el libro sigue, pero ya no apunta a nadie."""
    with Session(engine) as session:
        libro = session.exec(select(Libro).where(Libro.titulo == titulo)).one()
        libro.editorial_id = None
        session.add(libro)
        session.commit()
        session.refresh(libro)
        print(f"{libro.titulo} ya no está en ninguna editorial")

Fíjate en que mover_libro y desconectar_libro son el mismo código con un valor distinto. La diferencia entre mover y soltar está en el dato, no en la operación.

Advertencia — lo que NO es desconectar

Borrar la editorial es otra cosa: la clave foránea dice «este valor tiene que existir», pero no dice «bórralo todo cuando yo desaparezca». Qué pasa con los libros huérfanos al borrar su editorial es un problema aparte, y lo resuelve la clase 21.

Yo lo resolvería decidiendo explícitamente una de las dos reglas: o la columna no admite nulos y el borrado de la editorial falla mientras tenga libros, o se permite el nulo y se acepta que habrá libros sin editorial. Lo que no se puede es no decidir: ahí es donde aparecen los datos fantasma».

7.3 · Síntesis: siete ideas para llevarse

01

Una clave foránea es una columna que dice «este valor tiene que existir en aquella tabla»: o está vacía, o es un id real.

02

El orden de los commit() importa: hasta que el padre se guarda, su id no existe.

03

El JOIN normal solo trae las filas que tienen pareja en las dos tablas; las huérfanas se pierden.

04

Mover y desconectar son la misma operación con un dato distinto: el editorial_id.

05

Desconectar no es borrar: el libro sigue existiendo, solo que ya no apunta a nadie.

06

Una clave foránea comprueba al escribir, pero no decide qué pasa al borrar: eso hay que decidirlo aparte.

07

El contrato de la API manda también sobre las relaciones: el cliente recibe el nombre de la editorial, no su id.
