💡 ¿Por qué una base de datos?

Si guardas los datos en un archivo, se pierden al apagar la app y no soportan muchos usuarios. Una base de datos como PostgreSQL guarda los datos de forma segura y duradera, y permite que muchos usuarios lean y escriban a la vez.

🐘 PostgreSQL: la base de datos

⏱️ 35 minutos · "Donde viven los datos"

🧠 ¿Qué es PostgreSQL?

PostgreSQL es un sistema de gestión de bases de datos (SGBD). Es donde guardamos los datos de forma organizada, en tablas con filas y columnas. Es gratuito, muy potente y uno de los más usados del mundo.

📊

Tablas

Los datos se organizan en tablas con filas (registros) y columnas (campos).

🔒

Seguro

Protege los datos y evita que se corrompan.

👥

Concurrente

💾

Duradero

⚡ asyncpg: el driver asíncrono

⏱️ 35 minutos · "El traductor entre Python y PostgreSQL"

🧠 ¿Qué es un driver?

Python no sabe hablar con PostgreSQL por sí solo. Necesita un driver: una librería que hace de traductor entre el código Python y la base de datos. asyncpg es el driver asíncrono de PostgreSQL: mientras espera la respuesta, no bloquea el programa.

🦹 El villano: la conexión síncrona

Un driver síncrono (como psycopg2) se queda esperando la respuesta de la BD sin hacer nada más. Si 100 usuarios piden datos a la vez, cada uno espera su turno. Con asyncpg, mientras la BD responde, la app atiende a otros usuarios.

database.py — crear el pool con asyncpg 
import asyncpg

async def connect(db_url):
    # create_pool abre varias conexiones y las mantiene listas
    pool = await asyncpg.create_pool(
        dsn=db_url,
        min_size=1,
        max_size=10,
    )
    return pool

💡 asyncpg = asíncrono + PostgreSQL

El nombre lo dice todo: async (asíncrono) + pg (PostgreSQL). Es el driver asíncrono más usado para PostgreSQL en Python. Sus métodos principales son fetch (leer varios), fetchrow (leer uno) y execute (insertar/actualizar/borrar).

🏊 Pool de conexiones

⏱️ 35 minutos · "No abras una conexión por request"

🦹 El villano: 1 conexión por request

Si cada request abre y cierra una conexión, abrir/cerrar cuesta tiempo (~30 ms) y PostgreSQL se satura con tantas conexiones nuevas. Con 100 usuarios por segundo, pierdes segundos solo en conexiones. La solución: un pool que mantiene conexiones abiertas y las reutiliza.

🧠 La idea central

Un pool de conexiones es un conjunto de conexiones ya abiertas que se reutilizan. En vez de abrir y cerrar por cada request, la app pide prestada una conexión del pool, la usa y la devuelve. Se crea con asyncpg.create_pool().

📉

min_size

Conexiones mínimas abiertas desde el inicio.

📈

max_size

Máximo de conexiones simultáneas permitidas.

⏱️

timeout

Cuánto esperar para adquirir una conexión.

♻️

Reutilizar

Las conexiones se devuelven y se vuelven a usar.

🔄 Actividad en pareja — 3 minutos

Con su compañero/a: imaginen que el pool es el parqueadero de un restaurante. min_size=1 es el carro siempre listo, max_size=10 el tope. ¿Qué pasaría si max_size=1? ¿Y si min_size=1000? Discutan qué se rompe en cada caso.

🔍 En la vida real

Una app con 1000 usuarios concurrentes no necesita 1000 conexiones: con max_size=10 suele bastar, porque cada request usa la conexión por milisegundos y la devuelve. El pool es un parqueadero compartido: pocos carros alcanzan para muchos viajes.

🔗 get_connection: la dependencia con yield

⏱️ 35 minutos · "Prestar y devolver una conexión"

🧠 La idea central

get_connection es una dependencia de FastAPI que adquiere una conexión del pool, la cede a la ruta con yield y, al terminar, la devuelve al pool. La ruta nunca abre ni cierra nada: solo recibe una conexión lista y la usa.

database.py — get_connection 
async def get_connection():
    if db.pool is None:
        raise RuntimeError("El pool no está inicializado")

    # adquiere una conexión del pool
    async with db.pool.acquire() as conn:
        yield conn  # la cede a la ruta
    # al terminar, la conexión regresa al pool

🦹 El villano: la conexión colgada

Si adquieres una conexión y nunca la devuelves, el pool se queda sin conexiones y nadie más puede entrar. El async with garantiza que la conexión siempre regrese al pool, incluso si la ruta lanza un error. No hay fugas.

💡 yield vs return

Con return la función termina. Con yield la función se pausa, entrega el valor y, cuando la ruta termina, retoma para ejecutar la limpieza (devolver la conexión). Por eso es ideal para "pedir prestado y devolver".

🔄 Lifespan: conectar y desconectar

⏱️ 35 minutos · "El pool vive desde que arranca hasta que apaga"

🦹 El villano: el pool que nunca se cierra

Si creas el pool al arrancar pero nunca lo cierras, cada reinicio deja conexiones zombis en PostgreSQL. Tras unos días, la BD se queda sin conexiones y nadie puede entrar. La solución: cerrar el pool en el lifespan.

🧠 La idea central

El pool se crea una sola vez al arrancar la app y se cierra una sola vez al apagarla. Esto se hace en el lifespan de FastAPI, que ya vimos en la clase 2. Jamás se crea dentro de una ruta.

main.py — lifespan con el pool 
@asynccontextmanager
async def lifespan(app: FastAPI):
    await db.connect(DATABASE_URL)   # arranque: abrir pool
    yield
    await db.close()                # apagado: cerrar pool

app = FastAPI(lifespan=lifespan)

💡 El flujo completo

Al arrancar: se abre el pool. Durante la vida de la app: cada request pide prestada una conexión y la devuelve. Al apagar: se cierra el pool. Todo limpio, sin conexiones zombis.

🔄 Actividad en pareja — 2 minutos

🔍 En la vida real

Este patrón (abrir al arrancar, cerrar al apagar) es universal en backends profesionales. El pool vive desde que el servidor arranca hasta que se apaga, y cada request solo "pide prestada" una conexión por milisegundos.

🛠️ Taller: diagnóstico de un backend que colapsa

⏱️ 40 minutos · "Aplica todo lo aprendido"

🛠️ Taller final El caso del backend que se queda sin conexiones

Una app funciona bien al principio, pero después de unos días nadie puede entrar: la base de datos dice "demasiadas conexiones". Tu misión es diagnosticar qué está mal.

🧠 Las pistas

  • El código abre una conexión por cada request.
  • El pool se crea pero nunca se cierra al apagar.
  • No hay get_connection con yield: las conexiones se quedan colgadas.
