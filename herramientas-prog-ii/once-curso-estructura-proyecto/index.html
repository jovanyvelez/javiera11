El objetivo, en una frase

Convertir un proyecto plano —siete archivos .py sueltos en la raíz— en una estructura de tres capas con responsabilidades separadas: conexión, lógica y diseño. El objetivo no es que quede bonito: es que cualquier persona del equipo sepa, sin preguntar, en qué archivo va una cosa nueva y dónde vive la que ya existe. Y que la aplicación quede exactamente igual para quien la usa. Si el usuario nota el cambio, es porque la reorganización se hizo mal.

⚠️ Cinco trampas de Windows que te van a parar (y cómo salir de ellas)

  • «python» no se reconoce como comando. En Windows el lanzador se llama py. Escribe py app.py en vez de python app.py. Si tampoco funciona, es que Python no está en el PATH: reinstálalo marcando «Add Python to PATH».
  • Las barras. En Windows las rutas usan \ y en Mac y Linux usan /. En los imports de Python da igual: from presentacion.rutas.autores import … funciona en los tres sistemas con la misma barra. Lo que sí es relativo al sistema es el directory="presentacion/templates" de Jinja2Templates, y también ahí funciona con /.
  • Los acentos se rompen al escribir archivos desde la terminal. Si creas un archivo con acentos o con la raya «—» usando el comando, hay que especificar la codificación. Por eso los comandos de esta clase que escriben archivos llevan -Encoding UTF8. Si prefieres evitarlo, crea los archivos en el editor: es más fácil y nunca falla.
  • «export» no se reconoce como comando. Ese es de Mac y Linux: en PowerShell las variables de entorno se escriben distinto. Para poner la de la base de datos: $env:DATABASE_URL = "postgresql://…", sin espacios alrededor del =. Ojo: la variable dura lo que dure esa terminal; si la cierras, hay que ponerla otra vez antes de arrancar el servidor.
  • «El proceso no puede acceder al archivo porque está siendo utilizado por otro proceso». Es Windows bloqueando el borrado o el movimiento de una carpeta que tiene el servidor funcionando. Cierra la terminal donde corre el servidor (o presiona Ctrl+C ahí) y vuelve a intentar. En Mac y Linux esto casi nunca pasa: es una protección propia de Windows.

§ 01 · El síntoma

Tener muchos archivos no es lo mismo que estar organizado

⏱️ 30 minutos · «Saber que algo está mal, aunque todavía funcione»

La idea central

biblioteca/ no está desordenada porque tenga siete archivos. Está desordenada porque los siete hacen cosas distintas y ninguno lo dice. Un archivo de 164 líneas que declara rutas, valida datos, elige plantilla y llama al SQL no se puede nombrar bien: no hay un nombre que lo describa. Y cuando no hay nombre, no hay lugar; y cuando no hay lugar, cada cambio es una búsqueda a ciegas.

La segunda regla: el nombre es la primera prueba

Antes de discutir si un archivo es grande o pequeño, hazle esta pregunta: ¿puedo decir qué hace en una frase, sin abrirlo? repositorio.py → «las consultas a la base de datos». Sí se puede. vistas.py → «las rutas… y también los SQL… y también los errores». No se puede. Un archivo al que no puedes nombrar bien no tiene una responsabilidad: tiene varias. Y un archivo con varias responsabilidades no se puede mover, no se puede probar y no se puede leer.

El antihéroe: la carpeta que no dice nada

Cuando alguien no sabe cómo organizar, crea la carpeta utils/. ¿Qué es un util? ¿La función que formatea una fecha? ¿La que valida un ISBN? ¿La que abre la conexión? Eso es un cajón de basura con otro nombre: cuando la necesitas, tienes que abrir la carpeta entera para ver si está ahí.

El criterio para evitarlo es simple: una carpeta se nombra por su responsabilidad, y todo lo que hay dentro comparte esa misma responsabilidad. Si algo no encaja, esa cosa no debería estar ahí. Y esa es exactamente la señal de que falta una carpeta, o de que el archivo está en el lugar equivocado.

Otros nombres que no dicen nada: misc/, cosas/, helpers2/, pruebas/ (¿pruebas de qué?), nuevo/, o ese temp/ que nadie borra. Cada uno de esos nombres es una pregunta que tu equipo te va a terminar haciendo.

Matiz importante: no es «organizar por tecnología»

Existe una organización que suena lógico y es un error: carpeta_python/, carpeta_html/, carpeta_sql/. ¿Por qué falla?Porque esas carpetas describen el lenguaje, no la responsabilidad. Van a funcionar exactamente igual el día que tu lógica esté en JavaScript y tus plantillas en otro motor, y ese día no te van a servir de nada. Además obligan a que una misma ruta viva lejos de sus propias pruebas.

Regla práctica: si el nombre de la carpeta cambia cuando cambias de tecnología, es una mala carpeta.

§ 02 · Mecánica

Cómo encuentra Python tus archivos (y por qué deja de encontrarlos)

⏱️ 40 minutos · «Módulos, paquetes y el __init__.py que todos tememos»

La idea central

Cuando escribes from database import db, Python hace dos cosas: busca un archivo llamado database.py dentro de una lista de carpetas, y luego lo registra como módulo disponible. Si la búsqueda falla, el programa no arranca, y el error te dice exactamente por qué. Hoy vas a ver esa búsqueda con tus propios ojos, porque es la llave para que el taller del bloque 06 no te desarme a mitad de camino.

Módulo, paquete, subpaquete

Tres palabras que se usan como sinónimos y no lo son:

PalabraQué es en la prácticaEjemplo en tu proyecto
Módulo Un archivo .py. Su nombre, sin el .py, es el nombre con el que se importa. repositorio.py → import repositorio
Paquete Una carpeta que además contiene un archivo __init__.py. Ese archivo es lo que convierte una simple carpeta en algo que Python puede importar como una unidad. dominio/__init__.py → from dominio import servicios
Subpaquete Un paquete dentro de otro paquete. Funciona igual: necesita su propio __init__.py. presentacion/rutas/__init__.py
🔎 la búsqueda, paso a paso
# Supongamos esto, lanzado desde la carpeta biblioteca/:
import nucleo.conexion

# 1. Python recorre una lista de carpetas donde puede buscar.
#    La primera de esa lista es la carpeta desde la que LANZASTE
#    el programa. Las otras las agrega el intérprete.
# 2. En cada carpeta busca una subcarpeta llamada  nucleo/
# 3. Dentro, busca el archivo  __init__.py
#    ├─ ¿Existe? → es un paquete. Sigue: busca  conexion.py  adentro.
#    └─ ¿No?    → no puede tratarla como paquete y te lo dice.
# 4. Ejecuta ese archivo UNA vez y guarda sus nombres en el módulo.
#    Por eso el segundo import del mismo archivo es instantáneo.

# Y esto es lo que hace que funcione:
uvicorn main:app # ← lanzado desde biblioteca/ → '.' es la raíz

El error que vas a ver, y cómo anticiparlo

Si borras un __init__.py, o si lanzas el servidor desde la carpeta equivocada, aparece esto:

ModuleNotFoundError: No module named 'nucleo'

# Y el más confuso de todos, el que desarmamos por completo en el bloque 04:
ImportError: cannot import name 'calcular_multa' from partially
initialized module 'dominio.servicios' (most likely due to a circular import)

El primero significa «no te encontré la carpeta»: o falta el __init__.py, o no estás parado en la raíz del proyecto. El segundo significa «dos archivos se están esperando mutuamente», y es el error que más cuesta cuando uno empieza a organizar. Lo desarmamos por completo en el bloque 04.

Import absoluto e import relativo

Cuando un archivo importa a otro hay dos formas de escribirlo. Las dos funcionan; el orden de la clase es una, y la razón es la legibilidad.

dominio/servicios.py
# ✅ ABSOLUTO — el que usamos en todo el proyecto.
#    Empieza en la raíz del proyecto. Se lee igual desde
#    cualquier archivo, sin importar dónde estés parado.
from nucleo.conexion import get_conexion
from dominio.repositorios import obtener_autores

# ◐ RELATIVO — relativo a QUIÉN está importando.
#    El punto significa «sube a mi carpeta». Un punto más es un
#    nivel más arriba.
from .repositorios import obtener_autores      # el que está a mi lado
from ..nucleo.conexion import get_conexion    # subo un nivel

# ¿Por qué absolutos? Porque al leer
#   from nucleo.conexion import get_conexion
# sabes de inmediato DÓNDE está ese archivo, sin contar
# puntos. Con los relativos tienes que saber dónde estás
# parado para poder entender la línea.

¿Qué va dentro de __init__.py?

Casi nada. Su trabajo es marcar la carpeta como paquete y, si quieres, exponer desde afuera lo que tenga sentido exponer. En este proyecto va una frase que dice qué hay adentro. Un __init__.py de trescientas líneas es un archivón disfrazado.

# nucleo/__init__.py
"""Capa 1 — Conexión. Configuración y pool de base de datos."""

# dominio/__init__.py
"""Capa 2 — Lógica. Reglas de la biblioteca, validación y repositorios."""

# presentacion/__init__.py
"""Capa 3 — Diseño. Rutas, plantillas y archivos estáticos."""

Más adelante, si quisieras escribir from dominio import servicios en vez de from dominio.servicios import …, el atajo se declara ahí. Hoy no hace falta: dejamos el archivo limpio.

§ 03 · Arquitectura

Tres capas, tres responsabilidades, tres carpetas

⏱️ 40 minutos · «El mapa del territorio»

La idea central

Una capa es un conjunto de archivos que comparten una sola responsabilidad. Cuando esa responsabilidad es la conexión, sus archivos viven juntos en nucleo/; cuando es la lógica del negocio, en dominio/; cuando es lo que el usuario ve, en presentacion/. Eso es todo: no hay magia, no hay framework, no hay nada más que cumplir un acuerdo. Y ese acuerdo es exactamente lo que convierte siete archivos sueltos en algo que se puede mantener, ampliar y entender.

El árbol final

Este es el destino, y es la referencia de todo el taller: cada archivo que crees tiene su lugar aquí. Haz clic en cada nodo para leer su contrato y entender por qué está donde está.

Selecciona un archivo o una carpeta del árbol para leer su contrato.

La tercera regla: el objetivo no es verse profesional

La estructura no existe para que tu proyecto se vea elegante en una exposición. Existe para que el próximo cambio sea barato. Si un cambio te obliga a abrir cuatro archivos, la estructura está mal. Si te obliga a abrir uno, está bien — sin importar cuántas carpetas tenga el árbol. Ármate de ese criterio para todo lo que viene.

Convenciones de nombres, para que el árbol se lea solo

  • Minúsculas, sin tildes, sin espacios. Carpetas y archivos: presentacion/, repositorios.py. Los imports se escriben más fácil y no hay sorpresas entre sistemas operativos.

  • El nombre es la primera documentación. Un archivo nuevo llamado cosas.py no lo va a abrir nadie. Uno llamado repositorios.py ya te dice qué buscar adentro.
  • Consistencia en el plural. No mezcles autor.py con autores.py en la misma carpeta.

§ 04 · La regla que lo sostiene todo

La flecha de dependencia: hacia dónde se puede importar

⏱️ 45 minutos · «La regla que separa la arquitectura de un montón de carpetas»

La idea central

Crear las carpetas es lo fácil. Lo que las convierte en arquitectura es una regla de una sola línea: las dependencias solo bajan. La capa de diseño puede usar la de lógica; la de lógica puede usar la de conexión; la de conexión no puede usar ninguna. Nunca hacia arriba, nunca al lado, nunca en círculo. Esa flecha es la razón por la que puedes cambiar la base de datos, la interfaz o la tecnología sin reescribir el negocio.

Capa 3 · la de arriba
presentacion/
Rutas, plantillas, estilos. Sabe que hay lógica y que hay conexión.
↓
Capa 2 · la del medio
dominio/
Reglas, validación y SQL. Sabe que hay conexión. No sabe que exista una interfaz.
↓
Capa 1 · la de abajo
nucleo/
Configuración y conexiones. No sabe que existen las otras dos.

Cómo se lee: cada capa solo tiene permiso para mirar hacia abajo, y las flechas nunca se cruzan. Por eso se llama «dependencia»: cuando cambias algo abajo, lo de arriba ni se entera; cuando cambias algo arriba, lo de abajo tampoco.

El villano número uno: el import que sube

La tentación aparece siempre en la capa de conexión. «Es que el pool necesita saber la URL… pero la URL está en un archivo de arriba». Y entonces aparece esto en nucleo/conexion.py:

# ❌ en nucleo/conexion.py — import hacia ARRIBA
from presentacion.config import CONFIGURACION   # prohibido

# ✅ la solución es DARLO POR PARÁMETRO (se llama «inversión»)
async def conectar(url: str):
    """La capa de conexión no sabe de dónde salió la URL. Solo la usa."""
    ...

# y en main.py, que sí puede ver todo, se hace la unión:
from nucleo.conexion import conectar
from nucleo.configuracion import CONFIGURACION
conectar(CONFIGURACION.base_datos)

La prueba para detectarlo: pregúntate «¿esta función de la capa de abajo está hablando de algo de arriba?». Si la respuesta es sí, casi siempre la respuesta es «pásaselo como parámetro».

El villano número dos: los imports circulares

Ocurren cuando A importa a B y B importa a A. Python intenta cargarlos y, cuando llega al segundo, se encuentra con que el primero todavía no terminó de cargarse:

❌ el error exacto que vas a ver
ImportError: cannot import name 'calcular_multa' from partially
initialized module 'dominio.servicios' (most likely due to a circular import)

Las tres causas típicas y cómo se arreglan, en orden de preferencia:

CausaCómo se veArreglo
Constante compartida en el lugar equivocado Dos módulos necesitan TARIFA_POR_DIA y cada uno tiene su propia copia escrita. Bájala a la capa que usan los dos —nucleo/configuracion.py si es configuración— o al tercer archivo más bajo que ambos puedan importar.
Una función que quedó en la capa de arriba dominio/servicios.py importa desde presentacion/rutas/… para «reutilizar» algo que en realidad es de negocio. Baja la función a dominio/, que es donde pertenece, y deja que presentacion/ la importe. La flecha queda bien y el círculo desaparece.
Un archivo «de utilidades» que lo importa todo Todos importan utils.py, y utils.py importa a todos para tenerlos a mano. Elimínalo. Cada cosa va con lo suyo. Un archivo que lo importa todo no es una capa: es un nudo.

El truco que la industria usa en serio: invertir el control

Cuando dominio/servicios.py necesita guardar un autor hay dos caminos. El primero —el que tentaría a un estudiante— es que el servicio importe el repositorio. El segundo es que se lo pasen por parámetro:

# presentacion/rutas/autores.py — quien lo ve todo, decide
from dominio.servicios import registrar_autor

# El servicio no importa nada: recibe lo que necesita.
async def registrar_autor(conn, datos, guardar):
    autor = validar(datos)                  # regla
    total = await contar_autores(conn)          # consulta
    if total >= 1000:                     # regla de negocio
        raise LimiteAlcanzado()
    return await guardar(conn, autor)          # me lo dieron hecho

# …y así, un día, puedes probarlo con una «guardar» falsa:
autores = []
await registrar_autor(None, datos,
                        guardar=lambda c, a: autores.append(a))

Esto se llama inversión de dependencias, y es la diferencia entre un código que se puede probar y un código que solo se puede ejecutar con la base de datos real conectada. No tienes que dominarlo hoy: basta con que sepas que existe, para que el día que lo veas en un tutorial no te asuste.

Dos palabras que vas a escuchar siempre

Cohesión alta — lo que buscamos

Un archivo donde todo lo que hay adentro hace cosas parecidas. Es lo que produce el nombre del archivo: si tienes que pensarlo mucho, la cohesión es baja. Un buen repositorios.py tiene cohesión alta.

Acoplamiento bajo — lo que buscamos

Cuánto depende un archivo de los demás. Bajo acoplamiento significa que cambiar un archivo no obliga a tocar los demás. La flecha de dependencia existe justamente para bajar el acoplamiento.

La cuarta regla: si una capa necesita mirar hacia arriba, es que algo está mal

Casi siempre, el problema real no es el import: es que esa función no estaba en la capa correcta. Mover el archivo a donde pertenece arregla el import y además arregla el nombre. Cuando te toque pelear con un import hacia arriba, no busques el truco para esquivarlo: pregúntate qué responsabilidad está haciendo esa capa y muévela.

    async with pool.acquire() as conn:
        yield conn            # la entrega a la ruta…
                          # …y la devuelve sola al terminar
La diferencia con el proyecto plano: antes esto eran database.py y dependencias.py, dos archivos en la raíz, sin ningún indicio de que fueran infraestructura. Ahora están juntos, y el nombre nucleo/ lo dice.

from typing import AsyncGenerator

import asyncpg

from nucleo.configuracion import CONFIGURACION


class Conexion:
    """Abre y cierra el pool de conexiones. No sabe nada de la biblioteca."""

    def __init__(self) -> None:
        self.pool: asyncpg.Pool | None = None

    async def conectar(self, url: str) -> None:
        if self.pool is not None:
            return
        self.pool = await asyncpg.create_pool(
            dsn=url, min_size=1, max_size=10
        )

    async def cerrar(self) -> None:
        if self.pool is not None:
            await self.pool.close()
            self.pool = None


conexion = Conexion()


async def get_conexion() -> AsyncGenerator[asyncpg.Connection, None]:
    """Dependencia de FastAPI: cede una conexión del pool y la devuelve."""
    if conexion.pool is None:
        raise RuntimeError("El pool no está abierto.")
    async with conexion.pool.acquire() as conn:
        yield conn

# El alias que antes vivía solo en dependencias.py, ahora con su casa:
ConexionDep = Annotated[asyncpg.Connection, Depends(get_conexion)]

"""Reglas de la biblioteca.

Aquí vive lo que la biblioteca sabe hacer. No sabe de HTTP,
no sabe de plantillas y no abre conexiones: las recibe.
"""

from dominio import repositorios


async def listar_autores(conn) -> list[dict]:
    """Todos los autores, de la más antigua a la más nueva."""
    return await repositorios.obtener_autores(conn)


async def registrar_autor(conn, nombre: str, pais: str | None, nacimiento: int | None) -> dict:
    """Crea un autor. Regla: no se puede registrar dos veces el mismo nombre."""
    repetido = await repositorios.existe_autor_con_nombre(conn, nombre)

    if repetido:
        raise AutorDuplicado(nombre)

    return await repositorios.crear_autor(conn, nombre, pais, nacimiento)


class AutorDuplicado(Exception):
    """Regla violada: ya existe un autor con ese nombre."""

async def existe_autor_con_nombre(conn, nombre: str) -> bool:
    """¿Ya existe un autor con ese nombre? La pregunta más simple de todas."""
    return await conn.fetchval(
        "SELECT EXISTS(SELECT 1 FROM autores WHERE nombre = $1)", nombre
