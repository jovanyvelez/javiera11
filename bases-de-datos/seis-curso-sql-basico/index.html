🗣️ ¿Cómo le hablas a una base de datos?

En la Clase 4 modelamos entidades y relaciones, y en la Clase 5 normalizamos hasta 3FN. Sabemos qué tablas debe tener una BD. Pero… ¿cómo le decimos a PostgreSQL que las cree? ¿Cómo le pedimos que inserte un cliente, que muestre todos los libros de 2024, que actualice un precio o que borre un préstamo? La respuesta es SQL, el Structured Query Language: un lenguaje inglés-like que inventó IBM en los 70 y que hoy hablan todas las bases de datos del planeta. Hoy vamos a aprender su estructura general y los dos sub-lenguajes que abren todas las puertas: DDL (para construir la BD) y DML (para manejar sus datos).

📜 ¿Qué es SQL?

Misión 01 · Historia, sub-lenguajes y sintaxis general · ~30 min

SQL (Structured Query Language, lenguaje de consulta estructurado) es el lenguaje que usamos para hablar con las bases de datos relacionales. Lo inventaron Donald Chamberlin y Raymond Boyce en IBM en 1974, basándose en las ideas de Edgar F. Codd (el mismo Codd de la normalización de la Clase 5). Hoy lo hablan PostgreSQL, MySQL, SQLite, Oracle, SQL Server y hasta motores NoSQL como Cassandra con un dialecto parecido. Es, sin exagerar, el segundo lenguaje más útil del mundo después del inglés.

📖 Definición formal

SQL es un lenguaje declarativo de acceso a bases de datos relacionales. «Declarativo» significa que describes el resultado que quieres, no la secuencia de pasos para obtenerlo. El SGBD (PostgreSQL) traduce tu sentencia a un plan de ejecución interno, optimiza índices y devuelve el resultado.

🧩 SQL no es un solo lenguaje: es una familia

SQL se divide en sub-lenguajes, cada uno con un trabajo distinto. Conocer esta división es lo que distingue a quien "sabe SQL" de quien "sólo hace SELECT". Hoy cubriremos los dos primeros; los demás los verás en clases siguientes.

Sub-lenguajeSiglaPara qué sirveComandos estrella
Data Definition LanguageDDLDefinir la estructura: crear, modificar y destruir bases de datos y tablas.CREATE, DROP, ALTER
Data Manipulation LanguageDMLManipular los datos: insertar, consultar, actualizar y borrar filas.INSERT, SELECT, UPDATE, DELETE
Data Query LanguageDQLConsultar datos (técnicamente SELECT solo). Muchos lo incluyen en DML.SELECT
Data Control LanguageDCLPermisos: quién puede hacer qué.GRANT, REVOKE
Transaction Control LanguageTCLTransacciones: agrupar operaciones que se hacen todas o ninguna.BEGIN, COMMIT, ROLLBACK

🧠 ¿Por qué SQL se parece al inglés?

Porque fue diseñado para que personas no programadoras pudieran consultar datos sin aprender un lenguaje de programación. Por eso las sentencias se leen casi como oraciones: SELECT nombre FROM clientes WHERE ciudad = 'Medellín'; → «Selecciona el nombre de los clientes donde la ciudad sea Medellín». Esa fue la idea original, y aunque hoy lo usamos sobre todo programadores, la filosofía sigue: claridad primero.

📐 Estructura general de una sentencia SQL

Toda sentencia SQL se compone de cláusulas: palabras clave seguidas de argumentos. El orden importa. Aquí van las más comunes, en el orden en que las escribes:

SQL — anatomía de un SELECT 
SELECT nombre, correo              -- 1. QUÉ columnas quieres ver
FROM   clientes                    -- 2. DE QUÉ tabla
WHERE  ciudad = 'Medellín'        -- 3. QUÉ filas (filtro)
ORDER BY nombre ASC;               -- 4. CÓMO ordenarlas

Las cláusulas SELECT, FROM, WHERE, ORDER BY van siempre en ese orden. Olvidarlo es el error #1 de principiantes. PostgreSQL te dará un error de sintaxis y no te dejará avanzar.

📏 Convenciones de sintaxis (para el cuaderno)

  • Mayúsculas y minúsculas no importan para las palabras clave: select = SELECT = Select. Pero sí importan para los valores: 'Medellín' ≠ 'medellín'.
  • Cada sentencia termina en punto y coma ;. Sin él, psql espera que sigas escribiendo.
  • Las cadenas van entre comillas simples: 'Ana Torres'. Las dobles "..." se usan para identificadores (nombres de columnas con espacios), y casi nunca las necesitas.
  • Los comentarios se escriben con -- (una línea) o /* ... */ (varias líneas).
  • Los identificadores (nombres de tablas, columnas) van en minúsculas por defecto. Si los escribes en mayúsculas, PostgreSQL los convierte a minúsculas. Por convención, en este curso usaremos snake_case: clientes, fecha_nacimiento.

💡 Mayúsculas para keywords, minúsculas para identificadores

Por legibilidad, escribiremos las palabras clave en MAYÚSCULAS (SELECT, FROM, WHERE) y los nombres de tablas/columnas en minúsculas (clientes, nombre). PostgreSQL no distingue, pero tu cerebro sí: así se lee mucho mejor.

🦹 El villano: "SQL es solo SELECT"

Muchos creen que SQL es únicamente SELECT para consultar. ¡Falso! Hoy verás que CREATE, INSERT, UPDATE y DELETE son igual de importantes. Un backend sin DDL no crea tablas, y sin DML no inserta nada. SQL es el lenguaje completo; SELECT es sólo su palabra más famosa.

🏗️ DDL: construir la base de datos

Misión 02 · CREATE / DROP / ALTER DATABASE · ~35 min

El Data Definition Language (DDL) es el sub-lenguaje que construye y destruye la estructura de la BD: las bases de datos mismas, las tablas, las columnas, las restricciones. Sus tres comandos estrella son CREATE (crear), DROP (destruir) y ALTER (modificar). Hoy trabajaremos los dos primeros; ALTER lo mencionamos para que sepas que existe.

🗄️ Bases de datos vs esquemas vs tablas

PostgreSQL tiene una jerarquía que conviene entender antes de escribir nada:

  • Un servidor PostgreSQL puede tener muchas bases de datos.
  • Una base de datos tiene por defecto un esquema llamado public, y dentro de él viven las tablas.
  • Una tabla tiene columnas y filas.

En este curso nos basta con: una base de datos → varias tablas. No tocaremos esquemas personalizados.

➕ CREATE DATABASE

Para crear una base de datos nueva, el comando es directísimo:

SQL — crear una base de datos 
CREATE DATABASE tienda_gamer;

Tras ejecutarlo, PostgreSQL responde CREATE DATABASE (en mayúsculas, así confirma). A partir de ese momento, tienda_gamer existe y puede tener tablas. Para empezar a usarla, te conectas a ella con \c tienda_gamer en psql, o la seleccionas al arrancar la conexión.

💡 Reglas para nombrar bases de datos

  • Minúsculas, sin espacios, sin tildes: tienda_gamer ✓ · Tienda Gamer ✗.
  • Usa snake_case con guion bajo: colegio_db, biblioteca_2026.
  • El nombre debe describir el proyecto: evita bd1, mibase, test.
  • No uses palabras reservadas de SQL (select, table, order...) como nombre.

🗑️ DROP DATABASE

Para borrar una base de datos entera —con todas sus tablas y datos— el comando es:

SQL — borrar una base de datos 
DROP DATABASE tienda_gamer;

🦹 El villano: "borrar la BD equivocada"

DROP DATABASE es irreversible: borra todo sin pedir confirmación. No hay papelera de reciclaje. Si lo ejecutas sobre la BD de producción por error, pierdes el trabajo de años. Reglas de oro: (1) nunca ejecutes DROP el lunes por la mañana; (2) antes de un DROP DATABASE, haz un pg_dump (backup); (3) si tienes dudas, añade IF EXISTS para que no falle si la BD no existe: DROP DATABASE IF EXISTS tienda_gamer;.

🔧 ALTER DATABASE

Para modificar propiedades de una BD existente (renombrarla, cambiar su dueño, configurar parámetros). No lo usaremos hoy, pero conviene conocerlo:

SQL — renombrar una base de datos 
ALTER DATABASE tienda_gamer RENAME TO tienda_gamer_v2;

🧪 Flujo típico de trabajo

El ciclo normal al empezar un proyecto nuevo es:

  1. CREATE DATABASE tienda_gamer;
  2. Conectarte a ella (\c tienda_gamer en psql).
  3. CREATE TABLE clientes (...); — lo veremos en el módulo 3.
  4. CREATE TABLE productos (...);
  5. … y así con todas las tablas del modelo.

📋 CREATE TABLE a fondo

Misión 03 · Columnas, tipos, PK, FK y restricciones · ~40 min

Una vez creada la base de datos, el siguiente paso es crear las tablas. El comando CREATE TABLE es el más rico de DDL: define columnas, tipos de datos, claves primarias, claves foráneas y restricciones. Es el momento en el que tu modelo normalizado (Clase 5) se vuelve real.

🧩 Anatomía de un CREATE TABLE

SQL — anatomía de CREATE TABLE 
CREATE TABLE clientes (
    id         SERIAL       PRIMARY KEY,         -- columna 1
    nombre     VARCHAR(100) NOT NULL,           -- columna 2
    correo     VARCHAR(150) UNIQUE,              -- columna 3
    ciudad_id  INTEGER      REFERENCES ciudades(id), -- columna 4 (FK)
    activo     BOOLEAN      DEFAULT TRUE            -- columna 5
);

Entre paréntesis van las columnas, separadas por comas. Cada columna tiene:

  • Nombre: id, nombre, correo… en snake_case.
  • Tipo de dato: SERIAL, VARCHAR(n), INTEGER, DECIMAL(p,s), DATE, BOOLEAN… (los vimos en la Clase 4).
  • Restricciones (opcionales): PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, REFERENCES (FK), CHECK.

🔑 Restricciones de columna (las más comunes)

RestricciónQué garantizaEjemplo
PRIMARY KEYLa columna es la clave primaria: única y no nula.id SERIAL PRIMARY KEY
NOT NULLLa columna no admite NULL: obligatoria en cada fila.nombre VARCHAR(100) NOT NULL
UNIQUENo se pueden repetir valores en la columna.correo VARCHAR(150) UNIQUE
DEFAULTValor por defecto si no se especifica al insertar.activo BOOLEAN DEFAULT TRUE
REFERENCES (FK)La columna es clave foránea: debe existir en la tabla referenciada.ciudad_id INTEGER REFERENCES ciudades(id)
CHECKUna condición que toda fila debe cumplir.edad INTEGER CHECK (edad >= 0)

💡 La diferencia entre PRIMARY KEY y UNIQUE

A simple vista parecen lo mismo (ambos impiden duplicados), pero PRIMARY KEY implica además NOT NULL automáticamente y sólo puede haber una por tabla. UNIQUE admite NULL (sí, raro pero cierto) y puedes tener varias columnas UNIQUE en la misma tabla. La PK es el "DNI" de la fila; UNIQUE es un "alias obligatorio pero no identificativo".

🔗 Claves foráneas (repaso activo)

Recordatorio de la Clase 4: una clave foránea conecta una tabla con otra. Al declarar ciudad_id INTEGER REFERENCES ciudades(id), PostgreSQL no permite insertar un cliente cuyo ciudad_id no exista en ciudades.id. Es la integridad referencial que ya conocemos, ahora escrita en SQL.

SQL — FK con comportamiento ON DELETE 
CREATE TABLE ventas_items (
    venta_id     INTEGER REFERENCES ventas(id) ON DELETE CASCADE,
    producto_id  INTEGER REFERENCES productos(id),
    cantidad     INTEGER NOT NULL CHECK (cantidad > 0),
    PRIMARY KEY (venta_id, producto_id)
);

Aquí tenemos una PK compuesta (venta_id, producto_id) (recordando la Clase 4: las N:M necesitan tabla puente con PK compuesta), una FK con ON DELETE CASCADE (si se borra una venta, se borran sus ítems automáticamente), y una restricción CHECK que prohíbe cantidades negativas o cero.

🦹 El villano: "la tabla sin PRIMARY KEY"

Si creas una tabla sin PK, PostgreSQL te lo permite (a diferencia de otros motores), pero es un error grave: nada garantiza que no haya filas duplicadas idénticas, y las relaciones FK no tienen a dónde apuntar. Siempre, siempre, siempre define una PK al crear una tabla. Si no se te ocurre una natural, usa id SERIAL PRIMARY KEY.

📏 El orden importa: tablas sin FK primero

Cuando tengas varias tablas con FK entre ellas, crea primero las que no dependen de nadie, y luego las que las referencian. Si intentas crear clientes (con FK a ciudades) antes que ciudades, PostgreSQL te dará el error relation "ciudades" does not exist.

SQL — orden correcto de creación (Tienda Gamer) 
-- 1. Tablas sin dependencias
CREATE TABLE ciudades (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE categorias (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(60) NOT NULL UNIQUE
);

-- 2. Tablas que referencian a las anteriores
CREATE TABLE clientes (
    id         SERIAL PRIMARY KEY,
    nombre     VARCHAR(100) NOT NULL,
    correo     VARCHAR(150) UNIQUE,
    ciudad_id  INTEGER REFERENCES ciudades(id)
);

CREATE TABLE productos (
    id            SERIAL PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL,
    categoria_id  INTEGER REFERENCES categorias(id),
    precio        DECIMAL(10,2) NOT NULL CHECK (precio > 0)
);

📌 DROP TABLE también existe (y también es peligroso)

Para borrar una tabla entera con todos sus datos: DROP TABLE clientes;. Mismas reglas que DROP DATABASE: es irreversible, usa IF EXISTS para evitar errores, y respeta el orden inverso al de creación (primero borra las que tienen FK, luego las referenciadas). Nunca uses DROP TABLE en producción sin un backup.

📝 DML: manipular los datos

Misión 04 · INSERT / SELECT / UPDATE / DELETE · ~40 min

El Data Manipulation Language (DML) es el sub-lenguaje que trabaja con las filas de las tablas: las inserta, las consulta, las actualiza y las borra. Sus cuatro comandos estrella son las operaciones CRUD (Create, Read, Update, Delete) que toda app hace contra una BD. Aprenderlos es el 80% de usar SQL.

Operación CRUDComando SQLQué hace
CreateINSERTAñade filas nuevas a una tabla.
ReadSELECTConsulta filas (con filtros, orden, etc.).
UpdateUPDATEModifica filas existentes.
DeleteDELETEBorra filas existentes.

➕ INSERT — añadir filas

Hay dos formas. La buena (explicitando columnas) y la peligrosa (sin columnas).

SQL — INSERT (forma recomendada) 
-- ✅ Forma buena: explicita las columnas a llenar
INSERT INTO clientes (nombre, correo, ciudad_id)
VALUES ('Ana Torres', 'ana@x.co', 1);

-- Se pueden insertar varias filas a la vez
INSERT INTO clientes (nombre, correo, ciudad_id)
VALUES
    ('Beto Ruiz',  'beto@x.co',  1),
    ('Carla Díaz', 'carla@x.co', 2);

🦹 El villano: "INSERT sin columnas"

INSERT INTO clientes VALUES (1, 'Ana', 'ana@x.co', 1, TRUE); parece corto y cómodo, pero depende del orden exacto de las columnas en la tabla. Si mañana alguien añade una columna nueva con ALTER TABLE, tu INSERT se rompe silenciosamente: el valor que creías mandar a correo podría ir a otra columna. Siempre explicita las columnas: INSERT INTO clientes (nombre, correo) VALUES (...). Es más largo pero inmune a cambios.

💡 SERIAL no se inserta

Si la PK es id SERIAL, no la incluyas en el INSERT: PostgreSQL le asigna automáticamente el siguiente número. Por eso omitimos id en los ejemplos de arriba. Si quisieras saber qué id se asignó, usa INSERT ... RETURNING id;.

🔎 SELECT — consultar filas

El comando más usado de SQL. Su estructura es la que vimos en el Módulo 1: SELECT ... FROM ... WHERE ... ORDER BY ....

SQL — SELECT en sus variantes 
-- Todos los clientes
SELECT * FROM clientes;

-- Sólo nombre y correo de los de Medellín (ciudad_id = 1)
SELECT nombre, correo FROM clientes WHERE ciudad_id = 1;

-- Ordenados por nombre descendente, sólo los 3 primeros
SELECT nombre, correo FROM clientes
ORDER BY nombre DESC
LIMIT 3;

-- Contar cuántos clientes hay por ciudad
SELECT ciudad_id, COUNT(*) FROM clientes GROUP BY ciudad_id;

El asterisco * significa "todas las columnas". Es útil para explorar, pero en producción conviene listar las columnas que necesitas (por rendimiento y claridad).

🧠 WHERE con operadores

El WHERE acepta muchos operadores: =, <> (distinto), >, <, >=, BETWEEN ... AND ..., IN (...), LIKE '%ana%' (patrón), IS NULL, AND, OR, NOT. Por ejemplo: WHERE nombre LIKE 'A%' filtra los que empiezan por A. WHERE edad BETWEEN 15 AND 17 filtra por rango. Los veremos con más profundidad en la próxima clase.

✏️ UPDATE — modificar filas

SQL — UPDATE con WHERE 
-- Cambiar el correo de Ana (id = 1)
UPDATE clientes
SET    correo = 'ana.nuevo@x.co'
WHERE  id = 1;

🦹 El villano: "UPDATE sin WHERE"

Si escribes UPDATE clientes SET correo = 'x@x.co'; sin WHERE, PostgreSQL cambiará el correo de todas las filas de la tabla. Sin confirmación. Sin papelera. Es el error más caro del mundo SQL. Regla de oro: antes de ejecutar un UPDATE, ejecuta el SELECT equivalente (SELECT * FROM clientes WHERE id = 1;) para confirmar que el filtro apunta a las filas correctas.

🗑️ DELETE — borrar filas

SQL — DELETE con WHERE 
-- Borrar el cliente con id = 5
DELETE FROM clientes WHERE id = 5;

-- Borrar todos los clientes inactivos
DELETE FROM clientes WHERE activo = FALSE;

🦹 El villano gemelo: "DELETE sin WHERE"

Igual que UPDATE, un DELETE FROM clientes; sin WHERE borra todas las filas de la tabla. Es el "DROP TABLE" silencioso: la tabla sigue existiendo, pero vacía. Siempre escribe el WHERE primero en el cuaderno, antes de la sentencia. Y si quieres vaciar una tabla entera a propósito, usa TRUNCATE TABLE clientes; (más rápido, pero igual de irreversible).

📦 Taller entregable: "Mascotitas"

Misión 06 · Caso end-to-end: crea la BD, las tablas y manipula datos · ~50 min

Taller final · Entregable Sistema de inventario y clientes para la tienda de mascotas "Mascotitas"

La tienda de mascotas Mascotitas quiere digitalizar su inventario y sus clientes. Tu misión, en pareja, es crear la BD y las tablas con DDL, insertar datos con DML, y consultarlos y actualizarlos. La entrega es un archivo SQL .sql que tu profe podrá ejecutar en PostgreSQL sin errores.

📋 Enunciado

Mascotitas vende productos (con nombre, precio y categoría) a clientes (con nombre, correo y teléfono). Cada producto pertenece a una categoría (Alimentos, Accesorios, Higiene, Juguetes). Cada cliente puede tener varias mascotas registradas (con nombre y especie: perro, gato, conejo, etc.). Necesitan:

  1. Una base de datos llamada mascotitas.
  2. Las tablas necesarias (modelo ya normalizado): categorias, productos, clientes, mascotas.
  3. Datos de ejemplo: 4 categorías, 6 productos, 4 clientes, 5 mascotas.
  4. Consultas que respondan preguntas del dueño.

🎯 Objetivos del entregable

Tu entrega, en pareja, debe contener seis partes dentro de un único archivo .sql:

  1. Creación de la BD: CREATE DATABASE + conectarse.
  2. DDL — creación de tablas: CREATE TABLE con PK, FK, NOT NULL, UNIQUE y CHECK, en el orden correcto.
  3. DML — inserciones: INSERT para las 4 categorías, 6 productos, 4 clientes y 5 mascotas.
  4. DML — consultas: 4 SELECT que respondan las preguntas del dueño (ver abajo).
  5. DML — una actualización y un borrado: un UPDATE y un DELETE con WHERE.
  6. Reflexión (en un bloque de comentarios al final): ¿qué comando te costó más escribir y por qué.

1 Crea la base de datos

Escribe la sentencia DDL para crear la BD mascotitas. Recuerda que en psql luego te conectas con \c mascotitas.

CREATE DATABASE mascotitas;
\c mascotitas
-- A partir de aquí, todas las sentencias se ejecutan dentro de mascotitas

2 Crea las tablas (DDL)

Modelo relacional normalizado:

  • categorias(id PK, nombre UNIQUE)
  • productos(id PK, nombre, precio DECIMAL(10,2) CHECK > 0, categoria_id FK → categorias)
  • clientes(id PK, nombre, correo UNIQUE, telefono)
  • mascotas(id PK, nombre, especie, cliente_id FK → clientes)

Escribe los 4 CREATE TABLE en el orden correcto (¡primero las que no tienen FK!).

-- 1. Tablas sin dependencias
CREATE TABLE categorias (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(60) NOT NULL UNIQUE
);

-- 2. Tabla que referencia categorias
CREATE TABLE productos (
    id            SERIAL PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL,
    precio        DECIMAL(10,2) NOT NULL CHECK (precio > 0),
    categoria_id  INTEGER REFERENCES categorias(id)
);

-- 3. Tabla sin dependencias (clientes)
CREATE TABLE clientes (
    id        SERIAL PRIMARY KEY,
    nombre    VARCHAR(100) NOT NULL,
    correo    VARCHAR(150) UNIQUE,
    telefono  VARCHAR(20)
);

-- 4. Mascotas referencia clientes
CREATE TABLE mascotas (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(80) NOT NULL,
    especie     VARCHAR(40) NOT NULL,
    cliente_id  INTEGER REFERENCES clientes(id)
);

4 Escribe 4 consultas (DML)

El dueño necesita responder estas preguntas con SELECT:

  1. ¿Qué productos cuestan más de $20.000?
  2. ¿Cuántas mascotas hay por especie?
  3. ¿Qué clientes no tienen teléfono registrado?
  4. Lista los productos de la categoría "Alimentos" ordenados por precio descendente.
-- 1. Productos que cuestan más de $20.000
SELECT nombre, precio FROM productos WHERE precio > 20000;

-- 2. Cuántas mascotas hay por especie
SELECT especie, COUNT(*) FROM mascotas GROUP BY especie;

-- 3. Clientes sin teléfono
SELECT nombre, correo FROM clientes WHERE telefono IS NULL;

-- 4. Productos de Alimentos ordenados por precio descendente
SELECT nombre, precio FROM productos
WHERE categoria_id = 1
ORDER BY precio DESC;

5 Una actualización y un borrado

Escribe:

  • Un UPDATE que cambie el teléfono del cliente "Dani Lozano" (que estaba vacío) a '3154445555'.
  • Un DELETE que borre la mascota "Bola" (la del cliente Carla).

Recuerda: ambos deben llevar WHERE. Antes de ejecutarlos, escribe en un comentario el SELECT de verificación.

-- Verificación previa al UPDATE
SELECT id, nombre, telefono FROM clientes WHERE nombre = 'Dani Lozano';
-- UPDATE: asignar teléfono a Dani
UPDATE clientes SET telefono = '3154445555' WHERE nombre = 'Dani Lozano';

-- Verificación previa al DELETE
SELECT id, nombre, especie FROM mascotas WHERE nombre = 'Bola';
-- DELETE: borrar a Bola
DELETE FROM mascotas WHERE nombre = 'Bola' AND cliente_id = 3;

Nota: usar nombre en el WHERE es correcto aquí porque los nombres son únicos en los datos de ejemplo; en una BD real usarías el id para evitar borrar varias "Bola" si las hubiera.
