🔌 database.py · Conexión y pool ▶
La URL de la BD, el pool de conexiones (init_db_pool, close_db_pool) y la dependencia get_db que presta una conexión a cada endpoint.
database.py — código completo 
from typing import AsyncGenerator

import asyncpg
from loguru import logger

DATABASE_URL = "postgresql://estudiantes:***@ep-withered-wind-apq7hmfj-pooler.c-7.us-east-1.aws.neon.tech/neondb?sslmode=require"

_pool: asyncpg.Pool | None = None


async def init_db_pool():
    """Inicializa el pool de conexiones."""
    global _pool
    if _pool is None:
        try:
            _pool = await asyncpg.create_pool(
                DATABASE_URL,
                min_size=10,      # conexiones mínimas abiertas
                max_size=20,      # máx. conexiones simultáneas
                max_queries=50000,  # reinicia tras X consultas
                max_inactive_connection_lifetime=300.0,
            )
            logger.info("Connection pool con PostgreSQL creado exitosamente.")
        except Exception as e:
            logger.error(f"Error al crear el connection pool: {e}")
            raise e


async def close_db_pool():
    """Cierra el pool de conexiones limpiamente."""
    global _pool
    if _pool is not None:
        await _pool.close()
        logger.info("Connection pool con PostgreSQL cerrado.")


async def get_db() -> AsyncGenerator[asyncpg.Connection, None]:
    """
    Dependencia para FastAPI.
    Adquiere una conexión del pool y la devuelve.
    Garantiza que la conexión se libere al terminar el request.
    """
    if _pool is None:
        raise RuntimeError("El pool de conexiones no ha sido inicializado.")

    async with _pool.acquire() as connection:
        yield connection
📖 consultas.py · Lógica y consultas ▶
Las consultas SQL y el endpoint /autores que ejecuta SELECT y devuelve los registros como JSON.
consultas.py — código completo 
import asyncpg
from fastapi import Depends, HTTPException
from loguru import logger

from database import get_db


async def autores(db: asyncpg.Connection = Depends(get_db)):
    """
    Endpoint concurrente. `db` es una conexión lista para usar
    tomada eficientemente del pool.
    """
    try:
        query = "SELECT * FROM autores LIMIT 10;"
        rows = await db.fetch(query)
        logger.info("ingreso a consultas")
        registros = [dict(row) for row in rows]
        logger.debug(f"los usuarios son: {registros}")
        return registros

    except Exception as e:
        raise HTTPException(
            status_code=500, detail=f"Error en la base de datos: {str(e)}"
        )
🚀 main.py · Arranque de la app ▶
La app FastAPI con el lifespan que crea el pool al arrancar y lo cierra al apagar, y registra el endpoint /usuarios.
main.py — código completo 
from contextlib import asynccontextmanager

from fastapi import FastAPI, Depends

from database import close_db_pool, get_db, init_db_pool
from consultas import autores


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Evento de inicio: creamos el pool
    await init_db_pool()
    yield
    # Evento de apagado: cerramos el pool
    await close_db_pool()


app = FastAPI(lifespan=lifespan)


@app.get("/usuarios")
async def listar_usuarios(datos=Depends(autores)):
    """
    Endpoint concurrente. `datos` proviene de una conexión lista
    para usar tomada eficientemente del pool.
    """
    return datos

💡 ¿Por qué tres archivos y no uno?

Separar la conexión (database), la lógica (consultas) y el arranque (main) es una buena práctica de organización. Cada archivo tiene una sola responsabilidad. Si mañana añades más tablas (libros, usuarios), solo tocas consultas.py; si cambias de BD, solo tocas database.py. Así escala un proyecto real.

⚡ asyncpg: el driver asíncrono

⏱️ 35 minutos · "El traductor entre Python y PostgreSQL" — async/await para la BD

🧠 ¿Qué es un driver de base de datos?

Python no sabe hablar con PostgreSQL por sí solo. Necesita un driver: una biblioteca que hace de traductor entre el código Python y el lenguaje de la BD. Existen varios drivers para PostgreSQL, y cada uno tiene sus características:

  • psycopg2 — El más antiguo y usado. Es síncrono: cuando envía una consulta, se queda esperando la respuesta sin hacer nada más.
  • asyncpg — Más moderno. Es asíncrono: mientras espera la respuesta, cede el control y deja que la app siga atendiendo a otros usuarios.

Ambos conectan a la misma BD y hacen lo mismo (consultar, insertar, actualizar). La diferencia es cómo esperan: psycopg2 se queda quieto; asyncpg aprovecha ese tiempo. Por eso asyncpg es más rápido en apps con muchos usuarios concurrentes.

🦹 El villano: el endpoint que bloquea el event loop

Tu API recibe 100 requests por segundo. Cada uno abre una conexión con psycopg2 (síncrono) y espera 50 ms a que la BD responda. Mientras espera, el hilo de FastAPI queda congelado: no puede atender a nadie más. Los usuarios ven la ruedita girar. La app "se cae" sin haberse caído. Ese es el problema de mezclar un driver síncrono con un framework asíncrono. La solución se llama asyncpg.

🧠 La idea central

asyncpg es una biblioteca de Python para hablar con PostgreSQL de forma asíncrona. Mientras la BD procesa la consulta, asyncpg cede el control al event loop con await, y FastAPI puede seguir atendiendo a otros usuarios. Es como un mesero que, en vez de quedarse parado esperando el plato, atiende a otras mesas y vuelve cuando la cocina está lista.

⚡

Asíncrono

Usa await para no bloquear. FastAPI puede atender 1000 requests a la vez.

🐰

Rápido

Está escrito en Cython. Es ~3× más veloz que psycopg2 en pruebas de rendimiento.

🐘

PostgreSQL puro

Habla el protocolo binario de Postgres. Soporta tipos, arrays, JSON, UUID.

🔧

API simple

fetch(), fetchrow(), execute(). Métodos directos para consultar, sin capas intermedias.

💡 ¿Qué es exactamente "asíncrono"?

Una función async def puede esperar con await sin congelar el programa. Mientras espera (a la BD, a la red, a un archivo), el event loop hace otras cosas. Es concurrencia sin hilos. FastAPI está construido sobre esto, y asyncpg encaja perfecto.

🔍 En la vida real

Instagram, Netflix y cualquier API con miles de usuarios concurrentes usan drivers asíncronos. Si usaran psycopg2 síncrono en FastAPI, cada query de 50 ms bloquearía a todos los demás usuarios. Con asyncpg, ese tiempo se aprovecha para atender a los demás. Esa es la diferencia entre una app que aguanta y una que no.

🏊 Pool de conexiones

⏱️ 35 minutos · "No abras una conexión por request" — el superpoder del pool

🦹 El villano: abrir 1 conexión por request

Cada vez que entra un usuario, la app abre una conexión TCP a PostgreSQL, hace la query y la cierra. Abrir y cerrar una conexión cuesta ~30 ms. Si tienes 100 usuarios por segundo, pierdes 3 segundos solo en conexiones. Y PostgreSQL se ahoga con tantas conexiones nuevas. La solución: un pool que mantiene conexiones abiertas y las reutiliza.

🧠 La idea central

Un pool de conexiones es un conjunto de conexiones ya abiertas que se reutilizan. En vez de abrir y cerrar por cada request, la app pide prestada una conexión del pool, la usa y la devuelve. En asyncpg se crea con asyncpg.create_pool() y tiene parámetros clave que controlan cuántas conexiones hay.

🎮 Interactivo: Anatomía de create_pool

Toca cada parámetro para entender qué controla. Son los que aparecen en database.py.

🏊 Parámetros de asyncpg.create_pool()
📉min_size Conexiones mínimas abiertas desde el inicio.
📈max_size Máximo de conexiones simultáneas permitidas.
🔄max_queries Reinicia la conexión tras X consultas (libera memoria).
⏲️max_inactive_connection_lifetime Cierra conexiones inactivas tras X segundos.

Toca un parámetro para ver su detalle

Cada parámetro controla un aspecto del ciclo de vida de las conexiones del pool.

database.py — init_db_pool() 
async def init_db_pool():
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(
            DATABASE_URL,
            min_size=10,                          # mín. abiertas
            max_size=20,                          # máx. simultáneas
            max_queries=50000,                   # reinicia tras X consultas
            max_inactive_connection_lifetime=300.0, # cierra inactivas tras 300s
        )

💡 Las dos funciones que gestionan el ciclo de vida

El pool se crea una sola vez al arrancar la app (init_db_pool) y se cierra una sola vez al apagarla (close_db_pool). Jamás se crea dentro de un endpoint. Si lo hicieras, abrirías un pool por cada request y volverías al problema del villano.

🔍 En la vida real

Una app con 1000 usuarios concurrentes no necesita 1000 conexiones: con max_size=20 suele bastar, porque cada request usa la conexión por milisegundos y la devuelve. El pool es como un parqueadero compartido: 20 carros alcanzan para 1000 viajes si cada uno dura poco.

🔗 get_db: la dependencia con yield

⏱️ 35 minutos · "Prestar y devolver" — cómo un endpoint obtiene una conexión sin preocuparse

🧠 La idea central

FastAPI permite definir dependencias: funciones que preparan algo que el endpoint necesita. get_db() es una dependencia que adquiere una conexión del pool, la cede al endpoint con yield y, al terminar el request, la devuelve al pool automáticamente. El endpoint nunca abre ni cierra nada: solo recibe una conexión lista y la usa.

database.py — get_db() 
async def get_db():
    # Adquiere una conexión del pool
    async with _pool.acquire() as connection:
        yield connection  # la cede al endpoint
    # al terminar el request, la conexión regresa al pool

🔄 Actividad en pareja — 2 minutos

Con su compañero/a: yield es como return pero con un "regresa después". ¿Qué creen que pasa si el endpoint lanza un error a mitad de la consulta? ¿Se devuelve la conexión al pool o se queda colgada? Adivinen (pista: async with la protege).

💡 yield vs return

Con return la función termina. Con yield la función se pausa, entrega el valor y, cuando el endpoint termina, retoma para ejecutar el código de limpieza (el bloque que sale del async with). Por eso es ideal para "pedir prestado y devolver".

🔍 En la vida real

El patrón "dependencia con yield" es tan útil que FastAPI lo usa para todo: conexiones de BD, sesiones de usuario, archivos abiertos, transacciones. Si el endpoint falla, el async with garantiza que la conexión siempre regresa al pool. No hay fugas de conexiones.

🚀 Lifespan + endpoint

⏱️ 35 minutos · "El ciclo de vida de la app" — arrancar, servir, apagar

🦹 El villano: el pool que nunca se cierra

La app crea el pool al arrancar… pero nunca lo cierra. Cada vez que reinicias el servidor, quedan conexiones zombis en PostgreSQL. Tras unos días, la BD se queda sin conexiones disponibles y nadie puede entrar. La solución es el patrón lifespan: un bloque que ejecuta algo al arrancar y algo al apagar.

🧠 La idea central

FastAPI usa @asynccontextmanager para definir un lifespan: código que corre antes de que la app empiece a recibir requests (abrir el pool) y después de que se apague (cerrar el pool). El endpoint solo declara que necesita una conexión con Depends(get_db) y FastAPI hace el resto.

main.py — lifespan + endpoint 
@asynccontextmanager
async def lifespan(app: FastAPI):
    await init_db_pool()   # arranque
    yield                   # la app sirve aquí
    await close_db_pool()  # apagado

app = FastAPI(lifespan=lifespan)

@app.get("/usuarios")
async def listar_usuarios(datos=Depends(autores)):
    return datos

🔄 El flujo completo de un request

En el código de arriba, listar_usuarios depende de autores (una función que vive en consultas.py y que a su vez depende de get_db). Cuando entra un request, FastAPI resuelve esa cadena de dependencias automáticamente. Veamos el viaje completo, paso a paso:

PasoQuiénQué hace
1ClienteEnvía GET /usuarios
2FastAPIResuelve Depends(autores) → Depends(get_db)
3get_dbAdquiere conexión del pool con async with
4autoresEjecuta db.fetch("SELECT * FROM autores LIMIT 10")
5asyncpgEnvía la query a PostgreSQL y await el resultado
6autoresConvierte rows a dict y devuelve
7get_dbEl async with termina y devuelve la conexión al pool
8FastAPIResponde JSON al cliente

Con su compañero/a: sigan los 8 pasos de la tabla en orden. ¿En qué paso se devuelve la conexión al pool? ¿Qué pasaría si el paso 4 (la consulta) fallara con un error? ¿Llegaría al paso 7? Discutan (pista: async with protege hasta en errores).

💡 ¿Por qué Depends y no importar get_db directo?

Con Depends(get_db), FastAPI se encarga de inyectar la conexión, de manejar el ciclo yield y de liberarla al final. Si la importaras y la llamaras a mano, tendrías que gestionar todo eso tú. Depends es el patrón oficial de FastAPI para dependencias con limpieza.

🔍 En la vida real

Cada vez que entras a Netflix y ves tu perfil, un endpoint como este corre: el request entra, FastAPI pide una conexión del pool, asyncpg consulta tu usuario, la conexión regresa al pool y te llega el JSON. Todo en menos de 50 ms. Y el pool nunca se abre ni se cierra por request: vive desde que arranca el servidor.

✨ Buenas prácticas de FastAPI

⏱️ 35 minutos · "El código que se lee solo" — Annotated, APIRouter, response_model

🧠 La idea central

FastAPI tiene convenciones oficiales que hacen el código reutilizable, tipado y documentado. Las cuatro que aplicamos en este proyecto: Annotated para dependencias, APIRouter para organizar rutas, response_model para validar la respuesta y type alias para reutilizar la dependencia de BD.

📊 Las 4 prácticas clave

🏷️

Annotated

Declarar dependencias y parámetros con Annotated[T, Depends(...)] en vez de T = Depends(...). Respeta los tipos y permite reutilizar.

🧩

APIRouter

Agrupar rutas en un router con prefix y tags propios. El router vive sus reglas, no include_router.

🛡️

response_model

Declarar response_model=MiModelo valida, filtra y serializa la respuesta. No expone campos sensibles por accidente.

♻️

Type alias

Crear DbDep = Annotated[Connection, Depends(get_db)] y reutilizarlo en cualquier endpoint sin repetir.

consultas.py — con buenas prácticas 
from typing import Annotated
from fastapi import APIRouter, Query
from database import DbDep

router = APIRouter(prefix="/autores", tags=["autores"])

@router.get("/", response_model=list[Autor])
async def autores(
    db: DbDep,
    limite: Annotated[int, Query(ge=1, le=100)] = 10,
):
    return await db.fetch("SELECT * FROM autores LIMIT $1", limite)

💡 ¿Por qué LIMIT $1 y no LIMIT {limite}?

Escribir f"SELECT ... LIMIT {limite}" pegaría el valor directo en la consulta. Si un usuario malintencionado envía limite = "10; DROP TABLE autores", la BD ejecutaría ambas sentencias y borraría la tabla. Eso se llama inyección SQL. En cambio, con $1, asyncpg envía el valor por separado y PostgreSQL lo trata como un número, no como código. Siempre parametriza: nunca pegues valores del usuario en una consulta con f-strings.

💡 La regla de oro

Si una dependencia se usa en más de un endpoint, créale un type alias (DbDep) y reutilízalo. Si un grupo de rutas comparte un prefijo (como /autores), ponlas en un APIRouter. 🔍 En la vida real

En un backend real con 50 endpoints, sin APIRouter tendrías un main.py de 1000 líneas. Con routers separados (autores.py, libros.py, usuarios.py), cada archivo tiene 100 líneas y se puede mantener por separado. Esa es la diferencia entre un proyecto que escala y uno que se vuelve inmanejable.

📋 El caso
