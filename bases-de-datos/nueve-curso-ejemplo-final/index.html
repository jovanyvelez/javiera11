🗺️ Entregable A: Modelo Entidad-Relación (MER)

Misión 01 · Entidades, atributos, PK, FK y diagrama · ~35 min

El primer paso de cualquier BD es el modelo. Antes de escribir una sola línea de SQL, tenemos que identificar las entidades (qué tablas habrá), sus atributos (qué columnas), las llaves primarias (PK) que identifican cada fila, y las llaves foráneas (FK) que conectan las tablas entre sí.

🧩 Identificando entidades

De las reglas de negocio del módulo anterior, podemos identificar 5 entidades:

Entidad¿Por qué?Tabla
DeporteCada torneo pertenece a un deporte (Fútbol, Baloncesto…)deportes
TorneoSe crean múltiples torneos para diferentes deportes y categoríastorneos
EquipoCada torneo tiene equipos inscritosequipos
JugadorUn jugador pertenece a un equipo; tiene fecha de nacimientojugadores
PartidoSe programan y se juegan partidos entre dos equipospartidos

🔑 Atributos, PK y FK

Aquí está el detalle de cada entidad con sus columnas, llaves y relaciones:

MER — descripción de entidades 
-- deportes (catálogo de deportes)
deportes(
  id          SERIAL PRIMARY KEY,      -- PK
  nombre      VARCHAR(50) NOT NULL UNIQUE  -- "Fútbol", "Baloncesto"...
)

-- torneos (cada torneo pertenece a un deporte y tiene una categoría)
torneos(
  id          SERIAL PRIMARY KEY,
  nombre      VARCHAR(100) NOT NULL,
  deporte_id  INTEGER REFERENCES deportes(id),  -- FK → deportes
  categoria   VARCHAR(20) NOT NULL       -- "Infantil", "Junior", "Veteranos"
)

-- equipos (cada equipo está inscrito en un torneo)
equipos(
  id          SERIAL PRIMARY KEY,
  nombre      VARCHAR(80) NOT NULL,
  torneo_id   INTEGER REFERENCES torneos(id)   -- FK → torneos
)

-- jugadores (cada jugador pertenece a un equipo)
jugadores(
  id          SERIAL PRIMARY KEY,
  nombre      VARCHAR(100) NOT NULL,
  fecha_nac   DATE NOT NULL,                  -- para validar categoría
  equipo_id   INTEGER REFERENCES equipos(id)   -- FK → equipos
)

-- partidos (local vs visitante, programados o finalizados)
partidos(
  id              SERIAL PRIMARY KEY,
  torneo_id       INTEGER REFERENCES torneos(id),
  fecha           DATE NOT NULL,
  hora            VARCHAR(5) NOT NULL,         -- "15:00"
  cancha          VARCHAR(60) NOT NULL,
  local_id        INTEGER REFERENCES equipos(id),  -- FK → equipos
  visitante_id    INTEGER REFERENCES equipos(id),  -- FK → equipos
  goles_local     INTEGER,                       -- NULL si no se ha jugado
  goles_visitante INTEGER,                       -- NULL si no se ha jugado
  estado          VARCHAR(15) NOT NULL        -- "programado" | "finalizado"
)

💡 Una FK puede apuntar a la misma tabla

En partidos, tanto local_id como visitante_id apuntan a equipos(id). Es una relación recursiva: un equipo es local en algunos partidos y visitante en otros. Esto es perfectamente válido en SQL — una tabla puede tener varias FK hacia la misma tabla destino.

🧠 Cardinalidades del modelo

  • Deportes → Torneos (1:N): un deporte tiene muchos torneos; un torneo tiene un deporte.
  • Torneos → Equipos (1:N): un torneo inscribe muchos equipos; un equipo pertenece a un torneo.
  • Equipos → Jugadores (1:N): un equipo tiene muchos jugadores; un jugador pertenece a un equipo.
  • Torneos → Partidos (1:N): un torneo programa muchos partidos; un partido pertenece a un torneo.
  • Equipos → Partidos (1:N, dos veces): un equipo es local en muchos partidos y visitante en muchos otros.

🏗️ Entregable B: Script DDL (CREATE TABLE)

Misión 02 · Creación de tablas con restricciones CHECK, FK, NOT NULL · ~35 min

Con el MER listo (módulo 1), el siguiente paso es traducirlo a SQL: crear las tablas con CREATE TABLE, definiendo las columnas, los tipos, las llaves primarias y foráneas, y las restricciones que garantizan que los datos siempre sean válidos. Es el momento en el que el modelo se vuelve real.

📐 El orden de creación importa

Recordatorio de la Clase 6: crea primero las tablas sin FK, y luego las que las referencian. Si intentas crear torneos (con FK a deportes) antes que deportes, PostgreSQL te dará un error.

DDL — CREATE TABLE (orden correcto) 
-- 1. Tabla sin dependencias (raíz del modelo)
CREATE TABLE deportes (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(50) NOT NULL UNIQUE
);

-- 2. Torneos (FK → deportes) + CHECK para categoría
CREATE TABLE torneos (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    deporte_id  INTEGER REFERENCES deportes(id),
    categoria   VARCHAR(20) NOT NULL
                CHECK (categoria IN ('Infantil', 'Junior', 'Veteranos'))
);

-- 3. Equipos (FK → torneos)
CREATE TABLE equipos (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(80) NOT NULL,
    torneo_id   INTEGER REFERENCES torneos(id)
);

-- 4. Jugadores (FK → equipos) + CHECK para fecha de nacimiento
CREATE TABLE jugadores (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    fecha_nac   DATE NOT NULL,
    equipo_id   INTEGER REFERENCES equipos(id)
);

-- 5. Partidos (2 FK → equipos + FK → torneos + CHECK para estado)
CREATE TABLE partidos (
    id              SERIAL PRIMARY KEY,
    torneo_id       INTEGER REFERENCES torneos(id),
    fecha           DATE NOT NULL,
    hora            VARCHAR(5) NOT NULL,
    cancha          VARCHAR(60) NOT NULL,
    local_id        INTEGER REFERENCES equipos(id),
    visitante_id    INTEGER REFERENCES equipos(id),
    goles_local     INTEGER,
    goles_visitante INTEGER,
    estado          VARCHAR(15) NOT NULL
                    CHECK (estado IN ('programado', 'finalizado'))
);

🛡️ Restricciones CHECK: validando las reglas de negocio

Las restricciones CHECK son la forma de traducir las reglas de negocio directamente al esquema de la BD. En este proyecto usamos dos:

RestricciónTablaQué garantiza
CHECK (categoria IN ('Infantil', 'Junior', 'Veteranos'))torneosSólo se permiten las 3 categorías oficiales. Cualquier otro valor es rechazado.
CHECK (estado IN ('programado', 'finalizado'))partidosUn partido sólo puede estar programado o finalizado (no "en juego", "cancelado", etc.).

💡 CHECK con fechas para validar categorías

La regla de negocio dice que la fecha de nacimiento del jugador debe validar a qué categoría pertenece. En una BD real, esto se validaría con un CHECK más complejo o con un TRIGGER que compare fecha_nac con la categoría del torneo del equipo. Por simplicidad, aquí sólo garantizamos que fecha_nac no sea NULL; la validación de categoría se hace en la capa de la app. Pero el concepto es el mismo: la BD protege sus propios datos.

🦹 El villano: "crear tablas en el orden equivocado"

Si intentas crear torneos antes que deportes, PostgreSQL te dará: ERROR: relation "deportes" does not exist. La FK no puede apuntar a una tabla que aún no existe. Regla de oro: crea en orden de dependencias (raíz primero), y borra en orden inverso (hijas primero).

💡 NULL explícito en INSERT

Para insertar un valor NULL explícitamente (como en los goles de un partido programado), se escribe la palabra NULL en el VALUES: NULL, NULL, 'programado'. PostgreSQL lo interpreta como «sin valor». Esto es distinto de omitir la columna (que sólo funciona si la columna admite NULL por defecto).

🔍 Entregable D: Consultas SQL (DQL)

Misión 04 · Las 4 consultas que necesita la app del colegio · ~40 min

La BD está diseñada y poblada. Ahora viene la parte que más se usa: las consultas. La app del colegio necesita cuatro consultas clave: registrar datos, listar próximos partidos, ver el histórico de resultados y calcular la tabla de posiciones. Cada una combina lo que aprendiste en las clases 6, 7 y 8.

1️⃣ Creación/Registro: nuevo torneo, equipo y jugadores

La app necesita INSERTs para que el coordinador registre nuevos torneos, inscriba equipos y asocie jugadores. Aquí van las sentencias de ejemplo:

DQL — Sentencias de registro (INSERT) 
-- 1. Registrar un nuevo torneo de Voleibol Infantil
INSERT INTO torneos (nombre, deporte_id, categoria)
VALUES ('Copa Voleibol Infantil 2026', 3, 'Infantil')
RETURNING id;

-- 2. Inscribir un equipo en ese torneo (usar el id devuelto)
INSERT INTO equipos (nombre, torneo_id)
VALUES ('Los Lobos', 4)  -- 4 = id del torneo recién creado
RETURNING id;

-- 3. Asociar jugadores al equipo (multi-fila con RETURNING)
INSERT INTO jugadores (nombre, fecha_nac, equipo_id) VALUES
    ('Daniela Ríos', '2014-03-10', 7),
    ('Andrés Soto', '2014-07-22', 7),
    ('Valentina Díaz', '2013-11-15', 7)
RETURNING id, nombre;

2️⃣ Próximos partidos programados

La app muestra a los estudiantes qué partidos vienen. Esta consulta cruza partidos con equipos (dos veces: local y visitante) y torneos para mostrar nombres legibles:

DQL — Próximos partidos (JOIN + WHERE + ORDER BY) 
SELECT  p.fecha, p.hora, p.cancha,
        t.nombre AS torneo,
        l.nombre AS local,
        v.nombre AS visitante
FROM partidos p
JOIN torneos t ON p.torneo_id = t.id
JOIN equipos l ON p.local_id = l.id
JOIN equipos v ON p.visitante_id = v.id
WHERE p.estado = 'programado'
ORDER BY p.fecha ASC;

💡 El mismo JOIN dos veces con aliases diferentes

Para traer el nombre del equipo local y del visitante en la misma fila, hacemos JOIN equipos dos veces, una con alias l (local) y otra con v (visitante). Cada JOIN conecta local_id o visitante_id con equipos.id. Así, en una sola fila, tienes ambos nombres. Es el patrón más útil de los JOINs.

3️⃣ Histórico de resultados

Los partidos ya jugados con sus marcadores, del más reciente al más antiguo:

DQL — Histórico de resultados (JOIN + WHERE + ORDER BY DESC) 
SELECT  p.fecha,
        l.nombre AS local,
        v.nombre AS visitante,
        p.goles_local,
        p.goles_visitante
FROM partidos p
JOIN equipos l ON p.local_id = l.id
JOIN equipos v ON p.visitante_id = v.id
WHERE p.estado = 'finalizado'
ORDER BY p.fecha DESC;

4️⃣ Tabla de posiciones

La consulta más compleja: calcular por equipo los partidos jugados (PJ), ganados (PG), empatados (PE), perdidos (PP), goles a favor (GF), goles en contra (GC), diferencia (DG) y puntos. Esto requiere agregación (COUNT, SUM) y GROUP BY — que veremos a fondo en la próxima clase. Aquí va una versión simplificada usando CASE WHEN dentro del SUM:

DQL — Tabla de posiciones (agregación con CASE WHEN) 
SELECT
    e.nombre AS equipo,
    COUNT(*) AS PJ,
    SUM(CASE WHEN p.goles_local > p.goles_visitante THEN 1 ELSE 0 END) AS PG,
    SUM(CASE WHEN p.goles_local = p.goles_visitante THEN 1 ELSE 0 END) AS PE,
    SUM(CASE WHEN p.goles_local < p.goles_visitante THEN 1 ELSE 0 END) AS PP,
    SUM(p.goles_local) AS GF,
    SUM(p.goles_visitante) AS GC,
    SUM(p.goles_local) - SUM(p.goles_visitante) AS DG,
    SUM(CASE WHEN p.goles_local > p.goles_visitante THEN 3
              WHEN p.goles_local = p.goles_visitante THEN 1
              ELSE 0 END) AS puntos
FROM partidos p
JOIN equipos e ON p.local_id = e.id
WHERE p.estado = 'finalizado'
GROUP BY e.nombre
ORDER BY puntos DESC;

🧠 ¿Qué hace CASE WHEN ... THEN ... ELSE ... END?

Es el if-then-else de SQL. Dentro de un SUM, cuenta cuántas filas cumplen la condición. Por ejemplo, SUM(CASE WHEN goles_local > goles_visitante THEN 1 ELSE 0 END) suma 1 por cada partido ganado como local y 0 por los demás — el resultado es el número de partidos ganados (PG). Es la forma de calcular estadísticas sin escribir código procedural.

2 DDL — CREATE TABLE × 5

Escribe los 5 CREATE TABLE en el orden correcto (deportes → torneos → equipos → jugadores → partidos) con todas las restricciones (PK, FK, NOT NULL, UNIQUE, CHECK).

CREATE TABLE deportes (
    id      SERIAL PRIMARY KEY,
    nombre  VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE torneos (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    deporte_id  INTEGER REFERENCES deportes(id),
    categoria   VARCHAR(20) NOT NULL
                CHECK (categoria IN ('Infantil', 'Junior', 'Veteranos'))
);

CREATE TABLE equipos (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(80) NOT NULL,
    torneo_id   INTEGER REFERENCES torneos(id)
);

CREATE TABLE jugadores (
    id          SERIAL PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    fecha_nac   DATE NOT NULL,
    equipo_id   INTEGER REFERENCES equipos(id)
);

CREATE TABLE partidos (
    id              SERIAL PRIMARY KEY,
    torneo_id       INTEGER REFERENCES torneos(id),
    fecha           DATE NOT NULL,
    hora            VARCHAR(5) NOT NULL,
    cancha          VARCHAR(60) NOT NULL,
    local_id        INTEGER REFERENCES equipos(id),
    visitante_id    INTEGER REFERENCES equipos(id),
    goles_local     INTEGER,
    goles_visitante INTEGER,
    estado          VARCHAR(15) NOT NULL
                    CHECK (estado IN ('programado', 'finalizado'))
);

4 DQL — Próximos partidos

Escribe la consulta que lista los partidos programados con fecha, hora, cancha, nombre del torneo y nombres de los equipos local y visitante. Usa 3 JOINs y ORDER BY fecha ASC.

-- Próximos partidos programados
SELECT  p.fecha, p.hora, p.cancha,
        t.nombre AS torneo,
        l.nombre AS local,
        v.nombre AS visitante
FROM partidos p
JOIN torneos t ON p.torneo_id = t.id
JOIN equipos l ON p.local_id = l.id
JOIN equipos v ON p.visitante_id = v.id
WHERE p.estado = 'programado'
ORDER BY p.fecha ASC;

5 DQL — Histórico de resultados

Escribe la consulta que lista los partidos finalizados con fecha, nombres de equipos y marcador, ordenados por fecha descendente (más recientes primero).

-- Histórico de resultados
SELECT  p.fecha,
        l.nombre AS local,
        v.nombre AS visitante,
        p.goles_local,
        p.goles_visitante
FROM partidos p
JOIN equipos l ON p.local_id = l.id
JOIN equipos v ON p.visitante_id = v.id
WHERE p.estado = 'finalizado'
ORDER BY p.fecha DESC;

/*
  Reflexión final:
  Lo más difícil fue el modelo de partidos: al principio no
  entendíamos cómo un partido podía tener dos equipos (local y
  visitante) apuntando a la misma tabla. Lo resolvimos con dos
  FK diferentes (local_id y visitante_id) y aprendimos que una
  tabla puede tener varias FK hacia la misma tabla destino.

  La consulta que más nos costó fue la de próximos partidos,
  porque requiere 3 JOINs en una sola sentencia (torneos + 2x
  equipos). Al principio repetíamos el alias "equipos" dos veces
  y PostgreSQL daba error. Aprendimos que cada JOIN necesita su
  propio alias (l y v) para distinguirlos.

  La gran lección: el MER es el plano, el DDL es el cemento, el
  DML son los muebles y el DQL es usar la casa. Sin plano, todo
  se cae.
*/
