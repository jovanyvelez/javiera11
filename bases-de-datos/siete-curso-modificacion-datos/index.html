➕ INSERT a fondo

Misión 01 · Multi-fila · RETURNING · ON CONFLICT · ~35 min

En la Clase 6 viste el INSERT básico. Hoy lo llevamos a nivel profesional con tres trucos que usas todos los días en un backend real: insertar varias filas a la vez, recuperar lo que se insertó (incluido el id generado) y evitar duplicados con ON CONFLICT.

🧩 Recordatorio: la forma correcta

La base de todo sigue siendo la misma — siempre con columnas explícitas y sin el id SERIAL:

SQL — INSERT de una fila 
INSERT INTO productos (nombre, precio, stock, categoria_id)
VALUES ('Croquetas', 45000, 12, 1);

📚 Multi-fila: un INSERT, muchas filas

Cuando hay que cargar varios registros (los datos de ejemplo, un lote de importación…), no ejecutes un INSERT por fila: separe con comas los grupos de valores en un solo INSERT. Menos viajes a la BD, más rápido, y si una fila falla sabes exactamente dónde.

SQL — INSERT multi-fila (3 filas de una vez) 
INSERT INTO productos (nombre, precio, stock, categoria_id)
VALUES
    ('Croquetas', 45000, 12, 1),
    ('Collar Antipulgas',  18000, 30, 2),
    ('Champú Mascota 500ml', 22000, 8, 3);

💡 El orden de los valores importa

Cada (valor1, valor2, ...) debe coincidir columna por columna con la lista entre paréntesis del INSERT INTO: el primer valor va a la primera columna, el segundo a la segunda, y así. Si los cambias de orden, el dato queda en la columna equivocada y PostgreSQL no te avisará si los tipos coinciden. ¡Silencio peligroso!

🔙 RETURNING: lee lo que acabas de insertar

Problema clásico: insertas un producto y necesitas su id para usarlo en la siguiente operación (por ejemplo, en una venta). La solución se llama RETURNING: le pides a PostgreSQL que te devuelva las columnas de la fila recién insertada, ¡en la misma sentencia!

SQL — INSERT ... RETURNING id 
INSERT INTO productos (nombre, precio, stock, categoria_id)
VALUES ('Correa Retráctil', 28000, 15, 2)
RETURNING id, nombre;

PostgreSQL responde algo así:

SQL — respuesta del motor 
 id |      nombre
----+------------------
  4 | Correa Retráctil
(1 fila)

Con RETURNING * te devuelve todas las columnas de la fila insertada. Es la forma profesional de confirmar que el dato quedó exactamente como esperabas.

⚔️ ON CONFLICT: inserta sin duplicar (upsert)

¿Qué pasa si intentas insertar un correo que ya existe (columna UNIQUE)? PostgreSQL lanza un error y la sentencia falla. Con ON CONFLICT decides qué hacer cuando hay choque:

SQL — ON CONFLICT DO NOTHING vs DO UPDATE 
-- 1. Si el nombre ya existe, ignora el INSERT sin error
INSERT INTO productos (nombre, precio, stock, categoria_id)
VALUES ('Croquetas', 45000, 12, 1)
ON CONFLICT (nombre) DO NOTHING;

-- 2. Si el nombre ya existe, actualiza el precio (UPSERT)
INSERT INTO productos (nombre, precio, stock, categoria_id)
VALUES ('Croquetas', 47000, 12, 1)
ON CONFLICT (nombre)
DO UPDATE SET precio = excluded.precio
RETURNING id, nombre, precio;

📖 ¿Qué es excluded?

Dentro de DO UPDATE SET, la palabra excluded se refiere a los valores que intentabas insertar (los del VALUES). Así puedes escribir cosas como precio = excluded.precio («toma el precio nuevo») o stock = productos.stock + excluded.stock («suma el stock nuevo al que ya había»). Es como comparar el «antes» (la fila existente) con el «intento» (excluded).

🛡️ ¿Dónde se usa esto en la vida real?

El upsert (insertar-o-actualizar) es pan de cada día: sincronizar un catálogo, importar datos de otro sistema, registrar eventos que pueden repetirse… En vez de hacer un SELECT para ver si existe y luego decidir entre INSERT o UPDATE (dos viajes a la BD), haces una sola sentencia que se encarga de todo. Así trabajan los backends de verdad.

🦹 El villano: "INSERT sin columnas"

INSERT INTO productos VALUES (1, 'Croquetas', 45000, ...); depende del orden exacto de las columnas de la tabla. Si mañana alguien añade una columna con ALTER TABLE, el valor que iba al precio puede terminar en otra parte sin que nadie se dé cuenta. Regla inquebrantable: siempre explícita las columnas.

✏️ UPDATE a fondo

Misión 02 · WHERE · Varias columnas · Expresiones · RETURNING · ~35 min

El UPDATE modifica filas existentes. Su estructura es: UPDATE tabla SET columna = valor WHERE condición. Lo que hace profesional el UPDATE no es la sintaxis: es el filtro. Hoy veremos cómo escribir condiciones precisas, actualizar varias columnas de una vez, usar expresiones sobre las columnas (¡aumentar precios sin sacar la calculadora!) y verificar siempre antes de tocar.

🎯 El WHERE: tu único seguro de vida

Todo el poder (y todo el peligro) del UPDATE está en el WHERE. Sin él, la sentencia afecta todas las filas de la tabla. Con un buen WHERE, afecta exactamente las que quieres:

SQL — UPDATE con filtro por id 
-- Cambia el precio SOLO del producto con id = 1
UPDATE productos
SET    precio = 48000
WHERE  id = 1;

💡 Filtrar por id cuando sea posible

El id es la PK: única e intocable. Cuando la app conoce el id (lo sacó de un RETURNING o de la URL), filtra por id: es la condición más precisa que existe. Filtrar por otros campos (nombre, correo) funciona, pero si hay dos «Ana Torres» cambiarás las dos.

🧬 Actualizar varias columnas a la vez

Si la edición toca varios campos (piensa en «editar perfil»), sepáralos con comas en el SET — una sola sentencia, un solo viaje a la BD:

SQL — UPDATE de varias columnas 
UPDATE productos
SET    nombre = 'Croquetas Premium',
        precio = 52000,
        stock  = 25
WHERE  id = 1;

🧮 Expresiones: que la BD haga la cuenta

El SET no acepta solo valores fijos: acepta expresiones que usan el valor actual de la columna. El caso estrella: aumentar un 10% el precio de un producto. La fórmula precio = precio * 1.1 lee el valor viejo, lo multiplica y lo guarda:

SQL — UPDATE con expresión sobre la misma columna 
-- Sube un 10% el precio del producto id = 1
UPDATE productos
SET    precio = precio * 1.1
WHERE  id = 1
RETURNING id, nombre, precio;

También puedes combinar texto y columnas (SET nombre = UPPER(nombre) para poner el nombre en mayúsculas), sumar stock (stock = stock + 10) o combinar columnas con COALESCE. La BD hace el cálculo; tú solo describes el resultado.

🛡️ WHERE con condiciones compuestas

El WHERE del UPDATE acepta lo mismo que el del SELECT: AND, OR, NOT, IS NULL, IN (...), BETWEEN… Ejemplo: UPDATE productos SET activo = FALSE WHERE stock = 0 AND categoria_id = 3; — desactiva en una sola pasada todos los productos sin existencias de la categoría 3.

🦹 El villano: "UPDATE sin WHERE"

UPDATE productos SET precio = 1000; sin WHERE cambiará el precio de todas las filas de la tabla. Sin confirmación, sin papelera, sin «¿estás seguro?». Es uno de los errores más caros de la historia de SQL. La regla de oro: antes de ejecutar un UPDATE, ejecuta el SELECT equivalente con el mismo WHERE: SELECT * FROM productos WHERE id = 1;. Si el SELECT muestra exactamente las filas que quieres tocar, recién ahí ejecutas el UPDATE. (En el módulo 5 verás la red de seguridad definitiva: las transacciones.)

🗑️ DELETE a fondo

Misión 03 · Filtros seguros · DELETE vs TRUNCATE · FK y CASCADE · ~35 min

El DELETE borra filas para siempre. Es el comando con menos sintaxis y más responsabilidad: DELETE FROM tabla WHERE condición. Hoy verás cómo filtrar con precisión, qué pasa con las tablas relacionadas (FK), y cuándo conviene TRUNCATE en lugar de DELETE.

🎯 DELETE con filtro: borra solo lo que toca

La receta es idéntica a la del UPDATE: condición precisa + verificación previa.

SQL — DELETE con filtro 
-- Borra SOLO el producto con id = 3
DELETE FROM productos WHERE id = 3;

-- Borra todos los productos sin existencias de la categoría 1
DELETE FROM productos WHERE stock = 0 AND categoria_id = 1;

💡 DELETE también tiene RETURNING

Igual que INSERT y UPDATE, el DELETE acepta RETURNING para ver qué filas se borraron: DELETE FROM productos WHERE id = 3 RETURNING id, nombre;. Útil para confirmar que el filtro apuntaba a la fila correcta (y para auditar).

🔗 ¿Qué pasa con las FK? CASCADE vs RESTRICT

Cuando borras una fila que otras tablas referencian (una FK), PostgreSQL aplica la regla que definiste al crear la tabla (Clase 6):

Regla de la FKQué pasa al borrar la fila padre
ON DELETE RESTRICT (por defecto)PostgreSQL bloquea el borrado con un error si existen filas que la referencian. Seguro, pero a veces frustrante.
ON DELETE CASCADEBorra automáticamente las filas hijas junto con la madre. Práctico… y peligroso si no lo tenías en mente.
ON DELETE SET NULLDeja en NULL el valor de la FK en las filas hijas (la relación «se olvida»).
SQL — el error clásico de FK 
mascotitas=# DELETE FROM categorias WHERE id = 1;
-- ERROR:  update or delete on table "categorias" violates foreign key
-- constraint "productos_categoria_id_fkey" on table "productos"
-- DETAIL:  Key (id)=(1) is still referenced from table "productos".

Ese error es buena señal: PostgreSQL acaba de evitar que rompas la integridad de tus datos (Clase 4). La solución correcta casi siempre es borrar primero lo que referencia, y después lo referenciado:

SQL — borrar en orden (hijos primero) 
-- 1. Borra los productos que apuntan a la categoría 1
DELETE FROM productos WHERE categoria_id = 1;

-- 2. Ahora sí, borra la categoría
DELETE FROM categorias WHERE id = 1;

⚖️ DELETE vs TRUNCATE: ¿cuándo vaciar?

A veces quieres vaciar una tabla entera a propósito (datos de prueba, limpieza total). Hay dos caminos, y no son lo mismo:

DELETE FROM productos;TRUNCATE TABLE productos;
¿Puede llevar WHERE?✅ Sí (borrado selectivo)❌ No (vacía todo)
Velocidad con muchas filasLenta (borra fila por fila)Rapidísima (libera bloques)
¿Reinicia el SERIAL?❌ No, sigue desde el último id✅ Sí, vuelve a 1
¿Se puede usar RETURNING?✅ Sí❌ No

🦹 El villano gemelo: "DELETE sin WHERE"

DELETE FROM productos; sin WHERE vacía la tabla completa, fila por fila, sin pedir nada. Es el «DROP TABLE» silencioso: la tabla existe, pero quedó en cero. Igual que con el UPDATE: primero el SELECT de verificación, después el DELETE. Y si de verdad quieres vaciarla a propósito, piénsalo dos veces y usa TRUNCATE — al menos queda claro (para quien lea tu código) que la intención era borrar todo.

🗂️ Borrado lógico: la alternativa profesional

En sistemas reales casi nunca se borra de verdad: se desactiva con una columna activo BOOLEAN DEFAULT TRUE y se hace UPDATE productos SET activo = FALSE WHERE id = 3;. Se llama borrado lógico (soft delete): los datos se conservan por si se necesitan después (historial, facturas, auditoría). El DELETE duro se reserva para datos realmente inservibles. Los dos enfoques conviven en el mundo real.

🛡️ Transacciones: el "deshacer" de la BD

Misión 04 · BEGIN / COMMIT / ROLLBACK · Atomicidad · ~30 min

Ya sabes insertar, actualizar y borrar. Pero ¿qué pasa si en medio de la operación te das cuenta de que el DELETE no tenía WHERE? Hasta ahora, la respuesta era «malas noticias». Hoy cambia todo: con el TCL (Transaction Control Language) puedes deshacer. Es la diferencia entre manejar un cuchillo sin mango y con mango.

🧱 ¿Qué es una transacción?

Una transacción es un grupo de sentencias SQL que se ejecutan todas o ninguna (atomicidad). Puedes encadenar varios INSERT, UPDATE y DELETE, revisar el resultado, y recién entonces decidir: lo confirmo (COMMIT) o lo tiro a la basura (ROLLBACK). Mientras la transacción está abierta, solo tú ves los cambios.

📖 Definición formal

Una transacción es una unidad lógica de trabajo: un conjunto de operaciones que el SGBD ejecuta de forma atómica (todo o nada), consistente (la BD pasa de un estado válido a otro), aislada (los cambios intermedios no se ven desde fuera) y duradera (una vez confirmada, sobrevive a cualquier fallo). Son las siglas ACID: Atomicity, Consistency, Isolation, Durability.

🎮 Los tres comandos del TCL

ComandoQué hace
BEGINAbre una transacción. Desde aquí, tus cambios están «en el aire».
COMMITConfirma (guarda) todos los cambios de la transacción para siempre.
ROLLBACKDescarta todos los cambios y deja la BD como estaba antes del BEGIN.

🛠️ El caso que nos salva el día

Operación típica de un backend: cobrar una venta significa varias cosas a la vez (crear la venta, descontar stock, actualizar el total del cliente). Si la primera funciona y la segunda falla, quedarías con datos a medias. La transacción lo arregla:

SQL — transacción completa 
BEGIN;

INSERT INTO ventas (cliente_id, total) VALUES (2, 18000) RETURNING id;
UPDATE productos SET stock = stock - 1 WHERE id = 4;
UPDATE clientes SET total_gastado = total_gastado + 18000 WHERE id = 2;

-- ¿Todo salió bien? Revisemos…
SELECT * FROM productos WHERE id = 4;

COMMIT;  -- ✅ Todo bien: guardo los 3 cambios juntos

Y si algo se ve mal en la revisión, en vez de COMMIT ejecutas ROLLBACK y nada de lo anterior ocurrió:

SQL — deshacer con ROLLBACK 
BEGIN;
DELETE FROM productos WHERE stock = 0;   -- ¡Uy! No era mi intención
SELECT COUNT(*) FROM productos;             -- ¡No, espera!
ROLLBACK;                                 -- 😮‍💨 Los datos volvieron

-- Verificamos: todo sigue donde estaba
SELECT COUNT(*) FROM productos;

💡 El hábito profesional: todo cambio riesgoso va en transacción

Los desarrolladores serios envuelven toda operación que modifica datos en un BEGIN … COMMIT (o ROLLBACK si algo falla). No solo te salva del error humano: si una de las sentencias falla a la mitad, la BD queda intacta en vez de a medias. Transacción = red de seguridad.

🦹 El villano: "el error sin red de seguridad"

Ejecutar DELETE/UPDATE directamente, sin BEGIN, es jugar a la ruleta rusa: en PostgreSQL cada sentencia se autoconfirma al instante (autocommit). Si sale mal, ya no hay vuelta atrás. Con BEGIN primero, ganas la libertad de equivocarte y corregir antes de COMMIT. Por eso decimos: el WHERE evita el error, y la transacción lo perdona.

📦 Taller entregable: "Mascotitas: operaciones de inventario"

Misión 06 · Caso end-to-end: modificar y proteger los datos de una BD real · ~50 min

Taller final · Entregable Operaciones DML seguras para la tienda de mascotas "Mascotitas"

La tienda Mascotitas ya tiene su BD montada (la creaste en la Clase 6 con categorias, productos, clientes y mascotas, llena de datos). Hoy el dueño te pide operaciones sobre esos datos: cargar inventario nuevo, reajustar precios, retirar productos descontinuados y hacer una operación riesgosa protegida con transacciones. La entrega es un archivo SQL .sql ejecutable en PostgreSQL sin errores.

📋 Enunciado

Mascotitas terminó diciembre con las tablas llenas. En enero el dueño necesita:

  1. Verificar qué hay en la BD antes de tocar nada (regla de oro del curso).
  2. Cargar 4 productos nuevos en un solo INSERT multi-fila.
  3. Reajustar precios y stock con UPDATE: un aumento del 10% y un reposición de stock, cada uno con su verificación previa.
  4. Retirar 2 productos descontinuados con DELETE + WHERE.
  5. Realizar una operación riesgosa dentro de una transacción: si algo se ve mal, ROLLBACK y listo.

🎯 Objetivos del entregable

Tu entrega, en pareja, debe contener seis partes dentro de un único archivo .sql:

  1. Verificación inicial: SELECT para conocer los datos actuales.
  2. INSERT multi-fila: los 4 productos nuevos, con RETURNING id.
  3. UPDATEs: aumento del 10% de precio y reposición de stock, cada uno precedido de su SELECT de verificación.
  4. DELETEs: retirar 2 productos con WHERE preciso y RETURNING.
  5. Transacción: BEGIN + operación destructiva + decisión COMMIT/ROLLBACK.
  6. Reflexión (en un bloque de comentarios al final): el comando que más te costó y por qué.

1 Verifica el estado actual

Antes de tocar nada, escribe los SELECT que le muestren al dueño (y a ti) qué hay hoy: listar todos los productos con su categoría, y contar cuántos hay por categoría. Guarda esos resultados: te servirán para comparar al final.

-- Estado inicial: todos los productos
SELECT id, nombre, precio, stock, categoria_id FROM productos ORDER BY id;

-- Cuántos productos hay por categoría
SELECT categoria_id, COUNT(*) FROM productos GROUP BY categoria_id;

2 Carga 4 productos nuevos (INSERT multi-fila)

El dueño trajo 4 productos de la distribuidora: Croquetas Gato 1.5kg ($32.000, 20 uds, Alimentos), Correa Retráctil ($28.000, 15 uds, Accesorios), Champú Mascota 500ml ($22.000, 10 uds, Higiene) y Pelota de Goma ($9.000, 40 uds, Juguetes… crea la categoría Juguetes con id 4 si no existe). Escríbelo en un solo INSERT con RETURNING id, nombre. Recuerda: no insertes el id SERIAL.

-- Si no existe la categoría Juguetes (id 4 en el taller de la Clase 6)
INSERT INTO categorias (nombre) VALUES ('Juguetes');

-- Los 4 productos nuevos en un solo INSERT multi-fila
INSERT INTO productos (nombre, precio, stock, categoria_id) VALUES
    ('Croquetas Gato 1.5kg',   32000, 20, 1),
    ('Correa Retráctil',       28000, 15, 2),
    ('Champú Mascota 500ml',   22000, 10, 3),
    ('Pelota de Goma',          9000, 40, 4)
RETURNING id, nombre;

-- Si tu BD ya tiene esos productos, cambia los nombres
-- o usa ON CONFLICT (nombre) DO NOTHING para no duplicar.

3 Reajusta precios y stock (UPDATE)

El dueño quiere dos cambios: aumentar un 10% el precio de todos los productos de la categoría Alimentos (id 1), y reponer +5 unidades de stock al producto Correa Retráctil. Para cada uno: primero el SELECT de verificación con el mismo WHERE, luego el UPDATE, y termina con RETURNING para confirmar. Usa expresiones (precio = precio * 1.1, stock = stock + 5), no valores calculados a mano.

-- VERIFICACIÓN 1: qué productos de Alimentos hay hoy
SELECT id, nombre, precio FROM productos WHERE categoria_id = 1;

-- UPDATE 1: +10% a todos los de Alimentos (expresión sobre la columna)
UPDATE productos SET precio = precio * 1.1
WHERE categoria_id = 1
RETURNING id, nombre, precio;

-- VERIFICACIÓN 2: el stock actual de la Correa Retráctil
SELECT id, nombre, stock FROM productos WHERE nombre = 'Correa Retráctil';

-- UPDATE 2: reponer 5 unidades (stock = stock + 5)
UPDATE productos SET stock = stock + 5
WHERE nombre = 'Correa Retráctil'
RETURNING id, nombre, stock;

Nota: usar nombre en el WHERE funciona aquí por los datos de ejemplo; en una BD real filtrarías por id.

4 Retira productos descontinuados (DELETE)

La distribuidora dejó de producir Champú Mascota 500ml y Pelota de Goma. Bórralos con WHERE preciso: verificación previa, DELETE con RETURNING para confirmar qué se borró, y una verificación final de que ya no están.

-- VERIFICACIÓN: ¿existen esos productos hoy?
SELECT id, nombre FROM productos WHERE nombre IN ('Champú Mascota 500ml', 'Pelota de Goma');

-- DELETE con WHERE preciso + RETURNING para confirmar
DELETE FROM productos
WHERE nombre IN ('Champú Mascota 500ml', 'Pelota de Goma')
RETURNING id, nombre;

-- VERIFICACIÓN FINAL: ya no deben aparecer
SELECT id, nombre FROM productos WHERE nombre IN ('Champú Mascota 500ml', 'Pelota de Goma');

5 Operación riesgosa en transacción

El dueño quiere vaciar el stock de una categoría entera (borrar los productos sin existencias)… pero dudó y quiere que lo hagas a salvo. Escríbelo así: BEGIN, el UPDATE o DELETE destructivo, un SELECT de revisión, y la decisión final. Si al revisar todo se ve bien → COMMIT; si el filtro borró de más → ROLLBACK. Explica en un comentario tu decisión.

BEGIN;

-- Operación destructiva: borrar productos sin existencias de Higiene (categoria_id = 3)
DELETE FROM productos WHERE stock = 0 AND categoria_id = 3;

-- Revisión: ¿qué productos quedan en Higiene?
SELECT id, nombre, stock FROM productos WHERE categoria_id = 3;

-- Decisión (escríbanla en su archivo):
-- Si la revisión muestra lo esperado -> COMMIT;
-- Si el filtro tocó de más             -> ROLLBACK;
COMMIT;

-- Verificación final tras el commit
SELECT COUNT(*) FROM productos;

Al final del archivo .sql, en un bloque de comentarios (/* ... */), respondan en pareja: ¿qué comando te costó más escribir y por qué? ¿Cuándo usaste RETURNING y qué te devolvió? ¿Qué papel jugó la transacción en el paso 5?

Ejemplo (escríbanlo con sus palabras, no lo copien):

/*
  Reflexión:
  Lo que más nos costó fue el UPDATE con expresión: al principio
  escribimos SET precio = 49500 (calculado a mano) en vez de
  SET precio = precio * 1.1. La profe nos hizo ver que a mano
