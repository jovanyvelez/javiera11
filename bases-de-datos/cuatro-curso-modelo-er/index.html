📐 El Modelo Entidad-Relación

Misión 01 · Entidades, atributos, relaciones y cardinalidades · ~40 min

El modelo Entidad-Relación (ER), propuesto por Peter Chen en 1976, es la forma más extendida de representar conceptualmente la información de un problema antes de pensar en tablas. No es SQL, no es código: es un dibujo con tres piezas.

🧩 Las tres piezas del modelo ER

📦

Entidad

Una "cosa" del mundo real, distinguible de las demás, sobre la que queremos guardar información. Se dibuja como un rectángulo.

Ejemplos: Libro, Cliente, Préstamo, Profesor.

🏷️

Atributo

Una propiedad de una entidad o de una relación. Se dibuja como un óvalo unido a su entidad.

Ejemplos: titulo, isbn, nombre, fecha_nacimiento.

🔗

Relación

Un vínculo entre dos o más entidades. Se dibuja como un rombo conectado con líneas a las entidades.

Ejemplos: escribe (Libro↔Autor), presta (Usuario↔Libro), matricula (Estudiante↔Curso).

🧠 Definición formal (para el cuaderno)

Entidad: objeto o concepto del mundo real sobre el que se almacena información. Cada ocurrencia individual se llama instancia. Atributo: dato atómico que describe una entidad o relación. Relación: asociación entre entidades con un significado propio.

🎨 Un primer diagrama (en texto)

Para una pequeña biblioteca, el modelo ER conceptual sería:

Aquí LIBRO y AUTOR son entidades; isbn, titulo, nombre… son atributos; escribe es la relación entre ambos. La notación N : M indica la cardinalidad, que veremos justo ahora.

📊 Cardinalidad: cuántos con cuántos

La cardinalidad indica cuántas instancias de una entidad pueden relacionarse con cuántas de la otra. Existen tres casos básicos:

1 : 1 — Uno a uno

Cada instancia de A se relaciona con una sola de B, y viceversa.

Ej: Usuario ↔ Carnet. Cada usuario tiene un carnet único; cada carnet pertenece a un usuario.

1 : N — Uno a muchos

Una instancia de A se relaciona con varias de B, pero cada B se relaciona con una sola A.

Ej: Cliente ↔ Pedido. Un cliente hace muchos pedidos; cada pedido pertenece a un único cliente.

N : M — Muchos a muchos

Una instancia de A puede relacionarse con varias de B, y una B con varias de A.

Ej: Estudiante ↔ Curso. Un estudiante toma muchos cursos; un curso tiene muchos estudiantes.

👨‍🏫 En el aula — 3 minutos

Pida a las parejas que digan en voz alta dos ejemplos de cada cardinalidad que existan en su colegio. Ejemplos típicos: 1:1 Estudiante↔Documento; 1:N Profesor↔Asignatura; N:M Estudiante↔Asignatura. Escriba los mejores en el tablero para usarlos más adelante.

💡 La cardinalidad se lee en ambos sentidos

Cuando decimos Cliente 1:N Pedido, también está implícito Pedido N:1 Cliente. El orden importa: lee siempre desde la entidad donde está el "1" hacia donde está el "N". Así evitas confundir quién es el "padre" y quién el "hijo" al construir las tablas.

🔑 Claves primarias y foráneas

Misión 02 · PK, FK, integridad referencial y claves compuestas · ~40 min

Cuando empezamos a transformar el modelo ER en tablas, surge una pregunta inmediata: ¿cómo identifico unívocamente cada fila? Y otra: ¿cómo连接o una tabla con otra sin equivocarme? Las respuestas son, respectivamente, la clave primaria y la clave foránea.

🗝️ Clave primaria (PK — Primary Key)

Definición

Una clave primaria es una columna (o combinación de columnas) cuyos valores identifican unívocamente cada fila de la tabla. Debe cumplir tres reglas:

  • No nula — ningún valor puede ser NULL.
  • Única — no se repite entre filas.
  • Estable — no cambia con el tiempo.
SQL — crear tabla con PK 
CREATE TABLE autores (
    id        SERIAL      PRIMARY KEY,
    nombre    VARCHAR(100) NOT NULL,
    pais      VARCHAR(50)
);

Aquí id es la PK. El tipo SERIAL de PostgreSQL es un entero que se autoincrementa (cada insert recibe un número nuevo). Así garantizamos unicidad sin pensarla.

🔗 Clave foránea (FK — Foreign Key)

Definición

Una clave foránea es una columna (o conjunto) de una tabla cuyos valores hacen referencia a la clave primaria de otra tabla. Es el "puente" entre dos tablas: dice "esta fila pertenece a aquella".

SQL — FK que conecta libros con autores 
CREATE TABLE libros (
    isbn       VARCHAR(13) PRIMARY KEY,
    titulo     VARCHAR(200) NOT NULL,
    autor_id   INTEGER REFERENCES autores(id),
    anio       INTEGER
);

La columna autor_id es una FK que apunta a autores.id. Cada libro "sabe" quién es su autor sin repetir el nombre del autor. La BD se encarga de que la conexión sea válida.

🛡️ Integridad referencial

¿Qué garantiza una FK?

Cuando declaras una FOREIGN KEY, el SGBD no permite insertar un libro cuyo autor_id no exista en autores. Tampoco permite (por defecto) borrar un autor que tiene libros asociados. A esta garantía se le llama integridad referencial, y es la que mata al villano "pedido huérfano".

🦹 El villano: el pedido huérfano

Imagina que una tabla pedidos guarda cliente_id = 47… pero el cliente 47 fue borrado. El pedido apunta a la nada. Sin integridad referencial, nadie se entera hasta que la app explota. Con FOREIGN KEY, el SGBD bloquea el borrado o lo propaga en cascada, según lo que decidamos.

🧩 Claves compuestas

A veces una sola columna no basta para identificar una fila. Por ejemplo, una tabla notas que guarda la nota de cada estudiante en cada asignatura necesita ambos identificadores para ser única.

SQL — PK compuesta 
CREATE TABLE notas (
    estudiante_id  INTEGER REFERENCES estudiantes(id),
    asignatura_id  INTEGER REFERENCES asignaturas(id),
    nota           DECIMAL(4,2),
    PRIMARY KEY (estudiante_id, asignatura_id)
);

Aquí ningún estudiante puede tener dos notas para la misma asignatura en la misma tabla. La PK compuesta lo impide.

💡 PK natural vs surrogate

Una PK natural usa datos reales (el isbn de un libro, el nif de una persona). Una PK surrogate usa un número inventado (SERIAL, id). La surrogate es más segura: nunca cambia aunque el dato real sea corregido, y no reveala datos sensibles.

🔄 Del modelo ER al modelo relacional

Misión 03 · Reglas de transformación · simulador de cardinalidad · ~45 min

El modelo ER es conceptual: describe el problema. El modelo relacional es lógico: describe las tablas. El paso de uno a otro sigue reglas mecánicas que vamos a practicar ahora. Las dominas una vez y las aplicas a cualquier problema.

📐 Reglas de transformación

Elemento ERCómo se transformaEjemplo
Entidad fuerteUna tabla. La PK de la entidad → PK de la tabla.AUTOR → autores(id PK)
AtributoColumna de la tabla de su entidad.nombre → columna nombre
Relación 1:1Se fusiona en una sola tabla o se pone la PK de una como FK en la otra (con UNIQUE).Usuario↔Carnet
Relación 1:NLa PK del lado "1" se copia como FK en la tabla del lado "N".cliente_id FK en pedidos
Relación N:MSe crea una tabla puente con PK compuesta (las dos PK de las entidades).estudiante_curso(estudiante_id, curso_id)
Atributo de relaciónColumna de la tabla puente (N:M) o de la tabla donde fue la FK (1:N).fecha_prestamo en prestamos

💡 La regla de oro

En una relación 1:N, la FK siempre vive en la tabla del lado "N". Jamás al revés. Si un cliente tiene muchos pedidos, cliente_id va en pedidos, no pedido_id en clientes. Pensa: si pusieras pedido_id en clientes, un cliente solo podría tener un pedido.

🦹 El villano: la N:M mal resuelta

El error clásico de principiantes es meter una relación N:M en una sola columna: "Estudiante tiene una columna cursos con '1,4,7'". Eso rompe el modelo relacional: no puedes hacer JOIN ni garantizar consistencia. La solución correcta es siempre crear una tabla puente.

📖 Ejemplo completo: la biblioteca

Imagina la biblioteca del módulo 1: LIBRO, AUTOR y la relación escribe (N:M, porque un libro puede tener varios autores y un autor varios libros). Aplicamos las reglas:

SQL — biblioteca básica (N:M entre Libro y Autor) 
CREATE TABLE autores (
    id        SERIAL       PRIMARY KEY,
    nombre    VARCHAR(100) NOT NULL,
    pais      VARCHAR(50)
);

CREATE TABLE libros (
    isbn      VARCHAR(13) PRIMARY KEY,
    titulo    VARCHAR(200) NOT NULL,
    anio      INTEGER
);

-- Tabla puente: la relación N:M "escribe" se materializa aquí
CREATE TABLE libro_autor (
    isbn       VARCHAR(13) REFERENCES libros(isbn),
    autor_id   INTEGER     REFERENCES autores(id),
    PRIMARY KEY (isbn, autor_id)
);

La tabla libro_autor es la tabla puente: su PK es compuesta (las dos PK de las entidades) y cada fila representa "el autor X coescribió el libro Y". Si la relación tuviera un atributo (por ejemplo rol para distinguir "autor principal" de "coautor"), sería una columna más de esta tabla puente.

💡 Nominar tablas puentes

Las tablas puente suelen nombrarse con los dos entidades en minúsculas, separados por guion bajo: libro_autor, estudiante_curso, usuario_rol. Si la relación tiene un nombre propio más claro, úsalo: prestamos en vez de usuario_libro. La claridad le gana a la mecánica.

🔢 Tipos de datos en SQL

Misión 04 · Elegir el tipo correcto por dominio · ~35 min

Antes de escribir el CREATE TABLE final, toca decidir qué tipo de dato va en cada columna. Elegir mal el tipo es un villano silencioso: una edad guardada como TEXT no se puede ordenar numéricamente; un precio guardado como INTEGER pierde los decimales.

📋 Los tipos esenciales (PostgreSQL)

TipoUsoEjemplo
INTEGER / SERIALNúmeros enteros. SERIAL se autoincrementa (ideal para PK).cantidad INTEGER
DECIMAL(p,s) / NUMERICNúmeros con decimales exactos (dinero, notas). p=precisión total, s=decimales.precio DECIMAL(10,2)
VARCHAR(n)Texto de longitud variable, hasta n caracteres.titulo VARCHAR(200)
TEXTTexto sin límite explícito. Útil para descripciones largas.sinopsis TEXT
DATESolo fecha (año, mes, día).fecha_nac DATE
TIMESTAMPFecha y hora.creado_en TIMESTAMP
BOOLEANVerdadero / falso.activo BOOLEAN
UUIDIdentificador universal único. Útil para PK distribuidas.id UUID

🦹 El villano: la edad en texto

Si guardas edad como VARCHAR(3), podrías escribir '20', 'veinte' y ' 20 '. El SGBD no sabrá que son números y no podrás calcular promedios ni ordenar correctamente. La edad es un número: edad INTEGER.

💡 El villano gemelo: el precio en entero

Si guardas precio como INTEGER, un libro de $19.99 se convierte en $19 (truncado) o en $20 (redondeado). Pierdes precisión en cada operación. Usa DECIMAL(10,2): 10 dígitos totales, 2 decimales. Para notas académicas basta con DECIMAL(4,2) (de 0.00 a 99.99).

¿Por qué no FLOAT para dinero?

Los FLOAT / REAL usan aritmética de coma flotante binaria, que no es exacta: 0.1 + 0.2 puede dar 0.30000000000000004. Para dinero, siempre DECIMAL / NUMERIC, que son exactos. Para cálculos científicos, sí, FLOAT.

✨ Diagramas ER con Mermaid

Misión 05 · Sintaxis erDiagram y cardinalidad Crow's foot · ~45 min

Mermaid es un lenguaje de texto a diagrama: escribes en un mini-lenguaje y se dibuja solo. Lo entienden GitHub (en los .md), Notion, Obsidian y ChatGPT. Para nosotros es la herramienta definitiva: el diagrama ER y el SQL viven juntos en texto.

📐 Sintaxis básica de erDiagram

Un diagrama ER en Mermaid se escribe así:

Mermaid — erDiagram básico 
erDiagram
    LIBRO ||--o{ AUTOR : escribe
    LIBRO {
        varchar isbn PK
        varchar titulo
        integer anio
    }
    AUTOR {
        serial id PK
        varchar nombre
        varchar nacionalidad
    }

Aquí la línea LIBRO ||--o{ AUTOR : escribe declara la relación con su cardinalidad. La notación ||--o{ es Crow's foot: || significa "exactly one" (1) y o{ significa "zero or many" (0..N). Entre llaves se listan los atributos de cada entidad, marcando PK para la clave primaria.

🔤 Cardinalidades en Mermaid (Crow's foot)

NotaciónSignificadoCardinalidad
||--||One to one1 : 1
||--o{One to zero-or-many1 : N
}o--o{Zero or many to zero or manyN : M
||--|{One to one-or-many1 : 1..N

💡 Cómo leer la línea

La relación A ||--o{ B : escribe se lee de izquierda a derecha: "un A tiene muchos B, y la relación se llama escribe". El lado izquierdo || es el "1"; el derecho o{ es el "muchos". Si lo giras, sigue siendo válido: la flecha del pato (Crow's foot) siempre apunta al "muchos".

🛠️ Taller: Biblioteca online

Misión 06 · Caso end-to-end: diseño ER + transformación + diagrama Mermaid · ~50 min

Taller final Sistema de préstamos para la biblioteca del colegio

La biblioteca del colegio necesita una base de datos para gestionar libros, usuarios y préstamos. Tu misión es, en pareja:

  1. Identificar las entidades y sus atributos.
  2. Detectar las relaciones y sus cardinalidades.
  3. Diseñar el modelo ER.
  4. Transformarlo al modelo relacional (tablas con PK y FK).
  5. Dibujar el diagrama con Mermaid.
  6. Escribir el CREATE TABLE en SQL.

📋 Enunciado

La biblioteca tiene libros (cada uno con su ISBN, título y año de publicación) y usuarios (cada uno con su número de carnet, nombre y correo). Cada usuario puede pedir prestados varios libros a la vez, y cada libro puede ser prestado a un usuario a la vez (no hay dos préstamos activos del mismo ejemplar). Cada préstamo registra la fecha de préstamo y la fecha de devolución (que puede ser NULL mientras no se devuelva). Un libro puede tener varios autores, y un autor puede escribir varios libros. De cada autor guardamos nombre y nacionalidad.

1 Identifica las entidades

En parejas: escriban en el cuaderno las entidades que ven en el enunciado y, junto a cada una, sus atributos. Marquen la PK de cada una con un asterisco.

Entidades y atributos:

  • LIBRO — isbn* (PK), titulo, anio
  • AUTOR — id* (PK), nombre, nacionalidad
  • USUARIO — carnet* (PK), nombre, correo
  • PRESTAMO — es una relación entre USUARIO y LIBRO con atributos fecha_prestamo y fecha_devolucion. Al transformarla se convertirá en tabla.

2 Detecta las relaciones y cardinalidades

Para cada par de entidades que se relaciona, anota la cardinalidad (1:1, 1:N o N:M).

  • AUTOR escribe LIBRO → N:M (un autor escribe varios libros; un libro puede tener varios autores).
  • USUARIO pide LIBRO → N:M en lo conceptual, porque un usuario pide muchos libros y un libro es prestado a muchos usuarios a lo largo del tiempo. Pero ojo: un préstamo activo es 1:1 con el libro. La tabla puente prestamos llevará la fecha de préstamo y de devolución.

En el modelo relacional, ambas se materializan como tablas puente.

3 Dibuja el diagrama en Mermaid

En el constructor del módulo 6 (o en tu cuaderno con la notación Crow's foot), escribe el diagrama. Compara con la solución.

        serial id PK

4 Escribe el SQL completo

Transforma el diagrama en sentencias CREATE TABLE con PK y FK. Recuerda el orden: primero las tablas sin FK, luego las que referencian.

-- 1. Tablas sin dependencias
CREATE TABLE autores (
    id           SERIAL PRIMARY KEY,
    nombre       VARCHAR(100) NOT NULL,
    nacionalidad VARCHAR(50)
);

CREATE TABLE libros (
    isbn   VARCHAR(13) PRIMARY KEY,
    titulo VARCHAR(200) NOT NULL,
    anio   INTEGER
);

CREATE TABLE usuarios (
    carnet VARCHAR(20) PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    correo VARCHAR(150) NOT NULL UNIQUE
);

-- 2. Tabla puente N:M autor-libro
CREATE TABLE libro_autor (
    isbn     VARCHAR(13) REFERENCES libros(isbn),
    autor_id INTEGER     REFERENCES autores(id),
    PRIMARY KEY (isbn, autor_id)
);

-- 3. Tabla de préstamos (atributos de la relación)
CREATE TABLE prestamos (
    id              SERIAL PRIMARY KEY,
    carnet          VARCHAR(20)  REFERENCES usuarios(carnet),
    isbn            VARCHAR(13)  REFERENCES libros(isbn),
    fecha_prestamo  DATE NOT NULL,
    fecha_devolucion DATE
);

5 Reflexiona

Contesta en pareja: ¿por qué fecha_devolucion admite NULL? ¿Por qué prestamos tiene su propia PK id SERIAL en vez de una PK compuesta (carnet, isbn)? Discútanlo 2 minutos y luego lean la respuesta.

fecha_devolucion admite NULL porque el préstamo está activo mientras no se haya devuelto: no podemos inventar una fecha futura. Cuando el usuario devuelve el libro, ese campo se actualiza. Una PK compuesta (carnet, isbn) impediría que un mismo usuario pidiera prestado el mismo libro dos veces (hoy y dentro de un mes): la PK exigiría unicidad. Por eso usamos id SERIAL como PK surrogate, y dejamos que (carnet, isbn, fecha_prestamo) sea un UNIQUE si queremos impedir dos préstamos activos del mismo ejemplar.

👨‍🏫 Cierre del aula — 5 minutos

Cada pareja muestra su diagrama Mermaid en pantalla. La clase valida: ¿está bien la cardinalidad? ¿La FK está en la tabla correcta? El profesor refuerza la regla de oro: la FK vive en el lado N. El taller se da por completado cuando las parejas tienen las 5 tablas creadas en SQL.

🎯 ¿Cómo saber si lo lograste?

Tu diseño está completo cuando: (1) tienes 5 tablas: autores, libros, usuarios, libro_autor, prestamos; (2) cada tabla con PK tiene marcada su PK con PRIMARY KEY; (3) las relaciones N:M tienen tabla puente con PK compuesta; (4) los tipos de datos son correctos (no VARCHAR para fechas ni INTEGER para el ISBN); (5) el diagrama Mermaid se renderiza sin error. Si lo conseguiste, diseñaste una BD real. 🔬

🧩 Investigación: ¿y si un libro tiene ejemplares?

En la vida real, una biblioteca tiene varios ejemplares del mismo libro. Nuestro modelo no contempla eso (cada ISBN es un único libro físico). ¿Cómo lo ampliarías? Pista: una nueva entidad EJEMPLAR con su propia PK, referenciando a libros(isbn), y el préstamo apunta al ejemplar, no al libro. Discútanlo y propongan el SQL extra.
